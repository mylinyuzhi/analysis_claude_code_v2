# Plan Mode Prompt Surface

> Scope: model-facing Plan Mode text in 2.1.193: tool prompts, attachment reminders, approval-result content, custom workflow injection, and remote Ultraplan scaffolding.

## Summary

Plan Mode uses several prompt layers rather than one monolithic instruction:

- tool prompts explain when the model should enter or exit plan mode;
- `EnterPlanMode` and `ExitPlanMode` tool results give immediate local state transitions;
- `plan_mode` attachments enforce the read-only workflow throughout planning;
- `plan_mode_reentry` and `plan_mode_exit` attachments mark boundary transitions;
- remote Ultraplan prompts add cloud-session constraints and teleport handling.

This split is deliberate. The tool prompts help the model choose the right tool, while attachments enforce the operational contract after the mode has changed.

## Tool Prompts

`ExitPlanMode` prompt text is embedded before the tool object at `cli_inner_pretty.js:380560-380581`. Its key constraints are:

- the plan must already be written to the plan file;
- the tool does not take plan content as a normal model parameter;
- the user reviews the plan file contents;
- research-only tasks should not use `ExitPlanMode`;
- unresolved requirements should use `AskUserQuestion` before final approval;
- `AskUserQuestion` must not be used to ask whether the plan is okay.

`EnterPlanMode` prompt text is generated by `getEnterPlanModeToolPrompt` (`yGp`, `cli_inner_pretty.js:381748-381823`). It tells the model to use Plan Mode for non-trivial implementation tasks, multi-file work, architectural decisions, unclear requirements, and cases where user preferences matter. The inserted "What Happens in Plan Mode" fragment is `hGp` at `cli_inner_pretty.js:381733-381746`.

The extracted tool assets at `/lyz/codespace/claude-code-bomb/versions/2.1.193/extract/assets/tools/EnterPlanMode.md` and `ExitPlanMode.md` corroborate the same model-facing prompt bodies.

## Key Algorithms and Decisions

### Prompt Responsibility Split

**What it does:** Separates "when to use the tool" guidance from "what rules apply while planning" guidance.

**How it works:**
1. `EnterPlanMode.prompt()` returns `fKa()` at `cli_inner_pretty.js:381896-381897`; `fKa` returns the proactive usage guide from `yGp` at `cli_inner_pretty.js:381825-381827`.
2. `ExitPlanMode.prompt()` returns the approval-specific prompt (`cli_inner_pretty.js:381539-381540`).
3. `EnterPlanMode.mapToolResultToToolResultBlockParam` gives a short immediate planning reminder after entry (`cli_inner_pretty.js:381934-381950`).
4. The longer read-only workflow is injected by `plan_mode` attachments rendered through `o5f` (`cli_inner_pretty.js:601213-601216`).

**Why this approach:**
- Tool prompts influence tool selection before the mode changes.
- Attachments are available after the mode changes and can be repeated throughout the planning session.
- Short tool results avoid depending on one large result message as the only source of truth.

**Key insight:** Plan Mode's strongest safety text is not the `EnterPlanMode` prompt. It is the recurring attachment surface.

### Full Workflow Prompt

**What it does:** Gives the model the complete planning protocol when a full `plan_mode` reminder is selected.

**How it works:**
1. The full renderer `i5f` starts at `cli_inner_pretty.js:601224`.
2. It selects plan-file instructions based on whether the plan already exists (`cli_inner_pretty.js:601226-601228`).
3. It emits the read-only preamble and plan-file-only edit rule (`cli_inner_pretty.js:601246-601250`).
4. It defines Phase 1 initial understanding and exploration-agent use (`cli_inner_pretty.js:601254-601263`).
5. It defines Phase 2 design and Plan-agent use (`cli_inner_pretty.js:601265-601295`).
6. It defines Phase 3 review and clarification (`cli_inner_pretty.js:601297-601301`).
7. It inserts the final-plan phase `s5f` (`cli_inner_pretty.js:601303`; definition at `602480-602487`).
8. It appends the ExitPlanMode footer `GQl` (`cli_inner_pretty.js:601305-601306`; definition at `601218-601222`).

**Why this approach:**
- The full workflow gives a repeatable planning recipe, not just a prohibition on edits.
- It explicitly steers the model toward reuse of existing functions/utilities and verification steps.
- It makes `ExitPlanMode` the only plan-approval endpoint, reducing ambiguous "does this look good?" text exchanges.

**Key insight:** The full prompt is both a safety prompt and a quality prompt. It forbids implementation while also forcing concrete file/function/verification planning.

### Custom Plan Workflow Injection

**What it does:** Allows a custom workflow body to replace the default five-phase body while preserving the safety wrapper.

**How it works:**
1. `planModeInstructions` is carried into compact reconstruction (`KKn`, `cli_inner_pretty.js:470052-470064`) and normal reminders (`muf`, `cli_inner_pretty.js:473434-473440`).
2. If `e.customInstructions` is present, `i5f` builds a custom full reminder (`cli_inner_pretty.js:601229-601242`).
3. The custom path still includes the read-only preamble, plan-file info, and the `Call ExitPlanMode` footer (`cli_inner_pretty.js:601230-601241`).
4. SDK/init schemas describe this field as a custom workflow body that replaces the default implementation phases while keeping the wrapper (`cli_inner_pretty.js:700728-700731`; `712419`).

**Why this approach:**
- Product/API callers can customize the planning method without removing the core Plan Mode safety contract.
- The wrapper prevents custom instructions from accidentally omitting the read-only constraint or approval protocol.
- Carrying the field through compaction avoids losing custom workflow state mid-session.

**Key insight:** `planModeInstructions` customizes the workflow, not the permission contract.

### Remote Ultraplan Prompting

**What it does:** Adds cloud/remote planning instructions for Ultraplan sessions.

**How it works:**
1. `remotePlanModeReminderLight` (`lUl`) starts at `cli_inner_pretty.js:537540`.
2. `remotePlanModeReminderWithDiagram` (`cUl`) starts at `cli_inner_pretty.js:537576`.
3. `remotePlanModeReminderMultiAgent` (`uUl`) starts at `cli_inner_pretty.js:537612`.
4. All three tell the model to call `ExitPlanMode` and handle the `__ULTRAPLAN_TELEPORT_LOCAL__` sentinel (`cli_inner_pretty.js:537562-537568`, `537583-537592`, `537613-537620`).
5. The sentinel constant is `H0f` at `cli_inner_pretty.js:537528`.

**Why this approach:**
- Remote plans may be edited or approved outside the local TUI, so the prompt must describe what happens after `ExitPlanMode`.
- The teleport sentinel prevents the remote model from revising or implementing after control has moved back to the local terminal.
- The multi-agent variant makes critique/reconciliation explicit before final approval.

**Key insight:** Ultraplan prompts are Plan Mode prompts with a transport protocol layered on top: draft remotely, approve through `ExitPlanMode`, then hand off locally if teleported.

## Tool Result Prompt Surface

`ExitPlanMode.mapToolResultToToolResultBlockParam` creates different text for different approval outcomes:

- awaiting leader approval: `cli_inner_pretty.js:381685-381702`;
- agent approval `"ok"` branch: `cli_inner_pretty.js:381703-381708`;
- empty plan approval branch: `cli_inner_pretty.js:381709-381714`;
- approved plan branch with optional named-teammate hint and edited-plan label: `cli_inner_pretty.js:381715-381730`.

These branches matter because downstream Ultraplan parsing looks for the `## Approved Plan:` or `## Approved Plan (edited by user):` marker. The 2.1.88 named source confirms this in `src/utils/ultraplan/ccrSession.ts`, which parses approved plan text from the tool result rather than from a hidden parameter.
