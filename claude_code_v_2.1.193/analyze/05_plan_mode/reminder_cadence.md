# Plan Mode Reminder Cadence

> Scope: how 2.1.193 decides when to inject `plan_mode`, `plan_mode_reentry`, and `plan_mode_exit` attachments, and how those attachments are rendered for the model. This is current-state coverage, not a new v2.1.193 delta.

## Summary

Plan Mode reminders are generated as transcript attachments, not as one-time tool-result text. The main attachment builder is `buildPlanModeAttachments` (`muf`, `cli_inner_pretty.js:473421`), registered under the `plan_mode` attachment lane at `cli_inner_pretty.js:473250`. Exit notices are generated by `buildPlanModeExitAttachment` (`HEl`, `cli_inner_pretty.js:473445`), registered under the `plan_mode_exit` lane at `cli_inner_pretty.js:473251`.

The cadence has three separate jobs:

- keep the read-only planning contract visible while the session remains in `"plan"` mode;
- avoid repeating the full planning workflow during every tool loop;
- mark re-entry and exit boundaries so a new planning cycle starts cleanly.

## Attachment Pipeline

The attachment scheduler invokes Plan Mode in the same batch as other ambient context providers:

- `plan_mode` lane: `Lg("plan_mode", () => muf(e, o, t, i))` at `cli_inner_pretty.js:473250`.
- `plan_mode_exit` lane: `Lg("plan_mode_exit", () => HEl(o, t))` at `cli_inner_pretty.js:473251`.
- The wrapper `Lg` measures attachment compute duration and recovers from attachment errors at `cli_inner_pretty.js:473293-473314`.

This placement matters because reminders are recomputed as part of the normal message-to-model pipeline. Plan Mode does not depend on the model remembering the `EnterPlanMode` result forever; it reasserts the contract through attachments while the permission context says the session is in plan mode.

## Key Algorithms and Decisions

### Human-Turn Throttle

**What it does:** Prevents full or sparse Plan Mode reminders from being emitted too frequently.

**How it works:**
1. `countHumanTurnsSinceLastPlanAttachment` (`Pko`) scans the message list backward from the newest entry (`cli_inner_pretty.js:473394-473408`).
2. It increments `turnCount` only for non-meta user messages that do not contain tool-result content (`cli_inner_pretty.js:473399`).
3. It stops when it finds the most recent `plan_mode` or `plan_mode_reentry` attachment (`cli_inner_pretty.js:473400-473405`).
4. It also stops at a `plan_mode_exit` boundary so a previous cycle does not throttle the next cycle (`cli_inner_pretty.js:473406`).
5. `buildPlanModeAttachments` suppresses a new reminder when a prior Plan Mode attachment exists and the human-turn count is below `TURNS_BETWEEN_ATTACHMENTS` (`cli_inner_pretty.js:473423-473425`).

**Why this approach:**
- Assistant/tool turns can be numerous during exploration. Counting them would cause the reminder to reappear after a few tool calls rather than after meaningful conversation progress.
- Human turns are the right signal because new user input can change scope, preferences, or approval state.
- The exit boundary prevents stale reminders from one planning cycle from affecting the next.

**Key insight:** The throttle is conversation-relative, not loop-relative. That is why Plan Mode can support long read-only exploration without flooding every tool round.

### Full vs Sparse Reminder Rotation

**What it does:** Alternates between the full workflow and a compact reminder.

**How it works:**
1. `countPlanModeAttachmentsSinceLastExit` (`fuf`) counts prior `plan_mode` attachments while scanning backward (`cli_inner_pretty.js:473410-473420`).
2. It stops at `plan_mode_exit` (`cli_inner_pretty.js:473415`).
3. `buildPlanModeAttachments` adds one to that count for the pending attachment (`cli_inner_pretty.js:473432`).
4. If `(count + 1) % FULL_REMINDER_EVERY_N_ATTACHMENTS === 1`, the reminder is `full`; otherwise it is `sparse` (`cli_inner_pretty.js:473432`).
5. The constants are both `5` in `PLAN_MODE_ATTACHMENT_CONFIG` (`Rko`, `cli_inner_pretty.js:474654`).

**Why this approach:**
- A full workflow is needed at entry and periodically thereafter because it carries the entire read-only and planning protocol.
- Sparse reminders are enough between full reminders because the model has already seen the complete contract.
- The modulo rule is simple, deterministic, and resets at explicit exit boundaries.

**Key insight:** The first attachment in a cycle is full because `(0 + 1) % 5 === 1`; the sixth, eleventh, and later every fifth attachment are also full.

### Re-entry Reminder

**What it does:** Adds a special reminder when the session returns to plan mode after having exited earlier in the same session.

**How it works:**
1. `ExitPlanMode` sets `hasExitedPlanModeInSession` through `setHasExitedPlanMode(true)` on approval paths (`kz`, `cli_inner_pretty.js:381657-381659`; UI paths also set it at `cli_inner_pretty.js:640855`, `640861`, `640888`, `640963`).
2. `buildPlanModeAttachments` checks `hasExitedPlanModeInSession()` and whether a plan file exists (`cli_inner_pretty.js:473428-473431`).
3. If both are true, it pushes `plan_mode_reentry` and clears the flag with `setHasExitedPlanMode(false)` (`cli_inner_pretty.js:473431`).
4. The renderer tells the model to read the existing plan, decide whether the current request is the same task or a different task, and edit the plan before calling `ExitPlanMode` again (`cli_inner_pretty.js:601513-601527`).

**Why this approach:**
- Re-entry is semantically different from first entry: there may be an old plan file that could be relevant, stale, or wrong.
- The one-time flag avoids repeating the re-entry warning after every subsequent reminder.
- Requiring an edit before exit prevents the model from treating an old plan as automatically approved for the new request.

**Key insight:** Re-entry is tied to a real plan file. If no prior plan exists, a normal `plan_mode` reminder is enough.

### Exit Notice Attachment

**What it does:** Emits a one-time `plan_mode_exit` message after the session has left plan mode.

**How it works:**
1. If the current permission mode is still `"plan"`, `buildPlanModeExitAttachment` clears `needsPlanModeExitAttachment` and returns no attachment (`cli_inner_pretty.js:473445-473446`).
2. Outside plan mode, it checks whether the explicit flag is set or whether the transcript contains a prior plan-mode attachment (`cli_inner_pretty.js:473447-473448`).
3. It clears the flag and emits `plan_mode_exit` with the current plan-file path and existence bit (`cli_inner_pretty.js:473449-473452`).
4. The renderer tells the model it has exited plan mode and may now edit, run tools, and take actions; if a plan file exists, it includes the file path (`cli_inner_pretty.js:602686-602693`).

**Why this approach:**
- The model needs an explicit boundary after approval because the previous reminder said not to edit.
- The attachment is one-time because repeating "you have exited" would waste context and could confuse later turns.
- The plan-file reference lets implementation continue from the approved artifact.

**Key insight:** Exit is communicated through both permission context and transcript context. The permission context allows editing; the exit attachment tells the model why the rules changed.

## Renderer Behavior

`renderPlanModeAttachment` (`o5f`) dispatches by attachment metadata:

- subagent attachment -> `renderSubagentPlanModeAttachment` (`l5f`, `cli_inner_pretty.js:601316`);
- sparse reminder -> `renderSparsePlanModeAttachment` (`a5f`, `cli_inner_pretty.js:601311`);
- otherwise -> `renderFullPlanModeAttachment` (`i5f`, `cli_inner_pretty.js:601224`).

The full renderer carries:

- a read-only preamble (`jQl`, `cli_inner_pretty.js:602488-602489`);
- plan-file existence/path instructions (`cli_inner_pretty.js:601226-601250`);
- five planning phases (`cli_inner_pretty.js:601254-601308`);
- the `ExitPlanMode` protocol footer (`GQl`, `cli_inner_pretty.js:601218-601222`).

The sparse renderer keeps only the invariant: plan mode is still active, only the plan file may be edited, and turns should end with `AskUserQuestion` or `ExitPlanMode` (`cli_inner_pretty.js:601311-601314`).

The subagent renderer is stricter because a subagent in plan mode should answer comprehensively and may clarify, but does not receive the full multi-agent planning workflow (`cli_inner_pretty.js:601316-601323`).

## Compact Carryover

Compaction can remove older tool-use attachments from the live context, so 2.1.193 rebuilds Plan Mode context explicitly:

- `buildPlanModeAttachmentForCompact` (`KKn`) starts at `cli_inner_pretty.js:470048`.
- It returns `undefined` unless the current mode is `"plan"` (`cli_inner_pretty.js:470049`).
- It emits a full `plan_mode` attachment with `reminderType: "full"`, plan file path, plan existence bit, subagent bit, and `planModeInstructions` (`cli_inner_pretty.js:470052-470064`).

This is cross-validated by the 2.1.88 named source in `src/utils/attachments.ts`, where `getPlanModeAttachments` and the compact attachment path use the same conceptual contract.
