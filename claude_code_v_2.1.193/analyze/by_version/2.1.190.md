### Why a "bug fixes only" release is published with no enumerated bullets

**What it does:** Advances the public version counter while shipping only small, internal-judgment fixes that the changelog does not itemize.

**How it works (release-engineering mechanics, inferred from the train shape):**
1. Internal `main` accumulates fixes continuously between feature tags — small correctness patches, reliability hardening, flake reductions, and follow-ups to the large 2.1.187 payload (a release that big often spawns small corrective patches in the releases right after it).
2. When a tag is cut, all merged commits since the last tag ship. The changelog is curated by hand to describe what a *user* would notice as a distinct, nameable change.
3. When the window's only work is a cluster of small fixes with no single nameable user-facing surface, the curated entry collapses to the boilerplate line "Bug fixes and reliability improvements."
4. The version is still published (rather than skipped) so the npm/release channel stays monotonic and the auto-updater has a clean, well-ordered sequence to walk. (The unpublished 2.1.184/.188/.189 numbers in this train show the opposite case — numbers that were cut internally but never shipped to the channel at all.)

**Why this approach (vs. folding the fixes into 2.1.191):**
- **Bisectability.** A maintenance release with a narrow, fixes-only scope is a clean bisect boundary. If a regression first appears in 2.1.191, the small scope of 2.1.190 makes it easy to rule in or out.
- **Risk isolation.** Reliability fixes — especially follow-ups to a large feature release like 2.1.187 — ship alone, so any fallout is attributable to a known, narrow scope rather than entangled with new features.
- **Cadence decoupling.** Shipping fixes promptly on their own version number gets corrections to users quickly without waiting for the next feature release to be ready.

**Key insight:** The *absence* of an enumerated user-facing diff is itself the honest finding. For a reverse-engineering pass that works only from shipped artifacts — and where no 2.1.187/2.1.190 intermediate build was extracted — the verifiable claim is not "here is the code 2.1.190 changed" (the bundle is the 2.1.193 *result*, and the version string is absent) but rather "2.1.190's changelog names no user-facing surface, and the surrounding train shape (a maintenance checkpoint between the heavy 2.1.187 payload and the feature-rich 2.1.191) is fully consistent with a fixes-only release."
