# v2.1.185 — Source Diff Analysis

**Theme: A single, small streaming-UX nicety — the mid-stream "no chunks arriving" hint was reworded and its trigger delayed.** 2.1.185 ships exactly one published bullet, and it touches one render path plus one timing constant. When a streaming response goes quiet (the SSE connection is open but no model output has arrived for a while), Claude Code surfaces an inline status line under the spinner. In 2.1.185 that line was (1) **reworded** from *"No response from API · Retrying in …"* to *"Waiting for API response · will retry in …"*, and (2) made **less trigger-happy** — the silence that must elapse before the hint appears was doubled from **10s to 20s**. Both are isolable to one declaration each: the rewritten JSX strings in the stall-status renderer (`Tyo`, cli_inner_pretty.js:366196–366240) and the doubled silence-threshold constant (`q2o = 20000`, cli_inner_pretty.js:596507, vs `u0o = 1e4` in the 2.1.183 before-picture). (Build under analysis: VERSION `2.1.193`, GIT_SHA `a1938d2a`, BUILD_TIME `2026-06-25T18:18:11Z`, cli_inner_pretty.js:162, 211 — a build embeds only its own version, so the string `"2.1.185"` appears nowhere in the bundle; the 2.1.185 delta is read out of the 2.1.193 *result* build and diffed against the 2.1.183 build.)

## 1. Stream-stall hint reworded "No response from API · Retrying in …" → "Waiting for API response · will retry in …", silence threshold 10s → 20s (IMPROVEMENT)

**Type:** improvement (streaming UX — string + timing) · **Modules:** Agent loop / LLM streaming, Retry status UI, Spinner/status renderer

### TL;DR

While a model response is streaming, a watchdog arms a timer after each received chunk. If no new chunk arrives within the **silence threshold**, the loop emits an `onRetryStatus({ kind: "stalled", … })` event and the spinner row renders an inline hint. 2.1.185 changed two things in that path:

1. **Wording.** *"No response from API · Retrying in `<countdown>` · check your network"* → *"Waiting for API response · will retry in `<countdown>` · check your network"*. The phrasing is softer and more accurate: the stream hasn't failed, it's just quiet, and the CLI hasn't actually retried yet — it's *about to*.
2. **Threshold.** The silence that must elapse before the hint shows was raised from **10 000 ms (10s)** to **20 000 ms (20s)** — the stall constant `q2o = 20000` (cli_inner_pretty.js:596507) versus the 2.1.183 value `u0o = 1e4` (cli_inner_pretty.js:584496, **(183)**).

### How it works

There are two collaborating pieces: the **detector** (a watchdog timer in the streaming loop that decides when a stream is "stalled") and the **renderer** (the JSX that draws the hint for a `kind: "stalled"` retry status).

**Detector — the silence-threshold timer.** Inside the API-call streaming loop, a re-armable timer (`xs`, cli_inner_pretty.js:594848–594861) is (re)started on every received chunk. It fires after `q2o` milliseconds; if, when it fires, no newer chunk has arrived (`Mn.lastAt` hasn't advanced past the value captured when the timer was armed), it flips a "stalled" flag and calls `onRetryStatus` with a `stalled` status:

```javascript
// ============================================
// streamStallWatchdog - arm a timer; if no chunk for q2o ms, mark the stream "stalled"
// Location: cli_inner_pretty.js:594848-594861 (193) ; threshold const cli_inner_pretty.js:596507 (193) vs 584496 (183)
// ============================================

// ORIGINAL (for source lookup, 193):
// q2o = 20000,                                         // :596507
let xs = function () {
  if (!s.onRetryStatus || !Mn) return;
  let Ho = Mn.lastAt, Y = performance.now();
  ((rs = setTimeout(() => {
    if (performance.now() - Y < q2o / 2) return;        // suspended-timer guard
    if (Mn.lastAt > Ho) { xs(); return; }               // a chunk arrived -> re-arm, not stalled
    ((ra = !0), s.onRetryStatus?.({ kind: "stalled", deadline: Date.now() + (Fn - q2o) }));
  }, q2o)),
    rs.unref?.());
};

// READABLE (for understanding):
const SILENCE_THRESHOLD_MS = 20000;                      // q2o (193); was 10000 (u0o, 183)
function armStallWatchdog() {
  if (!opts.onRetryStatus || !lastChunk) return;
  const armedAtChunkTime = lastChunk.lastAt;
  const armedAtWallClock = performance.now();
  stallTimer = setTimeout(() => {
    if (performance.now() - armedAtWallClock < SILENCE_THRESHOLD_MS / 2) return;  // timer fired early (host throttled/slept) -> ignore
    if (lastChunk.lastAt > armedAtChunkTime) { armStallWatchdog(); return; }      // progress since arming -> re-arm
    isStalled = true;
    opts.onRetryStatus({ kind: "stalled", deadline: Date.now() + (idleAbortTimeout - SILENCE_THRESHOLD_MS) });
  }, SILENCE_THRESHOLD_MS);
  stallTimer.unref?.();
}

// Mapping: xs→armStallWatchdog, q2o→SILENCE_THRESHOLD_MS, Mn.lastAt→lastChunk.lastAt, ra→isStalled, Fn→idleAbortTimeout, rs→stallTimer
```

Two details worth calling out. The `performance.now() - Y < q2o / 2` guard rejects a timer that fired too early in wall-clock terms — e.g. a laptop that slept and resumed, or a throttled background tab — so a suspended host doesn't produce a false "stalled" flash. And `deadline: Date.now() + (Fn - q2o)` makes the rendered countdown the time **remaining** until the hard idle-abort (`Fn`, the idle abort timeout at cli_inner_pretty.js:595167) rather than a fixed number — so doubling `q2o` to 20s also *shortens* the displayed "will retry in" countdown (same `Fn`, larger subtrahend), surfacing the hint closer to the actual abort.

**Renderer — the stalled-status JSX.** The retry-status component `Tyo` (cli_inner_pretty.js:366196) renders the `kind: "stalled"` branch (cli_inner_pretty.js:366217–366239). 2.1.185 rewrote the two strings in that branch:

Note the `<countdown>` slot (`a`) is shared with the **other** retry path — the rate-limit / API-error branch at cli_inner_pretty.js:366245 still reads *" · Retrying in `${a}…` · attempt N/M"*. That branch was **not** reworded; only the `kind === "stalled"` (open-but-silent connection) branch changed. The new lowercase *"will retry in"* therefore deliberately distinguishes "the connection is quiet, we're still waiting" (stalled) from "the request errored and we are actively retrying attempt N" (error retry).

### Why this approach

**Why reword.** *"No response from API"* reads like a failure — it implies the API returned nothing or errored, when in fact the SSE connection is open and the model is simply mid-generation with a gap between chunks (common during long tool-use planning or a slow first token). *"Waiting for API response"* states the true state. Likewise, *"Retrying in …"* over-promises: at that moment the CLI has **not** retried and may never need to — if the next chunk arrives, the hint just disappears. *"will retry in …"* (future tense, lowercase) frames it as a contingency, matching the watchdog's actual behavior (it only hard-aborts and retries at the idle-abort deadline `Fn`).

**Why 10s → 20s.** The 10-second trigger was firing on healthy-but-slow streams — a model spending 12–15s "thinking" before the first visible token would flash a scary red *"No response from API"* even though everything was fine, training users to ignore the warning. Doubling the threshold to 20s removes the most common false positive while still surfacing genuinely stuck streams well before the hard idle-abort. Because the rendered countdown is `Fn - q2o` (time left until that abort), the later trigger also means the hint, when it does appear, is a more urgent and more accurate "we really are about to give up" signal.

**Key insight:** This is a two-part change to one UX surface — *what* it says and *when* it says it move together. Softening the wording without delaying the trigger would still flash on every slow-first-token stream; delaying the trigger without softening the wording would still mislabel a quiet-but-alive connection as a failure. Doing both turns a noisy false-alarm into a quieter, more honest, later-firing hint.
