# 2.1.193 — Source Diff Analysis

**Theme:** **Auto-mode safety *surfacing* + observability, over a background-agent lifecycle correctness sweep.** Where 2.1.187 hardened the *gates*, 2.1.193 makes the autonomy surface **more transparent and self-healing**. The headline is a pair of auto-mode safety surfaces: a new `autoMode.classifyAllShell` setting that routes **every** Bash/PowerShell command through the danger classifier (not just arbitrary-code-execution patterns), and the surfacing of **auto-mode denial reasons** into the transcript, the denial toast, and `/permissions` recent denials. Alongside that is a real **observability** addition — the `claude_code.assistant_response` OpenTelemetry log event carrying the model's response text, with a genuine **upgrade gotcha**: when `OTEL_LOG_ASSISTANT_RESPONSES` is unset it *inherits* `OTEL_LOG_USER_PROMPTS`, so a deployment already logging prompt content starts receiving response content on upgrade. MCP gains self-healing auth — the `headersHelper` now re-runs and reconnects automatically on a 401/403 tool-call response (and feeds the carried-over needs-auth startup notice). The largest cluster is **background-agent lifecycle correctness**: idle background-shell **memory-pressure reaping**, a fix for backgrounding (←←) spuriously cancelling when all tasks carry over, suppression of a phantom "general-purpose (resumed)" subagent, the launch result no longer telling Claude to "end your response", a pinned-agent re-prompt fix, and a panel sibling-hiding fix. Two small surfaces round it out — live **path autocomplete in bash mode** (`!`) and **plugin `renames` auto-follow** — plus a clearer `/add-dir` message. The one out-of-scope bullet (the `/model` stale-after-`/login` fix) gets its primary analysis here: it is a net-new **org-keyed client-data cache**. (Build: VERSION `2.1.193` at `cli_inner_pretty.js:162`, build `a1938d2a`, `BUILD_TIME 2026-06-25T18:18:11Z`; line numbers are 193-bundle-specific.)

## 15. `/model` and client-data-gated UI showing stale/empty state immediately after `/login` (FIX — primary analysis here)

**Type:** fix · **Modules:** Client-data cache, Model picker, OAuth login · **Out of scope** (model-picker / client-data subsystem, not one of the twelve themes) — analyzed here.

### TL;DR

Immediately after `/login`, `/model` (and other UI gated on server-fetched "client data" — model notices, entitlement-driven feature flags, model-cost tables) could show **stale** data from the previous account/org, or an **empty** state, because the client-data cache was a single flat blob whose lookup key did not change when you switched accounts. 2.1.193 replaces the flat cache with an **org-keyed slot cache** (`clientDataCacheSlots`), so a login that changes the org produces a cache-key **miss** that forces a fresh fetch instead of serving the prior account's blob.

### How it works

Client data is fetched at startup/bootstrap by `ULe` (`api_bootstrap_fetch`, `cli_inner_pretty.js:350603`) and now persisted into a **keyed slot map** rather than a single field. The slot key is built by `mwn` (`cli_inner_pretty.js:148487`) from `[entrypoint, model, ccVersion, organizationUuid]` (sha256, first 16 hex chars), and the active key getter is installed at `cli_inner_pretty.js:350795` as `Vgo(() => mwn(Ggo()))`. The reader `getCachedClientData` (`Xk`, `cli_inner_pretty.js:604858`) looks up the slot for the **current** key first, falling back to the legacy flat `clientDataCache` only if no slot exists:

```javascript
// ============================================
// getCachedClientData - read the org-keyed client-data slot, legacy-fallback to flat cache
// Location: cli_inner_pretty.js:604855-604872 (v2.1.193)
// ============================================

// ORIGINAL (for source lookup):

function Xk() {
  if (!iXt) return null;
  let e = Lt(),
    t = iXt(),                                       // current cache key = mwn(Ggo())
    n = e.clientDataCacheSlots;
  if (n != null && Object.hasOwn(n, t)) return Rxi(n, t);   // hit the keyed slot
  let r = e.clientDataCache;                                // legacy flat fallback
  return typeof r === "object" && r !== null ? r : null;
}
function S4o() {                                     // hasClientDataCacheSlot
  if (!iXt) return !1;
  let e = Lt().clientDataCacheSlots;
  return e != null && Object.hasOwn(e, iXt());
}

  const state = getState(), key = cacheKeyGetter();           // key includes organizationUuid
  const slots = state.clientDataCacheSlots;
  if (slots != null && Object.hasOwn(slots, key)) return readSlot(slots, key);
  const legacy = state.clientDataCache;                       // pre-2.1.193 flat blob

// Mapping: Vgo→setClientDataCacheKeyGetter, Xk→getCachedClientData, S4o→hasClientDataCacheSlot,
//          iXt→cacheKeyGetter, mwn→buildClientDataCacheKey(organizationUuid,…), Ggo→currentCacheKeyInputs
```

`getCachedClientData` (`Xk`) is the read path for exactly the UI the bullet names — `/model`'s `model_notices` (`cli_inner_pretty.js:490493`), the picker's `pewter_owl_model` (`cli_inner_pretty.js:134964`), entitlement feature flags (`cli_inner_pretty.js:134973`), and the model-cost/system-prompt gates (`:134779`, `:134877`, `:592543`). Because its key now includes `organizationUuid`, switching accounts changes the key. The bootstrap fetch `ULe` keys its write on the **freshly-merged** oauth account (`A4a(m.oauthAccount, t.oauth_account)` → `organizationUuid`, `cli_inner_pretty.js:350646`) and records a `tengu_client_data_cache_key` event with `slot_hit`/`slot_stale`/`slot_changed`/`legacy_fallback` diagnostics (`cli_inner_pretty.js:350622`). The startup prefetch is gated on `hasClientDataCacheSlot` (`S4o`) at `cli_inner_pretty.js:713441` (`!cd() && !S4o()`) — after a login to a new org, the slot is absent, so the prefetch runs and repopulates fresh data. The `oauth_logout` mutator was also widened to clear all five cache fields (`additionalModelOptionsCache`, `additionalModelCostsCache`, `modelAccessCache`, `clientDataCache`, `clientDataCacheSlots`, `cli_inner_pretty.js:350425-350429`); 183's logout cleared only **three** of these five (`additionalModelOptionsCache` `:340788`, `additionalModelCostsCache` `:340789`, `clientDataCache` `:340790`) — the 193 delta is the two **added** clears `modelAccessCache` (`:350427`) and `clientDataCacheSlots` (`:350429`), the two fields that are themselves net-new in 193.

### Before / after vs 2.1.183

| | v2.1.183 | v2.1.193 |
|---|---|---|
| Cache shape | single flat `clientDataCache` blob (not account-keyed) | per-org-keyed `clientDataCacheSlots` (keyed by `organizationUuid`+model+version+entrypoint) |
| `clientDataCacheSlots` token count | **0** | **5** |
| `modelAccessCache` token count | **0** | **4** |
| `tengu_client_data_cache_key` diagnostic | absent | present (`slot_hit`/`slot_stale`/`slot_changed`/`legacy_fallback`) |
| Key getter (`setClientDataCacheKeyGetter`) | absent | `Vgo(() => mwn(Ggo()))` (`:350795`) |
| After `/login` to a new org | flat-cache key unchanged → serves prior account's blob (stale) or `null` (empty) | key changes → slot miss → fresh bootstrap fetch repopulates the correct data |
| Logout cache clear | 3 of 5 cache fields (`:340788`–`:340790`: model-options, model-costs, client-data) | all 5 (`:350425-350429`; **adds** `modelAccessCache`, `clientDataCacheSlots`) |

**Why:** the old single-slot cache assumed one account per machine, so a model picker reading `getCachedClientData()` right after switching accounts saw whatever the previous account had cached (stale) or nothing (empty), and there was no key change to trigger a refetch. Keying the cache by `organizationUuid` makes account identity part of the cache identity: an account switch is a key change, a key change is a slot miss, and a slot miss forces a fresh fetch — which is exactly the "show the *new* account's client data after `/login`" behavior the fix delivers. **Confidence: medium-high** — the org-keyed slot mechanism is net-new and verbatim (token counts 0→5/4/1), and `getCachedClientData` is verifiably the read path for `/model`'s notices and the picker's model gates; the attribution of *this* mechanism to *this specific* changelog bullet is inferred from the exact match between "client-data-gated UI stale/empty after `/login`" and an account-keyed client-data cache.
