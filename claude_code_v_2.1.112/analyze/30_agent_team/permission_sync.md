# Permission Sync — Agent Teams (v2.1.112)

## Overview

When a teammate needs user permission to execute a tool but cannot show its own UI prompt (typical of pane teammates running in a separate terminal, or in-process teammates whose user interaction is owned by the leader), the request is **routed over the mailbox** to the team lead, who decides on the worker's behalf.

The protocol is a request/response pair:
1. Worker sends `permission_request` to the leader's inbox.
2. Worker awaits a Promise tied to the request id.
3. Leader reads the request from its inbox, decides (typically by surfacing the request to the user).
4. Leader sends `permission_response` to the worker's inbox.
5. Worker's poll cycle picks up the response, resolves the Promise, returns the decision to the agent loop.

## Wire Format

### permission_request envelope

```typescript
type PermissionRequestText = {
  type: "permission_request";
  request_id: string;          // generated by worker
  agent_id: string;            // worker's sanitized name
  tool_name: string;
  tool_use_id: string;
  description: string;
  input: object;               // the tool's input
  permission_suggestions?: string[];
};
```

The mailbox-record `from` is the worker's name; `text` is the JSON-encoded payload.

### permission_response envelope

```typescript
type PermissionResponseText = {
  type: "permission_response";
  request_id: string;          // matches the request
  subtype: "success" | "error";
  // when subtype === "success":
  response?: {
    updated_input?: object;    // optional rewrite
    permission_updates?: PermissionDecisionUpdate[];   // e.g., add an allow rule
  };
  // when subtype === "error":
  error?: string;              // user-supplied feedback
};
```

The `from` is `"team-lead"` (the constant `Mz`).

## Worker → Leader: aI8

```javascript

// READABLE (for understanding):
async function sendPermissionRequest(args) {
  const leaderName = await getTeamLeaderName(args.teamName);
  if (!leaderName) {
    log("[PermissionSync] Cannot send permission request: leader name not found");
    return false;
  }
  try {
    const payload = buildPermissionRequest({
      request_id: args.id,
      agent_id: args.workerName,
      tool_name: args.toolName,
      tool_use_id: args.toolUseId,
      description: args.description,
      input: args.input,
      permission_suggestions: args.permissionSuggestions,
    });
    await writeToMailbox(leaderName, {
      from: args.workerName,
      text: JSON.stringify(payload),
      timestamp: new Date().toISOString(),
      color: args.workerColor,
    }, args.teamName);
    log(`[PermissionSync] Sent permission request ${args.id} to leader ${leaderName} via mailbox`);
    return true;
  } catch (e) {
    log(`[PermissionSync] Failed to send permission request via mailbox: ${e}`);
    return false;
  }
}
```

### bb4 — discovering the leader's name

```javascript
async function getTeamLeaderName(teamName) {
  const team = teamName || getCurrentTeamName();
  if (!team) return null;
  const config = await readTeamConfig(team);                  // $J6
  if (!config) return null;
  const leadAgentId = config.leadAgentId;
  return config.members.find(m => m.agentId === leadAgentId)?.name || "team-lead";
}
```

The fallback to `"team-lead"` handles the case where a leader was registered but the members list hasn't been persisted yet — early in spawn flow this can happen briefly.

```javascript
async function sendPermissionResponse(workerName, decision, requestId, teamName) {
  const team = teamName || getCurrentTeamName();

    log("[PermissionSync] Cannot send permission response: team name not found");
    return false;

      from: fromName,
      text: JSON.stringify(payload),
      timestamp: new Date().toISOString(),

    log(`[PermissionSync] Sent permission response for ${requestId} to worker ${workerName} via mailbox`);
    return true;
  } catch (e) {
    log(`[PermissionSync] Failed to send permission response via mailbox: ${e}`);
    return false;
  }
}
```

```javascript
function buildPermissionResponse(input) {

    return {
      type: "permission_response",
      request_id: input.request_id,
      subtype: "error",
      error: input.error || "Permission denied",
```

## Round-Trip Sequence Diagram

```
Worker (teammate)                     Leader
─────────────────                     ──────
  agentLoop yields tool_use
       │
       │  canUseTool = LXY(...)
       │  decides: "needs user approval"
       │
       ▼
  generate request_id
  store pending Promise in worker map
  aI8 → bb4 (read team file) → Ti1 (build) → F_ (write)
       │
       │   (permission_request now in leader's inbox)
       │
       │   ─── leader's poll picks up ───►
       │                                    msgs = readMailbox(leader, team)
       │                                    parse with j18
       │                                    surface to user (TUI)
       │                                       │
       │                                       │  user decides
       │                                       ▼
       │                                    sI8 → Vi1 (build) → F_ (write)
       │   ◄─── written to worker's inbox ───
       │
  worker's CXY poll picks up
       │
       │  parsePermissionResponse (KJ6)
       │  find pending Promise by request_id
       │  resolve(decision)
       ▼
  canUseTool returns to agentLoop
  agentLoop continues turn (with possibly updated_input)
```

Note the asymmetry:
- The worker's poll interval (CXY) determines its **wakeup latency** for the response.
- The leader's poll interval determines its **wakeup latency** for the incoming request.
- Both are 500ms, so the round-trip is at most ~1 second of polling, plus the user's decision time.

## Pending Promise Plumbing (LXY)

`LXY` (chunks.154.mjs:2203) holds an in-memory map `pendingPermissions: Map<request_id, Resolver>`. The flow:

```typescript
// Inside the canUseTool returned by LXY:
async function canUseTool(toolName, input, opts) {
  if (!needsLeaderApproval(toolName, input, opts)) return autoAllow();
  const requestId = randomUUID();
  const pending = new Promise<Decision>(resolve => {
    pendingPermissions.set(requestId, resolve);
  });
  await sendPermissionRequest({
    id: requestId, teamName, workerName, workerColor,
    toolName, toolUseId: opts.toolUseId,
    description: opts.description, input,
    permissionSuggestions: opts.suggestions,
  });
  // Block until the matching permission_response arrives via the next poll cycle
  return await raceWithAbort(pending, currentWorkAbort.signal);
}

// In the poll-handling path (when a permission_response arrives):
function onPermissionResponse(parsed) {
  const resolver = pendingPermissions.get(parsed.request_id);
  if (!resolver) return; // no matching request — noise/stale
  pendingPermissions.delete(parsed.request_id);
  resolver(translateResponseToDecision(parsed));
}
```

The map is per-runner, so concurrent permissions for the same teammate (rare but possible if the agent loop is mid-streaming) are individually keyed.

### Cancellation

If the user presses Escape while a permission is pending, `currentWorkAbort.signal` trips. `raceWithAbort` rejects the pending Promise, which propagates as a turn-level abort up to `bXY`. The map entry stays — the response (if it eventually arrives) is harmlessly discarded by the `if (!resolver) return` check.

## Sandbox Permission Variant

When a tool wants to escape the bash sandbox to reach a specific host (e.g., `curl https://api.example.com`), there is a sibling protocol:
- `sandbox_permission_request` (`ki1` builder) — `{requestId, workerId, workerName, workerColor, host}`.
- `sandbox_permission_response` (`Ni1` builder) — `{requestId, host, allow}`.

The dispatch functions `xb4` (chunks.100.mjs:1427) and `tI8` (chunks.100.mjs:1455) mirror `aI8` and `sI8`. The leader's UI surfaces a different prompt ("Allow alpha to access api.example.com?") and the response carries a boolean instead of a generic decision.

The reason for a separate type is that sandbox decisions don't have an `updated_input` analogue — the question is binary, and the `permission_updates` field would be inert. Carrying a focused payload keeps the JSON small and the TUI flow distinct.

## Why Round-Trip via Mailbox?

A naive design might bypass the mailbox by:
- Calling a local function on the leader's process (only works for in-process teammates; pane teammates can't reach into the leader's memory).
- Opening a UNIX domain socket (requires daemon, fragile across crashes).
- Sharing a SQLite database (overkill, harder to debug).

The mailbox approach gives:
- **Crash recovery.** If the leader crashes mid-decision, the request stays in its inbox; on restart, the leader can decide again.
- **Cross-process uniformity.** The same code path works for in-process and pane teammates.
- **Auditability.** The user can `cat ~/.claude/myteam/inboxes/team-lead.json | jq .` to see exactly what was requested.

The latency cost (up to one poll cycle on each end) is trivial relative to the user decision time (typically seconds).

## When the Worker Doesn't Use the Mailbox

If the teammate is **in-process** AND the leader can show a foreground prompt, `LXY` calls a local prompt handler instead:

```typescript
if (canShowLocalPrompt) {
  const decision = await showLocalPermissionPrompt({...});
  return decision;
}
// else fall through to mailbox path
```

This is the "fast path" — same process, same React tree, no FS round-trip. The team status renderer pauses the teammate's spinner and inlines a permission prompt in its row.

In-process teammates that *can't* prompt locally (e.g., the leader's TUI is suppressed or already showing another prompt) fall back to the mailbox path. Pane teammates always use the mailbox.

## Permission Suggestions

`permission_suggestions` is an array of UI hints like:
```
["Always allow Bash 'git status'", "Allow this command", "Run sandboxed"]
```
These are surfaced as quick-actions in the leader's prompt. The leader's `permission_response` may carry a `permission_updates` array if the user picked "Always allow…", which the worker's `LXY` translates back into a permission rule update for its local context.

## Failure Modes

| Failure | Cause | Recovery |
|---------|-------|----------|
| Leader's name unknown | Team config not yet written | Worker logs and returns `false` from `aI8`; canUseTool defaults to deny or retries on next event |
| Mailbox write fails | Lock contention exhausted | aI8 returns `false`; canUseTool denies |
| Response never arrives | Leader crash, network partition (for shared dirs) | Worker awaits the Promise indefinitely until `currentWorkAbort` trips (Escape) |
| Stale response (request was cancelled) | `if (!resolver) return` discards | No-op |
| Two responses for one request | Leader bug or duplicate poll | Second is discarded by `pendingPermissions.delete` after the first resolves |

The worker's primary recovery for "no response" is the per-turn abort: pressing Escape in the leader cancels everything and the teammate moves to its next poll cycle. Without that, a missing response would block the teammate forever.

## Telemetry

There are no specific `tengu_team_permission_*` events; the permission round-trip uses the standard tool-permission telemetry surface (`tengu_canUseTool_*` events fired by the underlying canUseTool machinery). Mailbox-routed permissions appear in the same logs as direct prompts, distinguished only by the mailbox tag in debug logs (`[PermissionSync]`).

This intentional consolidation keeps permission analytics agnostic to delivery mechanism.

---

## Why Not Encrypt or Sign?

The mailbox lives entirely under the user's home directory. Anyone with FS access has the same access as Claude. Adding crypto would protect against… nothing (anyone who can read the inbox can also modify the leader's process), and would complicate the debug-friendliness of plain JSON.

If multi-user teams cross machines (a future direction), this trade-off would have to revisit. Today's design is single-machine, single-user, so plaintext is acceptable.

---

## Summary

The permission sync subsystem reuses the mailbox protocol to ferry approval decisions between worker and leader. Builders/parsers (`Ti1`/`Vi1`/`j18`/`KJ6`) shape the payload; dispatchers (`aI8`/`sI8`) handle the I/O; `LXY` plumbs request/response into the worker's local Promise map. The result is a uniform, crash-resilient, debuggable permission flow that works identically for in-process and pane teammates.
