# Model-Invokable Built-in Slash Commands (v2.1.108)

## What it does

In v2.1.108 the model can discover and invoke built-in slash commands like `/init`, `/review`, and `/security-review` through the Skill tool. Previously these commands existed as `type: "prompt"` builtin commands but were either filtered out of the model-visible skill listing or rejected by the Skill tool's `validateInput`. Now they appear in the listing payload, and `validateInput` accepts them. Only commands that are **structurally** unsuitable (`local-jsx` UI commands, or `built-in CLI` no-op commands) remain rejected, and the rejection message has been split to distinguish the two cases.

## Why these three commands

All three are `type: "prompt"` with `source: "builtin"` in both v2.1.88 and v2.1.112:

| Command | v2.1.88 location | v2.1.112 chunk |
|---------|------------------|----------------|
| `/init` | `src/commands/init.ts:227` (`type: 'prompt'`, `source: 'builtin'`) | chunks.174.mjs:426-442 (`QbY`/`GBK`) |
| `/review` | `src/commands/review.ts:34` (`type: 'prompt'`, `source: 'builtin'`) | chunks.183.mjs:2153-2177 (`LdY`/`dr8`) |
| `/security-review` | `src/commands/security-review.ts:198` (via `createMovedToPluginCommand` -> `type: 'prompt'`, `source: 'builtin'`) | chunks.185.mjs:197-231 (`QnK`) |

So the type and source haven't changed - what changed is whether the model **sees** them in the skill listing and whether the Skill tool's `validateInput` **accepts** them.

## How it works

### 1. The listing path

The skill listing is generated by walking `getCommands(cwd)` and applying a series of filters. In v2.1.112, the relevant filters are:

- `cmd.type === "prompt"` - structurally required (Skill tool only handles prompts).
- `cmd.userInvocable !== false` OR `mid-message-bypass` - exclude commands marked model-only-invocable.
- `skillOverrides[cmd.name] !== "off"` AND `skillOverrides[cmd.name] !== "user-invocable-only"` - per-user filtering.
- `cmd.disableModelInvocation !== true` - per-skill flag.

Built-in commands like `/init`, `/review`, `/security-review` satisfy all four (none have `disableModelInvocation: true`, none have `userInvocable: false`, all are `type: 'prompt'`). The v2.1.108 listing change is that built-in commands are no longer filtered by a `cmd.source !== "builtin"` predicate. The intent: a model-proactive agent can choose `/review` mid-task when the user asks for a code review, just like it can choose any user-authored review skill.

The 2.1.105 cap raise (250 -> 1,536 chars) means built-in command descriptions don't get truncated as aggressively. `/review`'s description ("Review a pull request") and `/init`'s description ("Initialize a new CLAUDE.md file with codebase documentation") fit comfortably under both caps, but `/security-review`'s description ("Complete a security review of the pending changes on the current branch") is also well under the new cap.

A single uniform error for any non-prompt command. In v2.1.112, the error distinguishes:

- `local-jsx` commands (UI panels - e.g., `/ultrareview`, `/login`, `/permissions`, `/config`) - "UI command"
- everything else with `type !== "prompt"` (e.g., `local` commands like `/stats`, `/cost`, `/exit`) - "built-in CLI command"

The new message also tells the model what to do instead ("Ask the user to run /<name> themselves"), giving the model an actionable failure path rather than just a flat refusal.

### 3. Why didn't built-ins work via the Skill tool in v2.1.88?

The v2.1.88 SkillTool also accepts `type === 'prompt'`. So `/init`, `/review`, and `/security-review` would have passed `validateInput` in v2.1.88 too. The 2.1.108 change is not about the tool itself - it's about **the listing pipeline**. Built-in commands were filtered out of the model-visible skill listing.

Evidence: look at `formatCommandsWithinBudget` in v2.1.88 (`/lyz/codespace/3rd/claude-code/src/tools/SkillTool/prompt.ts:70-171`). The function takes `commands: Command[]` and formats them. The caller decides what goes into the list, and v2.1.88 callers excluded `source === "builtin"` commands. v2.1.112's caller path (chunks.97.mjs:710-769 `sh4`) does not filter by source.

So a v2.1.88 model could technically guess "/init" and call the Skill tool with `{skill: "init"}` - validation would pass, and the command would run. But the model wouldn't have known the command existed, because it wasn't in the listing. The 2.1.108 change is the **listing inclusion**, paired with the friendlier rejection message for commands that genuinely can't run that way.

### 4. Why include built-ins in the listing now?

The listing cap was 250 chars in v2.1.88 (`MAX_LISTING_DESC_CHARS = 250`). With the cap raised to 1,536 chars in v2.1.105, the listing has more headroom for additional entries. The 2.1.108 change uses that headroom to expose builtins.

The three builtin descriptions are short ("Review a pull request" - 21 chars, "Initialize a new CLAUDE.md file with codebase documentation" - 60 chars, "Complete a security review of the pending changes on the current branch" - 73 chars). Even with name overhead, three new entries fit well under the 8,000-char default budget. They're cheap to expose.

## Why this approach?

### Alternative 1: separate "builtin tools" exposed list

Instead of exposing builtins through the same Skill tool, the model could have a dedicated `Builtin` tool that lists `/init`, `/review`, etc. Why not?

- **Symmetry** - they're prompt-based commands just like user/project/plugin skills. Treating them as a different kind of thing would invent a distinction without a difference.
- **Discoverability** - the model already knows to check the Skill tool's listing. Putting builtins in a second listing means the model needs to look in two places.
- **Cap budgeting** - the skill listing has a unified char budget. A second list would need its own budget logic, which duplicates the truncation/names-only logic from `sh4`.

The Skill tool's listing is already the canonical "things the model can invoke as prompts" surface. Builtins fit there naturally.

### Alternative 2: expose builtins but reject them at validateInput time

Show them in the listing but have `validateInput` reject them with "use /name yourself" - same as `local-jsx` commands today. Why not?

- **Wasted model turns** - if the listing says "/init: Initialize a new CLAUDE.md file..." and then the model tries to call it and gets rejected, that's a wasted turn (and possibly a cascading failure if the model decides the rejection is a hard error).
- **Mismatch with intent** - the listing tells the model "you can use this." Rejecting at call time would be a UX bug, not a feature.

The 2.1.108 change is consistent: if the listing claims a command is invocable, the tool **lets it run**. Only commands that genuinely can't be invoked (UI panels, no-op CLI) are rejected.

### Alternative 3: add `userInvocable: false` to builtins

Mark built-in commands as model-only. Why not?

- **Backward compatibility** - users have been typing `/init` for ages. Removing user invocability would be a breaking change.
- **Symmetry, again** - user-authored skills can be either user-or-both-invocable. Forcing built-ins to be model-only would be the special case, not the rule.

The 2.1.108 change preserves both paths: a user can still type `/init`, and the model can also pick it from the listing.

## Key insight

The 2.1.108 changelog wording ("the model can now discover and invoke built-in slash commands like `/init`, `/review`, and `/security-review` via the Skill tool") is precise:

- **Discover** - they're now in the listing the model receives every turn.
- **Invoke** - validateInput now accepts them with a clearer rejection path for the truly-non-invocable cases.

This is a **distribution change**, not a capability change. The underlying mechanism (Skill tool calls `processPromptSlashCommand`, which expands the prompt into the conversation) was always there. v2.1.108 just makes the model aware of it for these specific commands. The clearer rejection split (`local-jsx` -> "UI", everything else -> "built-in CLI") is the user-facing tell that the team thought through the failure modes when widening the listing.

The change is also gated by the v2.1.105 cap raise - without 1,536 chars/entry, the listing budget was too tight to comfortably accommodate the new entries. So 2.1.105 and 2.1.108 are a pair of changes that together expand the model-invocable surface.
