## 1. `/tui` slash command (NEW — promotes NO_FLICKER to first-class)

**Type:** feature · **Modules:** Fullscreen renderer, Slash commands

### v2.1.88 baseline

No `/tui` command. The `CLAUDE_CODE_NO_FLICKER` env var (added in v2.1.89) was the only way to toggle alt-screen rendering, and it required restart to apply.

### v2.1.112 state

```javascript
const tuiCommandHandler = async (rawArgs) => {
  const arg = rawArgs.trim().toLowerCase();
  const validModes = ["default", "fullscreen"];

  // No arg: show current state
  if (arg === "") {
    return {
      type: "text",
      value: `Current renderer: ${getUserSettings().tui ?? (isFullscreenMode() ? "fullscreen" : "default")}. Usage: /tui <${validModes.join("|")}>`
    };

  if (!validModes.includes(arg)) {
    return { type: "text", value: `Unknown renderer "${arg}". Usage: /tui <${validModes.join("|")}>` };
  }

  const targetMode = arg;
  const targetIsFullscreen = targetMode === "fullscreen";

  // No-op
  if (targetIsFullscreen === isFullscreenMode()) {
    return { type: "text", value: `Already using the ${targetMode} renderer.` };
  }

  // Persist
  const { error } = saveSettings("userSettings", { tui: targetMode });
  if (error) return { type: "text", value: `Failed to save setting: ${error.message}` };

  // Telemetry + relaunch with the new mode
  logEvent("tengu_tui_command", { fullscreen: targetIsFullscreen });
  return relaunchSession({
    freshIfNoTranscript: true,
    env: { CLAUDE_CODE_TUI_JUST_SWITCHED: targetMode },
    dropEnv: ["CLAUDE_CODE_NO_FLICKER", "CLAUDE_CODE_FORCE_FULLSCREEN_UPSELL"]
  });

//          lq→isFullscreenMode, P7→saveSettings, d→logEvent, er8→relaunchSession
```

### Why this approach

**What `/tui fullscreen` does:**
1. Save `tui: "fullscreen"` to user settings.
2. Drop `CLAUDE_CODE_NO_FLICKER` (so the env-var override doesn't conflict).
3. Set `CLAUDE_CODE_TUI_JUST_SWITCHED=fullscreen` so the relaunch knows what to do.
4. Relaunch the session, preserving the conversation.

**Why a relaunch, not a hot-swap:** Switching renderers requires reinitializing the Ink instance, mouse-handling state, scrollback, alt-screen entry — too risky to do mid-session. The session-preserving relaunch (with `freshIfNoTranscript: true`) is the surgical option.

**Why drop `CLAUDE_CODE_NO_FLICKER` env:** The user has now explicitly chosen via setting; the env var (a different override path) shouldn't second-guess that. Settings are the durable record, env vars are session overrides.

**Why "tui" as the setting name:** The intent is the *terminal UI*, not just flicker. Future renderers can be added to the enum without renaming.

## 2. `/focus` slash command (split from Ctrl+O)

**Type:** UX · **Modules:** Focus mode, Slash commands

### v2.1.88 / v2.1.97 baseline

`Ctrl+O` had two responsibilities:
- Toggle verbose transcript visibility.
- In NO_FLICKER mode, also toggle focus view (the "show me only the final response" mode).

### v2.1.112 state — full handler with config persistence

```javascript
// ============================================

// Location: chunks.189.mjs (search 'name: "focus"')
// ============================================

// READABLE (for understanding):
const focusCommandDef = {
  type: "local-jsx",
  name: "focus",
  description: "Toggle focus view (show only your prompt, a tool summary, and the final response)",
  isEnabled: isFullscreenMode,   // hide from menu when not in fullscreen
  immediate: true,                // no confirmation prompt — toggle and go
  load: () => Promise.resolve({
    async call(emitMessage, ctx) {
      const next = !ctx.getAppState().briefTranscript;

      // 1. Update in-session state
      ctx.setAppState((s) => s.briefTranscript === next ? s : { ...s, briefTranscript: next });

      // 2. Persist to config if changed
      if (getAppConfig().briefTranscript !== next) {
        updateAppConfig((c) => ({ ...c, briefTranscript: next }));
      }

      // 3. User feedback
      emitMessage(next ? "Focus view enabled" : "Focus view disabled", { display: "system" });
      return null;
    }
  })
};

// Mapping: FoY→focusCommandDef, lq→isFullscreenMode, H8→getAppConfig, d8→updateAppConfig
```

### State semantics

`briefTranscript` lives in *two* places:
- **Session AppState** — drives current rendering immediately
- **App config** — persists across session restarts

The toggle writes both. This means a `/focus` invocation persists to the next session. A user who wants temporary focus would have to toggle off before exiting (or live with persistent focus).

`Ctrl+O` is now verbose-toggle only. Focus view is its own command `/focus` with `immediate: true` (no confirmation prompt).

### Why this approach

**The original conflation:** Two distinct UX behaviors got bound to one keychord because both were "show me less stuff." But:
- Verbose toggle changes *transcript detail* (full vs collapsed).
- Focus toggle changes *what's visible* (intermediate steps vs only final).

These are orthogonal — a user might want focus + verbose, or focus + non-verbose.

**Why a slash command for focus:**
- Focus is a *mode* (state persists across turns), not a momentary action.
- A slash command (with optional args) maps better to mode-toggle than a keychord.
- `Ctrl+O` is preserved for the simpler verbose toggle.

**`isEnabled: lq` (i.e. `isFullscreenMode`):** Focus view is meaningful only in fullscreen mode (which has alt-screen scrollback). In default mode, scrollback is the OS terminal's; focus would just hide-from-current-frame.

## 3. Push notification tool (NEW)

**Type:** feature · **Modules:** Tools, Remote Control

### v2.1.112 state — full prompt body

```javascript
// ============================================
// PushNotification tool definition + system-prompt augmentation
// Location: chunks.101.mjs:1261-1286
// ============================================

// Tool name
ic = "PushNotification"

// Short description (shown in tool list)
cI4 = "Send a notification to the user via their terminal and, when Remote Control is connected, also push to their mobile device"

// Full prompt body (lI4):
lI4 = `This tool sends a desktop notification in the user's terminal. If Remote Control is connected, it also pushes to their phone. Either way, it pulls their attention from whatever they're doing — a meeting, another task, dinner — to this session. That's the cost. The benefit is they learn something now that they'd want to know now: a long task finished while they were away, a build is ready, you've hit something that needs their decision before you can continue.

Because a notification they didn't need is annoying in a way that accumulates, err toward not sending one. Don't notify for routine progress, or to announce you've answered something they asked seconds ago and are clearly still watching, or when a quick task completes. Notify when there's a real chance they've walked away and there's something worth coming back for — or when they've explicitly asked you to notify them.

Keep the message under 200 characters, one line, no markdown. Lead with what they'd act on — "build failed: 2 auth tests" tells them more than "task done" and more than a status dump.

If the result says the push wasn't sent, that's expected — no action needed.`

// System-prompt augmentation when push is enabled (wr1)
function wr1() {
  return e56() ? `

When an event lands that the user would want to act on now — an error appeared, the status they were waiting on flipped — send a ${ic}. Not every event is worth a push; the ones that change what they'd do next are.` : ""
}

// Enable gate (e56)
function e56() {
  return I18() && H8().agentPushNotifEnabled === !0
}

// Mapping: ic→PUSH_NOTIFICATION_TOOL_NAME, cI4→pushDescription, lI4→pushFullPrompt,
//          wr1→getPushSystemPromptAugment, e56→isPushNotificationEnabled,
//          I18→isAmberSentinelGateEnabled (= u8("tengu_amber_sentinel", false)),
//          H8→getAppConfig
```

### Why this approach

**The "discipline-via-prompt" pattern:** The tool description is unusually long because it carries *behavioral guidance* alongside the spec. The prompt teaches the model when *not* to use the tool — and it does so with concrete examples:
- "err toward not sending one" — bias frame
- "Don't notify for routine progress, ... when a quick task completes" — anti-patterns
- "build failed: 2 auth tests" tells them more than "task done" — example of *good* message
- "task done" / "a status dump" — examples of *bad* messages
- "If the result says the push wasn't sent, that's expected — no action needed" — handles the failure mode without escalation

This is more effective than relying on a separate system prompt or post-hoc filter — it's right next to where the model decides whether to call the tool.

**System-prompt augmentation (`wr1`):** When push is enabled, an additional sentence is added to the system prompt: "When an event lands that the user would want to act on now ... send a PushNotification." This is the *reminder* path — the tool description teaches *how*; the system prompt teaches *when*.

**Why the `agentPushNotifEnabled` gate:** Push notifications are intrusive. Default-off respects user attention. The user explicitly opts in per-config.

**Why double-gating (`I18()` AND `agentPushNotifEnabled`):** The first gate (`tengu_amber_sentinel`) is the **server-side rollout** — Anthropic can disable the feature for a cohort by flipping the flag. The second gate is the **per-user opt-in**. Both must be true.

**Why also fire a desktop notification (not just push):** The terminal-notification path works locally without Remote Control. Push is the *additional* mobile delivery when bridge is connected. A user without Remote Control still benefits from local desktop alerts.

## 4. `Ctrl+O` reverts to verbose-only; `autoScrollEnabled` config

**Type:** UX · **Modules:** Fullscreen renderer

The `Ctrl+O` chord is now strictly "toggle verbose transcript view." Focus is split out (per §2).

`autoScrollEnabled` is a new config:
```javascript
// chunks.151.mjs:2323-2327
autoScrollEnabled: {
  source: "global",
  type: "boolean",
  description: "Auto-scroll conversation to bottom (fullscreen mode only)"
}
```

When false, the conversation does *not* auto-scroll to the bottom on new content. Users who like scrolling back to read prior content without being yanked forward turn this off.

## 5. `Ctrl+G` external editor: Claude's last response as commented context

**Type:** UX · **Modules:** External editor

When opening the external editor with `Ctrl+G`, an option (in `/config`) lets the user include Claude's last response as a `# commented` block at the top of the editor buffer.

### Why this approach

**Use case:** A user composing a long follow-up and wants to reference what Claude just said. Without this, they have to copy-paste from the terminal. With this, the response is right there, commented out (so it doesn't get sent back).

## Summary

v2.1.110 **promotes flicker-free rendering** from env-var-only to a first-class command + setting (`/tui`, `tui` key in settings). It splits the overloaded `Ctrl+O` chord into focus (`/focus`) and verbose toggle. The push notification tool joins the Monitor tool (v2.1.98) as a "the model can interact with the user's attention" surface. Remote Control gets broader coverage (slash commands, scheduled tasks, session names).

The pattern across this version: **previously-flagged features are turned into stable, settings-managed features.** "Stabilization" here means "graduate the env var to a setting and command."
