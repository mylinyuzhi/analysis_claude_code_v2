## 1. `EnterWorktree` `path` parameter (NEW)

**Type:** feature · **Modules:** Worktrees, Tools

### v2.1.88 baseline

`claude-code-kim/src/tools/EnterWorktreeTool/EnterWorktreeTool.ts` only supported *creating* a new worktree. No way to switch into an existing one.

### v2.1.112 schema — mutually-exclusive name vs path

```javascript
// ============================================

  path: y.string().optional()
    .describe("Path to an existing worktree of the current repository to switch into instead of creating a new one. Must appear in `git worktree list` for the current repo. Mutually exclusive with `name`.")

// READABLE (for understanding):

```

### v2.1.112 dispatch — `WvK` returns the effective path-or-name

```javascript
// chunks.151.mjs:390045
function WvK({ name: q, path: K }) {
  return K ?? q ?? ""        // path wins; else name; else empty (= random)
}
```

The handler then telemeters with different event names depending on which path was taken:

```javascript
// chunks.151.mjs (in the EnterWorktree handler)
process.chdir(K.worktreePath), ..., d(
  q.path ? "tengu_worktree_entered_existing" : "tengu_worktree_created",
  { mid_session: true }
);

let z = q.path ? "Entered" : "Created";
return { data: { worktreePath: K.worktreePath, ..., message: `${z} worktree...` } };
```

### Why this approach

**The need:** Multi-task workflows. A user with worktrees `feat-A`, `feat-B`, `feat-C` already set up wants the agent to hop between them, not create more.

**Why a parameter rather than a separate tool:**
- Conceptually it's "enter worktree X" whether X exists or not — one tool, two internal paths.
- Adding a separate `SwitchWorktree` tool would split the model's mental model.
- The mutually-exclusive validation ensures the model can't pass both ambiguously.

**Why telemetry differentiates `entered_existing` vs `created`:** Lets the team measure how often the new code path is exercised. If `entered_existing` is rare, the feature might not be worth its prompt budget.

**Edge case:** A `path` that *isn't* in `git worktree list` would fail at execution. The schema description tells the model "Must appear in `git worktree list` for the current repo" — guidance via spec.

## 2. PreCompact hook blocking (NEW)

**Type:** feature · **Modules:** Hooks, Compact

### v2.1.88 baseline

PreCompact hook existed (it's referenced in `claude-code-kim/src/types/hooks.ts`) but couldn't *block* compaction — only observe.

### v2.1.112 state

```javascript
// ============================================
// reactiveCompactDispatcher - check PreCompact block before compacting
// Location: chunks.101.mjs:1560-1582
// ============================================

// ORIGINAL (for source lookup):
let H = await oc({ trigger: "auto", customInstructions: null }, ...).catch(...);
if (H.blockedBy) {
  return E(`Reactive compact blocked by PreCompact hook: ${H.blockedBy}`),
         w.onCompactProgress?.({ type: "compact_end" }),
         w.setSDKStatus?.(null),
         null;
}
w.onCompactProgress?.({ type: "compact_start" });
let J = await Dr1(Y, A, { customInstructions: H.newCustomInstructions }).catch(...);

// READABLE (for understanding):
const preCompactResult = await runPreCompactHook(
  { trigger: "auto", customInstructions: null },
  context.abortController.signal
).catch((err) => { logError(err); return {}; });

if (preCompactResult.blockedBy) {
  log(`Reactive compact blocked by PreCompact hook: ${preCompactResult.blockedBy}`);
  context.onCompactProgress?.({ type: "compact_end" });
  context.setSDKStatus?.(null);
  return null;
}

context.onCompactProgress?.({ type: "compact_start" });
const compactResult = await performCompaction(messages, model, {
  customInstructions: preCompactResult.newCustomInstructions
}).catch(handleCompactError);

// Mapping: H→preCompactResult, J→compactResult, oc→runPreCompactHook,
//          Dr1→performCompaction, w→context, j6→logError
```

**Hook can block via:**
- Exit code 2
- `{"decision":"block"}` JSON return

### Why this approach

**What it does:** A hook can prevent compaction from happening. The next attempted compaction will re-invoke the hook.

**Use cases:**
- **Snapshot before compact:** A hook that takes a transcript snapshot before compact. If the snapshot fails, block compaction so the next try has a chance.
- **Deferred compact:** A hook that says "not now, the user is in the middle of an important debugging session — give them a few more turns before compacting."
- **Custom compact instructions:** Even when not blocking, the hook can return `{"newCustomInstructions": "..."}` to inject extra prompt instructions to the compacter.

**Why both exit-2 and JSON `{decision:"block"}`:**
- Exit-2 is the "shell-like" idiom for blocking — same convention as PreToolUse.
- JSON is for hooks that want to communicate richer state (block reason, custom instructions).

**Trade-off:** A buggy PreCompact hook can prevent compaction forever, leading to context overflow. The autocompact thrash circuit-breaker (v2.1.89) catches this case after 3 failed compactions.

## 3. Plugin `monitors` manifest key (NEW)

**Type:** feature · **Modules:** Plugins, Monitor tool

### v2.1.112 state — single monitor entry schema (`wi5`)

```javascript
// ============================================
// MonitorEntrySchema - per-entry shape for plugin monitors
// Location: chunks.18.mjs (search "wi5")
// ============================================

// ORIGINAL (for source lookup):
wi5 = C6(() => y.strictObject({
  name: y.string().min(1).describe("Identifier for this monitor, unique within the plugin. Used to dedupe so re-arming (plugin reload, repeat skill invoke) does not spawn duplicates."),
  command: y.string().min(1).describe('Shell command to run as a persistent background monitor. Each stdout line is delivered to the model as a <task_notification> event; the process runs for the session lifetime. ${CLAUDE_PLUGIN_ROOT}, ${CLAUDE_PLUGIN_DATA}, ${user_config.*}, and ${ENV_VAR} are substituted. Runs in the session cwd — prefix with `cd "${CLAUDE_PLUGIN_ROOT}" && ` if the script needs its own directory.'),
  description: y.string().min(1).describe("Short human-readable description of what is being monitored (shown in task panel and notification summary)."),
  when: y.union([
    y.literal("always"),
    y.string().startsWith("on-skill-invoke:").refine((q) => q.length > 16, {
      message: "on-skill-invoke: must specify a skill name"
    })
  ]).default("always").describe('Arm trigger. "always" arms at session start and on plugin reload. "on-skill-invoke:<skill>" arms the first time that skill is dispatched (via Skill tool or slash command).')
}))

// READABLE (for understanding):
const MonitorEntrySchema = z.strictObject({
  name: z.string().min(1)
    .describe("Unique-within-plugin identifier; used for deduping so re-arming doesn't spawn duplicates"),

  command: z.string().min(1)
    .describe(
      "Shell command to run as a persistent background monitor. Each stdout line " +
      "is delivered to the model as a <task_notification> event. " +
      "Variables substituted: ${CLAUDE_PLUGIN_ROOT}, ${CLAUDE_PLUGIN_DATA}, " +
      "${user_config.*}, ${ENV_VAR}."
    ),

  description: z.string().min(1)
    .describe("Short human-readable description shown in task panel and notification summary"),

  when: z.union([
    z.literal("always"),
    z.string().startsWith("on-skill-invoke:")
      .refine(s => s.length > 16, "on-skill-invoke: must specify a skill name")
  ]).default("always")
    .describe('"always" arms at session start; "on-skill-invoke:<skill>" arms when that skill dispatches')
});

// And the array constraint:
const MonitorArraySchema = z.array(MonitorEntrySchema)
  .refine(arr => new Set(arr.map(m => m.name)).size === arr.length,
          "Monitor names must be unique within a plugin");

// And the manifest entry:
const PluginManifestMonitors = z.object({
  monitors: z.union([
    pathSchema().describe("Path to a JSON file containing the monitors array, relative to the plugin root"),
    MonitorArraySchema
  ]).describe(
    "Background watch scripts the host arms as persistent Monitor tasks " +
    "(unsandboxed, same trust tier as hooks) so plugins need not instruct the model to arm them. " +
    "When omitted, monitors/monitors.json at the plugin root is loaded if present."
  )
});

// Mapping: wi5→MonitorEntrySchema, XO1→MonitorArraySchema, $i5→PluginManifestMonitors,
//          gA6→pathSchema, C6→lazyZodSchema
```

### Algorithm: How `when` resolves

| `when` value | Behavior |
|--------------|----------|
| `"always"` (default) | Monitor armed at session start and on plugin reload |
| `"on-skill-invoke:my-skill"` | Monitor armed the first time `my-skill` is dispatched (Skill tool or slash command) |

The validation `q.length > 16` enforces "on-skill-invoke:" + at least one char of skill name (16 = `"on-skill-invoke:".length`).

### Why this approach

**What it does:** A plugin can declare *background monitors* in its manifest. When the plugin is active, the host arms those monitors as persistent Monitor tasks (the v2.1.98 Monitor tool, but auto-armed instead of model-invoked).

**Difference from manual Monitor tool calls:**
| Aspect | Manual Monitor (model-invoked) | Plugin Monitor (host-armed) |
|--------|-------------------------------|----------------------------|
| Scope | Single turn | Session lifetime |
| Trigger | Model calls the tool | Plugin manifest at session start / skill invoke |
| Trust | Standard tool permission | Same trust tier as hooks (unsandboxed) |
| Example | "watch the deploy log for 30s while I think" | "always show me CI status changes" |

**Use case:** A plugin for a CI system declares a monitor that watches CI status. Whenever CI fails, a `<task_notification>` lands in the chat — the model doesn't need to remember to start a monitor.

**Trust tier — "unsandboxed, same trust tier as hooks":** Intentional. The user is trusting the plugin author to declare safe monitors; sandboxing them would limit useful integrations (CI/build/git status checks need full access).

**Why `monitors/monitors.json` auto-load:** Convention-over-configuration. A plugin with a `monitors/` directory implicitly opts in without manifest changes.

**Why dedup by `name`:** Plugin reloads (plugin update, `/reload-plugins`) would otherwise spawn duplicate monitor processes. The `name` provides identity for the dedup logic.

## 5. Stalled API stream handling — 5min abort + retry non-streaming

**Type:** infra · **Modules:** LLM API

Streams that produce no data for 5 minutes now abort and retry **non-streaming** instead of hanging indefinitely. (Different from a server-side stall — this is a client-side detection.)

### Why this approach

**The shape of the bug:** Network stalls (mid-stream TCP problems) wouldn't be detected by the client; the user saw a frozen spinner forever. The 5-min cap forces the client to give up and try a non-streaming call as a last resort.

**Why fall back to non-streaming:** Non-streaming gives a single result-or-error and avoids the streaming complexity. If the actual issue is network-level, both modes will fail; if it's streaming-protocol-specific, the non-streaming retry succeeds.

**v2.1.110 reverts the v2.1.110 cap on non-streaming fallback retries** because it traded long waits for outright failures during API overload.

## 10. Skill description handling — listing cap raised + warning

**Type:** infra · **Modules:** Skills

Listing cap raised from 250 chars to 1,536 chars. Added a startup warning when descriptions are truncated, so skill authors know to shorten.

### Why this approach

**The cap exists to prevent skill descriptions from dominating the prompt.** 250 was too tight — many useful skills have nuanced descriptions that need ~500 chars. 1,536 is roomy enough for almost all skills, with the warning catching outliers.

## 11. `WebFetch` strips `<style>` and `<script>` content

**Type:** perf · **Modules:** WebFetch

Many CSS-heavy pages have `<style>` blocks of 50-200KB that drown out the actual text content. WebFetch now strips them server-side (well, client-side, but before the prompt injection). Same for `<script>`.

### Why this approach

**The shape of the bug:** A user fetches a docs page; 80% of the response is CSS, 5% is JS, 15% is the actual content. The model never gets to read the content because the budget was exhausted on style rules.

**Why strip rather than truncate:** Truncation might cut off useful content. Stripping non-content tags preserves the signal.
