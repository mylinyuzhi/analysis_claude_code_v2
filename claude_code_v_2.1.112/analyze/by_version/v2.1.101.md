## 1. `/team-onboarding` command (NEW)

**Type:** feature · **Modules:** Slash commands

### v2.1.88 baseline

No `/team-onboarding`.

### v2.1.112 state

```javascript
// chunks.190.mjs:195-210
jsY = {
  type: "prompt",
  name: "team-onboarding",
  description: "Help teammates ramp on Claude Code with a guide from your usage",
  isEnabled: () => !0,
  disableModelInvocation: !0  // generates output, no model call
}
```

The command scans local Claude Code usage data (sessions, slash commands invoked, MCP servers configured) and generates a markdown ramp-up guide. Useful when onboarding a new team member who needs to understand the team's workflow.

### Why this approach

**The pain:** Configuring Claude Code in a team-friendly way (settings.json, plugins, skills) requires deep familiarity. New teammates struggle to discover what's set up.

**Why a command rather than docs:** The output is *team-specific* — it reflects how *this team's* sessions are actually run, not generic best practices. Static docs can't capture that.

**Why `disableModelInvocation: true`:** The command's output is deterministic from local data, no model needed. This makes it instant and free.

## 2. OS CA certificate store trust by default (NEW)

**Type:** feature · **Modules:** TLS, Auth

### v2.1.88 baseline

`claude-code-kim/src/upstreamproxy/upstreamproxy.ts:32` defaults to a Linux system CA bundle path; no automatic trust of the OS keychain. Enterprise users with corporate TLS proxies (Zscaler, Palo Alto) had to manually configure `NODE_EXTRA_CA_CERTS`.

### v2.1.112 state

```javascript
// ============================================
// resolveCaStores - select CA store sources from env/flags
// Location: chunks.19.mjs:2150-2167
// ============================================

// ORIGINAL (for source lookup):
function Mr5() {
  let q = process.env.CLAUDE_CODE_CERT_STORE;
  if (q) {
    let K = [];
    for (let _ of q.split(",")) {
      let z = _.trim().toLowerCase();
      if (z === "bundled" || z === "system") {
        if (!K.includes(z)) K.push(z)
      } else if (z) E(`CA certs: unrecognized CLAUDE_CODE_CERT_STORE source '${z}', ignoring`, { level: "warn" })
    }
    return K.length > 0 ? K : NU7
  }
  if (xD6("--use-system-ca") || xD6("--use-openssl-ca")) return ["system"];
  return NU7  // Default: ["bundled", "system"]
}

// READABLE (for understanding):
function resolveCaStores() {
  const explicit = process.env.CLAUDE_CODE_CERT_STORE;
  if (explicit) {
    const stores = [];
    for (const raw of explicit.split(",")) {
      const tag = raw.trim().toLowerCase();
      if (tag === "bundled" || tag === "system") {
        if (!stores.includes(tag)) stores.push(tag);
      } else if (tag) {
        log(`CA certs: unrecognized CLAUDE_CODE_CERT_STORE source '${tag}', ignoring`,
            { level: "warn" });
      }
    }
    return stores.length > 0 ? stores : DEFAULT_STORES;
  }
  if (hasCliFlag("--use-system-ca") || hasCliFlag("--use-openssl-ca")) {
    return ["system"];
  }
  return DEFAULT_STORES;  // ["bundled", "system"]
}

// Mapping: Mr5→resolveCaStores, NU7→DEFAULT_STORES, xD6→hasCliFlag, E→log
```

### Why this approach

**What changed:** The default is now `["bundled", "system"]` — both the bundled CA bundle (for known-good public CAs) AND the OS system store (for corporate/internal CAs). Previously only bundled.

**Why both stores by default:**
- Bundled-only fails for users behind corporate TLS proxies (which use private CAs).
- System-only fails on systems with broken or stale system stores.
- Trying both lets either succeed.

**Why `bundled` is opt-out:** Setting `CLAUDE_CODE_CERT_STORE=bundled` reverts to the v2.1.88 behavior. Useful for compliance environments that want strict known-CA-only trust.

**Edge case — TLS pinning:** Some enterprises *want* to fail-closed when a cert isn't from their CA. `CLAUDE_CODE_CERT_STORE=system` covers this.

**Trade-off:** Bundled bundle ages and becomes outdated; system store may include user-added shady CAs. Combining both is a "defense in depth" choice that prefers connectivity over strict policy.

## 3. `/ultraplan` auto-creates default cloud environment

**Type:** feature · **Modules:** Ultraplan

### v2.1.88 baseline

`claude-code-kim/src/commands/ultraplan.tsx` already exists. The teleport flow expected the user to *manually* configure a cloud environment first via the web UI. Without it, `/ultraplan` would error.

### v2.1.112 change

The teleport call now passes `useDefaultEnvironment: true`, which triggers automatic provisioning of a default environment if none exists. First-time users no longer have to detour to the web setup wizard.

### Why this approach

**The pain:** First-run UX was bad. Users invoked `/ultraplan`, got an error, had to leave the CLI for the web, configure an environment, come back. The default-environment auto-create eliminates the detour.

**Trade-off:** Users who *want* a custom environment must explicitly create one — but the default environment is fine for most users. Power-user customization is preserved via the web.

## 5. Focus mode self-contained summaries

**Type:** UX · **Modules:** Focus mode, Output

Now that focus mode shows only Claude's *final* message, Claude is informed of this in the system prompt. The model writes more self-contained summaries that don't reference earlier turns the user can't see.

### Why this approach

**The shape of the bug:** A user in focus mode sees only the final response. If the response says "as I mentioned above," the "above" is hidden. The fix is to tell the model *that the user is in focus mode* so it writes accordingly.

**This is prompt engineering through context awareness.** A pattern reused for `/recap` (v2.1.108) and other constrained-view modes.

## 10. Settings resilience — unrecognized hook event names

**Type:** infra · **Modules:** Settings

### Bug

If `settings.json` contained an unrecognized hook event name (e.g. typo of `PreToolUse` as `PreToolUSe`), the **entire** file was being ignored at parse time. The user lost ALL their hooks/permissions until they noticed.

### Fix

Unknown hook event names are now logged as warnings; the rest of the file loads normally. Aligns with the principle "don't fail-closed for typos."

## 16. POSIX `which` fallback command-injection (FIXED)

**Type:** security · **Modules:** LSP binary detection

When the LSP module fell back to POSIX `which` for binary detection, an attacker-controlled `PATH` containing shell metacharacters could trigger command injection. Now uses a hardened argument-array invocation.

---

## 17. Memory leak — historical message-list copies in virtual scroller

**Type:** fix · **Modules:** Virtual scroll

The virtual scroller was retaining dozens of historical copies of the full message list, each up to MBs. Long sessions accumulated 100s of MB. Fixed by holding only references rather than copies.

---

## 18. `--resume`/`--continue` losing context on large sessions

**Type:** fix · **Modules:** Resume

The resume loader was anchoring on a *dead-end branch* of the conversation tree (a branch that ended in an error/abort) instead of the live conversation. Result: large sessions resumed with only a fragment of context.

### Fix

The anchor selection now prefers the live conversation branch (longest path with non-error tail). Falls back to the dead-end branch only if no live branch exists.

---

## 19. `--resume` chain recovery bridging into unrelated subagent

**Type:** fix · **Modules:** Resume, Subagent

When a subagent message landed near a main-chain "write gap" (the chain was broken by an async write failure), the resume loader could *bridge* the gap into the subagent's conversation, conflating two streams.

### Fix

The bridge now respects subagent isolation: a subagent message is never selected as the bridge target for the main chain.

---

## 20. Crash on `--resume` when Edit/Write tool result missing `file_path`

**Type:** fix · **Modules:** Resume, Tools

A persisted Edit/Write result with a missing `file_path` (corrupted on write) crashed the resume loader. Now handled gracefully.

## 21. Hardcoded 5-minute request timeout

**Type:** fix · **Modules:** LLM API

A 5-minute hardcoded timeout was aborting slow backends (local LLMs, extended-thinking, slow gateways) regardless of `API_TIMEOUT_MS`. Now the env var actually wins.

---

## 22. `permissions.deny` overriding PreToolUse hook `permissionDecision: "ask"`

**Type:** security · **Modules:** Permissions

A PreToolUse hook returning `permissionDecision: "ask"` was *downgrading* a `permissions.deny` rule to a prompt. Now deny rules win over any hook decision.

### Why this matters

A misbehaving (or malicious) hook could effectively bypass deny rules by returning "ask" — the user would see a prompt and might approve. The fix ensures deny is final.

---

## 23. `--setting-sources` without `user` → cleanup ignores `cleanupPeriodDays`

**Type:** fix · **Modules:** Settings

When `--setting-sources` was specified without `user`, the background cleanup ignored `cleanupPeriodDays` and used a hardcoded 30-day default — deleting conversation history older than 30 days. Now cleanup respects the setting from any source.

## 24. Bedrock SigV4 + `ANTHROPIC_AUTH_TOKEN` (FIXED)

**Type:** fix · **Modules:** Bedrock auth

When `ANTHROPIC_AUTH_TOKEN`, `apiKeyHelper`, or `ANTHROPIC_CUSTOM_HEADERS` set an Authorization header, Bedrock SigV4 was failing with 403 because both auth schemes were attempting to write the header. Now the SigV4 path takes precedence over the env-set Authorization.

## Summary

v2.1.101 is a **resilience release**. The marquee features (`/team-onboarding`, OS CA trust, `/ultraplan` auto-env) are real but the bulk of the changelog is fixing edge-case failures from earlier features:
- `/resume` recovery from broken chains
- Settings/hook robustness against typos
- Memory leaks
- Bedrock SigV4 conflicts
- Plugin install/update consistency

The OS CA store change is quietly the biggest user-visible quality-of-life win — many enterprise users went from "can't connect" to "just works" without configuration.
