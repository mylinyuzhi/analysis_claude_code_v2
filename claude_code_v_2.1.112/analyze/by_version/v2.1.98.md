## 2. `CLAUDE_CODE_PERFORCE_MODE` env var (NEW)

**Type:** feature · **Modules:** Edit/Write tools

### v2.1.88 baseline

No Perforce awareness. Edit/Write to a Perforce-controlled read-only file would silently overwrite (or fail with a generic permission error).

### v2.1.112 state

```javascript
// ============================================
// isPerforceMode + isPerforceProtected - Perforce-aware Edit gate
// Location: chunks.16.mjs:3070-3076
// ============================================

// ORIGINAL (for source lookup):
function mY1() {
  return S6(process.env.CLAUDE_CODE_PERFORCE_MODE)
}
function gf6(q) {
  return mY1() && (q & 128) === 0   // 128 = S_IWUSR (writable bit)
}

// READABLE (for understanding):
function isPerforceMode() {
  return parseExplicitTrue(process.env.CLAUDE_CODE_PERFORCE_MODE);
}

// Returns true if Perforce mode is on AND the file lacks the user-write bit
// (i.e. file is read-only because Perforce hasn't checked it out yet).
function isPerforceProtected(fileMode) {
  const S_IWUSR = 0o200;  // 128 in decimal
  return isPerforceMode() && (fileMode & S_IWUSR) === 0;
}

// Mapping: mY1→isPerforceMode, gf6→isPerforceProtected, S6→parseExplicitTrue

// Error message at chunks.16.mjs:3320
const Ff6 = "File is read-only — it has not been opened for edit in Perforce. " +
            "Run `p4 edit <file>` to check it out, then retry. " +
            "Do not chmod the file writable; that bypasses Perforce tracking.";
```

### Why this approach

**The pain:** Perforce-managed files default to read-only on disk; you `p4 edit <file>` to mark them open for edit, which makes them writable. An LLM that sees a read-only file and *just chmod's it* would bypass Perforce — committing changes that aren't tracked.

**The fix:** When `CLAUDE_CODE_PERFORCE_MODE=1`, Edit/Write/NotebookEdit fail on read-only files with a *specific* error message telling the model to use `p4 edit`. The error explicitly warns against chmod.

**Why an opt-in env var:** Perforce is enterprise-only; defaulting it on would surprise the rest of the userbase with confusing read-only errors on intentionally-read-only files (e.g. system config files).

**Why the chmod warning in the error message:** A naive LLM would try `chmod +w file` as a workaround. The error explicitly forbids this. This is *prompt engineering through error text* — the error itself is part of the spec.

## 3. Monitor tool (NEW)

**Type:** feature · **Modules:** Tools

### v2.1.88 baseline

No Monitor tool. The PowerShell tool prompt at `src/tools/PowerShellTool/PowerShellTool.tsx:366` already *referenced* the Monitor tool ("For streaming events ... use the Monitor tool"), suggesting the tool was being prepared but not yet shipped — a documentation-leak.

### v2.1.112 state

The Monitor tool ships as a deferred tool (loaded lazily when needed). Located in `chunks.101.mjs` alongside the PushNotification tool. It streams events from a long-running background command, useful for:
- `tail -f /var/log/app.log | grep --line-buffered "ERROR"`
- WebSocket event listeners
- Polling APIs at intervals

### Why this approach

**The gap before Monitor:**
- Bash with `run_in_background: true` returns immediately with a process handle. Good for "fire and forget."
- Bash with default mode blocks. Good for "wait for completion."
- Neither was good for "stream events as they happen for a long time."

**Monitor's design:**
1. Take a command + a regex/grep filter.
2. Run the command in the background.
3. Stream matching lines back to the model as they arrive.
4. The model can decide when to stop monitoring.

**Why a separate tool:** This pattern has special concerns Bash doesn't:
- Buffering (`grep` defaults to block-buffered output, requires `--line-buffered`).
- Termination semantics (model needs to *end* the monitor, not the command).
- Coverage (the filter must match terminal states like crashes, not just successes — silence looks identical to "still running").

These concerns are baked into the tool prompt rather than left as user error in Bash.

## 4. Linux subprocess sandboxing with PID namespace (NEW)

**Type:** feature · **Modules:** Sandbox

### What it does

When `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` is set on Linux, subprocesses run in a **PID namespace**, so the subprocess can't see (and thus can't signal) other processes on the host. Combined with the existing seccomp filtering, this is a meaningful sandbox tightening.

### Why this approach

**The gap PID namespacing closes:** Without it, a sandboxed subprocess running `kill -9 1` could signal init. With PID namespacing, the subprocess sees a fresh PID 1 of its own.

**Why an env-var opt-in:** PID namespacing requires `unshare(CLONE_NEWPID)` which needs unprivileged-user-namespaces support. Older kernels and corporate-managed systems may not allow this. Opt-in keeps the feature available without breaking those environments.

## 6. `--exclude-dynamic-system-prompt-sections` flag (print mode)

**Type:** feature · **Modules:** Print mode, Prompt cache

For headless `-p` runs that share a prefix across many invocations, dynamic system-prompt sections (timestamp, env-specific bits) cause cache misses. This flag strips them, improving cross-user prompt caching.

### Why this approach

**The use case:** A platform running thousands of `claude -p "summarize: ..."` invocations wants every invocation to share the same prompt prefix, so the prompt cache hits across users. Dynamic sections (timestamps, working directory) destroy this.

**Why a flag:** Removing the dynamic sections changes the model's behavior subtly (no time awareness). Users opt in based on what they're optimizing for: throughput vs. context-aware behavior.

## 10. Bash tool permission bypass — backslash-escaped flag (FIXED)

**Type:** security · **Modules:** Bash permissions

### The vulnerability

A backslash-escaped flag like `git \-rm` was being parsed by the permission classifier as `git -rm` (a typo) and auto-allowed as a read-only command, but the *shell* would execute it as a command argument. An attacker could craft commands that bypassed the classifier this way.

### Fix

The classifier now respects backslash escaping in the same way the shell does — `\-rm` is `-rm` as an argument, not `-rm` as a flag. The auto-allow path checks that all args are flag-shaped or known-safe.

---

## 11. Compound Bash commands — forced perm prompts (FIXED)

**Type:** security · **Modules:** Bash permissions

### Bug

In auto and bypass-permissions modes, compound commands (`safecmd && dangerouscmd`) were bypassing the *forced* permission prompts for safety checks and explicit ask rules. The classifier was scoring the head of the chain only.

### Fix

Each segment of a compound command is independently classified. If any segment matches an ask rule, the whole compound prompts.

## 12. Read-only commands with env-var prefixes — gate to safe vars

**Type:** security · **Modules:** Bash permissions

## Summary

v2.1.98 is a **massive release** combining:
1. **Two big features:** Vertex wizard + Monitor tool + Perforce mode + Linux PID-namespace sandbox.
2. **Bash permission hardening:** the largest concentrated security pass in the v2.1.88-2.1.112 window.
3. **A long tail of fixes** carried over from v2.1.97 (resume picker, NO_FLICKER, OTEL).

The Bash hardening is notable: 8+ specific bypass classes fixed, with the backslash-escape and compound-command bypasses being the most consequential (both could lead to arbitrary code execution in auto mode). v2.1.98 is where the team treats Bash permission classification as a **first-class security surface** rather than a best-effort heuristic.
