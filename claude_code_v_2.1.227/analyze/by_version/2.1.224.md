# Claude Code 2.1.224 Implementation Analysis

## Release shape

The supplied 2.1.224 section has 31 bullets and introduces the largest new surfaces in the window:
self-hosted execution, HTTPS archive plugins, and cross-machine session messaging. It also expands
sandbox secret transformation and makes Remote Control history/connection state explicit.

  [`60_self_hosted_runner`](../60_self_hosted_runner/README.md).

- Bedrock model IDs prefer an explicit region prefix but retain partition guards, discovery-aware

### Self-hosted runner lease supervision

**What it does:** Converts an operator-controlled machine into a bounded execution pool without giving
one remote session authority over the runner supervisor.

**How it works:**
1. CLI argument validation resolves the base directory and proves it can be created and written before
   registration.
2. Registration returns runner identity and capacity; a derived poll interval avoids fixed-rate load.
3. The supervisor polls for leases only when local capacity is available.
4. Each accepted lease receives a dedicated directory, environment projection, and child process.
5. Heartbeat/completion operations remain in the supervisor; the child receives only session-scoped
   authority.
6. Failure paths report lease/session status and clean up local ownership.
7. Shutdown stops new polling, allows active children a bounded drain, and then terminates leftovers.

**Why this approach:**
- Preflight before registration prevents a dead runner record from being created for an unusable host.
- Separating supervisor credentials from child credentials limits compromise blast radius.
- Capacity-driven polling provides backpressure; accepting leases first and queueing locally would
  violate remote scheduling assumptions.

**Key insight:** Registration is not readiness. The runner proves its local execution substrate first,
then lets capacity and lease ownership drive every child lifecycle transition.

### Cross-session recipient pinning and inbound holds

**What it does:** Makes names convenient without allowing a same-named local or remote session to
replace an identity the sender already confirmed.

**How it works:**
1. Discovery merges reachable local and Remote Control candidates into one roster with stable refs.
2. An explicit ref resolves directly; a name can resolve only when ambiguity and transport checks pass.
3. Confirmation stores the selected identity, not just the display name.
4. Later sends prefer that pin and refuse substitution when one transport cannot be checked.
5. Delivery success is reported only after the recipient inbox/transport acknowledges the write.
6. On the receiving side, bypassed-permission sessions can hold inbound messages for approval.
7. Held messages have both a queue bound and expiry; headless/startup paths surface their pending state.

**Why this approach:**
- Names are human-friendly but not unique across machines. Stable pins turn a one-time confirmation into
  an identity guarantee.
- Refusing substitution sacrifices opportunistic delivery but prevents a message reaching the wrong
  session after a partial discovery failure.
- A bounded expiring hold queue preserves consent without becoming invisible permanent storage.

**Key insight:** Address discovery may be eventually consistent; confirmation pins make delivery
identity monotonic even when the roster is not.

### Archive install integrity pipeline

**What it does:** Installs a plugin from HTTPS without relying on git or npm while preserving source,
content, and filesystem boundaries.

**How it works:**
1. The manifest validates the archive URL and optional SHA-256 before network access.
2. Download follows only policy-approved redirects and strips headers that must not cross origins.
3. Response size and timeout are bounded.
4. When a digest is supplied, verification occurs before extraction or installation.
5. Extraction rejects traversal, absolute paths, links, and invalid archive shapes.
6. Plugin validation runs in a staging location; publication uses an atomic move/install record update.

**Why this approach:**
- Download-then-validate avoids executing package-manager lifecycle behavior.
- Digest pinning is optional for usability, so redirect and extraction policy remain mandatory.
- Staging plus atomic publication prevents a failed extraction from leaving a half-installed plugin.

**Key insight:** HTTPS authenticates the connection; the installer separately validates redirect
authority, archive bytes, and extracted filesystem shape.
