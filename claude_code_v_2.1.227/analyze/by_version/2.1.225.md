# Claude Code 2.1.225 Implementation Analysis

## Release shape

The supplied 2.1.225 section has 14 bullets. It is a reliability pass over newly introduced
cross-machine and self-hosted surfaces, with one important authentication correction: a rejected
caller-owned OAuth token must not silently become the stored login.

### Preserve caller-owned OAuth token identity

**What it does:** Handles a 401 without replacing an explicitly supplied long-lived OAuth token with a
different stored login's short-lived access token.

**How it works:**
1. Recovery clears credential caches and reads current persisted state.
2. An SDK token callback gets first priority when the embedding SDK owns rotation.
3. A local `CLAUDE_CODE_OAUTH_TOKEN` without remote-child or Unix-socket ownership enters a preserve
   branch.
4. That branch refuses to adopt the stored login even when it is newer and valid.
5. The runtime reports remediation: mint/restart with a new setup token or unset it and use `/login`.
6. Host-injected and remote-child sources may still adopt disk/environment rotation because their host
   is the declared credential owner.
7. A real refresh-token credential proceeds through locked refresh instead of source substitution.

**Why this approach:**
- Credential freshness cannot override explicit source authority. The stored login may belong to a
  different user, organization, plan, or lifetime contract.
- Disabling all recovery would break legitimate host rotation, so the decision uses provenance and
  session kind rather than one global rule.
- The trade-off is that a headless process with an expired user token fails until restart instead of
  opportunistically continuing under another identity.

**Key insight:** A 401 is evidence that one credential failed, not permission to select a different
identity source.

### Confirmed cross-machine recipient monotonicity

**What it does:** Retains the identity a sender confirmed even when a later local/remote discovery pass
is partial.

**How it works:**
1. The initial resolution records transport, stable session reference, and display name.
2. Later sends attempt to re-resolve the pinned identity, not merely the name.
3. If the pinned transport cannot be checked, a same-named candidate from another transport is not
   substituted.
4. Explicit new selection is required to change the pin.
5. A send is reported successful only after the chosen transport confirms delivery.

**Why this approach:**
- Eventual discovery makes absence ambiguous; it does not prove that the confirmed session ceased to
  exist.
- Refusing substitution can delay a message, but misdelivery to a same-named session is worse and hard
  to undo.

**Key insight:** Once confirmed, recipient identity is monotonic; degraded discovery can reduce
availability but cannot silently weaken identity.
