# Claude Code 2.1.222 Implementation Analysis

## Release shape

The supplied 2.1.222 section has 21 bullets. Its common theme is boundary enforcement: worktree
isolation must govern every execution surface, hook authority must not expand inside maintenance
tasks, cross-session messages must pass the same safety policy as local actions, and network liveness
must be measured from actual transport progress.

## Implementation themes

- Worktree containment now covers file edits and Bash in ordinary, forked, and subagent sessions. The
  runtime resolves repository/worktree identity before permission and execution rather than relying on
  the prompt alone. See [`53_subagent_limits`](../53_subagent_limits/delegation_and_containment.md).
- Restricted background operations do not inherit an auto-allow hook as an unrestricted grant. Hook
  output remains one input to the final permission decision. See
  [`41_hooks`](../41_hooks/hook_runtime_matching_execution_and_trust.md).
- Startup connectivity uses the configured proxy-aware request stack and an explicit timeout. Streaming
  distinguishes raw byte activity, meaningful events, and semantic completion. See
  [`57_api_reliability`](../57_api_reliability/README.md).
- MCP usage attribution is request-scoped and consumptive rather than a sticky “server was ever used”
  session bit. Missing local tools still produce visible errors. See
  [`39_mcp`](../39_mcp/mcp_runtime_configuration_auth_and_discovery.md) and
  [`44_telemetry`](../44_telemetry/telemetry_feature_flags_usage_and_export.md).
- Family aliases step down within the requested family under organization policy. Host model overlays
  outrank stale disk state. See [`47_models`](../47_models/resolution_policy_discovery_and_picker.md).
- Workspace diffs read raw git blobs rather than invoking configured diff drivers or text conversion.
  See [`56_chrome_ide`](../56_chrome_ide/ide_host_and_workspace_diff.md).
- Repository-local settings can turn Remote Control off but cannot turn it on. See
  [`54_remote_control`](../54_remote_control/enablement_and_client_state.md).

### Cross-session permission classification before dispatch

**What it does:** Applies auto-mode safety classification to a message before it crosses a session or
machine boundary.

**How it works:**
1. Recipient resolution identifies the intended session but does not itself authorize message content.
2. The SendMessage action is projected into the same permission-classifier input used for other
   consequential tools.
3. A denial stops before transport dispatch; the recipient never receives the disallowed request.
4. An approval remains scoped to the resolved action and current permission-mode generation.
5. Delivery errors are handled separately so a safe decision is not misreported as successful delivery.

**Why this approach:**
- Classifying before dispatch prevents remote delivery from becoming a bypass around local auto-mode
  policy.
- Treating recipient resolution as authorization would conflate identity correctness with action safety.
- Post-delivery classification could notify the sender, but it could not retract an already delivered
  instruction.

**Key insight:** Cross-session messaging is a transport, not a separate trust domain; the permission
decision must occur on the sending side before the irreversible boundary crossing.
