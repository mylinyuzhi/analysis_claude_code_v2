# v2.1.160 — Source Diff Analysis

**Theme:** **A permission-surface hardening + auto-mode/effort-message clarity release, wrapped around a renamed dynamic-workflow trigger and a long tail of `claude agents`/background-session reliability fixes.** Three sub-themes carry the weight. (1) **Write-permission tightening:** the "sensitive file" gate that previously prompted only for a tiny set of dotfiles (`.bashrc`, `.zshrc`, `.gitconfig`, …) was expanded to cover *shell-startup files that auto-execute* (`.zshenv`, `.zlogin`, `.bash_login`, …) and *build-tool config files that grant code execution* (`.npmrc`, `.yarnrc*`, `bunfig.toml`, `.bazelrc`, `.pre-commit-config.yaml`, `.devcontainer/`, lefthook, gradle/maven wrappers, …), plus the `~/.config/git/` directory — and because this gate runs *before* the `acceptEdits` auto-allow, even `acceptEdits` mode now prompts for these. (2) **Read-before-edit ergonomics:** a single-file `grep`/`egrep`/`fgrep` (or `rg`) command that matched now seeds the read-file-state cache, so `Edit` no longer demands a redundant `Read` after you already viewed the file through grep. (3) **Auto-mode / `/effort` message correctness:** the auto-mode-unavailable copy on third-party providers now points at the `CLAUDE_CODE_ENABLE_AUTO_MODE` opt-in instead of blaming the model; `/effort ultracode` distinguishes "model can't run xhigh" from "dynamic workflows off"; model-not-found errors stop suggesting `--model` under the SDK; and the auto-mode classifier was tuned to reason less on routine actions. On top sit the **focus-feature item** — the dynamic-workflow trigger keyword rename `workflow`→`ultracode` with a violet highlight (linked, not re-derived) — the removal of the now-no-op `CLAUDE_CODE_OPUS_4_6_FAST_MODE_OVERRIDE`, the removed JetBrains-plugin startup suggestion, and ~15 `claude agents`/background/Windows/WSL fixes.

## 1. Write-permission gate prompts before shell-startup files and `~/.config/git/` (NEW)

**Type:** fix (security) · **Modules:** Permissions, Edit/Write tools

### TL;DR

Writing to a shell startup file that the shell auto-sources on login — `.zshenv`, `.zlogin`, `.zlogout`, `.bash_login`, `.bash_aliases`, `.bash_logout` — or anywhere under `~/.config/git/` now triggers a manual-approval prompt ("…which is a sensitive file"), because dropping a command into one of these is a silent path to arbitrary code execution on the next shell. Pre-2.1.160 the sensitive-file set was tiny (10 dotfiles) and missed all of these.

### How it works

The sensitive-filename list `DANGEROUS_FILES` (`Sko`, cli_inner_pretty.js:575118-575156) and the lowercase lookup `Set` `DANGEROUS_FILES_LC` (`Eko`, cli_inner_pretty.js:575157) define what counts as a sensitive *file*; the sensitive-directory list (`H$l`, cli_inner_pretty.js:575158) and the sensitive-relative-path list (`v$l = [".config/git"]`, cli_inner_pretty.js:575159) define sensitive *directories*. The classifier `isSensitivePath` (`fyf`, cli_inner_pretty.js:574435-574474) walks a write target's path segments: if any segment matches a `H$l` directory (574444), the path lies under a `v$l` relative path such as `.config/git` (574466-574469), or the basename matches a `Sko` entry (574470-574473), it returns true.

That predicate is wired into the write-permission decision in `evaluateWriteSafety` (`Htt`, cli_inner_pretty.js:574492-574523): after the Windows-path and not-yet-granted checks, it loops the target paths through `fyf` and, on a hit, returns `safe:false` with the message `"Claude requested permissions to edit ${path} which is a sensitive file."` and `classifierApprovable:true` (574516-574522). The Edit/Write permission evaluator `editWritePermissionEvaluator` (`P0e`, cli_inner_pretty.js:574793-574871) turns that `safe:false` into a `behavior:"ask"` prompt (574836-574853).

## 2. `acceptEdits` mode now prompts before build-tool config files that grant code execution (NEW)

**Type:** fix (security) · **Modules:** Permissions, Edit/Write tools, `acceptEdits` mode

### TL;DR

`acceptEdits` auto-accepts ordinary file edits — but it now stops and prompts before writing `.npmrc`, `.yarnrc*`, `bunfig.toml`, `.bazelrc`, `.pre-commit-config.yaml`, `.devcontainer/`, lefthook configs, and the rest of the expanded sensitive list. These files can each cause code to run on a later `npm install` / `bazel build` / `pre-commit` / devcontainer rebuild, so "auto-accept my edits" must not silently mean "auto-accept a code-execution config change."

### How it works

The mechanism is *ordering*, not a new `acceptEdits`-specific branch. In the Edit/Write permission evaluator (cli_inner_pretty.js:574833-574871), the sequence is:

1. `_Ue(...)` — passthrough hook checks (574833).
2. **`Htt(o, …)` — the sensitive-file safety check (574835).** On a hit it returns `behavior:"ask"` *immediately* (574848-574853), with the file's allow-rule suggestion.
3. Plan-mode block (574855).
4. **`acceptEdits` auto-allow (574862-574863): `if (n.mode === "acceptEdits" && d) return { behavior:"allow", … }`.**

Because step 2 returns before step 4 is reached, a sensitive-file target never reaches the `acceptEdits` short-circuit. So the same expanded `DANGEROUS_FILES` list from §1 is what makes `acceptEdits` prompt for build-config files — no separate gate exists.

## 3. `Edit` satisfied by a prior single-file `grep`/`egrep`/`fgrep` (NEW)

**Type:** improvement · **Modules:** Bash tool, Edit tool, read-before-edit check

### TL;DR

`Edit` enforces a read-before-edit rule: a file must have been observed (its content + mtime cached in `readFileState`) before you can edit it, or you get *"File has not been read yet. Read it first before writing to it."* Now a **single-file** `grep`/`egrep`/`fgrep` (or `rg`) command that *matched* (exited 0) seeds that cache — so after `grep foo config.json` you can `Edit config.json` without a redundant `Read`.

### How it works

After a Bash tool call completes, `seedReadStateFromBashCommand` (`iXa`, cli_inner_pretty.js:447076-447118) parses the command into "read targets" via `extractReadTargets` (`mBp`, cli_inner_pretty.js:446877-446893) and, for each, reads the file and writes `{ content, timestamp, offset, limit }` into `readFileState` (447115). It is invoked from the Bash post-execution path with the command's exit code (cli_inner_pretty.js:450984: `await iXa(e.command, t.readFileState, i.signal, A.code)`), and it filters out any target whose parse demanded a zero exit but didn't get one (447077: `.filter((i) => !i.requiresExitZero || r === 0)`).

`extractReadTargets` tries a chain of per-command parsers; grep/rg are the **single-command-only** branch (446888: `t.length === 1 ? (vBp(r) ?? xBp(r)) : null`):

- `parseGrepTarget` (`vBp`, cli_inner_pretty.js:447013-447041): accepts `grep`/`egrep`/`fgrep` only, allows the safe context/line-number flags (`-A/-B/-C`, `-n`, `--color=…`, etc.), requires exactly one pattern + one literal file path (rejects globs `*?[{` and `-`), and returns `{ filePath, requiresExitZero: true }`.
- `parseRgTarget` (`xBp`, cli_inner_pretty.js:447042-447074): the equivalent for `rg`.

The `requiresExitZero: true` flag is the key guard: a grep that matched nothing (exit 1) does **not** prove the file was usefully observed, so it is dropped by the filter at 447077. The Edit read-check itself is unchanged — it just reads `readFileState.get(path)` (cli_inner_pretty.js:444621) and errors with `errorCode:6` (444636-444642) only when the entry is absent or a partial view.

```javascript

// Location: cli_inner_pretty.js:447013-447041
// ============================================

  for (let o = 1; o < t.length; o++) {
    let s = t[o];
    if (s.startsWith("-") && s !== "-") {
      if (s === "-A" || s === "-B" || s === "-C") { let i = t[++o]; if (i === void 0 || !/^\d+$/.test(i)) return null; continue; }
      if (SBp.test(s) || EBp.test(s) || bBp.test(s) || HBp.has(s)) continue;
      return null;
    }
    if (n === null) n = s; else if (r === null) r = s; else return null;
  }
  if (n === null || r === null || r === "-") return null;
  if (/[*?[{]/.test(r)) return null;

// READABLE (for understanding):
function parseGrepTarget(command) {

  if (!["grep","egrep","fgrep"].includes(argv[0])) return null;

      return null;                                  // an unrecognized flag → bail, don't seed
    }
    if (pattern === null) pattern = tok;            // first positional = pattern
    else if (filePath === null) filePath = tok;     // second = the single file
    else return null;                               // a third positional → multi-file, bail
  }
  if (pattern === null || filePath === null || filePath === "-") return null;
  if (/[*?[{]/.test(filePath)) return null;         // no globs — must be one concrete file
  return { filePath, startLine: undefined, endLine: undefined, requiresExitZero: true };
}
```

## 4. Auto-mode unavailability message on third-party providers points at the opt-in (FIX)

**Type:** fix · **Modules:** Auto mode, Model/provider gating

### How it works

The auto-mode gate `verifyAutoModeGateAccess` (`e2t`, cli_inner_pretty.js:586587-586629) classifies *why* auto mode is unavailable into a reason string, then `autoModeUnavailableMessage` (`Gne`, cli_inner_pretty.js:586570-586586) maps each reason to copy. ## 6. Model-not-found errors stop suggesting `--model` under the SDK / non-CLI hosts (FIX)

**Type:** fix · **Modules:** Model selection, Error messages, SDK host

### How it works

`modelNotFoundSuggestion` (`TFi`, cli_inner_pretty.js:229386-229389) decides what to suggest when a model can't be resolved:

```javascript
function TFi() {
  if (!xr()) return "/model";              // interactive CLI → suggest the /model picker
  return wU() === "sdk-cli" ? "--model" : void 0;  // sdk-cli host → --model; any other host → no suggestion
}
```

`xr()` is "this is the interactive CLI." When false, only the `sdk-cli` host gets the `--model` flag suggestion; every other embedding (the Agent SDK, IDE hosts, etc.) gets `undefined`, so the error omits the inapplicable `--model` hint. Callers at 229344/229354 splice the result into the model-not-found message.

| | |
|---|---|
| **Before** | A model-not-found error always suggested passing `--model`, even when running under the SDK or another host where no such CLI flag exists. |
| **After** | `--model` is suggested only for the interactive CLI (`/model`) and the `sdk-cli` host; other hosts get no flag suggestion. |
| **Why** | Telling an SDK consumer to "pass `--model`" is a non-actionable instruction — there is no command line. Suppressing it avoids sending users to a flag that doesn't apply to their entrypoint. |

## 7. Auto-mode classifier latency: less reasoning on routine actions (IMPROVEMENT)

**Type:** improvement · **Modules:** Auto mode, Permission classifier

### How it works

The auto-mode permission classifier's instruction prompt (cli_inner_pretty.js:370366) was retuned to spend reasoning budget proportional to ambiguity:

- **v2.1.156 (before):** *"…Use `<thinking>` before responding with `<block>`. Think for as long as needed — **at least several paragraphs for ambiguous or borderline actions**; do not cut your reasoning short on hard cases."* (v2.1.156:277996)
- **v2.1.183 (after):** *"…Use `<thinking>` before responding with `<block>`. **Think longer on ambiguous or borderline actions; keep reasoning brief for clear-cut ones.**"* (cli_inner_pretty.js:370366)

The old wording set a floor ("several paragraphs") on *every* classification; the new wording explicitly authorizes brief reasoning for clear-cut/routine actions. Less reasoning on routine actions → lower per-action latency → fewer cases where the classifier runs out of budget and emits the *"Auto mode could not evaluate this action and is blocking it for safety"* block (cli_inner_pretty.js:370279).

**Why:** The "could not evaluate" safety-block is a false-negative UX wart — a routine action getting blocked because the classifier over-deliberated and timed out. Rebalancing reasoning to match difficulty cuts both latency and those spurious blocks, without lowering scrutiny on genuinely ambiguous actions.

**Type:** behavior · **Modules:** Workflow (keyword trigger), Prompt input, `/config`

The per-turn keyword that auto-opts a prompt into the Workflow tool was renamed from `workflow`/`workflows` to **`ultracode`**, the matched keyword is now highlighted in **violet** in the prompt input, and a new `/config` toggle `workflowKeywordTriggerEnabled` (default `true`, labeled "Ultracode keyword trigger") gates it. The runtime detector switched from matching `workflows?` to matching the literal `ultracode` via the *unchanged* code-span-masking matcher `matchKeyword` (`hho`, called at cli_inner_pretty.js:464262 as `hho(e, "ultracode")`); the model-facing system-reminder now reads *'The user included the keyword "ultracode", opting this turn into multi-agent orchestration — use the Workflow tool…'* (cli_inner_pretty.js:590606-590612); the setting schema describe text is at cli_inner_pretty.js:56008-56011; the `/config` row is at cli_inner_pretty.js:479214-479224; and the violet shimmer (`color: "violet-ripple"`) is at cli_inner_pretty.js:551113 / 551141 / 551152. The word "workflow" in prose no longer triggers a run, but asking for one in your own words still works (the model can still choose the tool). **(v2.1.156 before:** the trigger keyword was `"workflow" or "workflows"`, v2.1.156:446735.)

This is a focus feature — the full mechanism (the masking matcher internals, the consent layer, the unchanged telemetry/journal spine, and the violet-vs-rainbow shimmer) is documented in **[../42_workflow/ultracode_keyword_trigger_delta.md](../42_workflow/ultracode_keyword_trigger_delta.md)** — not re-derived here.

## 9. `CLAUDE_CODE_OPUS_4_6_FAST_MODE_OVERRIDE` removed (now a no-op) (REMOVAL)

**Type:** removal · **Modules:** Model selection, Env vars

`CLAUDE_CODE_OPUS_4_6_FAST_MODE_OVERRIDE` still appears in the env-var *registry* (declared as `u8c = Oe.str()` at cli_inner_pretty.js:43436, exported at 43347/43402) — but it has **zero consumers** in the 2.1.183 bundle. ## 11. WSL copy-on-select now writes the Windows clipboard via PowerShell interop (FIX)

**Type:** fix · **Modules:** Clipboard, WSL/Windows

### How it works

The native clipboard-write helper `writeNativeClipboard` (`pyi`, cli_inner_pretty.js:155121-155145) has a dedicated `case "wsl":` (155136-155138) that shells `powershell.exe -NoProfile -NonInteractive -Command "<Set-Clipboard script>"`, where the script is `setClipboardPs` (`cyi`, cli_inner_pretty.js:155289 = `"[Console]::InputEncoding = [Text.Encoding]::UTF8; Set-Clipboard -Value ([Console]::In.ReadToEnd())"`). The unified writer `copyToClipboard` (`VC`, cli_inner_pretty.js:155103-155119) calls `pyi(e)` *and then also* emits an OSC 52 escape (155109). Terminals like MobaXterm don't honor OSC 52, so the PowerShell interop is what actually lands the text on the Windows clipboard for copy-on-select under WSL.

| | |
|---|---|
| **Before** | Copy-on-select under WSL relied on OSC 52, which terminals like MobaXterm silently ignore — so the selection never reached the Windows clipboard. |
| **After** | The WSL path uses PowerShell `Set-Clipboard` interop (155136-155137), independent of OSC 52 support. |
| **Why** | OSC 52 is a terminal-emulator feature, not a guaranteed one; routing through `powershell.exe Set-Clipboard` goes straight to the Windows clipboard via the WSL interop boundary, working regardless of the terminal's escape-sequence support. |

## 12. Background-session reliability and overnight-retire correctness fixes (FIX — Background Agents)

**Type:** fix · **Modules:** Background agents, Daemon lifecycle

A cluster of background-session fixes. These touch the background-agents subsystem documented in **[../36_background_agents/](../36_background_agents/README.md)** (daemon lifecycle, worker state machine, retire/resume, worktree isolation); per the focus-feature rule they're summarized here, not re-derived:

- **Restoring a completed session from `claude agents` no longer drops chat history / re-runs the original prompt.** A completed-session restore was re-seeding from the kickoff prompt instead of the saved transcript.
- **Background sessions re-attached after overnight retire no longer lose their conversation / re-run the original prompt.** Same class of bug as above, on the retire→resume path.
- **`claude --bg` no longer occasionally fails with "socket missing" during daemon cold-start on a loaded machine.** A race where the client connected before the cold-starting daemon had bound its socket.
- **[Windows] The directory a bg session started in is no longer un-deletable after `claude rm` until the daemon exits.** The daemon held a handle on the working dir.
- **Background agents that resumed work are no longer shown under "Completed" in the agents list.** A resumed agent was mis-categorized as done.
- **`claude agents` no longer freezes for several seconds returning to the session list** — the auto-updater was re-checking on every exit; that check was removed from the hot path.
- **Improved performance opening recently-inactive bg sessions** in `claude agents`.
- **Background-session teardown (`claude rm`/`stop`, idle reap) now sends SIGTERM before SIGKILL** to running shell subprocesses, so their cleanup handlers run. *(The graceful-then-forceful kill pattern appears throughout the process layer, e.g. the SIGTERM→`setTimeout(SIGKILL, 5000)` idiom at cli_inner_pretty.js:211096; the bg-teardown wiring is part of the daemon path and is not isolated to a single distinctive decl in this build.)*

**Confidence:** medium for the individual sites — these are described from the changelog + the background-agents subsystem shape; the retire/resume and daemon paths are covered in the module doc, and several of these are timing/lifecycle fixes without a single grep-able before/after string in the 2.1.183 build.

## Summary

v2.1.160 is a **permission-hardening + message-clarity** release. The two headline security fixes both ride a single mechanism: the "sensitive file" write gate (`evaluateWriteSafety`→`isSensitivePath`, cli_inner_pretty.js:574435-574523) had its `DANGEROUS_FILES` list (cli_inner_pretty.js:575118-575159) expanded from 10 dotfiles to 37 filenames + 9 dirs + `.config/git` — and because that gate sits *before* the `acceptEdits` auto-allow (cli_inner_pretty.js:574835 vs 574862), the same list change makes both `default` and `acceptEdits` modes prompt before shell-startup files and build-tool config files that grant code execution. The read-before-edit ergonomics fix (single-file `grep`→`readFileState`, `parseGrepTarget`/`iXa`) removes a redundant-`Read` friction with an exit-0-only guard that keeps it sound.

The auto-mode and `/effort` work is all about *correct attribution*: the third-party-provider message now points at `CLAUDE_CODE_ENABLE_AUTO_MODE=1` (the 2.1.158 opt-in) instead of blaming the model; `/effort ultracode` separates "model can't run xhigh" from "dynamic workflows off" and hides ultracode on unsupported models; model-not-found stops suggesting `--model` to SDK hosts; and the classifier prompt was retuned to reason less on routine actions, cutting latency and spurious "could not evaluate" blocks.

The focus-feature touch — the `workflow`→`ultracode` trigger rename with a violet highlight and a `/config` toggle — is a pure keyword/UX rename over byte-identical detector internals (covered in `../42_workflow/ultracode_keyword_trigger_delta.md`). Rounding out the release: the no-op removal of `CLAUDE_CODE_OPUS_4_6_FAST_MODE_OVERRIDE`, the removed JetBrains-plugin startup nudge, the WSL copy-on-select PowerShell interop, and the by-now-familiar background-agents polish arc (overnight-retire conversation loss, daemon cold-start "socket missing", agents-list freeze, SIGTERM-before-SIGKILL teardown) plus Windows/IME/voice/vim terminal-rendering fixes.
