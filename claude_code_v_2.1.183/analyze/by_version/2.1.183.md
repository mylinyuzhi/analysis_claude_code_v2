## 1. Auto-mode safety: destructive-git, `commit --amend`, and IaC-`destroy` blocks (IMPROVEMENT)

**Type:** improvement (auto-mode classifier prompt) · **Modules:** Auto-mode, Permissions, Danger classifier

### TL;DR

The auto-mode danger classifier's **soft-block** rule set — the `<user_soft_deny_rules_to_replace>` block injected into the classifier prompt (cli_inner_pretty.js:369316–369331) — was rewritten so that, when the user did **not** ask to discard local work, the classifier blocks: destructive git working-tree commands (`git reset --hard`, `git checkout -- .`, `git restore .`, `git clean -fd[x]`, `git stash drop`/`clear`); a `git commit --amend` whose HEAD pre-dates the session (amending the user's commit); and `terraform destroy` / `pulumi destroy` / `cdk destroy` / `terragrunt destroy`. Each now carries explicit "clears-when" conditions so legitimate flows (the user named the reset, the target is an agent-created worktree, the work was just stashed/backed-up, the user asked to amend/reword/fixup) still pass.

### How it works

This is **prompt-level enforcement**, not a regex gate. The auto-mode classifier is given a structured set of HARD-BLOCK / SOFT-BLOCK / ALLOW rules; the three relevant rules are:

- **Git Destructive** (cli_inner_pretty.js:369316) — gained the `commit --amend`-with-no-prior-`git commit` clause: *"HEAD pre-dates the session, so amending rewrites the user's commit; clears when the user asked to amend/reword/fixup or the agent visibly created HEAD."*
- **Modify Shared Resources** (cli_inner_pretty.js:369330) — extended the in-place-modification scope from a generic sentence to explicitly enumerate *"`terraform destroy`, `pulumi destroy`, `cdk destroy`, `terragrunt destroy`, or applying a plan that destroys resources."*
- **Irreversible Local Destruction** (cli_inner_pretty.js:369331) — the biggest rewrite: it now lists `git clean -fd[x]`, `git checkout -- .`, `git restore .`, `git reset --hard`, `git stash drop`/`clear` by name and adds a long "presume the tree is dirty … they clear when (a)/(b)/(c)" decision procedure with per-command carve-outs (e.g. `stash drop`/`clear` is the artifact, so a prior stash does *not* clear it; `clean` is not cleared by a stash because a stash doesn't capture untracked/ignored files).

There is a separate, pre-existing **warning-text** table (`E9d`, POSIX, cli_inner_pretty.js:297648–297721; `H9d`, PowerShell, cli_inner_pretty.js:297735–297795) that maps regexes like `/\bterraform\s+destroy\b/` → `"Note: may destroy Terraform infrastructure"` and `/\bgit\s+commit\b[^;&|\n]*--amend\b/` → `git_commit_amend`. That table produces the advisory "Note:" string shown to the user; it is **not** the block decision — the block lives in the classifier prompt above. The two were aligned in this release (the `terraform destroy` / `--amend` / `stash drop` patterns are present in both).

### Before / after

|---|---|---|
| Git Destructive | *"Force pushing, deleting remote branches, or rewriting remote history"* (cli_inner_pretty.js:276996, v2.1.156) — no `--amend` clause | adds `git commit --amend` on pre-session HEAD, with amend/reword/fixup clearing |

// ============================================

// ORIGINAL (v2.1.183 fragments, source lookup):

// READABLE (intent):

//   block(action) unless userExplicitlyNamedTarget(action)

**Why this approach:** Auto-mode runs commands without per-command human approval, so the *judgment* of "is this destroying something the user didn't ask me to destroy?" has to live in the model's reasoning, not in a static allowlist — a regex can't tell `git reset --hard` ("rebase the branch I asked you to rebase", allowed) from `git reset --hard` ("wipe my uncommitted work", blocked). Encoding the carve-outs in prose lets the classifier weigh transcript context (did the user name the target? is this an agent worktree? was the work just stashed?). The per-command exceptions in "Irreversible Local Destruction" are the clever part: they recognize that `stash drop` and `clean` have *different* recovery semantics than `reset`/`checkout` — a backup-stash clears a `reset` but is meaningless for `clean` (which deletes untracked files a stash never captured) and self-defeating for `stash drop` (the stash *is* the thing being destroyed).

## 2. Deprecated / auto-updated model warning on stderr in `-p`, covering agent frontmatter (NEW)

**Type:** feature · **Modules:** Model selection, Print mode (`-p`), Agents

### TL;DR

When the requested model is deprecated, retired, or silently remapped to a newer model, Claude Code now prints a warning to **stderr** at startup in **print mode (`-p`)** — previously the warning only appeared as an in-TUI notification, invisible to `-p` users. The check also now covers the model declared in an **agent's frontmatter** (it takes precedence over the resolved session model).

### How it works

The warning text is built by `Zwo` (cli_inner_pretty.js:549627) — for a remapped model it returns *"⚠ <model> is automatically remapped to <target> (...). Set CLAUDE_CODE_DISABLE_LEGACY_MODEL_REMAP=1 to keep the requested model."*; for a retired model, *"⚠ <model> will/was retired on <date>. Consider switching to a newer model."* (cli_inner_pretty.js:549634, 549639). The deprecation table is `Wxl` (cli_inner_pretty.js:549649+), keyed by model id with per-platform `retirementDates` and an optional `remappedTo`.

The **new** emission site is the startup print path (cli_inner_pretty.js:694437):

```javascript
// ============================================
// printModeModelDeprecationWarning - stderr deprecation warning in -p mode, covering frontmatter model
// Location: cli_inner_pretty.js:694437-694438 (v2.1.183)
// ============================================

// ORIGINAL (for source lookup):
let Jn = (a.continue || a.resume || ae) && !pRo() ? null : Zwo(Is ?? so);
if (Jn && R !== "json" && R !== "stream-json") a5(Jn);
// ... a5 (565722): process.stderr.write(yt.yellow(e) + "\n");

// READABLE (for understanding):
let warning = (flags.continue || flags.resume || isResumed) && !someGate()
  ? null
  : buildModelDeprecationWarning(agentFrontmatterModel ?? resolvedSessionModel);   // Is ?? so
if (warning && outputFormat !== "json" && outputFormat !== "stream-json")
  writeYellowToStderr(warning);                                                    // a5

// Mapping: Zwo→buildModelDeprecationWarning, Is→agentFrontmatterModel, so→resolvedSessionModel, a5→writeYellowToStderr, R→outputFormat
```

The `Is ?? so` is the load-bearing change: `Is` (agent-frontmatter model) is checked first, falling back to `so` (the resolved session model). The warning is suppressed for `json`/`stream-json` (machine-readable) output and on resume/continue.

### Before / after

| | v2.1.156 (before-picture) | v2.1.183 |
|---|---|---|
| Warning builder | `f6$` (cli_inner_pretty.js:525736, v2.1.156): remap text was just *"⚠ <model> has been updated to <target>."* | `Zwo`/`j6n` (549627/549619): richer remap text + `CLAUDE_CODE_DISABLE_LEGACY_MODEL_REMAP=1` opt-out hint |
| Where shown | only pushed as an in-TUI notification: `kz.push({key:"model-deprecation-warning", ...})` (cli_inner_pretty.js:645615–645618, v2.1.156) — never on stderr, never for `-p` | **also** written to stderr via `a5` in the print path (694437–694438), gated to non-JSON output |
| Frontmatter coverage | resolved-model only | `Is ?? so` — agent-frontmatter model checked first |

**Why:** A `-p` user scripting Claude Code never sees the TUI, so a model silently retiring or remapping was invisible until output quality changed. Routing it to **stderr** keeps it out of the captured stdout (so it doesn't pollute parsed output) while still surfacing it to a human watching the terminal or a CI log. Extending it to frontmatter closes the gap where an agent pinned to a now-retired model gave no warning at all.

## 4. `/config --help` lists shorthand keys; Enter/Space/Esc toggle overhaul (NEW + IMPROVEMENT)

**Type:** feature + behavior change · **Modules:** `/config` command, Settings dialog, Keybindings

### TL;DR

Two changes to `/config`: (1) `/config --help` (also `-h`, `help`) now prints **every available shorthand key** for `/config key=value`; (2) the interactive settings dialog's toggle keys changed — **Enter and Space both** now change the selected setting (previously only Space toggled; Enter "confirmed"), and **Esc now saves and closes** instead of reverting.

### How it works — `--help` listing

`/config`'s argument parser recognizes the help tokens `B3 = ["help", "-h", "--help"]` (cli_inner_pretty.js:45690) and the read-only tokens `aoe` (`list`/`show`/`get`/…, 45691). On a help/list token it emits the shorthand-key listing produced by `cWt` (cli_inner_pretty.js:479928), which walks the settings registry and formats each non-consent-gated setting as `id=true|false` / `id=opt1|opt2` / `id=<value>`, sorted (cli_inner_pretty.js:488004, 488032). The non-interactive `/config` handler `gVp` returns the same `Usage: /config key=value [key=value ...]` + listing (cli_inner_pretty.js:488026–488042).

### How it works — toggle keys

In the Config-tab component `Xil` (cli_inner_pretty.js:483273), the per-setting change is the `On` callback (cli_inner_pretty.js:483480): for a boolean it flips `Yt.value` and fires `tengu_config_changed`; for enums/sub-dialogs it opens the relevant picker. `On` is bound to the **`select:accept`** action (cli_inner_pretty.js:483564). The default keymap now maps **both** keys to that action: `space: "select:accept"` and `enter: "select:accept"` (cli_inner_pretty.js:177247–177248). The footer reflects it: the boolean-setting hint is now `chord: ["enter", "space"], action: "toggle"` with the Esc fallback labeled `description: "close"` (cli_inner_pretty.js:483871, 483874–483880).

### Before / after

| | v2.1.156 (before-picture) | v2.1.183 |
|---|---|---|
| Toggle key footer | `chord: "space", action: "toggle"` + `Esc … description: "cancel"` (cli_inner_pretty.js:574239, 574236, v2.1.156) | `chord: ["enter", "space"], action: "toggle"` + `Esc … description: "close"` (483871, 483879) |
| Enter behavior | "confirm" (didn't toggle the selected boolean) | toggles the selected setting (bound to `select:accept` = `On`) |
| Esc behavior | revert / cancel | saves and closes |
| `/config --help` | not present | lists all shorthand keys via `cWt` |

**Why:** The old split (Space toggles, Enter "confirms", Esc reverts) was a common foot-gun — users pressed Enter expecting it to apply their change, and pressed Esc expecting their just-made changes to *stick*. Mapping Enter **and** Space to the same toggle action and making Esc save-and-close aligns the dialog with the mental model "every keystroke I make takes effect; Esc just leaves." `/config --help` makes the shorthand surface discoverable without opening the panel.

**Type:** improvement (removal) · **Modules:** Startup, Notifications

### TL;DR

The startup notification *"Found N settings issue(s) · /doctor for details"* shown under the logo was removed. Configuration issues are now surfaced only on demand via `/doctor` or `--debug`.

### How it works

In v2.1.156 a startup effect pushed a high-priority warning notification whenever settings validation returned errors (cli_inner_pretty.js:471855–471860, v2.1.156): `Found ${K.length} settings ${K.length === 1 ? "issue" : "issues"} · /doctor for details`. **Why:** A red "N settings issues" banner at every startup is alarming for what are often benign or stylistic validation warnings, and it can't be acted on inline anyway — the user has to run `/doctor` regardless. Removing the unsolicited banner and pointing to `/doctor`/`--debug` keeps startup quiet while leaving the diagnostics one command away.

## 6. Fixed `thinking.disabled.display: Extra inputs are not permitted` 400 (FIX)

**Type:** fix (regression / serialization) · **Modules:** Thinking config, Subagent spawn, Title generation

### TL;DR

For configurations with `thinking.disabled.display` set, subagent spawns and session-title generation hit a 400 *"thinking.disabled.display: Extra inputs are not permitted"*. The fix stops serializing a `display` field onto a `{ type: "disabled" }` thinking config.

### How it works

The CLI flag serializer for a child `claude` process only forwards `--thinking-display` when thinking is **not** disabled (cli_inner_pretty.js:552913–552919):

```javascript
// ============================================
// serializeThinkingFlags - don't emit --thinking-display for a disabled thinking config
// Location: cli_inner_pretty.js:552913-552919 (v2.1.183)
// ============================================

// ORIGINAL (for source lookup):
M.push("--thinking", "disabled");
// ...
if (c.type !== "disabled" && c.display) M.push("--thinking-display", c.display);

// READABLE (for understanding):
flags.push("--thinking", "disabled");
// ...
if (thinkingConfig.type !== "disabled" && thinkingConfig.display)
  flags.push("--thinking-display", thinkingConfig.display);

// Mapping: c→thinkingConfig, M→flags
```

The disabled thinking schema is strictly `{ type: literal("disabled") }` (cli_inner_pretty.js:363556) — it has **no** `display` member — so a request carrying `display` alongside `type: "disabled"` fails Pydantic-style validation server-side with *"Extra inputs are not permitted"*. The `c.type !== "disabled" && c.display` guard ensures `display` is only attached to non-disabled configs (`{ type:"disabled" }` is emitted bare at cli_inner_pretty.js:428665, 461201, etc.).

**Why:** Subagent spawns and title-gen create a derived request from the parent's thinking config. A parent config that carried a `display` preference would leak that field into the disabled-thinking child request, which the API rejects. Gating `--thinking-display` on `type !== "disabled"` keeps the disabled config exactly schema-shaped.

**Confidence:** medium — the guard at 552919 and the strict disabled schema at 363556 are verified verbatim; the attribution of the *specific* 400 to this serialization path is inferred from the error string shape (`thinking.disabled.display` / "Extra inputs are not permitted") matching a `display` field on a `{type:"disabled"}` object.

### Before / after

| | v2.1.156 (before-picture) | v2.1.183 |
|---|---|---|
| `toolChoice` | `O ? {type:"tool", name:"web_search"} : void 0` — **only forced when the `tengu_plum_vx3` gate was on** (cli_inner_pretty.js:402927, v2.1.156) | always `{type:"tool", name:"web_search"}` (428671) |

## 8. Fixed MCP auth-stub tools leaking into headless/SDK mode (FIX)

**Type:** fix · **Modules:** MCP, Headless / SDK mode, Tools

### TL;DR

An MCP server that requires authentication exposes two placeholder "auth-stub" tools (an `authenticate` tool plus a helper) so the model can kick off the OAuth flow interactively. In **headless/SDK mode** (`-p`, non-interactive), where there is no human to complete a browser OAuth, those stub tools should not be offered to the model. They now aren't.

### How it works

The auth-stub generator `Jxn` (cli_inner_pretty.js:274617) gained a one-line headless guard:

```javascript

// mcpAuthStubTools - suppress auth-stub tools in headless/SDK mode
// Location: cli_inner_pretty.js:274617-274619 (v2.1.183)
// ============================================

// ORIGINAL (for source lookup):
function Jxn(e, t) {
  if (xr()) return [];          // xr(): !Ot.isInteractive — headless/SDK/print mode
  return [p2d(e, t), f2d(e)];   // the `authenticate` stub tool + helper
}

// READABLE (for understanding):
function buildMcpAuthStubTools(serverName, config) {
  if (isNonInteractive()) return [];
  return [authenticateStubTool(serverName, config), authStubHelper(serverName)];
}

// Mapping: Jxn→buildMcpAuthStubTools, xr→isNonInteractive (cli_inner_pretty.js:3151: return !Ot.isInteractive), p2d→authenticateStubTool
```

A `needs-auth` MCP client wires its tools via `Jxn` (cli_inner_pretty.js:283777, 283811). With `xr()` true, that list is empty, so the model in a headless session never sees a callable `mcp__<server>__authenticate` it could never actually complete.

### Before / after

| | v2.1.156 (before-picture) | v2.1.183 |
|---|---|---|
| stub-tool wiring | needs-auth client always wired `tools: [xc6(L,P), uc6(L)]` regardless of mode (cli_inner_pretty.js:432282, v2.1.156) | `tools: Jxn(g,h)`, and `Jxn` returns `[]` when non-interactive (274618, 283777) |

**Why:** In headless/SDK mode there is no interactive browser to complete an OAuth handshake, so an `authenticate` tool is a dead end — at best the model wastes a turn calling it, at worst it loops. Suppressing the stubs in non-interactive mode removes a tool the model can't usefully act on. (The `xr()` predicate, cli_inner_pretty.js:3151, is the canonical "not interactive" check used throughout the CLI.)

## 9. Fixed turns silently completing with only a thinking block — Claude re-prompts once (FIX)

**Type:** fix · **Modules:** Agent loop, Thinking mode

### TL;DR

If the model ended a turn with `stop_reason: end_turn`/`stop_sequence` but produced **only** a thinking block and no user-visible text, the turn completed silently with nothing on screen. Now Claude detects the empty-output turn and re-prompts itself **once** to produce a visible response.

### How it works

In the agent loop's turn-completion handling (cli_inner_pretty.js:458928–458962), after an `end_turn`/`stop_sequence` with no API error, not a compact turn, and **no assistant message containing a non-empty text block** (cli_inner_pretty.js:458933), the loop checks the one-shot flag `thinkingOnlyNudged` (`V`, state field at cli_inner_pretty.js:457698):

On the first occurrence it yields an `isMeta` user message *"[Your previous response had no visible output. Please continue and produce a user-visible response.]"* and re-loops with `thinkingOnlyNudged: true` and `transition.reason: "thinking_only_retry"`. On a second consecutive empty turn (`V` already set) it records `nudge_exhausted` and stops, so it never loops forever. Telemetry: `query_thinking_only_response` with `nudged` / `nudge_exhausted`.

**Why:** A thinking-only turn looks to the user like Claude "did nothing" — the turn ended, but the screen is blank. Auto-retrying once converts a dead turn into a useful response in the common case (the model thought, then forgot to emit text) while the single-shot `thinkingOnlyNudged` guard prevents an infinite re-prompt loop if the model genuinely keeps returning empty. Confirmed new: `thinkingOnlyNudged`/`query_thinking_only_response` are absent from the v2.1.156 bundle.

## 10. Fixed user-level skills appearing multiple times in autocomplete across plugins (FIX)

**Type:** fix · **Modules:** Skills, Plugins, Slash-command autocomplete

### TL;DR

When multiple plugins each bundled a copy of the same user-level skill, that skill appeared multiple times in slash-command autocomplete. The plugin-skill loader now de-duplicates by canonical file path, skipping any skill already surfaced by the skills-directory loader or by an earlier plugin.

### How it works

The plugin-skill loader (cli_inner_pretty.js:466651–466671) realpath-canonicalizes each plugin skill's file (cli_inner_pretty.js:466641) and checks it against two sets:

```javascript
// ============================================
// dedupePluginSkills - skip plugin skills already surfaced by the skills dir or another plugin
// Location: cli_inner_pretty.js:466651-466671 (v2.1.183)
// ============================================

// ORIGINAL (for source lookup, condensed):
for (let c = 0; c < o.length; c++) {
  let u = o[c]; if (u === void 0) continue;
  let d = s[c];                                 // realpath(u.filePath)
  if (d === null || d === void 0) { l.push(u.skill); continue; }
  if (i !== null && i.has(d)) {                 // already a user-level skill from the skills-dir loader
    v(`Skipping plugin skill '${u.skill.name}' — ${d} is a user-level skill already surfaced by the skills directory loader`);
    continue;
  }
  let p = a.get(d);                             // already loaded by an earlier plugin
  if (p !== void 0) { v(`Skipping duplicate plugin skill '${u.skill.name}' — ${d} already loaded as '${p}'`); continue; }
  a.set(d, u.skill.name); l.push(u.skill);
}

// READABLE (intent): canonical-path dedupe — userSkillRealpaths set (i) wins over plugins; a Map (a) catches plugin↔plugin dupes.

// Mapping: d→realpath(skillFile), i→userSkillRealpaths, a→loadedByRealpath, l→deduplicatedSkills
```

The end-of-load log makes the dedupe count explicit: *"Total plugin skills loaded: N (M duplicate/user-owned entries skipped)"* (cli_inner_pretty.js:466672).

**Why:** A skill is identified to autocomplete by its command name, but the *same* on-disk skill can be reachable through several plugins (and through the user's skills directory). Without dedupe each path produced a separate autocomplete entry for one underlying skill. Canonicalizing via `realpath` (so symlinks/relative paths collapse) and preferring the skills-directory copy gives one entry per real file. Confirmed new: the dedupe log strings are absent from v2.1.156.

## 11. Fixed scheduled-task / webhook deliveries treated as keyboard input (FIX)

**Type:** fix · **Modules:** Scheduled tasks, Webhooks / triggers, Auto-mode, Input classification

### TL;DR

Deliveries from a scheduled task or a GitHub webhook trigger were being treated as if the user had typed them on the keyboard — which meant they could approve a pending permission prompt or set the session title in auto mode. They are now classified as **task notifications**, which carry none of those keyboard-input privileges.

### How it works

The origin-classifier `k8t` (cli_inner_pretty.js:606139) maps a delivery's trigger source / client platform to an origin kind:

```javascript
// ============================================
// classifyDeliveryOrigin - trigger sources → task-notification, real clients → human
// Location: cli_inner_pretty.js:606139-606215 (v2.1.183)
// ============================================

// ORIGINAL (for source lookup):
function k8t(e, t) {
  if (e && e.kind !== "peer") return e;
  if (t && lCf.has(t)) return { kind: "task-notification" };
  if (t && aCf.has(t)) return { kind: "human" };
  return;
}
// lCf = new Set(["scheduled_trigger", "force_run_trigger", "github_webhook_trigger", "fire_routine", "pr_steward"]);  // :606215
// aCf = new Set(["ios", "android", "web_claude_ai", "desktop_app"]);                                                  // :606214

// READABLE (for understanding):
function classifyDeliveryOrigin(existingOrigin, source) {
  if (existingOrigin && existingOrigin.kind !== "peer") return existingOrigin;
  if (source && TRIGGER_SOURCES.has(source)) return { kind: "task-notification" };  // scheduled/webhook/routine/steward
  if (source && REAL_CLIENT_PLATFORMS.has(source)) return { kind: "human" };        // a real device
  return undefined;
}

// Mapping: k8t→classifyDeliveryOrigin, lCf→TRIGGER_SOURCES, aCf→REAL_CLIENT_PLATFORMS
```

The keyboard-input predicate `Y2` (cli_inner_pretty.js:233659) treats only `human` / `auto-continuation` / `undefined` origins as keyboard-eligible — a `task-notification` origin is explicitly **not** keyboard input. Downstream, the message-routing predicate `N2i` (cli_inner_pretty.js:233715) short-circuits a `task-notification` origin onto the notification path (cli_inner_pretty.js:233718), and the keepalive/turn-handling code carries `promptOrigin: { kind: "task-notification" }` for these meta deliveries (cli_inner_pretty.js:676483, 673540). Because the origin isn't `human`, a scheduled/webhook delivery can no longer satisfy a pending approval or set the auto-mode session title.

**Why:** A scheduled-task or webhook delivery arriving as a message looks structurally like a typed prompt, but it carries no human intent — letting it approve a destructive action a human had been asked to confirm, or letting it title the session, conflates "an automated event fired" with "the user pressed a key." Routing trigger sources to a distinct `task-notification` origin kind, which the keyboard-input predicate excludes, makes that distinction load-bearing. Confirmed new: the trigger-source identifiers (`scheduled_trigger`, `github_webhook_trigger`, `fire_routine`, `pr_steward`) are absent from v2.1.156 (the scheduled-task/routine/webhook infrastructure post-dates it).

## 12. Fixed focus mode showing "Ran N PostToolUse hooks" timing lines under each response (FIX)

**Type:** fix (rendering) · **Modules:** Focus mode, Hooks UI, Message rendering

### TL;DR

In **focus mode** — where the user is meant to see only Claude's final text message per response — the *"Ran N PostToolUse hooks"* timing line was being rendered under each response. These hook-timing lines are now handled correctly so they don't clutter the focus-mode view.

### How it works (and a candor note)

The hook-timing line is rendered by `fvp` (cli_inner_pretty.js:383062): for a `stop_hook_summary` system message with a `hookLabel` (PostToolUse), it emits *"Ran <count> <hookLabel> hook(s)"* (cli_inner_pretty.js:383092). Consecutive same-label hook summaries are coalesced into one by `oyl` (cli_inner_pretty.js:517815, using the predicate `ryl` at cli_inner_pretty.js:517812). In the static/collapse render path `WYa` (cli_inner_pretty.js:445470), a `stop_hook_summary` with `hookLabel !== void 0` is explicitly retained rather than dropped (cli_inner_pretty.js:445527) — the opposite of v2.1.156's collapse, which routed any non-`informational` system message to the hide-set `else M.add(Z)` (cli_inner_pretty.js:435201–435202, v2.1.156).

**Candor:** the precise focus-mode suppression is **not isolated to a single distinctive declaration.** Focus mode's "show only the final text" behavior is enforced by a React render condition over the message stream, and the PostToolUse-hook-summary handling is spread across `fvp` (render), `oyl`/`ryl` (coalesce), and `WYa` (collapse) — none of which carries a grep-able "focus mode" marker. The verified anchors above bound the relevant code; the exact line that gates "render this hook-timing summary in focus mode vs not" is a render-time condition I could not pin to one declaration. (medium confidence on the mechanism, high confidence on the anchors.)

**Why:** Focus mode's contract is that the user sees the final answer, not the machinery — tool calls, results, and hook-timing lines are noise that defeats the purpose. The fix keeps the PostToolUse hook timing out of the per-response focus view.

## 13. Fixed tmux teammate panes failing on slow rc-init + keystroke leak (FIX — FOCUS: agent team)

**Type:** fix · **Modules:** Agent team (tmux backend), Teammate spawn

The cross-process tmux teammate-spawn path was reworked. In v2.1.156 the backend created a pane running the user's interactive login shell, slept 200 ms for rc-files to load, then **typed** the relaunch line with `send-keys` — which raced a slow-initializing shell (keystrokes swallowed/mangled) and could leak keystrokes typed in the leader during the spawn window into the new pane. v2.1.183 instead creates the pane running a benign holding process — `cat` (`Gke`, cli_inner_pretty.js:362642) via `tmux split-window -d … -- cat` — then **replaces** it directly with `tmux respawn-pane -k -t <pane> -- "cd … && env … claude …"` (`a3n`, cli_inner_pretty.js:421874). `respawn-pane` `exec`s the command as the pane's process image: no interactive shell prompt to race, no readline buffer to leak into, no init-delay sleep. A defense-in-depth control-character guard `Slt` (cli_inner_pretty.js:362755) was added on top. Full mechanism, before/after diagrams, and the `send-keys → respawn-pane` rewrite:

→ [../30_agent_team/spawn_backends_and_tmux_fix.md](../30_agent_team/spawn_backends_and_tmux_fix.md)

## 14. Fixed background tasks started by a teammate being killed at the teammate's turn-end (FIX — FOCUS: agent team / background)

**Type:** fix · **Modules:** Agent team (coordinator), Background tasks, Keepalive

When a teammate finished its turn, background tasks **it** had started were being killed along with it. The repair lives in the task-notification builder `G4e` (`enqueueAgentNotification`, cli_inner_pretty.js:445827) and rides on the pre-existing keepalive infrastructure: `isCompletedButParked` (`YR`) and the keepalive predicate `Lye`. A teammate that finished its turn has `status === "completed"`, but if it still holds `agent:`-keepalive reasons (live child tasks), it is **parked, not gone** — eviction is only scheduled once the last keepalive reason drops. The v2.1.183 builder `G4e` now respects that park state and routes the notification to the live owner, so the teammate's children gate the parent's teardown instead of being reaped with it. Full before/after (`G4e` vs the v2.1.156 builder `c5H`) and the keepalive primitives:
