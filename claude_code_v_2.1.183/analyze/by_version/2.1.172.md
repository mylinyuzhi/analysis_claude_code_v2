# v2.1.172 — Source Diff Analysis

**Theme:** **The "depth, clamps, and allowlists" flagship.** 2.1.172 is one of the densest releases in the 2.1.157→2.1.183 window, and it lands four genuinely structural changes plus a long tail of correctness fixes that all cluster around three subsystems: **agent recursion**, **model selection**, and **provider config**. The headline is **nested sub-agents** — a sub-agent can now spawn its *own* sub-agents up to **5 levels deep**, implemented as a universal numeric depth gate (`SUBAGENT_DEPTH_LIMIT = 5`) that replaces the v2.1.156 team-only boolean and applies to foreground and background subagents alike (FOCUS-bg). Three more flagship items each close a "permanently stuck / silently wrong" trap: a **1M-context-without-credits session** now auto-compacts back under the 200k standard window instead of being pinned forever (FOCUS-compact); **memory recall** finally surfaces mounted `CLAUDE_MEMORY_STORES` team stores in *remote* sessions (FOCUS-mem); and **workflow validation** stops false-rejecting scripts that merely *mention* `Date.now()`/`Math.random()` in a string or comment (FOCUS-wf, the determinism check moved from a raw regex to an AST walk).

The non-focus body is a **model-restriction hardening pass** — almost every model bullet is a different facet of the new `availableModels` / "server-unavailable" enforcement subsystem (`KHe`/`ul`, both net-new vs. v2.1.156): version-specific IDs like `claude-opus-4-8` now resolve in allowlists, the doubled `[1M][1m]` suffix is de-duplicated (`Lq`), `opusplan[1m]` correctly upgrades to Opus 1M in plan mode, and the Bedrock `/model` picker stops offering models the provider doesn't serve. Around that sit two real platform additions — **Bedrock region from `~/.aws`** with a source-tagged `/status` line (`Rfr`/`tCa`), and a **`model` attribute on the `lines_of_code.count` OTEL metric** — plus a **WebFetch wildcard-domain fix** (`*.example.com` rules never matched subdomains; `uCp`/`g2a`), the multi-image "could not be processed" de-dup (`healsDistinctCarrier`), and a swarm of UI/perf/Windows fixes. Several of the latter are pure timing/rendering changes with no isolable declaration — those are called out honestly below.

> Confidence note: every anchor below was read line-by-line in the v2.1.183 bundle and, where a "before" claim is made, confirmed against the v2.1.156 bundle (usually a `grep -c` of the new string/regex returning `0`). Four items are pure UI/timing fixes with no single isolable decl and are tagged as such.

## 1. Sub-agents can spawn their own sub-agents — 5-level depth limit (NEW · FOCUS-bg)

**Type:** feature · **Modules:** Subagent, Agent Team, Tools, Background Agents

**TL;DR.** In v2.1.156 there was **no notion of agent depth** (`grep -c agentDepth` / `grep -c spawnDepth` = `0` in that bundle); a subagent could only re-spawn the Agent/Task tool when *team mode* was on, gated by the team-only boolean `R7() && mG()`. v2.1.172 replaces that with a **universal numeric gate**: a constant `SUBAGENT_DEPTH_LIMIT` (`v1i`, cli_inner_pretty.js:221800) hard-coded to **5**, a depth reader `getAgentDepth` (`Gz`, :103152) where `main` is depth `0`, and an enforcement line inside the *universal* tool filter `cio` (:371188): `if (Rc(i, vs)) return s < v1i;` — the Agent tool survives the filter **iff `agentDepth < 5`**. Each spawn surface threads `Gz(parent)+1` and persists it as `spawnDepth`/`agent_depth`. Because the Agent-tool line precedes the async block in `cio`, the gate is **not** async/team-specific — foreground and background subagents share one limit. Enforcement is by tool *removal* (a depth-5 agent simply isn't given the Agent tool); there is no "max depth exceeded" string.

This is a focus feature with a dedicated deep-dive that covers the constant → reader → gate → threading → persistence → telemetry chain end-to-end, plus the full v2.1.156 before-picture (`uE6` team-only gate):

→ **[../36_background_agents/nested_subagent_depth_limit.md](../36_background_agents/nested_subagent_depth_limit.md)**

> Note: the changelog's companion phrasing ("foreground subagents now respect the same depth limit") is the **2.1.181** half of the same mechanism — see the module doc; the limit was *introduced* here in 2.1.172.

## 2. 1M-context-without-credits sessions auto-compact back under the standard limit (FIX · FOCUS-compact)

**Type:** fix (structural) · **Modules:** Compaction, Model window resolver, Telemetry

**TL;DR.** A session running a 1M-token context window depends on the account having long-context usage credits. When those run out the API returns a `429` ("…required for long context"). In v2.1.156 the client recognized the message and told the user to enable credits, but did **nothing structural** — the model's window stayed pinned at `1e6`, so the conversation could never compact under a window it could afford. It was **permanently stuck**. v2.1.172 latches a new session flag `longContext1mCreditsBlocked` on the first such 429 (trip site `$Cd` @229192, one-shot `tengu_1m_credits_clamp_activated`); from then on the window cap `getContextWindowForModel` (`tH` @134105) clamps a 1M model **back down to `jQ = 200000`**, which re-windows the entire threshold ladder so the session immediately compacts under the smaller window. A second consumer in the reactive lane (`DFi` @229611) treats a mid-summarization 1M-credits error as a `prompt_too_long` event anchored at 200k, reported via `tengu_compact_credits_clamp_rescue`.

This is a focus feature with a dedicated deep-dive (both clamp consumers, the reactive boundary, the new telemetry, and the v2.1.156 before-picture):

→ **[../07_compact/one_million_credits_clamp.md](../07_compact/one_million_credits_clamp.md)**

## 3. Workflow validation no longer rejects scripts that *mention* `Date.now()`/`Math.random()` (FIX · FOCUS-wf)

**Type:** fix · **Modules:** Workflow

**TL;DR.** The Workflow tool's determinism check bans `Date.now()` / `Math.random()` / `new Date()` so a replayed workflow stays deterministic. In v2.1.156 that check was a **raw regex** over the script text, so it false-positived on those tokens appearing inside a *string literal* or a *comment* (e.g. a prompt string that says "don't call Date.now()"). v2.1.172 rewrites the check as an **AST walk** (`rWa` @416439) that flags only real `MemberExpression`/`NewExpression` nodes, so a mere textual mention is now allowed. The tool spine (factory, enablement gate, the five input fields, `checkPermissions`, the `meta` parser, the `call` launch path) is byte-unchanged.

This is a focus feature; the determinism rewrite (and the sibling `errorCode 7` server-fallback retraction, the `taskType`/`workflowName` output fields, and the per-agent `effort` opt) are documented in the workflow tool-object delta:

→ **[../42_workflow/tool_definition_fixes_delta.md](../42_workflow/tool_definition_fixes_delta.md)**

## 5. Amazon Bedrock reads the AWS region from `~/.aws` config; `/status` shows the source (NEW)

**Type:** feature · **Modules:** Model / Provider config, Status

### TL;DR

When `AWS_REGION` / `AWS_DEFAULT_REGION` is unset, Claude Code on Bedrock now falls back to the **shared AWS config file** (`~/.aws/config`, via `AWS_CONFIG_FILE` / `AWS_PROFILE`) using the AWS SDK's own `loadConfig` precedence, instead of hard-defaulting to `us-east-1`. The resolved region is tagged with where it came from (`env` / `shared-config` / `default`), and `/status` renders that source: a bare region, `"<region> (from AWS config)"`, or `"<region> (default — set AWS_REGION or add a region to your AWS config)"`.

### How it works

**Step 1 — Source-tagged resolution (`Rfr`, cli_inner_pretty.js:45604).** `Rfr()` returns `{ region, source }`. It checks env first (`source:"env"`), then a memoized shared-config lookup keyed by config-file/profile (`source:"shared-config"`), then the hard default `I$e()` = `us-east-1` (`source:"default"`).

**Step 2 — The shared-config loader (`HKc`, :45616).** A memoized (`wn(…)` by `Mfr()` key) async that dynamically imports the AWS SDK's `loadConfig` and `NODE_REGION_CONFIG_FILE_OPTIONS` and reads `config.region` from the resolved profile, caching the result into `jXo` (the same map `Rfr` reads synchronously). The cache key `Mfr()` is `${AWS_CONFIG_FILE}|${AWS_SHARED_CREDENTIALS_FILE}|${AWS_PROFILE}`, so changing profile invalidates the cache.

**Step 3 — `/status` display (`tCa`, :344244).** Switches on `Rfr().source` to produce the user-facing string; the `default` branch additionally fires `kU()` to warm the async loader for next time.

```javascript
// ============================================
// resolveBedrockRegion + statusRegionLine - region with provenance, shown in /status
// Location: cli_inner_pretty.js:45604-45610 (Rfr), 344244-344253 (tCa)
// ============================================

// ORIGINAL (for source lookup):
function Rfr() {
  let e = Ge.AWS_REGION || Ge.AWS_DEFAULT_REGION;
  if (e) return { region: e, source: "env" };
  let t = jXo.get(Mfr());
  if (t) return { region: t, source: "shared-config" };
  return { region: I$e(), source: "default" };
}
function tCa() {
  let { region: e, source: t } = Rfr();
  switch (t) {
    case "env": return e;
    case "shared-config": return `${e} (from AWS config)`;
    case "default": return (kU(), `${e} (default — set AWS_REGION or add a region to your AWS config)`);
  }
}

// READABLE (for understanding):
function resolveBedrockRegion() {
  const fromEnv = env.AWS_REGION || env.AWS_DEFAULT_REGION;
  if (fromEnv) return { region: fromEnv, source: "env" };
  const fromSharedConfig = regionCacheByProfileKey.get(awsProfileCacheKey()); // populated by HKc/loadConfig
  if (fromSharedConfig) return { region: fromSharedConfig, source: "shared-config" };
  return { region: defaultRegion() /* "us-east-1" */, source: "default" };
}
function statusRegionLine() {
  const { region, source } = resolveBedrockRegion();
  switch (source) {
    case "env":           return region;
    case "shared-config": return `${region} (from AWS config)`;
    case "default":       return (warmSharedConfigLoad(), `${region} (default — set AWS_REGION or add a region to your AWS config)`);
  }
}

// Mapping: Rfr→resolveBedrockRegion, tCa→statusRegionLine, jXo→regionCacheByProfileKey,
//   Mfr→awsProfileCacheKey, I$e→defaultRegion, kU→warmSharedConfigLoad, HKc→sharedConfigLoader (async)
```

### Why this approach

**Matching AWS SDK precedence.** The bullet explicitly says "matching AWS SDK precedence" — rather than reimplement INI parsing, v2.1.172 reuses the SDK's own `loadConfig` so the resolved region matches what `boto3`/the AWS CLI would compute for the same profile. The cost is a dynamic import on the cold path; the memoization (`HKc` cached by profile key) makes it one-time per profile. **Before:** v2.1.156's region path was env-only (`process.env.AWS_REGION || process.env.AWS_DEFAULT_REGION || "us-east-1"`, v2.1.156 :3569) with **no** `~/.aws` reading and **no** source tag — confirmed: `grep -c "from AWS config"` = `0`, `grep -c "shared-config"` = `0` in v2.1.156.

## 7. Model-restriction hardening — `availableModels` allowlists, version-specific IDs, doubled `[1m]`, `opusplan[1m]`, Bedrock picker (FIX cluster)

This is the single largest cluster in 2.1.172. All of it sits on a **net-new** model-restriction subsystem introduced in this window: the allowlist predicate `ul` (`isModelAllowed`, cli_inner_pretty.js:102242) and the server-availability predicate `KHe` (:102462). Both the `enforceAvailableModels` machinery and the `server-unavailable` notion are **absent from v2.1.156** (`grep -c enforceAvailableModels` = `0`, `grep -c server-unavailable` = `0`). The five bullets below are facets of the same code.

### 7a. `availableModels` restrictions now applied to subagent overrides, the dispatch picker, and the advisor

**Type:** fix · **Modules:** Model selection, Subagent, Permissions

The core gate `ul(model, opts)` (:102242) is now consulted on the previously-unguarded surfaces: subagent **model overrides**, the **agent dispatch** model picker, and the **advisor** model. The function resolves the candidate through the model-overrides map and aliases, then checks membership in the allowlist `availableModels` (from `policySettings`); an empty array means "only the default model" (`if (r.length === 0) return !1`). The plan-mode resolver `aL` (:102523) calls `ul(a)` before upgrading to the opusplan/haiku plan model, emitting a one-shot warn ("…the opusplan upgrade model is not in the availableModels allowlist; planning uses the resting model instead", :102531) and falling back to the resting model when the upgrade isn't allowed.

### 7b. `availableModels` allowlists no longer hide Opus/Sonnet 1M rows for version-specific IDs (e.g. `claude-opus-4-8`)

**Type:** fix · **Modules:** Model selection, `/model` UI

When an allowlist entry is a *version-specific* ID like `claude-opus-4-8` (rather than a family alias like `opus`), the `/model` picker previously failed to match the Opus/Sonnet **1M** rows. The fix lives in `ul`'s alias/version reconciliation tail (:102268-102289): it normalizes both the candidate and the allowlist entries (`Ul(...)`), expands aliases (`PM`/`_s`), and treats a concrete version ID and its 1M variant as matching the family rows. The `o1e`/`C2s` helpers distinguish a concrete-versioned entry from a resolvable alias so a `claude-opus-4-8` allowlist entry still lights the family's 1M row.

### 7c. Doubled `[1M][1m]` suffix de-duplicated (`Lq`)

**Type:** fix · **Modules:** Model selection

When `ANTHROPIC_DEFAULT_OPUS_MODEL` already carries a `[1m]` suffix and the resolver appends another, the model ID ended up as `…[1M][1m]`. The fix is a single canonicalizer applied at every 1M-suffix site:

### 7d. `opusplan` ships with 1M context in plan mode for entitled users; `opusplan[1m]` switches to Opus

**Type:** fix · **Modules:** Model selection, Plan mode

The plan-mode resolver `aL` (:102523) now branches on both `"opusplan"` **and** `"opusplan[1m]"` and computes the upgrade model as `o === "opusplan[1m]" || rv() ? ### 7e. Bedrock `/model` picker no longer offers models the provider doesn't serve

**Type:** fix · **Modules:** Model selection, `/model` UI, Bedrock

The server-availability predicate `KHe` (:102462) classifies a model as unavailable — `{reason:"disabled"|"absent", …}` — when the active provider doesn't serve it. The picker/override enforcement (`enforceAvailableModels`, around :102600-102740) drops candidates that `KHe(...)` rejects as "server-unavailable", logging "…no availableModels entry survived; … skipped as server-unavailable (…)" (:102727). (`KHe`'s firstParty-only early return at :102463 reflects that the disabled/absent checks are firstParty-specific; the Bedrock picker filtering routes through the same `enforceAvailableModels` server-availability pass.)

## 8. WebFetch `domain:*.example.com` wildcard rules now match subdomains; mid-pattern file-rule wildcards accepted (FIX)

**Type:** fix · **Modules:** Permissions

### TL;DR

`WebFetch(domain:*.example.com)` rules **never matched any subdomain** in allow/deny/ask position — and file permission rules with a wildcard in the *middle* of a pattern (e.g. `Read(secrets-*/config.json)`) were rejected at startup. v2.1.172 adds a proper wildcard domain matcher (`uCp`/`g2a`) that compiles `domain:*.x` into a regex requiring at least one subdomain label.

### How it works

The domain-rule lookup `m2n` (cli_inner_pretty.js:393444) walks rule entries: exact (`a === r`) matches win, and for any rule containing `*` it tries the wildcard matcher `uCp`:

```javascript
// ============================================
// matchWildcardDomainRule (uCp) + globToHostRegex (g2a) - *.x matches subdomains
// Location: cli_inner_pretty.js:393464-393481
// ============================================

// ORIGINAL (for source lookup):
function uCp(e, t) {
  if (!e.startsWith("domain:") || !t.startsWith("domain:")) return !1;
  if (e === "domain:*") return !0;
  let n;
  if (e.startsWith("domain:*.")) n = `^domain:(?:[^.:]+\\.)+${g2a(e.slice(9))}$`;
  else n = `^domain:${g2a(e.slice(7))}$`;
  return new RegExp(n, "i").test(t);
}
function g2a(e) {
  return e.split("*").map((t) => t.replace(/[.+?^${}()|[\]\\]/g, "\\$&")).join("[^.:]*");
}

// READABLE (for understanding):
function matchWildcardDomainRule(rulePattern, candidate) {
  if (!rulePattern.startsWith("domain:") || !candidate.startsWith("domain:")) return false;
  if (rulePattern === "domain:*") return true;                       // bare * matches anything
  let regexSrc;
  if (rulePattern.startsWith("domain:*.")) {
    // require ONE OR MORE subdomain labels before the suffix → *.example.com matches a.example.com
    regexSrc = `^domain:(?:[^.:]+\\.)+${globToHostRegex(rulePattern.slice(9))}$`;
  } else {
    regexSrc = `^domain:${globToHostRegex(rulePattern.slice(7))}$`;   // mid-pattern * → [^.:]* (no dot crossing)
  }
  return new RegExp(regexSrc, "i").test(candidate);
}
function globToHostRegex(pattern) {
  return pattern.split("*")
    .map((seg) => seg.replace(/[.+?^${}()|[\]\\]/g, "\\$&"))         // escape regex metachars per literal segment
    .join("[^.:]*");                                                 // * expands to "any chars except dot/colon"
}

// Mapping: uCp→matchWildcardDomainRule, g2a→globToHostRegex, e→rulePattern, t→candidate
```

The clever part is the `*.` branch: it emits `(?:[^.:]+\.)+` — **one or more** dot-terminated labels — so `*.example.com` matches `api.example.com` and `a.b.example.com` but not the bare apex `example.com`, exactly the expected subdomain-wildcard semantics. The `[^.:]*` expansion in `g2a` is what makes mid-pattern wildcards (`Read(secrets-*/config.json)`) compile to a valid regex instead of being rejected.

**Before:** v2.1.156 has `grep -c '(?:[^.:]+\.)+'` = `0` and `grep -c '[^.:]*'` for this matcher = `0` — there was no wildcard-domain matcher; rules with `*` simply never matched. (Confidence: high for the domain matcher, which is fully isolated; the file-rule mid-pattern half is the same `g2a` `[^.:]*` compilation applied to path globs — the changelog groups them as one fix.)

## 9. Repeating multi-image "could not be processed and was removed" error de-duplicated (FIX)

**Type:** fix · **Modules:** Conversation normalization, Image handling

### TL;DR

When the conversation contained **multiple** images and one was unprocessable, the "an image in the conversation could not be processed and was removed" heal-message was emitted **once per image**, repeating on every turn. v2.1.172 adds a per-distinct-carrier dedup so the message is attached once per carrier message rather than once per media item.

### How it works

The error string is built by `unt` (cli_inner_pretty.js:228951, unchanged). The fix is the new `healsDistinctCarrier` flag (4 occurrences, **all new** — `grep -c healsDistinctCarrier` = `0` in v2.1.156): set on a heal entry that carries structured `errorDetails` (`if (qNl(i)) i.healsDistinctCarrier = !0`, :587501), and consumed inside the heal-orchestrator `Cx` (:588170). `Cx` maintains a per-carrier `Map` (`c`) recording which media types (`image`/`document`) have already been healed for each carrier `uuid` at which "distinct-carrier index" `d`; the `healsDistinctCarrier` branch (:588199) filters the pending heal set against that map (`V === void 0 || V === d`) so an already-attached heal for the same carrier is skipped instead of re-emitted. `ESf` (:588095) maps each heal message back to the media-type set it covers (`unt("image") → {"image"}`, etc.) so the dedup is type-aware.

This is a substantive normalization change but its core is the new boolean signal plus the `Cx` map bookkeeping rather than one self-contained function. **Before:** the error string and the heal pass existed in v2.1.156, but with **no** `healsDistinctCarrier` gating — so a heal re-fired for each unprocessable item.

(Confidence: medium — the gating mechanism `altScreenMouseTracking = e && t` and the `UTe` emit guards are isolated; the specific Windows-console capability test that supplies `t=false` is in the platform-capability layer.)

## Cross-cutting reading

The four flagship items (§1-§4) are all "stop being permanently stuck / silently wrong" fixes that happen to each ship a *new mechanism*: a depth counter, a window clamp, a flag-independent enable gate, and an AST walk. The model-restriction cluster (§7, plus §18) is the second spine: one new allowlist subsystem (`ul`/`KHe`) whose corners — version IDs, doubled suffixes, opusplan, Bedrock serving — all needed individual fixes in the same release. The remaining bullets are the usual breadth tail: a provider-config addition (§5), a telemetry attribute (§6), a permissions matcher (§8), a normalization dedup (§9), and a long list of UI/perf/Windows/VSCode polish, several of which are honest non-isolable timing fixes.
