### Why a release collapses to "Bug fixes and reliability improvements"

This is the one genuinely interesting question for a boilerplate release, so it gets the deeper treatment.

**What it does:** Advances the public version counter while shipping a batch of fixes the changelog chooses not to enumerate.

**How it works (the release-engineering mechanics, inferred from the train shape):**
1. Internal `main` accrues many small fixes between tags — error-path hardening, render-timing tweaks, retry/timeout adjustments, platform-specific guards — each too narrow to deserve its own curated bullet.
2. When a tag is cut, all merged work ships; the curated changelog is written by hand to surface only what the author judges a user would *notice and want named*.
3. If that judgment yields nothing nameable (only diffuse reliability work), the changelog collapses to the standing line "Bug fixes and reliability improvements." This is a deliberate *editorial* outcome, not evidence that the diff was empty.
4. The version is still published (not skipped) to keep the release channel monotonic and give the auto-updater a clean, well-ordered sequence to walk.

**Why this approach (vs. writing a bullet per micro-fix or folding everything into the next big release):**
- **Signal-to-noise in the changelog.** A bullet per one-line render-timing fix would bury the genuinely important entries (like 2.1.166's `fallbackModel` or 2.1.169's `--safe-mode`) under noise. Rolling diffuse fixes under one standing line keeps the changelog scannable.
- **Cadence decoupling.** Shipping accumulated fixes on their own tag keeps the train moving steadily instead of pooling fixes into the next feature release, where a regression would be harder to bisect against the feature payload.
- **Monotonic channel.** Publishing rather than skipping the tag keeps npm versions and the auto-updater sequence clean and gap-free.

**Key insight:** For a reverse-engineering pass that works only from a shipped artifact, a boilerplate-changelog release is correctly documented as **un-anchorable at the source level** — not because nothing changed, but because the changelog deliberately supplies no nameable hook, and the bundle (the 2.1.183 *result*) embeds no 2.1.167-specific marker. The honest claim is "2.1.167 shipped un-enumerated reliability fixes; none is isolable to a single decl in the 2.1.183 bundle," not a fabricated anchor.
