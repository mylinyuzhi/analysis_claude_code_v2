### What this release is

2.1.159 is one of the periodic **plumbing-only releases** in the Claude Code train. The release exists to ship internal work — build-system, dependency, telemetry-plumbing, refactor, or test-harness changes — that has no observable effect on the CLI's behavior, prompts, tools, permissions, or UI. Anthropic ships these so internal `main` keeps moving and large in-flight refactors land incrementally behind the public version counter, rather than all at once inside a feature release where a regression would be hard to bisect.

### Why a release with no user-facing changes is published at all

This is the one genuinely interesting question for an internal-only version, so it warrants the deep treatment.

**What it does:** Advances the public version counter while shipping zero observable behavior.

**How it works (the release-engineering mechanics, inferred from the train shape):**
1. Internal `main` accumulates commits continuously — refactors, dependency bumps, build-config changes, test additions, and scaffolding for upcoming features that is gated off or not yet wired to any surface.
2. When a tagged release is cut, **all** merged commits since the last tag ship, regardless of whether any is user-facing. The changelog is curated by hand to describe only what a *user* would notice.
3. If, between two tags, the only merged work is plumbing, the curated changelog has nothing user-facing to list — so it collapses to the single boilerplate line.
4. The version is still published (rather than skipped) so the npm/release channel stays monotonic and the auto-updater has a clean, well-ordered sequence to walk.

**Why this approach (vs. folding the work into the next feature release):**
- **Bisectability.** A behavior-neutral version is a clean bisect boundary. If a user reports a regression first seen in 2.1.160, Anthropic can exclude 2.1.159 as "infra-only, no behavior" without re-reading its diff — the changelog *is* the assertion that it changed nothing observable.
- **Risk isolation.** Refactors that *intend* to be behavior-preserving sometimes are not. Shipping them alone means any fallout is attributable to exactly one release with a known, narrow scope, instead of being entangled with a feature payload where the feature and the refactor regression are confounded.
- **Incremental landing of big work.** The 2.1.160 payload (a dozen-plus `claude agents`/background-session fixes, new permission prompts for shell-startup and build-config files, the dynamic-workflow trigger rename) is large. Its non-user-facing scaffolding can land across quiet versions like 2.1.159 so the next release is mostly the *activation* of already-merged, already-soaked infrastructure.

**Key insight:** The *absence* of a user-facing diff is the deliverable. For a reverse-engineering pass that works only from shipped artifacts, an internal-only release is correctly documented as a **non-event at the behavioral surface**. The honest, verifiable claim is not "here is the code 2.1.159 changed" (we cannot see it — the bundle is the 2.1.183 *result*, and no 2.1.159 build was extracted) but rather "2.1.159 introduced nothing the user, the prompts, the tools, the permission engine, or the telemetry surface can observe, by the changelog's own statement, and the surrounding train shape is consistent with that."
