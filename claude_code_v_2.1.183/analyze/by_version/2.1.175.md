# v2.1.175 — Source Diff Analysis

**Theme:** **One managed-settings hardening: `enforceAvailableModels` turns the `availableModels` allowlist from a "what the user can pick" filter into a true policy boundary that also pins the *Default* model and that user/project settings can no longer widen.** Before 2.1.175, an enterprise admin's `availableModels` allowlist only constrained the explicit model menu — the "Default" pseudo-model still resolved to whatever the user's tier dictated, even if that concrete model was outside the allowlist. 2.1.175 adds the `enforceAvailableModels` boolean (managed-settings only in practice). When it's on and `availableModels` is a non-empty array: (1) a Default that would resolve to a disallowed model now falls back to the *first allowed* allowlist entry, and (2) the settings loader force-overrides `availableModels`/`enforceAvailableModels` with the policy-tier values, so a user or project `settings.json` can no longer broaden a managed list. The implementation is unusually defensive — it carries a small state machine that *refuses* to trust user/project settings (rather than failing open) whenever a policy source exists but fails to load.

> This release touches the model-selection / managed-settings subsystem only; it is not one of the five focus features, so the primary analysis lives here. Settings-merge and model-resolution symbols cross-reference `../00_overview/symbol_index_infra_platform.md`.

## 1. `enforceAvailableModels` managed setting — allowlist constrains the Default model and cannot be widened (NEW)

**Type:** feature (managed-settings / model policy) · **Modules:** Model selection, Settings merge, Managed/policy settings, `/model` picker

### TL;DR

A new optional boolean `enforceAvailableModels` joins `availableModels` and `modelOverrides` in the settings schema (cli_inner_pretty.js:55917-55921). With it enabled and a non-empty `availableModels`:

1. **Default is constrained.** The default-model resolver `resolveDefaultModel` (`ux`, cli_inner_pretty.js:2569 → 102569) now passes the tier-resolved default through the allowlist-enforcement engine `enforceAllowlistOnDefault` (`$un`, cli_inner_pretty.js:102580-102731). If the tier default isn't in `availableModels`, it returns the first allowlist entry that expands to a server-available model instead of the disallowed tier default.
2. **The list can't be widened.** The managed-settings merge `mergeManagedSettings` (`ggr`, cli_inner_pretty.js:57181-57193) only adopts a non-managed `availableModels` when no managed one exists (`t.availableModels === void 0 && e.availableModels`), and the settings loader `loadSettings` (`_gr`, cli_inner_pretty.js:57356-57358) then force-overwrites the merged `availableModels`/`enforceAvailableModels` with the *policy-tier* values (`r.availableModels = [...a.availableModels]`), so the admin's exact array wins over anything a user/project layer merged in.

### How it works

**Step 1 — Schema.** `enforceAvailableModels` is declared right after `availableModels` in the settings Zod schema (cli_inner_pretty.js:55917). Its `.describe()` text is the precise spec: *"When true and availableModels is a non-empty array, the Default model selection is also constrained: if the default model for the user tier is not in availableModels, Default resolves to the first allowed availableModels entry instead. Has no effect when availableModels is unset or an empty array."* A `.catch()` wrapper (cli_inner_pretty.js:56511-56519) makes a *malformed* value **fail closed** — an invalid `enforceAvailableModels` is treated as `true` ("treating it as true until it is fixed") rather than silently disabling enforcement.

**Step 2 — "Cannot widen" at the merge layer.** Two complementary guards:

- `mergeManagedSettings` (`ggr`) adopts the managed `availableModels` only if the *target* (already-merged) view doesn't have one — `if (t.availableModels === void 0 && e.availableModels) n.availableModels = e.availableModels;` (cli_inner_pretty.js:57192) — and unconditionally raises the enforce flag if any managed source sets it: `if (e.enforceAvailableModels === !0) n.enforceAvailableModels = !0;` (cli_inner_pretty.js:57193, the same any-source-true pattern as `allowManagedHooksOnly` etc.).
- After *all* settings layers are merged, `loadSettings` (`_gr`) captures the policy-tier object as `a` (cli_inner_pretty.js:57327, `a = u`) and, at the very end, force-overwrites the result: `if (a.availableModels !== void 0) r.availableModels = [...a.availableModels];` / `if (a.enforceAvailableModels !== void 0) r.enforceAvailableModels = a.enforceAvailableModels;` (cli_inner_pretty.js:57356-57358). This is the decisive "cannot widen" step: even if a user `settings.json` listed extra models, the policy view's exact array is the final value.

**Step 3 — Constraining Default.** The default-model resolver `resolveDefaultModel` (`ux`, cli_inner_pretty.js:102569-102572) computes the tier-appropriate setting/family/baseline via `resolveTierDefault` (`PCr`, cli_inner_pretty.js:102573-102579), then returns `enforceAllowlistOnDefault(setting, envFamily, concreteBaseline) ?? setting`. `enforceAllowlistOnDefault` (`$un`) returns `null` (i.e. "no override needed") when enforcement is off or the tier default is already allowed, and otherwise returns a *replacement* model from the allowlist. Because `resolveDefaultModel` is the single chokepoint the whole app uses for "what does Default mean" (main-loop model, per-session model, `_s` expansion — callers at cli_inner_pretty.js:101718, 551596, 478564, etc.), constraining it here constrains Default everywhere.

**Step 4 — The enforcement engine's policy state machine.** `enforceAllowlistOnDefault` first calls `getModelPolicyState` (`L2s`, cli_inner_pretty.js:102744-102795), which returns one of:
- `{ state: "refused" }` — a policy source *exists but failed to load*. Enforcement **refuses to trust** user/project settings entirely (cli_inner_pretty.js:102755-102768): rather than fail open to a possibly-wider user allowlist, it disables cascade-trust until the admin source is fixed.
- `{ state: "active", allowlist, overridesMap }` — a managed policy with `enforceAvailableModels === true` and a non-empty `availableModels` (cli_inner_pretty.js:102790). Enforcement uses the policy's own list and overrides.
- `{ state: "inactive", cascadeTrusted }` — no managed policy (or it doesn't enforce). `cascadeTrusted` says whether user/project `enforceAvailableModels` may still apply.

`enforceAllowlistOnDefault` bails to `null` (no constraint) when the state is `refused`, when there's no allowlist, or when neither the policy nor a cascade-trusted user setting turns enforcement on (cli_inner_pretty.js:102586-102592). Otherwise it resolves the tier default, and if that default isn't in the allowlist it walks the allowlist (expanding family aliases like `opus`, version prefixes like `opus-4-5`, and full IDs), skipping entries that resolve to server-unavailable models, and returns the first survivor — applying any managed `modelOverrides` mapping at the exit (cli_inner_pretty.js:102677-102730). If *no* allowlist entry expands to an available model it emits a one-time warning (deduped via the `AO` set) and falls back to pinning the env-free tier builtin.

**Step 5 — `/model` picker membership check.** The companion `isModelAllowed` (`NN`, cli_inner_pretty.js:102797-102806) reuses the same state machine to answer "is this concrete model selectable?" — returning `false` for `refused`, `null` (defer) for `inactive`, and an allowlist-membership test for `active`. Its callers gate the `/model` picker rows and migration paths (cli_inner_pretty.js:102528, 102547, 458138, 609424, 688256), so a model the allowlist forbids never becomes selectable.

```javascript
// ============================================
// enforceAllowlistOnDefault - Constrain the resolved Default model to availableModels
// Location: cli_inner_pretty.js:102569-102592, 102744-102795 (v2.1.183)
// ============================================

// ORIGINAL (for source lookup):
function ux() {
  let { setting: e, envFamily: t, concreteBaseline: n } = PCr();
  return $un(e, t, n) ?? e;
}
function $un(e, t, n) {
  let r = ts() || {}, o = r.availableModels, s = r.enforceAvailableModels, i = {}, a = L2s();
  if (a.state === "refused") return null;
  let l = a.state === "inactive" && a.cascadeTrusted;
  if (a.state === "active") ((o = a.allowlist), (s = !0), (i = a.overridesMap));
  else if (!a.cascadeTrusted) return null;
  if (!s) return null;
  if (l && Object.keys(i).length === 0 && r.modelOverrides) i = r.modelOverrides;
  if (!o || o.length === 0) return null;
  /* ...resolve tier default; if allowed -> return null; else walk allowlist,
     skip server-unavailable, apply modelOverrides, return first survivor... */
}

// READABLE (for understanding):
function resolveDefaultModel() {
  let { setting: tierDefault, envFamily, concreteBaseline } = resolveTierDefault();
  // If enforcement yields a replacement, use it; otherwise keep the tier default.
  return enforceAllowlistOnDefault(tierDefault, envFamily, concreteBaseline) ?? tierDefault;
}
function enforceAllowlistOnDefault(tierDefault, envFamily, concreteBaseline) {
  let settings = getSettings() || {},
      allowlist = settings.availableModels,
      enforce = settings.enforceAvailableModels,
      overridesMap = {},
      policy = getModelPolicyState();           // refused | active | inactive
  if (policy.state === "refused") return null;   // fail closed: don't auto-allow user list
  let cascadeFromUserSettings = policy.state === "inactive" && policy.cascadeTrusted;
  if (policy.state === "active") {
    allowlist = policy.allowlist; enforce = true; overridesMap = policy.overridesMap;
  } else if (!policy.cascadeTrusted) return null;
  if (!enforce) return null;                              // flag off -> no constraint
  if (cascadeFromUserSettings && Object.keys(overridesMap).length === 0 && settings.modelOverrides)
    overridesMap = settings.modelOverrides;
  if (!allowlist || allowlist.length === 0) return null;  // empty/unset -> no constraint
  // ...if tierDefault is in allowlist return null; else return first allowed,
  //    server-available, modelOverrides-mapped allowlist entry...
}

// Mapping: ux→resolveDefaultModel, $un→enforceAllowlistOnDefault, PCr→resolveTierDefault,
//          ts→getSettings, L2s→getModelPolicyState, o→allowlist, s/enforce, i→overridesMap,
//          l→cascadeFromUserSettings, AO→(deduped warning set), NN→isModelAllowed
```

Crucially, the **Default** pseudo-model resolved straight from the user's tier with no allowlist check — a Default that mapped to a model outside the admin's `availableModels` was still used. | **After (v2.1.175)** | `enforceAvailableModels: true` + non-empty `availableModels` makes the allowlist a hard boundary on Default (resolves to the first allowed entry) *and* makes the policy-tier list authoritative — `loadSettings` force-overwrites the merged `availableModels`/`enforceAvailableModels` with the policy values, so user/project settings cannot widen it. A malformed flag fails *closed* (treated as `true`); a policy source that fails to load makes enforcement *refuse* to trust user/project settings rather than fail open. |
| **Why** | An allowlist that only filtered the visible menu but let "Default" punch through to a disallowed model was a real enforcement hole for enterprises that must pin model usage (compliance, cost, region). Making Default flow through the same allowlist — and making the managed list non-wideable and fail-closed — closes that hole. The design deliberately prefers *over*-restriction (refuse / fail-closed) to under-restriction, which is the correct bias for an admin control: a momentarily-broken policy source must not silently grant access to models the admin meant to forbid. |

**Key insight:** The feature is two enforcement points sharing one policy state machine. The *merge/loader* layer (`ggr` + `_gr`'s final force-override) guarantees the **list itself** can't be widened by lower-trust settings; the *resolver* layer (`ux` → `$un`) guarantees the **Default selection** is pulled back inside the list. Routing both Default resolution (`$un`) and picker membership (`NN`) through the same `getModelPolicyState` (`L2s`) means the "is this model allowed?" decision is computed identically everywhere — and the `refused` state is what makes the control genuinely fail-closed: a half-loaded admin policy disables cascade-trust instead of leaking a wider user allowlist. The `.catch()`-treats-invalid-as-`true` schema wrapper is the same fail-closed bias applied at the parse boundary.
