# v2.1.174 — Source Diff Analysis

**Theme:** **A model-picker / model-naming correctness sweep, two provider-routing fixes (Bedrock GovCloud inference-profile prefix, background `ANTHROPIC_*` provider-env isolation), and a scattering of UX/attribution polish.** 2.1.174 has no big new subsystem — its one genuinely new user-facing surface is the `wheelScrollAccelerationEnabled` setting that lets you turn off mouse-wheel scroll acceleration in fullscreen mode. The weight of the release is in *fixes*: the `/model` picker stops hiding the family that **Default** resolves to (so Opus/Sonnet appear as their own selectable rows per plan tier), stops showing a hardcoded Sonnet version label when `ANTHROPIC_DEFAULT_SONNET_MODEL` pins a different Sonnet, and stops pre-selecting an `/advisor` model that the `availableModels` allowlist forbids; git commit co-author attribution stops fabricating a wrong model name; Bedrock GovCloud (`us-gov-*`) regions stop deriving a `global` inference-profile prefix (which 400'd); and background sessions stop inheriting another session's `ANTHROPIC_*` provider env. Two of the bullets are focus-feature items — the Workflow `agent()` attribution-header fix and the background provider-env isolation — and are summarized here with verified anchors and links into their depth modules rather than re-derived.

## 1. `wheelScrollAccelerationEnabled` setting — disable mouse-wheel scroll acceleration (NEW)

**Type:** feature · **Modules:** Settings, TUI scroll engine

### TL;DR

A new boolean user setting, `wheelScrollAccelerationEnabled` (default `true`), lets you turn off the "ramp scroll speed during fast scrolls" behavior in fullscreen mode. When set to `false`, the wheel-scroll state machine keeps its multiplier pinned at `base` and never enters the accelerated "wheelMode" ramp.

### How it works

**Step 1 — Schema.** The setting is declared in the user-settings Zod schema right next to `autoScrollEnabled` (cli_inner_pretty.js:56426-56428), described as *"Ramp mouse-wheel scroll speed during fast scrolls (fullscreen mode only)"*. It is **new in this window** — `grep` for `wheelScrollAccelerationEnabled` returns zero hits in the v2.1.156 bundle.

**Step 2 — Read at scroll-state construction.** The scroll-engine factory `Mll` (cli_inner_pretty.js:489533-489542) reads the setting via `Ec("wheelScrollAccelerationEnabled", !0)` (config getter with default `true`) and threads it as the 4th argument into the scroll-state constructor `I6p` (cli_inner_pretty.js:489517-489532), which stores it as `accelEnabled`. The debug log appends `· accelDisabled` when it is off.

**Step 3 — Gate the acceleration math.** Every acceleration branch in the per-tick scroll updater is guarded by `accelEnabled`: the multiplier only ramps `if (e.accelEnabled)` (cli_inner_pretty.js:489465), the burst/wheelMode ramp only runs `if (e.wheelMode && e.accelEnabled)` (cli_inner_pretty.js:489490), and the multiplier is force-reset to `base` when `!e.accelEnabled` (cli_inner_pretty.js:489496, 489506). With the flag off, scroll velocity is constant.

|---|---|
| **Type** | Feature (settings toggle) |
| **Before** | Fast wheel scrolling always ramped speed (the `wheelMode`/`burstCount` acceleration existed in 2.1.156 but was unconditional); users on jittery trackpads/terminals couldn't opt out. |

It is a minimal "make the existing behavior optional" patch, not a new scroll engine.

## 2. `/model` picker stops hiding the family that Default resolves to (FIX)

**Type:** fix · **Modules:** Model picker

### TL;DR

The `/model` picker computes the option list per plan tier. A bug made the family that **Default** resolves to disappear as its own selectable row: on Max / Team Premium / Enterprise, Opus would not appear as a standalone row; on Pro / Team, Sonnet would not; on pay-as-you-go API, Opus would not. After the fix each tier shows its resolved-default family as a distinct, selectable row alongside `Default`.

### How it works

The model-option list is assembled by `Gwd` (cli_inner_pretty.js:227631-227685), which starts with the `Default (recommended)` row (`Cwn`, cli_inner_pretty.js:227371-227381) and then conditionally appends family rows. Each family is gated by `ZAe(familyKey)` (cli_inner_pretty.js:227686-227690) — "is this model family available under the active provider, or model-overridden?" — and the per-row builders are `Lqr` (Sonnet, 227402), `IBi`/`OBi`/`Owd`/`$wd` (the Opus variants), `LBi`/`Uwd` (Haiku), etc. The fix is in *which rows are unconditionally included* per branch: the `pd()` (Pro-tier) branch (227645-227657) and the API/pay-as-you-go branch (227659-227684) each now push the resolved-default family's own row even when `Default` already points at it, instead of treating "Default already covers this family" as a reason to skip the explicit row.

This is a **list-composition fix inside one large branchy function**, not a single isolable predicate — the change is distributed across the `Gwd` row-assembly arms (227634-227684). The behavior is verifiable from the structure (`Default` row + a per-family `push` whose presence is what the changelog describes), but there is no single distinctive grep-able line that *is* the fix.

| | |
|---|---|
| **Type** | Fix (picker row composition) |
| **Before** | The family Default resolves to was absorbed into the `Default` row and not shown separately — you could not explicitly pin "Opus" (Max/Enterprise) or "Sonnet" (Pro/Team) as a named choice. |
| **After** | Each tier's resolved-default family appears as its own row: Opus on Max/Team Premium/Enterprise and pay-as-you-go API, Sonnet on Pro/Team. |
| **Why** | "Default" is dynamic (it can change with entitlements); a user who wants to *pin* the current family needs that family as an explicit, stable selection. Hiding it forced them to either accept the moving `Default` or guess the version-specific ID. |

**Confidence:** medium. `Gwd`/`Cwn`/`ZAe` and the per-family row builders are verified verbatim; the precise 2.1.173→2.1.174 line-level delta inside `Gwd` cannot be diffed from a single build, so the fix is attributed by the function's shape and the changelog wording.

## 3. `/model` picker no longer shows a hardcoded Sonnet label when `ANTHROPIC_DEFAULT_SONNET_MODEL` is pinned (FIX)

**Type:** fix · **Modules:** Model picker, Provider env

### How it works

The custom-Sonnet picker row builder `wBi` (cli_inner_pretty.js:227389-227401) fires when `ANTHROPIC_DEFAULT_SONNET_MODEL` is set (and the tier predicate `Lwn` allows it). Its `label` is `process.env.ANTHROPIC_DEFAULT_SONNET_MODEL_NAME ?? e` — i.e. the operator-supplied display name, or the pinned model ID itself — **not** a hardcoded `"Sonnet 4.6"` string. The standalone built-in Sonnet row `Lqr` (cli_inner_pretty.js:227402-227409, label `"Sonnet"`, description `"Sonnet 4.6 · …"`) is only used when *no* custom Sonnet is pinned. So pinning a different Sonnet via `ANTHROPIC_DEFAULT_SONNET_MODEL` now surfaces *that* model's name in the picker rather than a stale hardcoded version.

// Location: cli_inner_pretty.js:227389-227401
// ============================================

      descriptionForModel: `${process.env.ANTHROPIC_DEFAULT_SONNET_MODEL_DESCRIPTION ?? `Custom Sonnet model${t ? " with 1M context" : ""}`} (${e})` };

// Mapping: wBi→customSonnetRow, Lwn→tierAllowsCustomSonnet, by→has1MSuffix, e→pinned

**Why:** When an enterprise pins a non-default Sonnet (e.g. an older snapshot, or a Bedrock alias) via `ANTHROPIC_DEFAULT_SONNET_MODEL`, showing the literal `"Sonnet 4.6"` label misrepresented what the session would actually use. Keying the label off `…_MODEL_NAME ?? <id>` makes the picker honest about the pinned model.

## 4. Git commit co-author attribution no longer fabricates a wrong model name (FIX)

**Type:** fix · **Modules:** Git attribution, Model naming

### TL;DR

The `Co-Authored-By:` line appended to commits derives the model display name from the *resolved session model*. A bug made it fall back to a **hardcoded `"Claude Opus 4.8"`** whenever the display-name lookup didn't recognize the model (custom IDs, version-suffixed IDs, Bedrock aliases) — so some models got the wrong name in their commit attribution. The fix gates the name behind a real model-recognition predicate and falls back to a generic `"Claude"` instead of a fabricated version.

### How it works

**Before (v2.1.156, `bFp`-equivalent, cli_inner_pretty.js:438717-438720 v2.1.156):**

```javascript
let H = X7(),
  $ = ZOH(H) !== null ? Q76(H) : "Claude Opus 4.8",   // <-- hardcoded fabricated fallback
  K = `Co-Authored-By: ${$} <noreply@anthropic.com>`;
```

When `ZOH(H)` (the display-name lookup) returned `null` — true for any model the table didn't recognize — the co-author name became the literal string `"Claude Opus 4.8"`, regardless of which model actually ran.

**After (v2.1.183, `bFp`, cli_inner_pretty.js:449605-449614):** the model name is computed by a three-way recognition gate against the resolved model `Gs()`:

```javascript
function bFp() {
  let e = Gs(),                                  // resolved session model id
    t = pT(e) ? Fun(MHe.firstParty)              // Fable → canonical first-party id
      : oJa(e) ? Fun(e)                          // recognized first-party model → "Claude <DisplayName>"
      : "Claude",                                // anything else → generic "Claude", no fabricated version
    r = `Co-Authored-By: ${t} <noreply@anthropic.com>`;
  ...
}
```

`oJa(e)` (cli_inner_pretty.js:449616-449638) is the new recognizer: it returns `false` unless the id maps to a known canonical model *and* matches the first-party-ID shape via a strict version-suffix regex (`/^(?:-fast|-latest)?(?:-v\d+@\d{8}|[-@]\d{8})?…/`), with special handling for Bedrock `application-inference-profile` ARNs. `Fun(e)` (cli_inner_pretty.js:103001-103005) formats as `Claude ${displayName}` or `Claude (${id})`. So an unrecognized model now yields `"Claude"` — never a wrong version number.

| | |
|---|---|
| **Type** | Fix (attribution correctness) |
| **Before** | Any model whose display-name lookup missed (custom/version-suffixed/Bedrock) got `Co-Authored-By: Claude Opus 4.8` regardless of the real model. |
| **After** | Known first-party model → its true display name; Fable → the canonical Fable first-party id; anything unrecognized → generic `Claude`. |
| **Why** | A commit's co-author line is a durable, public artifact; stamping every unrecognized model as "Opus 4.8" was actively misleading. Falling back to `"Claude"` is honest when the exact model can't be named. |

**Key insight:** The formatter (`Fun`/`Q76` → `Claude ${name}`) is essentially unchanged between builds; the fix is the *guarding predicate* `oJa` plus replacing the hardcoded `"Claude Opus 4.8"` literal with the `pT`/`oJa`/`"Claude"` ladder. The bug was a default-value bug, not a formatting bug.

## 5. Bedrock GovCloud (`us-gov-*`) inference-profile prefix derivation fixed (FIX)

**Type:** fix · **Modules:** Bedrock provider, Model ID resolution

### TL;DR

Bedrock derives a geo *inference-profile prefix* (`us`, `eu`, `apac`, `us-gov`, `global`) from the AWS region and prepends it to the model ID. GovCloud regions (`us-gov-*`) fell through to `global`, producing model IDs like `global.anthropic.claude-…` that GovCloud rejects with 400. The fix adds a dedicated `us-gov` branch that runs **before** the `us-` branch.

### How it works

The prefix deriver is `Noe(region)` (cli_inner_pretty.js:94936-94943). Its output feeds `q7e(modelId, prefix)` (cli_inner_pretty.js:94930-94934), which swaps or prepends the geo prefix onto the Bedrock model ID; both are called from the Bedrock model-resolution paths (cli_inner_pretty.js:95278-95302, 355617-355618, 355807).

**Before (v2.1.156, `We`, cli_inner_pretty.js:91635-91640):**

```javascript
function We(H) {
  let $ = H ?? "";
  if ($.startsWith("us-") && !$.startsWith("us-gov-")) return "us";  // explicitly EXCLUDES us-gov-*
  if ($.startsWith("eu-")) return "eu";
  if ($.startsWith("ap-")) return "apac";
  return "global";   // <-- us-gov-* lands here → wrong prefix → 400 on derived model IDs
}
```

A `us-gov-west-1` region was deliberately excluded from the `us` branch but had *no branch of its own*, so it fell through to `"global"`.

**After (v2.1.183, `Noe`, cli_inner_pretty.js:94936-94943):**

```javascript
function Noe(e) {
  let t = e ?? "";
  if (t.startsWith("us-gov-")) return "us-gov";   // <-- NEW dedicated branch, checked first
  if (t.startsWith("us-")) return "us";
  if (t.startsWith("eu-")) return "eu";
  if (t.startsWith("ap-")) return "apac";
  return "global";
}
```

`us-gov` is now a valid member of the prefix set `Uvt = ["us","eu","apac","jp","au","us-gov","global"]` (cli_inner_pretty.js:81463) that `Xln`/`q7e` recognize when swapping an existing prefix.

| | |
|---|---|
| **Type** | Fix (provider routing) |
| **Before** | `us-gov-*` regions derived a `global` inference-profile prefix; derived model IDs (`global.anthropic.claude-…`) 400'd in GovCloud. |
| **After** | `us-gov-*` derives `us-gov`; model IDs are prefixed correctly and accepted. |
| **Why** | GovCloud partitions are isolated; their inference profiles use the `us-gov.` prefix, not `global.`. The old code's exclusion of `us-gov-*` from the `us` branch without a replacement branch was an incomplete special-case. Putting the `us-gov-` check first makes the order-sensitive prefix string correct. |

## 6. `/advisor` dialog no longer pre-selects a model blocked by `availableModels` (FIX)

**Type:** fix · **Modules:** Advisor tool, Model allowlist

### How it works

The `/advisor` dialog (`Xlf`, cli_inner_pretty.js:546736+) pre-selects the saved `advisorModel` only when it passes the advisor validator `uFn` (cli_inner_pretty.js:546747): `i = r && !a && uFn(r) ? { label: NP(r), value: r } : void 0`. The validator `uFn(e)` → `o0e(Af(_s(e)))` (cli_inner_pretty.js:373374-373386), and `o0e` now **first** rejects any model not in the allowlist: `if (!ul(e)) return !1;` (cli_inner_pretty.js:373381), where `ul` is `isModelAllowed` (the `availableModels` allowlist check, exported at cli_inner_pretty.js:102322). The advisor option *list* itself (`sct`, cli_inner_pretty.js:373377-373379) is built as `SSp.filter((e) => uFn(e))`, so a blocked model is neither offered nor pre-selected.

| | |
|---|---|
| **Type** | Fix (allowlist enforcement) |
| **Before** | A previously-saved `advisorModel` was pre-selected in the dialog even when `availableModels` no longer permitted it — letting the user re-confirm a forbidden advisor. |
| **After** | `uFn`/`o0e` gate on `isModelAllowed` (`ul`); a blocked saved model is filtered out of the list and not pre-selected. |
| **Why** | Part of the broader `availableModels`-enforcement tightening (cf. 2.1.172's subagent/dispatch/advisor allowlist fixes). The advisor is just another model selection that must obey the org allowlist; pre-selecting a forbidden one was a hole in that enforcement. |

## 7. Skill hot-reload re-announces only the changed skill (FIX)

**Type:** fix · **Modules:** Skills, Hooks

### How it works

A hook can request a skill reload via `reloadSkills` in its `hookSpecificOutput` (schema at cli_inner_pretty.js:364219, 367553; surfaced from the hook result at cli_inner_pretty.js:577547; the reload-requested log at cli_inner_pretty.js:578991, `Hook … requested reloadSkills`). The reload itself is `reloadSkills()` (cli_inner_pretty.js:553751), and the flag is consumed where `if (p.reloadSkills) u = !0` (cli_inner_pretty.js:232398) drives a re-announce. The 2.1.174 fix changes the re-announce to diff the new skill listing against the previous one and re-send **only the changed skill(s)** to the model, instead of re-emitting the entire skill catalog on every single-skill change.

This is a **diff-and-emit behavior change inside the reload/announce path** rather than a new declaration — the `reloadSkills` plumbing (schema, hook output, the `reloadSkills()` method) is pre-existing and structurally unchanged; what changed is the announce step deciding *which* skills to re-send. No single distinctive grep string isolates the diff logic.

| | |
|---|---|
| **Type** | Fix (incremental reload) |
| **Before** | Editing one skill (or a hook firing `reloadSkills`) re-sent the entire skill listing to the model — wasted tokens and a noisy context churn. |
| **After** | Only the skills that actually changed are re-announced. |
| **Why** | Skill listings can be large; re-emitting all of them on a one-skill edit bloats the conversation and the prompt. Diffing keeps hot-reload cheap, which matters because hot-reload is meant to be used frequently during skill authoring. |

**Confidence:** medium — the `reloadSkills` plumbing is verified verbatim; the "only changed skills" diff is attributed from the changelog plus the shape of the reload/announce path, not a captured before/after line.

## 11. Pre-warmed background workers no longer fail auth after sitting idle (FIX — focus: Background)

**Type:** fix · **Modules:** Background agents, Worker auth/claim
