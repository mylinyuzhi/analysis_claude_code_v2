### 2. Plugins in `.claude/skills` auto-load without a marketplace (IMPROVEMENT)

**Type:** improvement · **Modules:** Plugins, Marketplace policy

#### TL;DR

A plugin directory placed under `.claude/skills/<name>/` (project or `~/.claude/skills/`) is now discovered and loaded automatically as `<name>@skills-dir` — no `marketplace.json`, no `marketplace add`, no `enabledPlugins` entry. The reserved `skills-dir` "marketplace" name is the sentinel for this scan, and managed settings can opt it in/out via a `{"source":"skills-dir"}` entry in `strictKnownMarketplaces`/`blockedMarketplaces`.

#### How it works

The scan is gated by `Rot` (cli_inner_pretty.js:289929-289932): if `blockedMarketplaces` lists `{source:"skills-dir"}` the scan is off; if `strictKnownMarketplaces` is set, the scan runs only when that allowlist *includes* `{source:"skills-dir"}` (any allowlist otherwise blocks it). The per-directory recognizer `T$l` (cli_inner_pretty.js:574265-574290) maps a path under `./.claude/skills/` or `~/.claude/skills/` to a `{skillName, pattern}`, and the new-plugin discovery walks `Ybp = [".claude/skills", ".claude/commands"]` (cli_inner_pretty.js:372282). Loading honors workspace trust: if the workspace was untrusted when plugins were scanned, project `@skills-dir` plugins are *not* loaded until `/reload-plugins` (cli_inner_pretty.js:471420), and a post-trust re-discovery fires after the trust dialog is accepted (cli_inner_pretty.js:680370).

| | |
|---|---|
| **Type** | Improvement (default-on auto-load) |
| **Modules** | Plugins, Marketplace policy, Trust |
| **Before (v2.1.156)** | The `skills-dir` sentinel and `@skills-dir` plumbing already existed in the bundle, but a `.claude/skills` plugin was not loaded as a plugin in the general user flow — you registered a marketplace or enabled it explicitly. |
| **After** | A plugin under `.claude/skills/` auto-loads as `<name>@skills-dir`, subject only to workspace trust and the managed-settings `skills-dir` policy sentinel. |
| **Why** | Collapses the "skill vs plugin" authoring gap: the same `.claude/skills/` directory users already populate with `SKILL.md` files now also hosts full plugins (commands, agents, monitors) with zero registration. The policy sentinel gives enterprises a single on/off switch without disturbing their other marketplace allow/block lists. |

> **Honest scoping note (medium confidence).** The `skills-dir` / `@skills-dir` infrastructure is present in *both* the v2.1.156 and v2.1.183 bundles, so the v2.1.157 change is the *activation/defaulting* of project-scope `.claude/skills` plugin auto-load (the changelog framing), not the introduction of the mechanism. The recognizer (`T$l`), the policy gate (`Rot`), the discovery dir list (`Ybp`), and the trust-gated reload are all verified at the lines above; the precise commit that flipped the default is not isolable to a single decl from the bundle alone.

## Sub-theme B — `claude agents` honors the `agent` field + `--agent`

### 4. Dispatched sessions honor `settings.json` `agent`, overridable by `--agent <name>` (NEW)

**Type:** feature · **Modules:** Agents, Dispatch, Settings, CLI

#### TL;DR

When `claude agents` dispatches a session, the `agent` field from `settings.json` is now used to select which agent definition runs as the main session, and `--agent <name>` on the command line overrides it. Previously the dispatch defaults builder carried `permissionMode`/`model`/`effort`/`allowBypass` but had no notion of a default agent.

#### How it works

The dispatch-defaults builder `LJl` (cli_inner_pretty.js:661062-661074) now resolves `agent` as `e?.agent ?? jr().agent` — the CLI/launch-supplied agent first (`--agent`), falling back to the merged settings `agent` field (`jr()` = the settings reader) — and threads it into the returned defaults object alongside the existing fields. The early-return guards are widened to keep the defaults alive when *only* an agent is set (`if (!e && !t) return;` and `if (!o && !e?.model && !a && !t && !s) return;`).

## Sub-theme C — `EnterWorktree` mid-session switching + worktree unlock

### 5. `EnterWorktree` can switch between Claude-managed worktrees mid-session (IMPROVEMENT)

**Type:** improvement · **Modules:** Worktrees, Tools, Agents

#### TL;DR

`EnterWorktree({ path })` now switches an already-in-a-worktree session (or a cwd-pinned subagent) into a *different* existing Claude-managed worktree, leaving the previous worktree on disk untouched and tracking only the new one for exit-time cleanup. Previously, being in a worktree session forced you to `ExitWorktree` before entering another.

#### How it works

The tool's `validateInput` (cli_inner_pretty.js:429926-429958) now lets `path` through even from a pinned subagent (`isolation: "worktree"` or explicit `cwd`) and from an already-in-a-worktree session — only *creating* (`name`) from those states is rejected. The `call` body handles two new branches:

- **Pinned subagent + `path`** (cli_inner_pretty.js:429936-429972): resolves the target with `requireManagedLocation`/`requireCwdInsideRepo`, switches *this agent's* cwd, updates the agent metadata cwd, and emits `tengu_worktree_entered_existing` with `{ mid_session: true, cwd_override: true }` — the switch affects only this agent, not the parent's process-wide cwd.
- **In-session + `path`** (cli_inner_pretty.js:429975-430010): `process.chdir`s into the new worktree, re-points write access, clears caches, refreshes the git branch, and emits `tengu_worktree_entered_existing` (or `tengu_worktree_created`) with `{ mid_session: true }`.

The tool prompt documents the new contract directly (cli_inner_pretty.js:429823): *"Switching with `path` also works when the session is already in a worktree (the previous worktree is left on disk, untouched, and only the new one is tracked for exit-time cleanup)… After a further switch, previously-visited worktrees are no longer writable — re-issue EnterWorktree with `path` to return to one."*

| **Before** | "Already in a worktree session. Use ExitWorktree to leave this one before creating a new worktree." — no in-place switch. |

### 6. Claude-managed worktrees left **unlocked** when the agent finishes (FIX)

**Type:** fix · **Modules:** Worktrees, Background agents, Git

#### TL;DR

When a Claude agent finishes and its worktree is *kept* (because it has uncommitted changes or commits ahead), the worktree's git lock is now released, so a later `git worktree remove`/`prune` can clean it up. Previously the lock (taken at creation to mark the worktree as "owned by a running agent") was left in place on the kept path, blocking removal.

#### How it works

### 7. Background-agent worktrees under `.claude/worktrees/` no longer orphaned after the 30-day retention sweep (FIX)

**Type:** fix · **Modules:** Background agents, Worktrees, Retention

#### TL;DR

After the 30-day background-job retention sweep, stale worktrees under `.claude/worktrees/` are now reliably cleaned. The stale-worktree sweeper `Yko` (`cleanupStaleAgentWorktrees`, cli_inner_pretty.js:580377-580406) is invoked from the retention pass (`let t = await Yko(e)`, cli_inner_pretty.js:626215; the 30-day retention constant `tDf = 30` is at cli_inner_pretty.js:626219), removing worktrees older than the cutoff that pass the orphan predicate `WOl` (cli_inner_pretty.js:580365-580375: clean status, HEAD merged/unreferenced) and then `git worktree prune`.

The sweeper function itself is carryover (present in v2.1.156 as `QKq`, cli_inner_pretty.js:555185-555226, before-picture) — the fix is the *lock state* that lets it work, not a new sweeper. Confidence: high for the mechanism, medium for attributing the full orphan fix exclusively to the unlock change vs. an additional sweep-invocation tweak.

### 27. Background sessions re-attached after a sleep/wake are told the correct (current) date (FIX)

**Type:** fix · **Modules:** Background agents, System reminders, Date context

#### TL;DR

When a background (`claude agents` / bridge) session is re-attached after the machine slept and woke — potentially across a day boundary — the model is now told the *current* date instead of the stale date frozen at the session's original startup. The date the model sees comes from a process-lifetime memoized "today" (`SCe`), and on a live sleep/wake reattach (same process, no disk resume) that memo was never invalidated, so the conversation kept reporting yesterday's date.

#### How it works

The model learns the date from two surfaces, both keyed off `SCe()` — `Itt()` (today as `YYYY-MM-DD`) memoized once per process via `wn` (cli_inner_pretty.js:220209-220222):

1. The user-context line `currentDate: M1i(SCe())` → "Today's date is …" (cli_inner_pretty.js:222386-222390, 226664), baked into the cached system/user-context block.
2. The per-turn `date_change` system-reminder produced by `ftl` (cli_inner_pretty.js:464855-464863): it compares fresh `Itt()` to the memoized `SCe()`, and on a mismatch emits `{ type: "date_change", newDate }` → *"The date has changed. Today's date is now … DO NOT mention this to the user explicitly because they are already aware."* (cli_inner_pretty.js:590591-590597).

The invalidation primitive already exists: `clearSessionCaches` (`Jyo`, cli_inner_pretty.js:476428-476459) clears `SCe.cache` (cli_inner_pretty.js:476435) and resets `lastEmittedDate` via `cyt(null)` (cli_inner_pretty.js:476442). It runs on `--continue`/`--resume`/print-mode session (re)hydration from disk (callers at cli_inner_pretty.js:689844, 689902, 694736, …). The bug class was a **live background-session reattach after sleep/wake** — the same long-lived process resuming, with no disk resume and thus no `clearSessionCaches` — leaving `SCe()` frozen at the pre-sleep date so neither surface reported the new day.

**Honest non-isolable note (medium confidence).** The conversation-side date machinery is byte-identical between v2.1.156 and v2.1.183: the detector (`ftl` ≡ v2.1.156 `Mw4`, cli_inner_pretty.js:412901-412910 before-picture), the memoize (`SCe = wn(Itt)` ≡ `NlH = v8(WwH)`, cli_inner_pretty.js:212561-212574 before-picture), and the cache-clear (`SCe.cache.clear?.()` + `cyt(null)` ≡ `NlH.cache.clear?.()` + `F7$(null)` in `rr6`, cli_inner_pretty.js:456612-456616 before-picture) are all unchanged, and `date_change` resolves to the same 5 occurrences with the same strings in both bundles. So the v2.1.157 fix is **not** a new declaration in the date logic — it is a reattach/wake-flow change in the background-session subsystem that makes the wake path invalidate the memoized date (or re-run the attachment pipeline so `ftl` fires). That flow change is **not isolated to a single declaration** from the bundle alone; it is documented at the subsystem level in the background-agents module.

| | |
|---|---|
| **Type** | Fix (stale date on live reattach) |
| **Before (v2.1.156)** | A background session resumed after sleep/wake kept reporting the date memoized at original startup — the user-context "Today's date is …" line and the `date_change` reminder both read the frozen `SCe()`/`NlH()`, and the live wake path did not invalidate it (the date machinery is otherwise identical to v2.1.183). |
| **After** | The sleep/wake reattach path refreshes the date so the model is told the current date on resume. |
| **Why** | Memoizing "today" once per process keeps the date stable and cheap to compute within a session, and the `date_change` reminder + `clearSessionCaches` handle day-rollover and disk-resume. The missing case was a *live* process that slept across a day boundary and reattached without going through disk resume — exactly the long-lived background-session shape. |

## Summary

v2.1.157 is a **plugin-ergonomics + `claude agents`/worktree polish** release wrapped around the window's largest fix batch. The four genuinely-new mechanisms are tightly clustered: `claude plugin init` scaffolds the `.claude/skills` plugins that now auto-load as `<name>@skills-dir`; `claude agents` finally honors the `settings.json` `agent` field (with a `--agent` override) by threading it through the dispatch-defaults builder; `EnterWorktree({ path })` switches between managed worktrees mid-session; and `tool_decision` OTEL events gain a `tool_parameters` payload under `OTEL_LOG_TOOL_DETAILS=1`.

The fixes carry the volume. The image-attachment hardening is the most broadly-felt: moving the "could not be processed → text placeholder" fallback *into* the central converter `XM` turns a crash on a zero-byte/corrupt image (from any of paste/MCP/dialog) into a graceful text block. The worktree changes form a coherent cluster — unlock-on-finish lets `git worktree prune` reclaim kept worktrees, which in turn unblocks the 30-day retention sweep's orphan cleanup, and a one-argument fix to the `--worktree`/`--worktree --tmux` launch runner (`fromCwd: e`) makes the session restore to the linked worktree you launched from rather than the canonical repo root it had to chdir through. The `--resume` background-subagent report stops the model from acting on phantom results after a crash, and a companion background-session fix ensures a live session re-attached after a sleep/wake is told the *current* date rather than the one memoized at startup (a wake-flow change in the background subsystem, not a new date-logic decl — the date machinery is byte-identical to v2.1.156). The rest is the by-now-familiar terminal/UI/WSL/IDE long tail (tmux `set-clipboard` regression, GPU-accel for garbled glyphs, fast-mode on Opus 4.8, two startup-banner removals, the workflow-keyword backspace-dismiss + `/config` toggle), several of which are pure rendering/timing fixes with no isolable decl and are flagged as such.
