# v2.1.173 — Source Diff Analysis

**Theme:** **Two small, pointed correctness fixes — one in the model-ID normalizer, one in the sandbox startup-warning path.** 2.1.173 ships exactly two user-facing bullets, both fixes, neither touching a focus feature. The first cleans up how the new **Fable 5** model handles a `[1m]` (1M-context) suffix: because Fable 5 ships with a 1M context window *by default*, an explicit `fable[1m]` / `claude-fable-5[1m]` request is now normalized so the redundant suffix is stripped on the first-party endpoint rather than leaking through as a distinct (and possibly unrecognized) model ID. The second fixes a **Windows** startup warning that wrongly claimed *"sandbox dependencies missing"* when the real situation is that Windows is simply not a supported sandbox platform — the platform check now short-circuits on Windows so the warning path reports "platform unsupported (requires macOS, Linux, or WSL2)" instead of falling through into the dependency-missing branch.

Both changes are tiny in surface area (a single guard clause / a single normalization branch) but precise, and both are isolable to a concrete declaration in the bundle.

> Provenance: every citation below is `cli_inner_pretty.js:<line>` in the **v2.1.183** bundle (`/lyz/codespace/claude-code-bomb/versions/2.1.183/extract/`). Before-picture lines tagged "v2.1.156" come from `/lyz/codespace/claude-code-bomb/versions/2.1.156/extract/cli_inner_pretty.js`. Note: **Fable 5 did not exist yet in the v2.1.156 build** (the alias list there is `["sonnet","opus","haiku","best","sonnet[1m]","opus[1m]","opusplan"]`, cli_inner_pretty.js:98586 v2.1.156 — no `fable`), so the "before" for item 1 is "the fable suffix-strip branch was absent/incorrect in an earlier build," not a clean 2.1.172→2.1.173 byte diff.

## 1. Fable 5 `[1m]` suffix normalization — 1M is the default, so the suffix is stripped

**Type:** fix (model-ID normalization) · **Modules:** Model selection / resolution

### TL;DR

Fable 5 (`claude-fable-5`) ships with a **1M context window by default**. The 1M-context suffix `[1m]` only carries meaning for models whose *baseline* context is smaller (Opus/Sonnet), where it selects the upgraded long-context deployment. When a user writes `fable[1m]` or `claude-fable-5[1m]`, that suffix is redundant — and, worse, an un-normalized `claude-fable-5[1m]` can be treated as a *different* model ID than `claude-fable-5`. 2.1.173's model resolver now detects the fable-on-first-party case and **strips the `[1m]` suffix** so the request collapses back to the canonical `claude-fable-5`.

### How it works

The canonical model resolver `resolveModelAlias` (`_s`, cli_inner_pretty.js:103006-103033) takes a raw model token, lowercases/trims it, and decides what concrete model ID to emit. Two pieces matter here.

**Step 1 — Detect the `[1m]` request.** `hasOneMRequest` (`by`, cli_inner_pretty.js:134061-134064) is just `/\[1m\]/i.test(e)` (gated off when sandbox-eval mode is on). So `r = by(n)` is true whenever the token carries `[1m]`.

**Step 2 — The fable-specific strip branch.** Before the generic "re-append `[1m]`" fallback, the resolver checks (cli_inner_pretty.js:103030):

```javascript
if (r && Mz() && GPu(o) && BN(o)) return t.replace(/(\[1m\])+$/i, "").trim();
```

- `r` — the token requested `[1m]`.
- `Mz()` (`isFirstPartyDirect`, cli_inner_pretty.js:95238-95239) — `Ir() === "firstParty" && Pu()`: we're on the genuine first-party Anthropic endpoint (not Bedrock/Vertex/a gateway).
- `GPu(o)` (`isFableToken`, cli_inner_pretty.js:102478-102480) — `e.toLowerCase().includes("fable")`.
- `BN(o)` (`isNativeOneMModel`, cli_inner_pretty.js:134065-134078) — true only for models whose deployment *natively is* the 1M variant (`claude-fable-5`, `claude-mythos-5`, `claude-mythos-preview`, `claude-opus-4-7`, `claude-opus-4-8`) on a first-party/AWS/mantle endpoint.

When all four hold, the suffix is removed via `t.replace(/(\[1m\])+$/i, "").trim()` (the `(...)+` swallows even a doubled `[1m][1m]`), yielding the bare `claude-fable-5`. Contrast the generic tail at cli_inner_pretty.js:103031, `if (r) return t.replace(/(\[1m\])+$/i, "").trim() + "[1m]";` — for ordinary Opus/Sonnet aliases the resolver strips any existing suffix and re-appends exactly one `[1m]`. The fable branch is the *one place that deliberately does not re-append it*, because for fable the 1M deployment already **is** the base model.

The same "fable is already 1M" stance shows up in two sibling spots:
- The `"fable"` alias case (cli_inner_pretty.js:103013-103015) resolves to `yQ()` and only appends `[1m]` when `r && !Mz() && !by(s)` — i.e. it appends the suffix on *non*-first-party endpoints (Bedrock/Vertex/gateway, where the long-context deployment may need to be named explicitly) but suppresses it on first-party where it's the default.
- `normalizeFableModel` (`yQ`/`LCr`, cli_inner_pretty.js:102487-102494) runs the resolved fable ID through `stripOneM` (`dwt`, cli_inner_pretty.js:103089-103091, `e.replace(/\[1m\]/gi, "")`) whenever `Mz()` is true, scrubbing any `[1m]` out of the first-party fable ID before it's used.

```javascript
// ============================================
// resolveModelAlias (fable [1m]-strip branch) - Fable 5 is 1M by default, drop the redundant suffix
// Location: cli_inner_pretty.js:103006-103033 (branch at 103030)
// ============================================

// ORIGINAL (for source lookup):
function _s(e) {
  let t = e.trim(), n = t.toLowerCase(), r = by(n), o = r ? Ul(n).trim() : n;
  if (PM(o))
    switch (o) {
      case "fable": { let s = yQ(); return s + (r && !Mz() && !by(s) ? "[1m]" : ""); }
      case "opus": return r ? Lq(I_()) : I_();
      // ... sonnet / haiku / opusplan / best ...
    }
  if (pd() && qoe(o) && s1e()) return r ? Lq(I_()) : I_();
  if (r && Mz() && GPu(o) && BN(o)) return t.replace(/(\[1m\])+$/i, "").trim();   // <-- fable: strip, don't re-append
  if (r) return t.replace(/(\[1m\])+$/i, "").trim() + "[1m]";                      //     others: strip then re-append one [1m]
  return t;
}

// READABLE (for understanding):
function resolveModelAlias(rawToken) {
  let trimmed = rawToken.trim(),
      lower = trimmed.toLowerCase(),
      wantsOneM = hasOneMRequest(lower),                 // by(): token carried "[1m]"
      base = wantsOneM ? stripSuffix(lower).trim() : lower;
  if (isKnownAlias(base))                                 // PM()
    switch (base) {
      case "fable": {
        let id = normalizeFableModel();                  // yQ(): first-party-aware fable id (already 1M)
        // only append [1m] off-first-party, where the long-context deployment must be named:
        return id + (wantsOneM && !isFirstPartyDirect() && !hasOneMRequest(id) ? "[1m]" : "");
      }
      case "opus": return wantsOneM ? withOneM(defaultOpus()) : defaultOpus();
      // ... sonnet / haiku / opusplan / best ...
    }
  if (isOpus48Era() && isLegacyRemapAlias(base) && legacyRemapEnabled())
    return wantsOneM ? withOneM(defaultOpus()) : defaultOpus();
  // Fable 5 (and other natively-1M models) on first-party: 1M IS the default → strip the redundant suffix
  if (wantsOneM && isFirstPartyDirect() && isFableToken(base) && isNativeOneMModel(base))
    return stripAllOneM(trimmed).trim();
  // Every other model that asked for [1m]: normalize to exactly one suffix
  if (wantsOneM) return stripAllOneM(trimmed).trim() + "[1m]";
  return trimmed;
}

// Mapping: _s→resolveModelAlias, by→hasOneMRequest, Mz→isFirstPartyDirect, GPu→isFableToken,
//          BN→isNativeOneMModel, yQ→normalizeFableModel, PM→isKnownAlias, Lq→withOneM,
//          I_→defaultOpus, dwt→stripAllOneM (via yQ), t.replace(/(\[1m\])+$/i,"")→stripAllOneM
```

| **Modules touched** | Model resolution / selection |
| **Before** | A `fable[1m]` / `claude-fable-5[1m]` request kept its `[1m]` suffix on the first-party path. **Key insight:** Note the deliberate asymmetry between line 103030 (fable/native-1M: **strip and stop**) and line 103031 (everything else: **strip then re-append exactly one `[1m]`**). The generic path normalizes *toward* having the suffix because that's how Opus/Sonnet name their long-context deployment; the fable path normalizes *away from* it because the suffix is already baked into the base model. The endpoint guard (`Mz()` = first-party only) matters because on Bedrock/Vertex/gateways the explicit suffixed deployment name may still be required — there, the `"fable"` alias case at 103015 *does* append `[1m]` (`r && !Mz() && ...`). So the same conceptual "Fable is 1M" produces opposite suffix handling depending on whether the endpoint serves 1M as the default deployment.

## 2. Spurious "sandbox dependencies missing" Windows startup warning fixed

**Type:** fix (startup warning correctness) · **Modules:** Sandbox (platform support check), Startup notifications

### TL;DR

With `sandbox.enabled: true` in settings on **Windows**, the startup health check could emit *"sandbox is enabled but dependencies are missing: …"* — which is misleading, because the real reason sandboxing can't run on Windows is that **Windows is not a supported sandbox platform at all** (sandboxing requires macOS, Linux, or WSL2). 2.1.173 makes the platform-support predicate short-circuit to `false` on Windows, so the warning path now reports the correct "platform unsupported" reason and never reaches the dependency-missing branch.

### How it works

The startup warning string is built by `getSandboxUnavailableReason` (`jSd`, cli_inner_pretty.js:211683-211703). Its branch order is what makes this fix work:

1. `if (!AUe()) return;` — sandbox not enabled in settings → no warning (cli_inner_pretty.js:211684).
2. `if (!mTn()) return;` — platform not in the managed `enabledPlatforms` list → no warning (cli_inner_pretty.js:211685).
3. **`if (!fTn()) { ... return "…is not supported (requires macOS, Linux, or WSL2)"; }`** — platform unsupported → return the *platform* message and stop (cli_inner_pretty.js:211686-211690).
4. Only if the platform *is* supported does it evaluate `ePt()` (`checkDependencies`) and, on errors, return *"…dependencies are missing: …"* (cli_inner_pretty.js:211691-211701).

The fix is in step 3's predicate, `isSupportedPlatform` (`fTn`, cli_inner_pretty.js:211914-211917):

```javascript
fTn = wn(() => {
  if (Kt() === "windows") return !1;   // NEW: Windows is decisively unsupported, before any dep check
  return tE.isSupportedPlatform();
});
```

`Kt()` is the platform detector (`getPlatform`, returns `"windows"` / `"macos"` / `"linux"` / `"wsl"`; cli_inner_pretty.js:46437). By returning `false` immediately for Windows, `fTn()` makes the `!fTn()` branch in `jSd` (step 3) fire — so a Windows user with sandbox enabled gets *"sandbox is enabled but windows is not supported (requires macOS, Linux, or WSL2)"* and the code never advances to the `ePt().errors.length > 0` dependency-missing branch (step 4). The same `fTn()` guard short-circuits `isSandboxingEnabled` (`ATn`, cli_inner_pretty.js:211675-211682, `if (!fTn()) return !1`), so Windows also never *attempts* to initialize the sandbox.

**Before (v2.1.156):** `isSupportedPlatform` (`U98`) delegated entirely to the native runtime with no Windows guard (cli_inner_pretty.js:207590-207592 v2.1.156):

```javascript
U98 = v8(() => { return ww.isSupportedPlatform(); });   // no Windows special-case
```

The warning builder there (`vT5`, cli_inner_pretty.js:207381-207401 v2.1.156) had the identical branch structure, so whether a Windows user saw "unsupported" or the spurious "dependencies missing" depended on what the native `ww.isSupportedPlatform()` / `dD$()` dependency check returned on Windows — which could surface a missing-dependency error and route to the wrong message.

```javascript
// ============================================
// isSupportedPlatform - Short-circuit Windows so the warning reports "unsupported", not "deps missing"
// Location: cli_inner_pretty.js:211914-211917 (before: cli_inner_pretty.js:207590-207592 v2.1.156)
// ============================================

// ORIGINAL (v2.1.183, for source lookup):
fTn = wn(() => {
  if (Kt() === "windows") return !1;
  return tE.isSupportedPlatform();
});

// ORIGINAL (v2.1.156 before-picture):
U98 = v8(() => {
  return ww.isSupportedPlatform();
});

// READABLE (for understanding):
isSupportedPlatform = memoize(() => {
  if (getPlatform() === "windows") return false;   // NEW: Windows can never sandbox → say so explicitly
  return nativeSandbox.isSupportedPlatform();       // macOS/Linux/WSL2: defer to the native runtime probe
});

// Mapping: fTn/U98→isSupportedPlatform, Kt→getPlatform, tE/ww→nativeSandbox, wn/v8→memoize
```

| | |
|---|---|
| **Type** | Fix (startup warning correctness, Windows) |
| **Modules touched** | Sandbox platform-support check, startup unavailable-reason message |
| **Before** | On Windows with `sandbox.enabled: true`, `isSupportedPlatform()` deferred to the native runtime probe. Depending on what that probe / the dependency check reported, the startup warning could fall through to *"sandbox is enabled but dependencies are missing: …"* — telling the user to install tools that would not help, since Windows can't host the sandbox at all. |
| **After** | `isSupportedPlatform()` returns `false` immediately on Windows. The warning builder's `!fTn()` branch fires first, producing *"…windows is not supported (requires macOS, Linux, or WSL2)"*. The dependency-missing branch is unreachable on Windows. |
| **Why** | The two failure modes — "wrong platform" vs. "right platform, missing tools" — have completely different remedies. Telling a Windows user their *dependencies* are missing sends them to install `bubblewrap`/`socat` (Linux tools that don't exist on Windows) instead of telling them the truth: use WSL2. A single explicit guard at the top of the platform predicate makes the message correct and also prevents a doomed sandbox-init attempt on Windows. |

**Key insight:** This is a classic "make the cheapest, most-decisive check run first" fix. Platform support is a hard, static fact (`getPlatform() === "windows"`); dependency availability is a softer, probe-based fact. By promoting the static check ahead of the probe — and making it authoritative for Windows — the warning system reports the *root* cause rather than a downstream symptom. The branch order in `getSandboxUnavailableReason` was already correct (platform check precedes dependency check); the bug was that `isSupportedPlatform` didn't actually return `false` for Windows, so the platform branch never engaged.

## Summary

2.1.173 is a **two-fix maintenance release**, both narrow and both cleanly anchorable. The **Fable 5 `[1m]` normalization** teaches the model resolver that the 1M-context suffix is meaningless for a model that is *already* 1M by default: on the first-party endpoint, `resolveModelAlias` now strips `[1m]` from any fable request (branch at cli_inner_pretty.js:103030) instead of preserving or re-appending it as it does for Opus/Sonnet, keeping `claude-fable-5` as the single canonical ID and avoiding a phantom suffixed variant. The **Windows sandbox-warning fix** promotes the static platform check above the dependency probe by making `isSupportedPlatform` return `false` outright for Windows (cli_inner_pretty.js:211914-211917), so a Windows user with sandbox enabled is told the truth — the platform is unsupported (use WSL2) — rather than being misdirected to install Linux-only sandbox dependencies.

Neither bullet touches one of the five focus features (Agent Team, Workflow, Background Agents, Compaction, Auto Memory), so the primary analysis lives here. Both before-pictures are corroborated against the v2.1.156 build: Fable did not exist there (its alias list lacked `fable` entirely, cli_inner_pretty.js:98586 v2.1.156), and `isSupportedPlatform` had no Windows guard (cli_inner_pretty.js:207590-207592 v2.1.156).
