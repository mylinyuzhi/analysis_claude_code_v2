## A. New operator escape hatches

### 1. `--safe-mode` / `CLAUDE_CODE_SAFE_MODE` — boot with every customization disabled (NEW)

**Type:** feature · **Modules:** CLI, Startup, Hooks, MCP, Plugins, Skills, Settings, Memory

#### TL;DR

A new top-level flag `--safe-mode` (and the equivalent `CLAUDE_CODE_SAFE_MODE=1` env var) starts Claude Code with **all user/project customizations turned off** — `CLAUDE.md`/memory files, plugins, skills, hooks, MCP servers, custom slash commands & agents, output styles, custom themes, keybindings — so you can isolate which piece of your configuration is broken. Crucially, the things you *can't* break are left fully working: auth, model selection, built-in tools, permissions, and **admin-managed (policy) settings still apply**.

#### How it works

**Step 1 — The flag and the predicate.** `--safe-mode` is registered as a top-level CLI option (cli_inner_pretty.js:693112-693113) whose help text spells out exactly what it disables and that it sets `CLAUDE_CODE_SAFE_MODE=1`. The single source of truth for "are we in safe mode?" is `isSafeMode` (`Nl`, cli_inner_pretty.js:763): it returns true if either `CLAUDE_CODE_SAFE_MODE` is truthy *or* the `--safe-mode` argv flag is present.

**Step 2 — At startup, normalize env so child processes inherit it.** When `isSafeMode()` is true at boot, the startup path stamps both `CLAUDE_CODE_SAFE_MODE=1` and `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` into `process.env` and fires the `startup_safe_mode` telemetry event (cli_inner_pretty.js:693452-693454). Promoting the flag into an env var means every subprocess — including a re-exec, a `--bg` worker, or a hook command — sees safe mode too, not just the top-level argv.

**Step 3 — Fan the predicate out to every customization surface.** `isSafeMode()` is queried at each load site rather than via one global mutation, so each subsystem honors it independently:
- **Hooks:** the hook resolver returns only managed hooks under safe mode — `if (e?.allowManagedHooksOnly === true || Nl()) return e?.hooks ?? {}` (cli_inner_pretty.js:150360), i.e. safe mode is treated identically to the enterprise "managed hooks only" policy.
- **Settings:** project/local setting keys are forced to their default unless allowlisted — `if (Nl() && !pQu[e]) return true` (cli_inner_pretty.js:150263, the "is this setting suppressed?" check).
- **OTEL helper:** even telemetry header helpers fall back to the *policy* one (cli_inner_pretty.js:135920).
- **MCP / skills / plugins / status line:** the same `Nl()` guard gates each (e.g. the `/statusline` setup flow refuses with a safe-mode-specific message at cli_inner_pretty.js:550871, telling the user to `restart without --safe-mode`).
- **Telemetry tagging:** every event carries `safe_mode: String(Nl())` (cli_inner_pretty.js:194120, :194135) so safe-mode sessions are distinguishable in analytics.

`restartHint` (`VH`, cli_inner_pretty.js:766) generates the correct "how to leave safe mode" string depending on whether it was entered via flag (`"restart without --safe-mode"`) or env var (`"unset CLAUDE_CODE_SAFE_MODE"`).

### 2. `/cd` — relocate a live session without resetting the prompt cache (NEW)

**Type:** feature · **Modules:** Slash commands, Working directory, Permissions, Transcript

#### TL;DR

A new `/cd <path>` slash command moves the current session to a different working directory in place. The point is *cache preservation*: changing cwd by quitting and re-launching (or by other means) used to reset the conversation's prompt cache; `/cd` performs the chdir + transcript relocation while keeping the session — and therefore its cached prefix — intact, so the next turn doesn't re-prime the whole cache.

#### How it works

**Step 1 — Command registration.** `/cd` is a `local-jsx` slash command: `{ name: "cd", description: "Move this session to a new working directory", argumentHint: "<path>" }` (cli_inner_pretty.js:475784-475787).

**Step 2 — Validate + permission-gate the target.** The handler resolves and `realpath`s the requested path, rejects non-directories / `ENOENT` / `EACCES`, and short-circuits if you're already there (cli_inner_pretty.js:475698-475719). It then runs the move through a permission check (`hol`, called at cli_inner_pretty.js:475720) — `/cd` is governed by `Cd` permission rules, so a managed/project policy can restrict which directories you may move to. The denial messages are explicit: if `/cd` is *turned off* by a Cd deny rule (cli_inner_pretty.js:475683) or *limited to allowed patterns* (cli_inner_pretty.js:475686), it tells you which rule and where, and points at `/permissions`.

**Step 3 — Perform the move, preserving the session.** The actual relocation is `e5p(s)` (declared at cli_inner_pretty.js:475646, invoked at :475727) which chdirs and **moves the transcript file** to the new directory's session home. If the transcript move fails but the rollback chdir also fails, it logs and completes the move leaving the transcript in its old home rather than wedging the session (cli_inner_pretty.js:475658-475661). On success it posts a `system` meta-message `Moved to <dir>` (cli_inner_pretty.js:475728). A confirmation dialog (`_ol`, cli_inner_pretty.js:475737) is shown unless the target is already trusted (`Ppt(s)`, cli_inner_pretty.js:475736).

|---|---|
| **Type** | Feature (new slash command) |

| **Before** | No in-session way to change the working directory. Switching projects mid-conversation meant a new session (losing context) or relaunching, both of which discard the prompt cache and force a full re-prime on the next turn. |
| **After** | `/cd <path>` chdirs and relocates the transcript in place, keeping the live session and its cached prefix; permission-gated by `Cd` rules; confirmation dialog for untrusted targets. |

### 3. `disableBundledSkills` setting + `CLAUDE_CODE_DISABLE_BUNDLED_SKILLS` (NEW)

### 4. Managed MCP policy now enforced on reconnect, IDE configs, and first-session `--mcp-config` (FIX)

**Type:** fix (security/enterprise) · **Modules:** MCP, Managed settings, Reconnect loop

#### TL;DR

Enterprise managed MCP policies (`allowedMcpServers` / `deniedMcpServers`, plus `allowManagedMcpServersOnly`) were enforced at the *initial* connect but several paths slipped past them: a server that **reconnected** after a drop, **IDE-typed** MCP configs, `--mcp-config` servers during the **first session after install**, and any connection attempted **before remote settings had loaded**. 2.1.169 closes all of these, and also fixes slow cold starts for orgs *without* remote settings (they were waiting on a remote fetch that would never matter).

#### How it works

The policy primitives live in the MCP module: `isMcpServerAllowedByPolicy` (`Cee`, cli_inner_pretty.js:271751), `isMcpServerBlockedAtConnectTime` (`a8`), `isMcpServerDenied` (`Rrt`), and `filterMcpServersByPolicy` (`IG`, cli_inner_pretty.js:271762). The settings primitives are the schema fields `allowedMcpServers`/`deniedMcpServers` (cli_inner_pretty.js:55949-55954) and the lockdown flag `allowManagedMcpServersOnly` (cli_inner_pretty.js:56041-56045) which, in managed settings, makes `allowedMcpServers` *managed-only* while still letting users add denies for themselves.

The fix is that the connect-time policy check `a8`/`isMcpServerBlockedAtConnectTime` is now also evaluated **inside the reconnect retry loop**: when a dropped server tries to come back, it is re-checked and, if blocked, the retry is *stopped* and the server marked failed with `"Blocked by enterprise managed policy"` (cli_inner_pretty.js:499639-499648). The same guard fires after an OAuth refresh — `MCP server <name> blocked by managed policy after OAuth — skipping reconnect` (cli_inner_pretty.js:688733) — and at first connect for IDE/`--mcp-config` servers, with operator-visible warnings (cli_inner_pretty.js:499881 "blocked by managed policy at connect time", :499958 for claude.ai connectors, :387027 for agent-scoped servers).

**Why this matters:** an allowlist that only applies at *initial* connect is a security hole — a server merely had to drop and reconnect (or get re-typed in the IDE, or be passed via `--mcp-config` on a fresh install before remote settings landed) to escape the policy. Re-running the same `isMcpServerBlockedAtConnectTime` guard at every (re)connect point makes the allowlist a true invariant rather than a one-time gate. The cold-start fix is the dual: orgs with *no* remote settings no longer block startup waiting for a fetch whose result can't change the local-only policy outcome.

### 5. Remote-managed settings: apply valid policies, surface invalid ones (IMPROVEMENT)

**Type:** improvement (enterprise robustness) · **Modules:** Managed settings, MCP

#### TL;DR

Previously, a single invalid entry in a remote-managed settings payload could cause the whole payload to be silently dropped. Now the valid policies still apply and the validation error is surfaced instead of swallowed.

#### How it works

The managed-settings loader validates `allowedMcpServers`/`deniedMcpServers` independently and degrades gracefully per-field rather than all-or-nothing. If `allowedMcpServers` is present but invalid, it **enforces an empty allowlist** (admit no MCP servers) until fixed — fail *closed*, not open — and records a structured error (cli_inner_pretty.js:56484-56492): `'"allowedMcpServers" was present but invalid; enforcing an empty allowlist (no MCP servers admitted) until it is fixed.'`. If `deniedMcpServers` is invalid it is dropped with its own surfaced error (cli_inner_pretty.js:56494-56498). Each policy field is validated through its own `Cns(...)` call with a `.catch` that pushes a path-tagged validation error rather than rejecting the whole settings object.

**Key insight:** the per-field degrade is also a *security* choice — an unparseable allowlist enforces "deny all," so a corrupted policy can't accidentally widen access. Surfacing the error (instead of silently dropping) is what lets an admin notice and fix the typo instead of wondering why nothing applied.

### 6. OTEL client-certificate paths now require trust confirmation (FIX, security)

**Type:** fix (security) · **Modules:** Telemetry/OTEL, Settings trust · **Confidence:** medium (locus identified; exact diff site not isolated to one decl)

#### TL;DR

Untrusted project settings could previously set OTEL client-certificate paths (`OTEL_EXPORTER_OTLP_*_CLIENT_CERTIFICATE` / `_CLIENT_KEY` / `_CERTIFICATE`) via the settings `env` block without a trust prompt. An untrusted repo could thus point Claude's telemetry exporter at attacker-controlled filesystem paths. #### How it works (and confidence note)

The OTEL exporter reads its cert/key/CA from the env vars `OTEL_EXPORTER_OTLP_${SIGNAL}_CLIENT_CERTIFICATE`, `_CLIENT_KEY`, and `_CERTIFICATE` inside the vendored OTel SDK reader (cli_inner_pretty.js:317102-317120, :334785-334800). I could not isolate the trust-gating change to a *single* new declaration with a stable string — the OTEL env names appear only inside the vendored SDK reader, and the project-settings-`env` trust filter is a generic key-classification path rather than a named "OTEL cert" check. So: the **locus is confirmed** (the path-valued OTEL cert/key env keys, applied via the settings `env` block, gated by the project-trust subsystem), but the exact diff line is **not isolated**; treat this bullet's anchor as medium confidence.

### 8. Vertex/Foundry idle-timeout restored (default 5 min); `API_FORCE_IDLE_TIMEOUT=0` opts out (FIX)

**Type:** fix (regression) · **Modules:** API client, Streaming, Vertex/Foundry

#### TL;DR

A stalled Vertex/Foundry stream could hang indefinitely. 2.1.169 restores a default ~5-minute idle timeout so a stream that stops producing chunks aborts. Setting `API_FORCE_IDLE_TIMEOUT=0` opts out (no timeout).

#### How it works

The fetch-options builder `db` (cli_inner_pretty.js:81372) decides whether to *disable* undici's idle timeout (`timeout: !1`). It only disables the timeout when, for the Anthropic-shaped API path, `API_FORCE_IDLE_TIMEOUT` is **not** falsy *and* a body-level idle watchdog is active (or the env value is otherwise truthy): `n = e.forAnthropicAPI && !st(t) && (e.hasBodyIdleWatchdog || yl(t))`. Concretely, `API_FORCE_IDLE_TIMEOUT=0` → `st(t)` is true → `n` is false → the timeout is **left active** (the opt-*out*). For Vertex/Foundry/Bedrock requests the body watchdog predicate `_8u` (cli_inner_pretty.js:133829: `if (!sti()) return false; return rti(e) && rti(Ir())`) is wired into the request via `hasBodyIdleWatchdog: _8u(h)` at the streaming call site (cli_inner_pretty.js:133482), so a stalled stream trips the watchdog and aborts. The streaming layer raises `"Stream idle timeout - no chunks received"` (cli_inner_pretty.js:583755, with byte-level variant at :583796); the default idle window is the `300000`-ms (5-minute) constant family used across the API client (e.g. cli_inner_pretty.js:81432 `Agu = 300000`).

|---|---|
| **Before** | A Vertex/Foundry stream that went silent mid-response would hang with no abort, blocking the turn indefinitely. |
| **After** | A default ~5-min idle window aborts a stalled stream (`Stream idle timeout`); `API_FORCE_IDLE_TIMEOUT=0` disables it for users who genuinely need unbounded streams. |
| **Why** | "Hang forever" is worse than "abort and retry" — an idle watchdog converts an invisible deadlock into a recoverable error. The opt-out exists because some long-running tool/agent streams legitimately go quiet for minutes. |

### 9. Plugin `.in_use` PID lock files swept once per day (FIX)

**Type:** fix (disk hygiene) · **Modules:** Plugins, Lock files

#### TL;DR

Plugin `.in_use` PID lock files (one per live session under each plugin dir) accumulated without bound — a session that crashed left its marker forever. Now stale markers (from dead PIDs) are swept **once per day**.

#### How it works

Each session writes a marker `<pluginDir>/.in_use/<pid>` containing `{ pid, procStart }` via `writeInUseMarker` (`Ltl`, cli_inner_pretty.js:466071-466080) and registers an `exit`-time cleanup (`F4p`, cli_inner_pretty.js:466068). The actual reaper `lGt` (cli_inner_pretty.js:466097-466129) reads each marker, parses `{ pid, procStart }`, and `rm`s it unless the PID is still alive *and* its process start time matches (`OC(l.data.pid, l.data.procStart)`, cli_inner_pretty.js:466123) — the start-time check prevents reaping a *recycled* PID that now belongs to a different process.

### 10. CLAUDE.md "too long" warning threshold now scales with the model's context window (IMPROVEMENT)

**Type:** improvement · **Modules:** Memory, Doctor/health, Model

#### TL;DR

The "Large CLAUDE.md file detected" warning used to fire at a **fixed 40 000 characters**. Now the threshold scales with the active model's context window, so a big-context model doesn't nag you about a CLAUDE.md it can easily fit.

#### How it works

The health check `$zp` builds the warning and compares each CLAUDE.md against a threshold `t = NCe()` (cli_inner_pretty.js:493015-493027). In 2.1.183, `claudeMdWarnThreshold` (`NCe`, cli_inner_pretty.js:225660-225664) is **computed from the current model's context window** rather than a constant:

```javascript
// ============================================
// claudeMdWarnThreshold - context-window-scaled CLAUDE.md size warning
// Location: cli_inner_pretty.js:225660-225664 (v2.1.183) vs constant 40000 (v2.1.156)
// ============================================

// ORIGINAL (for source lookup) — v2.1.183:
function NCe(e = Gs()) {
  let t = tH(e, Wb()),
    n = Number.isFinite(t) && t > 0 ? t : mxt;   // mxt = 200000 fallback
  return Math.max(TNi, Math.round(n * vNi * ww(e)));  // TNi=40000, vNi=0.05
}

// READABLE (for understanding):
function claudeMdWarnThreshold(model = currentModel()) {
  let contextWindow = getContextWindowTokens(model, getModelTier());
  let tokens = Number.isFinite(contextWindow) && contextWindow > 0 ? contextWindow : 200000; // fallback
  // floor 40k chars; otherwise 5% of context window converted tokens→chars
  return Math.max(40000, Math.round(tokens * 0.05 * charsPerToken(model)));
}

// v2.1.156 before-picture: the threshold was a bare constant.
//   l$H = 40000;   (cli_inner_pretty.js:220545, v2.1.156)
//   message uses `... chars > ${l$H...}`  (cli_inner_pretty.js:471974, v2.1.156)

// Mapping: NCe→claudeMdWarnThreshold, tH→getContextWindowTokens, ww→charsPerToken, Gs→currentModel, mxt→200000, TNi→40000, vNi→0.05
```

| | |
|---|---|
| **Before (v2.1.156)** | Fixed `40000`-char threshold (`l$H`, cli_inner_pretty.js:220545 v2.1.156). A 60 k-char CLAUDE.md warned on every model, even one with a 1 M-token window. |
| **After (v2.1.183)** | `max(40000, round(contextWindow_tokens × 0.05 × charsPerToken))` — the floor stays 40 k but the threshold grows to ~5 % of the model's context window in characters. |
| **Why** | "Too long" is relative to the model, not absolute. The warning's purpose is "this file is eating a meaningful slice of your context"; 60 k chars is a big slice of a 200 k-token window but trivial in a 1 M-token one. Keeping a 40 k floor prevents the warning from disappearing entirely on huge-context models for genuinely bloated files. |

### 11. `TaskCreate` input auto-repair + schema in validation errors for unloaded tools (IMPROVEMENT)

**Type:** improvement · **Modules:** Tools, TaskCreate, Tool input validation

#### TL;DR

`TaskCreate` reliability was improved: malformed inputs are auto-repaired (coerced) before validation, and when a tool is called with an empty input but has required params (the "unloaded tool" case), the validation error now **includes the schema** so the model can re-issue a valid call.

#### How it works

The tool-call dispatcher runs an optional **input coercer** before schema validation: `if (e.coerceInput) { A = e.coerceInput(n); if (A !== null) m = A.input; }` (cli_inner_pretty.js:437226-437229). The coercion is feature-gated by `emptyInputRepair` (`Wmi`, cli_inner_pretty.js:147791 → `Dkt().emptyInputRepair`) and reported via the telemetry event `tengu_tool_input_coerced` with `shapeClass` and an `outcome` of `coerced_valid` / `coerced_still_invalid` (cli_inner_pretty.js:437230-437236). `TaskCreate` itself (`Vw = "TaskCreate"`, cli_inner_pretty.js:221451) ships shape-specific repair guidance — e.g. rejecting a `tasks`/`todos` array param (cli_inner_pretty.js:430378) or Agent-tool params (cli_inner_pretty.js:430380) with a precise "call it like *this*" message.

For the **unloaded-tool / empty-input** case, when validation fails the dispatcher checks `isEmptyObject` (`Vmi`, cli_inner_pretty.js:147800) and, if so, calls `buildRequiredParamsError` (`zmi`, cli_inner_pretty.js:147803-147816) which walks the Zod object shape, picks the required keys, synthesizes a minimal valid example, and returns a message that **names the required params and shows the minimal valid call shape** (cli_inner_pretty.js:147813), replacing the bare validation error (wired in at cli_inner_pretty.js:437241-437244, inside the `if (!g.success)` branch).

**Key insight:** the coercer runs *before* `safeParse` and is observable via telemetry tagged `coerced_valid` vs `coerced_still_invalid`, so the team can measure how often auto-repair actually rescues a malformed call. The unloaded-tool branch synthesizes a *concrete* minimal example from the schema rather than dumping the raw Zod error — far more actionable for a model that called a tool it hadn't fully "loaded" the schema for.
