# v2.1.178 — Source Diff Analysis

**Theme:** **The Agent-Teams redesign release — plus a permissions-model expansion, a nested-`.claude/` resolution overhaul, an auto-mode safety closure, and a dense correctness batch (auth, sandbox, MCP, Remote Control, subagent UI).** 2.1.178 is a flagship: it rips out the explicit `TeamCreate`/`TeamDelete` tool pair and replaces it with **one implicit team per session**, spawned directly through the Agent tool's `name` parameter (the centerpiece, covered in depth by the `30_agent_team` module). Around that sit four genuinely new mechanisms — **`Tool(param:value)` permission rules** (the first time a rule can match a tool's *input parameters*, not just its name/path/command, e.g. `Agent(model:opus)`), **nested `.claude/skills` loading with `<dir>:<name>` disambiguation**, **nearest-`.claude/` precedence** for agents/workflows/output-styles, and an **auto-mode classifier gate on subagent spawns** that closes a real bypass (a subagent could previously request a blocked action with no classifier review). The workflow keyword trigger moves to a **violet shimmer + explicit-phrase-only** activation, and compaction finally **honors `--fallback-model`**. The remainder is a wide correctness sweep: a stale-FD **OOM crash**, Chrome OAuth account mismatch, an MCP **server-level `disallowedTools`** silent-ignore, a `KEEP_MARKETPLACE_ON_FAILURE` fresh-install regression, Linux-sandbox symlink startup, vim undo granularity, statusline custom-URI-scheme links, and a subagent transcript/messaging/`ctrl+b` cluster.

Five bullets touch the deeply-documented focus features (agent teams, workflow keyword, compaction fallback, background sessions). Those get a tight summary + the verified anchor + a link to the module doc that re-derives the full mechanism — they are **not** re-derived here. Every non-focus bullet gets primary analysis below.

## 1. Agent Teams redesign: `TeamCreate`/`TeamDelete` removed, one implicit team per session (FOCUS)

**Type:** feature (redesign) · **Modules:** Agent Team, Agent tool, Subagent

### Summary + anchor

With `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`, the model no longer *creates* a team. The `TeamCreate` and `TeamDelete` tools are **gone from the bundle entirely** (grep = 0), and a single team named `session-<sessionId[:8]>` is bootstrapped at CLI startup by `initializeSessionTeam` (`j3f`, cli_inner_pretty.js:682765; team-name helper `sessionTeamName`/`xic` at :682752). Teammates are now spawned by passing a non-empty `name` to the **Agent** tool; the routing predicate changed from "does `team_name` resolve to a team?" to "does the session have an implicit `teamContext`, was a `name` given, and is this not a fork?" — `let _ = Sl() ? A.teamContext : void 0; … if (_ && s && !L) …` (cli_inner_pretty.js:423548, :423573). The `team_name` parameter is **kept in the schema but documented `"Deprecated; ignored. The session has a single implicit team."`** (cli_inner_pretty.js:423458), so an older model prompt that still passes it does not hard-fail — it is accepted and silently dropped.

**Why kept-but-ignored:** removing the field would reject cached tool-use blocks and older agent prompts at schema-validation time. Keeping the field, ignoring the value, and documenting the truth is the graceful-deprecation choice — the routing in §2.1 of the module doc never reads it.

The full mechanism (startup bootstrap, the `if (_ && s && !L)` routing, the leaf spawners reading `getAppState().teamContext.teamName` instead of a passed `team_name`, and the `--team-name` thread onto the teammate sub-process) is re-derived in **[../30_agent_team/implicit_team_and_agent_tool_spawn.md](../30_agent_team/implicit_team_and_agent_tool_spawn.md)**.

## 2. `Tool(param:value)` permission-rule syntax with `*` wildcard (NEW)

**Type:** feature · **Modules:** Permissions

### TL;DR

Permission rules gained a way to match a tool's **input parameters**, not just its name. A rule like `Agent(model:opus)` matches any Agent-tool call whose `model` input is `opus`; `Agent(model:*)` matches any model; `Bash(command:git push*)`-style content was already special-cased, but this is the first *generic* per-parameter matcher that works for **any** tool field. Put `Agent(model:opus)` in `deny` to block Opus subagents.

### How it works

The matcher is `evaluateParameterRules` (`V9t`, cli_inner_pretty.js:585532). For a given tool + behavior (allow/deny/ask), it walks every rule whose `ruleContent` is set, splits the content on the **first** `:` into `key`/`value`, looks up the tool's live input `input[key]`, and tests `value` against `String(input[key])` with the same `*`-glob matcher (`ogr`, cli_inner_pretty.js:55488) used everywhere else for wildcards:

**Step 1 — split.** `let l = i.indexOf(":"); if (l <= 0) continue; let c = i.slice(0, l).trim(), u = i.slice(l + 1).trim();` (cli_inner_pretty.js:585537-585540). An empty key or value, or a `:`-less content, is skipped.

**Step 2 — skip the tool's *primary* content field.** `if (c === t.ruleContentField) continue;` (cli_inner_pretty.js:585542). Every gated tool declares a `ruleContentField` — `path`/`file_path` for Read/Edit, `command` for Bash, `url` for WebFetch (cli_inner_pretty.js:370770, 390617, 443114, 409285). That field is the tool's *legacy* single-value content (`Read(/etc/**)`, `Bash(npm run:*)`), already handled by the older path/command matchers. The param matcher deliberately skips it so the two systems don't double-fire on the same field.

**Step 3 — look up and glob-match.** `if (!Object.hasOwn(n, c)) continue; let d = n[c]; if (d === void 0 || d === null || typeof d === "object") continue; if (ogr(u, String(d).trim())) return a;` (cli_inner_pretty.js:585543-585546). Object/array/null params are skipped (only scalar fields are matchable); the value is stringified and trimmed and run through the `*`-to-`.*` regex.

`evaluateParameterRules` is wired into the three behavior legs of the central permission evaluator `getToolPermission` (`Xke`, cli_inner_pretty.js:585686 and the SDK twin `Qbf`, cli_inner_pretty.js:585726): deny first (cli_inner_pretty.js:585695, 585736), then the tool's own `checkPermissions`, then ask (cli_inner_pretty.js:585716, 585757). A param-deny produces `Permission to use ${name} with ${ruleContent} has been denied.` (cli_inner_pretty.js:585700).

```javascript
// ============================================
// evaluateParameterRules - Match a tool's input parameters against Tool(param:value) rules
// Location: cli_inner_pretty.js:585532-585549
// ============================================

// ORIGINAL (for source lookup):
function V9t(e, t, n, r) {
  let o = lOe(t);
  for (let s of [o, ...Enn(o, e.toolAliases)])
    for (let [i, a] of Vte(e, s, r)) {
      if (s !== o && !T0o(a)) continue;
      let l = i.indexOf(":");
      if (l <= 0) continue;
      let c = i.slice(0, l).trim(), u = i.slice(l + 1).trim();
      if (c === "" || u === "") continue;
      if (c === t.ruleContentField) continue;
      if (!Object.hasOwn(n, c)) continue;
      let d = n[c];
      if (d === void 0 || d === null || typeof d === "object") continue;
      if (ogr(u, String(d).trim())) return a;
    }
  return null;
}

// READABLE (for understanding):
function evaluateParameterRules(permCtx, tool, toolInput, behavior /* "allow"|"deny"|"ask" */) {
  let canonicalName = canonicalToolName(tool);
  for (let name of [canonicalName, ...aliasesOf(canonicalName, permCtx.toolAliases)])
    for (let [ruleContent, rule] of rulesFor(permCtx, name, behavior)) {  // ruleContent like "model:opus"
      if (name !== canonicalName && !ruleAppliesToAlias(rule)) continue;
      let colon = ruleContent.indexOf(":");
      if (colon <= 0) continue;
      let key   = ruleContent.slice(0, colon).trim(),   // "model"
          value = ruleContent.slice(colon + 1).trim();  // "opus"
      if (key === "" || value === "") continue;
      if (key === tool.ruleContentField) continue;       // the tool's legacy single-value field is handled elsewhere
      if (!Object.hasOwn(toolInput, key)) continue;
      let actual = toolInput[key];
      if (actual === undefined || actual === null || typeof actual === "object") continue; // scalars only
      if (globMatch(value, String(actual).trim())) return rule;  // "*"-wildcard match
    }
  return null;
}

// Mapping: V9t→evaluateParameterRules, lOe→canonicalToolName, Enn→aliasesOf, Vte→rulesFor, T0o→ruleAppliesToAlias, ogr→globMatch, t.ruleContentField→tool's legacy content field
```

| | |
|---|---|
| **Type** | Feature (permission-rule expansion) |
| **Modules touched** | Permissions evaluator (`Xke`/`Qbf`), rule parser (`EA`), glob matcher (`ogr`) |
| **Before** | A permission rule could only match the tool **name** (`Agent`), an MCP server (`mcp__github__*`), or the tool's single legacy content field (`Read(/etc/**)`, `Bash(npm run:*)`). There was **no** way to gate on an arbitrary input parameter. In 2.1.156 the only `:`-splitting in rule content was the Bash `npm run:*` prefix convention; there was no `ruleContentField`-aware generic matcher (`grep ruleContentField` = 0 in 2.1.156) and no `with ${ruleContent} has been denied` message. |
| **After** | `Tool(param:value)` matches any scalar input field with `*`-wildcards, across allow/deny/ask. `Agent(model:opus)` in deny blocks Opus subagents; `WebFetch(url:*internal*)` ask-gates internal fetches; etc. |
| **Why** | The Agent/teammate spawn surface (see §1) made "block a *kind* of subagent" a real need — you want to deny `model:opus` subagents without denying the Agent tool wholesale. A name-only rule grammar couldn't express that. Skipping `ruleContentField` keeps the new generic matcher from colliding with the established path/command/url conventions, so the two grammars compose instead of conflict. |

**Key insight:** the design choice that makes this safe to add is the `if (key === tool.ruleContentField) continue` guard. Every tool's "main" content (Read's path, Bash's command) already has a bespoke matcher that understands its semantics (path globs, command prefixes). The new generic matcher *opts out* of that field and only handles the *other* parameters, so introducing it required zero changes to the existing path/command/url logic — it's purely additive. Note rules are still parsed by the unchanged `EA` (cli_inner_pretty.js:55506): `Agent(model:opus)` becomes `{ toolName: "Agent", ruleContent: "model:opus" }`, and `V9t` does the new interpretation of that content.

## 3. Nested `.claude/skills` load + `<dir>:<name>` on clash (NEW)

**Type:** feature · **Modules:** Skills

### TL;DR

Skills in a **nested** `.claude/skills` directory (one below a subdirectory you're working in, not just the project root) now load when you operate on files there. If a nested skill's name clashes with a root-level one, the nested skill is surfaced as `<dir>:<name>` so **both** stay available instead of one shadowing the other.

### How it works

This is a skill-discovery + collision-resolution change spread across the skill loader rather than a single distinctive declaration — the nested directories themselves are enumerated from `[".claude/skills", ".claude/commands"]` (`Ybp`, cli_inner_pretty.js:372282), and per-skill names flow through the sanitizer `jet` (`sanitizedName`/`skillNameHash`, cli_inner_pretty.js:194025). Skill **source** is later joined with `:` to form a qualified display name in the command path (`let c = e.source ? \`${e.source}:${e.name}\` : e.name;`, cli_inner_pretty.js:386876), which is the same `<source/dir>:<name>` shape the changelog describes. The invocation-depth telemetry already distinguishes a `"nested-skill"` trigger from a `"claude-proactive"` one (`A = m > 0 ? "nested-skill" : "claude-proactive"`, cli_inner_pretty.js:392997, 393340), confirming the runtime now models nested-vs-root skills as a first-class distinction.

**Confidence:** medium. The qualified-name join (`${source}:${name}`) and the nested-vs-root telemetry split are verified verbatim; the precise file-path-walk that decides *which* nested `.claude/skills` dirs to scan for a given working file is not isolable to one decl (it lives in the skill-discovery scan, which has no unique grep string). The companion permission fix in §16 ("directory-qualified names blocked in non-interactive") is the strongest corroboration that `<dir>:<name>` qualified skills are a real new code path.

| | |
|---|---|
| **Before** | Only the project-root `.claude/skills` loaded; a nested one was ignored, and a name clash meant the root skill won and the nested one was unreachable. |
| **After** | Nested `.claude/skills` load when you work on files in that subtree; on a clash the nested one is `<dir>:<name>`, so both are callable. |
| **Why** | Monorepos and multi-package repos keep per-package skills. A flat root-only model forced every skill into one namespace and lost per-directory specialization; qualifying on clash preserves both without forcing the user to rename. |

## 4. Nearest-`.claude/` wins on collision for agents/workflows/output-styles (NEW)

**Type:** feature · **Modules:** Skills/Agents config resolution, Workflow

### TL;DR

When the same **agent**, **workflow**, or **output-style** name exists in more than one `.claude/` directory along the path from cwd up to the project root, the **closest one to the working directory now wins**. Relatedly, a **project-scope workflow save** now targets the closest *existing* `.claude/workflows/` directory rather than always the root.

### How it works

This is a directory-resolution precedence rule, not a tool change. The workflow-save half touches the Workflow subsystem's file paths but is the **directory-resolution** rule, not the ultracode keyword machinery — so it is out of scope of the [../42_workflow/ultracode_keyword_trigger_delta.md](../42_workflow/ultracode_keyword_trigger_delta.md) delta. The change is a comparator/ordering tweak in the config-walk that collects agents/workflows/output-styles from each ancestor `.claude/` directory: previously root-first-wins (or last-write-wins) flattening, now nearest-directory-wins. It is **not isolated to a single decl** — the collision rule is applied during the multi-directory merge, which has no distinctive grep-able string beyond the per-kind loaders.

**Confidence:** low-medium (mechanism inferred from the changelog; the precedence change is a merge-order tweak rather than a new function). The behavior is consistent with §3's nested-skills theme: 2.1.178 makes the whole `.claude/` config tree **directory-aware** instead of root-only.

| | |
|---|---|
| **Before** | Name collisions across ancestor `.claude/` dirs resolved to a fixed winner (root or last-merged), regardless of how close a directory was to where you were working. Project-scope workflow saves always wrote to the root `.claude/workflows/`. |
| **After** | The `.claude/` nearest the working directory wins for agents, workflows, and output-styles; workflow saves prefer the nearest existing `.claude/workflows/`. |
| **Why** | Same monorepo motivation as §3 — a per-package agent/output-style should override the repo-wide default when you're working in that package, and a workflow you save while inside a package should land in that package's `.claude/`, not the repo root. |

## 5. Auto mode evaluates subagent spawns through the classifier before launch (FIX — safety)

**Type:** fix (security) · **Modules:** Auto mode, Agent tool, Permissions

### TL;DR

In auto mode, an Agent-tool **subagent spawn** is now routed through the auto-mode classifier *before* the subagent launches. Previously the Agent tool returned `behavior: "allow"` unconditionally, so a spawn skipped the classifier entirely — and the spawned subagent could then request a blocked action with no review. This is a genuine bypass closure.

### How it works

The fix is a two-line change to the Agent tool's `checkPermissions`. In 2.1.156 it was:

```javascript
// Location (v2.1.156 BEFORE-PICTURE): cli_inner_pretty.js:399060-399062
async checkPermissions(H, $) {
  return { behavior: "allow", updatedInput: H };   // <-- ALWAYS allow, even in auto mode → classifier skipped
}
```

In 2.1.178 it became:

```javascript
// ============================================
// agentToolCheckPermissions - In auto mode, route spawn through the classifier
// Location: cli_inner_pretty.js:424241-424245
// ============================================

// ORIGINAL (for source lookup):
async checkPermissions(e, t) {
  if (Br(t).mode === "auto")
    return { behavior: "passthrough", message: "Agent tool requires permission to spawn subagents." };
  return { behavior: "allow", updatedInput: e };
}

// READABLE (for understanding):
async checkPermissions(input, ctx) {
  if (permissionContext(ctx).mode === "auto")
    // passthrough = "I have no rule-based verdict; let the auto-mode classifier decide"
    return { behavior: "passthrough", message: "Agent tool requires permission to spawn subagents." };
  return { behavior: "allow", updatedInput: input };  // non-auto modes unchanged
}

// Mapping: Br→permissionContext, e→input, t→ctx
```

`behavior: "passthrough"` is the signal that the tool has no rule-based verdict, so the permission evaluator (`Xke`, §2) falls through to the auto-mode classifier path instead of short-circuiting on `allow`. In every non-auto mode the original `allow` is preserved, so this only changes auto-mode behavior.

| | |
|---|---|
| **Type** | Fix (auto-mode safety bypass) |
| **Modules touched** | Agent tool `checkPermissions`, auto-mode classifier |
| **Before** | Agent tool always returned `allow`; a subagent spawn in auto mode never hit the classifier. The classifier's allow/soft-block/hard-block rules (the `autoMode.allow`/SOFT/HARD sections, cli_inner_pretty.js:55366-55382) were applied to the *parent's* actions but not to the *decision to spawn a child* — and a freshly spawned subagent could then perform an action the classifier would have blocked. |
| **After** | In auto mode the spawn is `passthrough` → classified before launch. A spawn that the classifier soft/hard-blocks is held for review. |
| **Why** | Auto mode's whole guarantee is "no blocked action runs without classifier review." A subagent is the user's process; letting the spawn skip review let an agent indirectly perform, via a child, an action it could not perform directly. Routing the spawn through the same classifier closes that indirection. |

**Key insight:** the smallest possible fix — flip the auto-mode return from `allow` to `passthrough`. The entire classifier machinery already existed; the only bug was that the Agent tool was *asserting* a verdict (`allow`) instead of *deferring* (`passthrough`), which suppressed the classifier. This is the kind of one-conditional security fix where the danger was in what the tool *claimed to know*.

## 7. Compaction honors `--fallback-model` (FOCUS)

**Type:** fix · **Modules:** Compact

### Summary + anchor

The compaction summarize LLM call now falls back through the configured `--fallback-model` chain on overload / model-availability errors instead of throwing. The summarizer `streamCompactSummary` (`del`, cli_inner_pretty.js:461088) wraps its streaming body in a `while(!0)` fallback-model loop (cli_inner_pretty.js:461192); the chain is built by `buildFallbackChain` (`ICn`, cli_inner_pretty.js:461078), filtered so a fallback never has a *smaller* context window than the primary (`isSmallerWindow`/`XHe`, cli_inner_pretty.js:102376); a `FallbackTriggeredError` (`vF`, cli_inner_pretty.js:460488) drives the fall-over, and a `model_blocked` reason surfaces a clean `"<model> is currently unavailable."` (cli_inner_pretty.js:461283) rather than a stack trace. In 2.1.156 the equivalent `_X4` was a single-pass stream against one hardcoded model with **no** `fallbackModel` and a direct throw on failure.

Full re-derivation (the loop, the window-filter rationale, the `cedar_lagoon` thinking gate, the chain resolver) is in **[../07_compact/fallback_model_in_compaction.md](../07_compact/fallback_model_in_compaction.md)**.

## 8. `/bug` requires a description and no longer titles the issue with model-refusal text (FIX)

**Type:** fix · **Modules:** Feedback / `/bug`

### TL;DR

Two `/bug` fixes: (a) submitting with an empty description is now rejected with *"Please describe the issue before submitting."*; and (b) the auto-generated GitHub-issue title no longer falls through to a model **refusal** string (e.g. "I can't help with that") — a refusal-shaped title is detected and replaced with a description-derived fallback.

### How it works

**(a) Description required.** The bug-report textarea's `onSubmit` now guards on empty input (cli_inner_pretty.js:475078-475081):

```javascript
// Location: cli_inner_pretty.js:475077-475083
onSubmit: (W) => {
  if (s !== "share" && W.trim() === "") {           // not a "share" flow, and empty
    _("Please describe the issue before submitting.");
    return;                                          // refuse to advance to the consent/scope step
  }
  (_(null), c(s === "share" ? "consent" : "scope"));
}
```

**(b) Refusal title rejection.** The title is generated by a Haiku call `generateIssueTitle` (`VWp`, cli_inner_pretty.js:475324) whose system prompt asks for a concise (max-80-char) GitHub-issue title. The result is now passed through `isRefusalTitle` (`KWp`, cli_inner_pretty.js:475363) before use:

```javascript
// ============================================
// isRefusalTitle - Detect a model-refusal string used as an issue title
// Location: cli_inner_pretty.js:475363-475366 (regex zWp at :475447)
// ============================================

// ORIGINAL (for source lookup):
function KWp(e) {
  let t = e.trim();
  return t === "" || zWp.test(t);
}
// zWp = /^(i can['’]t|i cannot|i['’]m unable|i am unable|i['’]m sorry|i am sorry|i apologize|sorry,)/i;

// READABLE (for understanding):
function isRefusalTitle(title) {
  let t = title.trim();
  return t === "" || REFUSAL_PREFIX_RE.test(t);  // empty OR starts with a refusal phrase
}
// REFUSAL_PREFIX_RE = /^(i can't|i cannot|i'm unable|i am unable|i'm sorry|i am sorry|i apologize|sorry,)/i

// Mapping: KWp→isRefusalTitle, zWp→REFUSAL_PREFIX_RE, Oyo→deriveTitleFromDescription
```

When `isRefusalTitle(generated)` is true (or the title is otherwise blank via the `t1` empty-check), `generateIssueTitle` returns `Oyo(e)` (`deriveTitleFromDescription`, cli_inner_pretty.js:475367) — a trimmed/clamped slice of the user's own description (the clamp logic at cli_inner_pretty.js:475371-475377, falling back to `"Bug Report"` when too short) — so the issue gets a sensible title instead of the model's refusal sentence.

| | |
|---|---|
| **Before** | An empty `/bug` advanced to consent/submit with no description. If the title-generation Haiku **refused** (e.g. the bug text tripped a safety pattern), its refusal sentence ("I can't help with that…") was used verbatim as the public GitHub issue title. |
| **After** | Empty description is rejected up front; a refusal-shaped title is detected by `zWp` and replaced with a description slice. |
| **Why** | A blank-description report is useless to triage; and a refusal sentence as a public issue title is both confusing and leaks that the model declined. Detecting the well-known refusal prefixes is a cheap, robust filter (it doesn't need to understand *why* the model refused — just that the output is a refusal, not a title). |

## 9. Stale websocket/OAuth file-descriptor inheritance no longer OOMs the CLI (FIX)

**Type:** fix (crash) · **Modules:** Auth, Credential FD reader

### TL;DR

When the CLI inherits a stale `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR` / `CLAUDE_CODE_API_KEY_FILE_DESCRIPTOR` from a parent process — pointing at a websocket/pipe that streams data forever rather than a small token file — the credential reader used to buffer the *entire* stream into memory and OOM-crash. The read is now **capped at 64 KB**.

### How it works

The FD reader `readCredentialFromFd` (`kMs`, cli_inner_pretty.js:96245) reads the token from `/proc/self/fd/${fd}`. In 2.1.156 this was an **unbounded** `readFileSync`:

```javascript
// Location (v2.1.156 BEFORE-PICTURE): cli_inner_pretty.js:92760-92762
let f = U$(), O = `/proc/self/fd/${Y}`,
  M = f.readFileSync(O, { encoding: "utf8" }).trim();   // <-- reads until EOF; a never-ending FIFO/socket → OOM
```

In 2.1.178 it reads with a `maxBytes` cap (`HTr = 65536`, cli_inner_pretty.js:96314):

```javascript
// ============================================
// readCredentialFromFd - Read a token from an inherited FD, bounded to 64 KB
// Location: cli_inner_pretty.js:96256-96260
// ============================================

// ORIGINAL (for source lookup):
let l = `/proc/self/fd/${a}`,
  c = xze(l, { maxBytes: HTr }).trim();
if (!c) return (v(`File descriptor contained empty ${n}`, { level: "error" }), o(null), null);
return (v(`Successfully read ${n} from file descriptor ${a}`), o(c), vTr(t, c, n), c);

// READABLE (for understanding):
let fdPath = `/proc/self/fd/${fdNum}`,
  token = readBounded(fdPath, { maxBytes: CREDENTIAL_FD_MAX_BYTES /* 65536 */ }).trim();
if (!token) { logError(`File descriptor contained empty ${label}`); setCached(null); return null; }
logDebug(`Successfully read ${label} from file descriptor ${fdNum}`);
setCached(token); persistToWellKnownPath(wellKnownPath, token, label);
return token;

// Mapping: xze→readBounded, HTr→CREDENTIAL_FD_MAX_BYTES (65536), a→fdNum, vTr→persistToWellKnownPath
```

| | |
|---|---|
| **Type** | Fix (out-of-memory crash) |
| **Modules touched** | Credential FD reader (`kMs`), API-key FD reader (the second `maxBytes: HTr` site at cli_inner_pretty.js:144738) |
| **Before** | `readFileSync(fdPath, "utf8")` with no size limit. A stale FD inherited from a parent (e.g. a leftover websocket or pipe descriptor) that never sends EOF caused an unbounded read → multi-GB buffer → OOM crash at startup. |
| **After** | Bounded read (`xze(..., { maxBytes: 65536 })`). A real token is far under 64 KB; a runaway stream is truncated and the read returns instead of growing without limit. |
| **Why** | A token fits in well under a kilobyte; there is no legitimate reason to read megabytes from a credential FD. Capping the read is the correct defense against an inherited descriptor that isn't actually a credential file — the CLI cannot control what FDs its parent leaks into its environment, so it must read defensively. |

## 10. MCP server-level `disallowedTools` specs are no longer silently ignored (FIX)

**Type:** fix · **Modules:** MCP, Subagent (Agent) definitions, Permissions

### TL;DR

A subagent definition could list `mcp__server`, `mcp__server__*`, or `mcp__*` in `disallowedTools` to remove every tool from that server (or all MCP tools). These **server-level** specs were silently dropped — only exact tool-name matches worked. They are now honored.

### How it works

The `disallowedTools` matcher `buildDisallowedToolMatcher` (`uio`, cli_inner_pretty.js:371202) gained an `isServerLevelDisallowed` predicate. It parses each entry through `kk` (the MCP-tool-name parser → `{serverName, toolName}`); if the spec is server-level (`toolName === undefined || "*"`), it records the server in a set (or sets a `mcp__*` wildcard flag). `isToolDisallowed` then ORs in that server-level check:

```javascript
// ============================================
// buildDisallowedToolMatcher - Honor mcp__server / mcp__* server-level disallow specs
// Location: cli_inner_pretty.js:371202-371228
// ============================================

// ORIGINAL (for source lookup):
function uio(e) {
  let t = new Set(), n = new Set(), r = new Set(), o = !1;
  for (let a of e ?? []) {
    let { toolName: l, ruleContent: c } = EA(a);
    if ((t.add(l), !c)) n.add(l);
    let u = kk(l);                                          // parse "mcp__github" → {serverName:"github", toolName:undefined}
    if (u !== null && (u.toolName === void 0 || u.toolName === "*"))
      if (u.serverName === "*") o = !0;                     // mcp__* → block ALL MCP servers
      else r.add(u.serverName);                             // mcp__github / mcp__github__* → block that server
  }
  let s = (a) => {
    if (!o && r.size === 0) return !1;
    let l = kk(a)?.serverName;
    return l !== void 0 && (o || r.has(l));
  };
  return {
    disallowedToolSet: t, bareDisallowedToolSet: n, isServerLevelDisallowed: s,
    isToolDisallowed: (a) => {
      let l = lOe(a);
      return t.has(a.name) || t.has(l) || s(l);              // exact name OR server-level
    },
  };
}

// Mapping: uio→buildDisallowedToolMatcher, EA→parseRule, kk→parseMcpToolName, lOe→canonicalToolName,
//          r→serverLevelSet, o→allMcpWildcard, s→isServerLevelDisallowed
```

In 2.1.156 the equivalent matcher (the resolver `no`/`uE6` at cli_inner_pretty.js:278972-278986 in the 2.1.156 bundle) only did flat-name matching: `for (let v of z ?? []) { O.add(E); … } let j = f.filter(v => !O.has(v.name));`. An entry like `mcp__github` was added to the set as a literal name; since no tool is literally named `mcp__github` (real tools are `mcp__github__create_issue` etc.), it matched **nothing** and was silently ignored (`grep isServerLevelDisallowed` = 0 in 2.1.156).

| | |
|---|---|
| **Before** | Subagent `disallowedTools: ["mcp__github"]` had no effect — flat name matching never expanded the server prefix. An admin/author couldn't block a whole MCP server for a subagent. |
| **After** | `mcp__server`, `mcp__server__*`, `mcp__*` each remove the right set (one server / one server / all MCP), via `isServerLevelDisallowed`. The schema describe text now documents this (cli_inner_pretty.js:364406). |
| **Why** | The documented contract said server-level specs work; the matcher didn't implement the expansion. Closing the gap matters most for least-privilege subagents — "this worker may not touch any GitHub MCP tool" should be one entry, not an exhaustive list of every tool name. |

## 11. `CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=1` no longer blocks fresh marketplace clones (FIX)

**Type:** fix (regression) · **Modules:** Plugins, Marketplace, Git

### TL;DR

With `KEEP_MARKETPLACE_ON_FAILURE=1` set, a **fresh** marketplace install (no clone on disk yet) was incorrectly treated as "keep the existing clone" and never cloned at all. The flag now only short-circuits when a clone actually exists.

### How it works

The marketplace updater bails out of a re-clone when the flag is set. In 2.1.156 the early return was **unconditional** (cli_inner_pretty.js:415208-415215 in the 2.1.156 bundle): if `KEEP_MARKETPLACE_ON_FAILURE` was set, it logged "keeping existing clone" and returned — even on a fresh install with nothing to keep. In 2.1.178 the early return is gated on an existing `marketplace.json`:

```javascript
// ============================================
// keepMarketplaceOnFailureGuard - Only keep an existing clone, never block a fresh one
// Location: cli_inner_pretty.js:467674-467687
// ============================================

// ORIGINAL (for source lookup):
if (st(process.env.CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE)) {
  let g = Bd.join(t, ".claude-plugin", "marketplace.json");
  if (await i.stat(g).then(() => !0, () => !1)) {            // <-- only if a clone with marketplace.json exists
    v(`git pull failed, keeping existing clone (CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE): ${A.stderr}`,
      { level: "warn" });
    return;
  }
}
v(`git pull failed, will re-clone: ${A.stderr}`, { level: "warn" });   // fresh install falls through to clone

// Mapping: t→marketplaceDir, g→marketplaceJsonPath, i.stat→fsStat
```

| | |
|---|---|
| **Before** | The flag's early return fired even when no clone existed, so a *first-time* install with the flag set produced "keeping existing clone" and never cloned — the marketplace silently failed to install. |
| **After** | The `await i.stat(marketplace.json)` guard means the "keep" path is only taken for an actual existing clone; a fresh install falls through to the normal clone. |
| **Why** | The flag's intent is "on an *update* failure, don't blow away the working clone I already have." It was never meant to suppress the initial clone. The bug was applying an *update*-recovery shortcut to the *install* path; the `stat` check distinguishes the two states. |

## 13. Remote Control error legibility: persistent red `/rc failed` + categorized "not yet enabled" (IMPROVEMENT)

**Type:** improvement · **Modules:** Remote Control, Footer UI

### TL;DR

Two Remote-Control error improvements: (a) a connection failure now shows a **persistent red `/rc failed`** pill in the footer; and (b) the "not yet enabled" error now **explains the cause** — a feature-flag gate, a check failure (service unreachable), a stale entitlement, an org policy denial, an API-only restriction, or a cloud-session restriction.

### How it works

**(a) Footer pill.** The footer-indicator state machine `remoteControlFooterState` (`gNn`, cli_inner_pretty.js:353653) now returns a red `error`-colored `/rc failed` label as its **first** branch when `error` is set, ahead of the success/connecting branches:

```javascript
// Location: cli_inner_pretty.js:353653-353658
function gNn({ error: e, connected: t, sessionActive: n, reconnecting: r }) {
  if (e) return { label: "/rc failed", color: "error" };        // persistent red on failure
  if (r) return { label: "/rc reconnecting", color: "warning" };
  if (n || t) return { label: "/rc active", color: "success" };
  return { label: "/rc connecting…", color: "warning" };
}
```

**(b) Categorized "not yet enabled".** The eligibility check `remoteControlUnavailableReason` (`Q6n`, cli_inner_pretty.js:591564) now returns a distinct message per cause, in priority order: API-only ("only available when using Claude via api.anthropic.com"), cloud-session, **org policy** (`disableRemoteControl` managed setting, cli_inner_pretty.js:591569), missing claude.ai subscription, inference-only-token (long-lived token limitation), unknown-org, org-policy-**denied**/compliance (cli_inner_pretty.js:591582-591586), **feature-flag gate disabled** (`DISABLE_GROWTHBOOK`, cli_inner_pretty.js:591592), **check failure** (flag service unreachable, cli_inner_pretty.js:591600), and finally a **stale-entitlement** hint that tells the user to `claude auth logout`/`login` to refresh (cli_inner_pretty.js:591602).

| | |
|---|---|
| **Before** | A connection failure left the footer in an ambiguous state, and "Remote Control is not yet enabled" was a single opaque message regardless of *why* — gate vs. unreachable vs. stale entitlement vs. org policy all read identically. |
| **After** | Red persistent `/rc failed` pill; the unavailable reason is one of ~10 specific messages, each with the concrete next step (refresh entitlement, contact admin, unset `DISABLE_GROWTHBOOK`, re-login). |
| **Why** | Remote Control eligibility depends on a chain of independent conditions (plan, scope, org policy, feature-flag service, entitlement freshness). Collapsing all failures into one message made it impossible for a user to self-diagnose; per-cause messages turn a support ticket into a one-line fix. |

## 15. `claude agents` worker 401 with custom gateway, and stale-cached-config auth-after-refresh (FIX)

**Type:** fix · **Modules:** Auth, `claude agents` daemon, API client

Two auth-routing fixes:

- **`claude agents` workers 401 `Invalid bearer token` with a custom gateway.** When the daemon was started from a shell with a custom API gateway (`ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`), dispatched workers failed with `401 Invalid bearer token`. The worker spawn wasn't carrying the gateway's auth token through to the request layer. This is in the daemon→worker env-propagation path (the bg worker env-builder `_Fl`, documented in `../36_background_agents/worker_env_isolation_2181.md`); **not isolated to a single decl** in this build, but it is the same env-scrub/propagation surface that the 2.1.174/2.1.181 worker-env fixes touch.
- **Stale cached request config after out-of-session credential refresh.** When credentials were refreshed *outside* the session (e.g. another process re-logged in), model requests kept failing with auth errors because a **cached request configuration** still carried the old credential. The fix invalidates/rebuilds that cached config on refresh. The cached-config + OAuth-account plumbing lives around the token resolver `ax`/`getOAuthToken` (cli_inner_pretty.js:135008, 95763 `tokenAccount`), but the precise cache-invalidation hook is **not isolable to one line**. **Confidence: medium-low.**

- **Skill-truncation warning now shows how many descriptions are affected.** The over-budget warning is `Skill listing over budget: ${e.length} skills, ${a} chars > ${o} budget — descriptions will be truncated. Pure UI.

The qualified name is now recognized by the non-interactive permission path. - **Claude in Chrome silent-fail on account mismatch.** Claude-in-Chrome silently failed to connect when the OAuth token belonged to a **different account** than the Claude Code login. The bridge fetches `getUserId()` and `getOAuthToken()` separately and builds the bridge URL `${url}/chrome/${userId}` (cli_inner_pretty.js:11954-11982); the mismatch is between the Chrome-side `userId` and the Claude-Code-side `tokenAccount.uuid` (cli_inner_pretty.js:95763). The fix surfaces the mismatch instead of silently failing. **Not isolated to a single distinctive decl** beyond the bridge-connect block; **confidence: medium-low.**
- **Linux sandbox fails to start when `.claude/skills` or `.claude/hooks` is a symlink.** The sandbox write-path enumerator (`Vbd`, cli_inner_pretty.js:209122) resolves each `allowOnly` path via `realpathSync` and skips a symlink only when `zvn(h, y)` says it points *outside* the expected tree (cli_inner_pretty.js:209138-209144). `zvn` (cli_inner_pretty.js:208621) is byte-identical to 2.1.156's `T98`, so the fix is in **which** `.claude/` paths get added to the bind set / the order in which symlinks under `.claude/skills`/`.claude/hooks` are resolved — a path-collection refinement (sibling to 2.1.176's `.claude/settings.json` symlink fix), **not isolated to a single line**.
- **MCP server-level `disallowedTools`** — see §10.
- **vim mode undo (`u`) steps through NORMAL/VISUAL commands one at a time.** Previously commands issued in quick succession were merged into a single undo step; `u` now undoes one command at a time. This is a change to the vim undo-coalescing granularity (the undo-history push boundary). **Not isolated to a distinctive decl** in this build; pure editor-state behavior.
- **Statusline links with custom URI schemes (e.g. `vscode://`) now open in `claude agents`.** The link-open scheme allowlist set (`m$r`, cli_inner_pretty.js:137490-137504) was expanded from 2.1.156's `["https:", "http:", "file:"]` (cli_inner_pretty.js:232718 in the 2.1.156 bundle) to also include `vscode:`, `vscode-insiders:`, `cursor:`, `windsurf:`, `zed:`, `jetbrains:`, `idea:`, `slack:`, `linear:`, `notion:`, `figma:`. *Before:* a `vscode://` statusline link did nothing on click. *After:* recognized editor/workspace deep-link schemes open.
- **[VSCode] Esc to dismiss a CJK IME candidate window no longer cancels the running Claude task.** The Esc keypress that closes an IME composition popup was being routed to the task-interrupt handler. Now an Esc consumed by IME composition does not propagate to interrupt. IDE-side input-routing fix; **not isolated to a single decl** in the CLI bundle.
