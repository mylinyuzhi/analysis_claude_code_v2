# v2.1.162 — Source Diff Analysis

**Theme:** **A "make the surfaces honest" release — small CLI/permission correctness wins wrapped around a very large `claude agents` reliability + startup-noise cleanup pass.** Three new/changed *capabilities* carry actual code weight: (1) `--tools Grep/Glob` now *opts the session into the native embedded-search tools* on builds that ship them, via a brand-new `searchToolsOptIn` flag that did not exist at all in v2.1.156; (2) `/effort` now appends an explicit "(saved as your default for new sessions)" confirmation when you pick a persisting level — the inverted mirror of the old "blank when persisting" copy; and (3) the LSP tool's `workspaceSymbol` operation finally accepts a `query` parameter instead of hard-coding an empty string that made every language server return nothing. Sitting alongside are five pointed **correctness fixes** that each flip an ordering or guard: WebFetch permission *rules now beat the preapproved-host auto-allow* (the deny/ask/allow rule checks moved *before* the preapproved short-circuit); Windows permission rules *now match backslash and case-variant paths* (the matcher normalizes separators via `ND` and case-folds via `LA` before comparing); MCP per-server `timeout` values below 1000 ms are now *ignored* instead of being floored to a 1-second watchdog that aborted every call; the config writer gained an *in-memory fallback* (`tengu_config_fallback_write`) so a read-only config dir no longer hangs startup on a blank screen; and the editor rebrand `Windsurf → Devin Desktop` propagates through `/ide`, `/terminal-setup`, and `/scroll-speed`. The rest of the release — the `waitingFor` field on `claude agents --json`, the agents-view width/truncation/paste/attach/reply-queue fixes, the SendMessage deep-tmpdir fix, and the entire startup-noise rewrite (severity grouping, quieter notices, removed "Claude in Chrome enabled" / "marketplace installed" lines, footer-pinned launch-prompt warnings, Remote Control footer pill) — is **focus-feature `background` + UI-polish territory**, summarized and linked here rather than re-derived.

## 1. `--tools Grep/Glob` opts the session into native embedded-search tools (NEW)

**Type:** feature · **Modules:** Tools, CLI flags, Search (Grep/Glob)

### TL;DR

On native `claude` builds that embed a search engine, the session keeps using the *generic* `Bash`-style ripgrep path unless it knows it is allowed to surface the dedicated `Grep`/`Glob` search tools. Pre-2.1.162, naming `Grep` or `Glob` in `--tools` (or `--allowedTools`) was silently dropped: the tool names existed but no flag flipped to enable the embedded-search variants. v2.1.162 adds a new global flag, `searchToolsOptIn`, that is set to `true` whenever the requested base/allowed tool list mentions `Glob` or `Grep`, so those dedicated tools are actually provided.

### How it works

## 2. `/effort` confirms when a level will persist as the default (NEW)

**Type:** feature (UX) · **Modules:** `/effort` slash command, settings persistence

**Type:** fix · **Modules:** LSP tool

### TL;DR

The LSP tool's `workspaceSymbol` operation always sent `params: { query: "" }` — and most language servers return *zero* results for an empty workspace-symbol query, so the operation looked broken. v2.1.162 adds an optional `query` parameter to the tool schema and threads it into the `workspace/symbol` request.

|---|---|

## 4. WebFetch permission rules now beat the preapproved-host auto-allow (FIX, security)

**Type:** fix (security) · **Modules:** Permissions, WebFetch tool

### TL;DR

Claude Code auto-allows WebFetch to a curated set of "preapproved" documentation hosts (`platform.claude.com`, `developer.mozilla.org`, `react.dev`, …). Pre-2.1.162 that auto-allow was checked *first*, so an explicit `WebFetch(domain:developer.mozilla.org)` **deny** (or ask) rule was silently bypassed for any preapproved host. v2.1.162 reorders the WebFetch permission evaluator so explicit deny/ask/allow rules are all consulted *before* the preapproved short-circuit.

### How it works

The preapproved check is `isPreapprovedUrl` (`tjn`, cli_inner_pretty.js:408554-408561), which delegates to the host/path matcher `matchesPreapprovedHost` (`T2a`, cli_inner_pretty.js:393700-393708) over the preapproved host `Set` (`hCp`/`yCp`, cli_inner_pretty.js:393711+). The fix is purely the *order* in `WebFetch.checkPermissions`:

```javascript
// ============================================
// WebFetch.checkPermissions - rules evaluated BEFORE preapproved auto-allow
// Location: cli_inner_pretty.js:409323-409349
// ============================================

    o = m2n(jY(n, gF, "deny"), r);

  let s = m2n(jY(n, gF, "ask"), r);
  if (s) return { behavior: "ask", message: `Claude requested permissions to use ${gF.name}, but you haven't granted it yet.`, decisionReason: { type: "rule", rule: s }, suggestions: Guo(r) };
  let i = m2n(jY(n, gF, "allow"), r);
  if (i) return { behavior: "allow", updatedInput: e, decisionReason: { type: "rule", rule: i } };
  if (tjn(e.url)) return { behavior: "allow", updatedInput: e, decisionReason: { type: "other", reason: "Preapproved host" } };

// READABLE (for understanding):
```

| | |
|---|---|
| **Before (v2.1.156)** | The very first thing `checkPermissions` did was `if (mL8(f.hostname, f.pathname)) return { behavior:"allow", reason:"Preapproved host" }` (v2.1.156:366277-366278), *before* any deny/ask/allow rule lookup. | **After** | Deny → ask → allow rule checks run first; the preapproved auto-allow only fires when no explicit rule matched. |

## 5. MCP per-server `timeout` below 1000 ms is now ignored, not floored to a 1s watchdog (FIX)

**Type:** fix · **Modules:** MCP client, tool-call timeout

### TL;DR

An MCP server config could set a per-server `timeout` (ms). Pre-2.1.162, *any* value — including `500` — was accepted and then `Math.max(value, 1000)` floored it to 1000 ms, installing a 1-second watchdog that aborted every tool call slower than a second. v2.1.162 *ignores* sub-1000 ms values (falling back to `MCP_TOOL_TIMEOUT` or the default) and annotates them in `claude mcp get`.

### How it works

Two parallel resolvers compute the effective timeout — `resolveMcpToolTimeout` (`mGd`, cli_inner_pretty.js:283351-283355) for tool calls and `resolveMcpHttpTimeout` (`fra`, cli_inner_pretty.js:283567-283571) for the HTTP transport. Both gained the same `>= 1000` guard:

```javascript
// ============================================
// resolveMcpToolTimeout - sub-1000ms per-server timeout now ignored
// Location: cli_inner_pretty.js:283351-283355
// ============================================

// ORIGINAL (for source lookup):
function mGd(e) {
  let t = parseInt(process.env.MCP_TOOL_TIMEOUT || "", 10),
    r = (e?.timeout !== void 0 && e.timeout >= 1000 ? e.timeout : void 0) ?? (t > 0 ? t : void 0) ?? fGd;
  return Math.min(Math.max(r, 1000), dra);
}

// READABLE (for understanding):
function resolveMcpToolTimeout(serverCfg) {
  let envTimeout = parseInt(process.env.MCP_TOOL_TIMEOUT || "", 10),
    resolved =
      (serverCfg?.timeout !== undefined && serverCfg.timeout >= 1000 ? serverCfg.timeout : undefined)  // sub-1000 → ignore
      ?? (envTimeout > 0 ? envTimeout : undefined)
      ?? DEFAULT_MCP_TOOL_TIMEOUT;
  return Math.min(Math.max(resolved, 1000), MAX_MCP_TOOL_TIMEOUT);
}

// Mapping: mGd→resolveMcpToolTimeout, fGd→DEFAULT_MCP_TOOL_TIMEOUT, dra→MAX_MCP_TOOL_TIMEOUT
```

The schema describe-text now spells the behavior out: *"Values below 1000ms are ignored (falls through to MCP_TOOL_TIMEOUT or the default)."* (cli_inner_pretty.js:363576).

| | |
|---|---|
| **Before (v2.1.156)** | `resolveMcpToolTimeout` (`VB_`, v2.1.156:431958-431962) did `q = H?.timeout ?? (...)`, accepting *any* config `timeout`, then `Math.min(Math.max(q, 1000), …)` floored it. So `timeout: 500` became a hard 1000 ms cap on every call. The HTTP arm (`zW4`, v2.1.156:432091-432095) had the same shape. |
| **After** | A config `timeout` is only honored when `>= 1000`; otherwise it's dropped and resolution falls through to `MCP_TOOL_TIMEOUT` or the default. `claude mcp get` annotates the ignored value. |
| **Why** | `Math.max(q, 1000)` was meant as a *sanity floor* on a sane override, but combined with "accept any value" it weaponized a too-small config into a guaranteed-abort watchdog — the opposite of what someone setting a small timeout for a *fast* server intends. Ignoring the impossible value (rather than silently clamping it to a value that still bites) restores the env/default path and makes the misconfiguration visible. |

**Key insight:** The floor (`Math.max(r, 1000)`) is *kept* — the change is the *input filter* `&& e.timeout >= 1000` that decides whether the config value is even eligible. A value the floor would override is now treated as "not provided" instead of "provided and clamped," which is the difference between an inert no-op and a foot-gun.

## 6. Read-only config dir no longer hangs startup — in-memory config fallback (FIX)

**Type:** fix · **Modules:** Global config persistence, startup

### TL;DR

When the config directory is read-only or unwritable, Claude Code now starts with an *in-memory* config (and surfaces the write error) instead of hanging on a blank screen. The config writer updates the in-memory cache *first*, then attempts the disk write, and continues — emitting `tengu_config_fallback_write` with `disk_ok:false` — when the write fails.

### How it works

The fallback writer is `writeConfigFallback` (`O7n`, cli_inner_pretty.js:592177-592195). The crucial ordering: it calls `setInMemoryConfig` (`r8t`, cli_inner_pretty.js:592143-592145) to publish the new config into the process cache *before* touching disk, so even a total disk failure leaves the session with a valid live config:

## 7. Windsurf → Devin Desktop rebrand across `/ide`, `/terminal-setup`, `/scroll-speed` (IMPROVEMENT)

**Type:** improvement (rename) · **Modules:** IDE integration, terminal setup, UI

### TL;DR

Following the editor's rebrand, the user-facing name "Windsurf" is now displayed as "Devin Desktop" everywhere it surfaces — the `/ide` connect menu, `/terminal-setup`, and `/scroll-speed` — while the *internal* terminal identifier stays `windsurf` for back-compat with the editor's still-`windsurf`-named server files and `TERM_PROGRAM`.

### How it works

The display rename is a small set of literal swaps plus a normalizer. The IDE display-name resolver returns `"Devin Desktop"` for the windsurf case (cli_inner_pretty.js:184325, 184713-184715), the IDE list copy reads "VSCode, Cursor, Devin Desktop, Zed" (cli_inner_pretty.js:184292), and a dedicated normalizer rewrites any residual "windsurf" substring: `e.replace(/windsurf/gi, "Devin Desktop")` (cli_inner_pretty.js:276642). The plugin/tool maps carry `windsurf: "Devin Desktop"` (cli_inner_pretty.js:277020, 276849).

Crucially, *detection* still keys on the old identifier: `TERM_PROGRAM` detection accepts both `devin` and `windsurf` and the `/^devin([ -]desktop)?$/i` regex maps back to the internal `"windsurf"` tool id (cli_inner_pretty.js:41795-41805, 276628), and the process-scan greps for both `Windsurf Helper` and `Devin Helper`/`Devin.app` (cli_inner_pretty.js:276675, 276689). So the split is: **internal id = `windsurf`, display = `Devin Desktop`.**

**Why this approach:** Renaming the *display* string without renaming the *internal id* is the standard way to handle a vendor rebrand mid-stream — the editor still ships `.windsurf-server` directories and a `windsurf` `TERM_PROGRAM`, so detection must keep matching the old name, while only the human-readable surface follows the new brand. A blanket id rename would have broken auto-detection on every installed copy.

## 10. `SendMessage` cross-session messaging and deep `CLAUDE_CODE_TMPDIR`/`$TMPDIR` (FIX — focus-adjacent)

**Type:** fix · **Modules:** Cross-session messaging (SendMessage), UDS sockets

### TL;DR

Cross-session `SendMessage` could silently break when `CLAUDE_CODE_TMPDIR` or `$TMPDIR` pointed at a deep directory, because AF_UNIX socket paths have a hard ~104-byte limit (`sun_path`). The peer/daemon messaging socket directory is built under a **short, hash-shortened** `/tmp` path rather than under the (potentially deep) temp override, which keeps the socket path within the AF_UNIX limit.

### How it works (and an honesty note)

The daemon/peer socket directory `daemonSocketDir` (`hne`, cli_inner_pretty.js:491674-491681) is `"/tmp/cc-daemon-${uid}/${hash8}"`, where `hash8` is the first 8 hex chars of `sha256(resolve(configDir))` (`configDirHash` / `szp`, cli_inner_pretty.js:491670-491672). Anchoring the socket dir at literal `/tmp` (or the TERMUX prefix) and compressing the config-dir path to 8 chars bounds the socket path length regardless of how deep the user's `CLAUDE_CODE_TMPDIR`/config dir is. The per-session and control sockets (`${e}.sock`, `control.sock`, `${e}.pty.sock`) all hang off this short dir (cli_inner_pretty.js:491617-491655). A related sandbox warning (cli_inner_pretty.js:292566) explicitly calls out "too long for AF_UNIX sockets" when `CLAUDE_CODE_TMPDIR` makes the per-uid temp dir oversized, and falls the child-process `$TMPDIR` back.

**Honesty / confidence (medium):** The `hne`/`szp` short-path mechanism is *byte-identical* to v2.1.156 (`Ds`/`Ws_`, v2.1.156:470729-470737), so this exact daemon-socket-dir code is **not** the v2.1.162 delta. The v2.1.162 SendMessage deep-tmpdir fix is therefore *not isolated to a single changed declaration* in this region — it is most plausibly a guard/fallback on the *peer messaging socket path* recorded in the session registry (`messagingSocketPath`, cli_inner_pretty.js:604232, read at 360081) or in how SendMessage resolves a peer's `uds:` address (`parsePeerAddress`/`LLa`, cli_inner_pretty.js:359974-359978). I could not pin a single v2.1.162-specific decl that differs from v2.1.156 for this bullet; the short-`/tmp` socket-dir mechanism above is the relevant existing machinery, cited so the verifier knows where to look.

The lone-surrogate detector regexes are defined at cli_inner_pretty.js:10250-10251 (`/[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]/`) and reused for the "too-complex / contains lone surrogate" Bash classifier guard at 215835 / 218138.

## 14. Windows permission rules now match backslash + case-variant paths (FIX, security)

**Type:** fix (security) · **Modules:** Permissions, path-rule matching, Windows

### TL;DR

On Windows, a `Read`/`Edit`/`Bash` permission rule (and the deny/ask/allow path matching behind it) failed to match a target path when the path used backslashes (`~\`, a UNC `\\server\share`, a drive-letter `C:\…`) or differed only in case from the rule pattern, because the matcher compared the raw OS path against a forward-slash rule pattern without normalizing separators or folding case. v2.1.162 normalizes both the input path and the pattern to forward slashes (and case-folds on Windows) before comparing, so a deny rule like `Read(//c/users/foo/**)` now hides a file the OS reports as `C:\Users\Foo\…`. The same normalization is what lets `Read(...)` deny rules hide files from `Glob`/`Grep` output on Windows.

### How it works

The permission-rule path matcher `matchesPathRule` (`uye`, cli_inner_pretty.js:574675-574691, exported at cli_inner_pretty.js:574230) now runs the candidate path through the Windows path normalizer `normalizeWindowsPath` (`ND`, cli_inner_pretty.js:47604-47611) whenever the target contains a backslash on Windows, and case-folds both the root and the path with `caseFold` (`LA`, cli_inner_pretty.js:574256-574260) before the ignore-style pattern test:

`normalizeWindowsPath` (`ND`, cli_inner_pretty.js:47604-47611) does the three Windows shapes: UNC `\\…` → `replaceAll("\\","/")`, a `C:\…` drive prefix → `"/" + driveLetter.toLowerCase() + rest.replaceAll("\\","/")`, and any other backslash path → forward slashes. `caseFold` (`LA`) is `.toLowerCase()` plus Turkish-i (`ı→i`) and long-s (`ſ→s`) folds.

| | |
|---|---|
| **Before (v2.1.156)** | The rule-parse helper (`lJz`, v2.1.156:549666-549682) handled a UNC *pattern* at parse time but the matcher never ran the *input* path through a backslash normalizer like `ND`, and there was no `caseFold`/`LA`-style lowercasing of the path before comparison (v2.1.156 has no `matchesPathRule:` export and no `ND` Windows-path helper feeding the matcher). So a rule written with `/` never matched an OS path with `\`, and a case difference defeated the match. |
| **After** | The candidate path is separator-normalized (`ND`) when it contains a backslash on Windows and both sides are case-folded (`LA`), so backslash/case-variant paths match the rule. This is also what makes `Read(...)` deny rules effective at hiding files from `Glob`/`Grep` results on Windows. |
| **Why** | Windows reports paths with `\` and is case-insensitive; a permission system that compared bytes against a `/`-shaped, case-sensitive pattern would silently fail open (a deny rule that never matches = no protection) or fail closed inconsistently. Normalizing to a single canonical form (forward slashes, folded case) before the gitignore-style test makes the rule mean the same thing regardless of how the OS spells the path. |

**Key insight:** The fix is two canonicalizers (`ND` for separators/drive-letter, `LA` for case) applied *symmetrically* to the path and the rule root right before the existing ignore-pattern engine runs — no change to the matching engine itself, just making its inputs comparable on Windows.
