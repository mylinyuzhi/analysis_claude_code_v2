# v2.1.181 — Source Diff Analysis

**Theme:** **A flagship maintenance release built around three genuinely new surfaces — `/config key=value` (set any setting from the prompt), `sandbox.allowAppleEvents` (opt-in macOS Apple-Events for sandboxed `open`/`osascript`/auth flows), and `CLAUDE_CLIENT_PRESENCE_FILE` (a marker file that suppresses mobile push while you're at the keyboard) — sitting on top of a deep streaming/retry/startup-latency hardening pass and roughly two dozen targeted fixes.** This is the largest single version in the v2.1.179→2.1.183 window by both surface area and breadth: it touches `/config`, the sandbox profile builder, the presence/push subsystem, the streaming reader (auto-retry on mid-thinking connection drops + line-by-line long-paragraph rendering), the bundled Bun runtime (1.4), atomic file writes (network-drive 0-byte verification), the AWS credential cache (min-lifetime TTL + `aws configure export-credentials` JSON shape), prompt caching on custom gateways/Foundry, three distinct **startup-latency** regressions (managed-settings fetch, account-settings fetch, null-project crash), the MCP connection-status reporting, Remote Control transcript confirmation, and a cluster of subagent-panel polish items.

The rest get their primary analysis below, grouped by sub-theme.

## Sub-theme A — New configuration & platform surfaces

### 1. `/config key=value` — set any setting from the prompt (NEW)

**Type:** feature · **Modules:** CLI, Slash commands, Settings

#### TL;DR

`/config` gained a `key=value` argument form (e.g. `/config thinking=false`) that writes a setting directly, without opening the panel. It works in interactive mode, in `-p` (a second **non-interactive** `/config` command variant, `lbo`, is registered with `supportsNonInteractive: !0`), and over Remote Control. Multiple pairs are accepted in one invocation (`/config key=value [key=value ...]`). This is brand new — `tengu_config_shorthand` and the `key=value` parse/apply path return **0 hits in v2.1.156**.

#### How it works

**Step 1 — Parse the argument.** `parseConfigPairs` (`aWt`, cli_inner_pretty.js:479866-479883) splits the argument: a single `key=value` token is parsed by finding the first `=`; a space-separated list requires every token to contain a `=` (each split at *its* first `=`). A token with whitespace in the key, or `=` at position 0, makes the whole parse fail and the command prints `Expected key=value, got "<arg>". Run /config to open settings.` (cli_inner_pretty.js:488012/488036).

**Step 2 — Resolve and apply each pair.** `applyConfigPair` (`pqp`, cli_inner_pretty.js:479892-479927) looks the key up against the same setting registry the panel uses (`uqp`, case-insensitive match on `id`), emits `tengu_config_shorthand` with a hashed key and a `matched` flag (cli_inner_pretty.js:479894), then dispatches on the setting's declared `type`:
- **`consentGated`** settings refuse: *"…can't be set with key=value — open /config to change it from the panel."* (cli_inner_pretty.js:479898) — security-sensitive toggles still require the dialog.
- **`boolean`** accepts `true|1|on|yes` / `false|0|off|no` (cli_inner_pretty.js:479902-479903); anything else returns *"…takes true or false, not …"*.
- **`enum`/`managedEnum`** validate the value against `options` (or a `coerce` function for managed enums) and report the allowed set on a miss (cli_inner_pretty.js:479909-479925).

Each applied pair runs the setting's `onChange` callback and surfaces a per-pair message; the non-interactive path joins them with newlines (cli_inner_pretty.js:488039-488041).

**Step 3 — Two command registrations.** The interactive `/config` (`hVp`, cli_inner_pretty.js:488050-488061) is `local-jsx` and, when given a key, opens the panel pre-filtered. The non-interactive twin (`lbo`, cli_inner_pretty.js:488062-488074) is `type: "local"`, `supportsNonInteractive: !0`, `description: "Set a setting by key"`, gated on `xr()` — this is the one that runs under `-p`/Remote Control and prints text rather than rendering a panel.

### 2. `sandbox.allowAppleEvents` — opt-in Apple Events for sandboxed macOS commands (NEW)

**Type:** feature · **Modules:** Sandbox (macOS), Settings

#### TL;DR

A new opt-in sandbox setting, `sandbox.allowAppleEvents`, injects Apple-Events rules into the generated `sandbox-exec` profile so sandboxed commands can run `open`, `osascript`, and browser-based auth flows that script other apps. It is **off by default**, **removes code-execution isolation** when on (a sandboxed command can launch other apps unsandboxed), and is honored **only** from user / managed / CLI (`--settings`) sources — **project settings are ignored**. New in v2.1.183 (0 hits in v2.1.156).

#### How it works

**Step 1 — Schema.** Declared on the sandbox settings schema as an optional boolean (cli_inner_pretty.js:53695-53703) with a describe string spelling out the exact trade-off and the project-settings exclusion. The same flag also appears in the sandbox option object (cli_inner_pretty.js:210704-210708).

**Step 2 — Source restriction.** When the effective sandbox config is assembled (cli_inner_pretty.js:211599-211601), `allowAppleEvents` is resolved by scanning **only** flag settings and user settings (`kn("flagSettings")`, `Ig("userSettings") ? kn("userSettings") : null`) plus managed entries — and taking the first defined value. Project/local `.claude/settings.json` are deliberately excluded from this `.map(...).find(...)` chain, which is what enforces the "project settings ignored" guarantee.

**Step 3 — Profile injection.** The profile builder (cli_inner_pretty.js:209456, gated by the `allowAppleEvents` parameter `p`) appends Apple-Events rules only when `p` is truthy (cli_inner_pretty.js:209500-209509): `(allow appleevent-send)`, a mach-lookup for `com.apple.coreservices.appleevents`, plus `(allow lsopen)` and `com.apple.CoreServices.coreservicesd` / quarantine-resolver lookups needed for Launch Services `open` on macOS 14/15 (the comment even notes the `-10822`/`-54` failures that occur without them).

### 3. `CLAUDE_CLIENT_PRESENCE_FILE` — suppress mobile push while at the machine (NEW)

**Type:** feature · **Modules:** Presence/push, Notifications, Env

#### TL;DR

Point `CLAUDE_CLIENT_PRESENCE_FILE` at a marker file; while that file exists, Claude Code pulses a "client present" signal to the backend right before any state that would otherwise trigger a mobile push notification, so the push is suppressed. New env var (0 hits in v2.1.156), registered in the env getter map (cli_inner_pretty.js:42926).

#### How it works

**Step 1 — Marker check.** `isClientPresent` (`ECf`, cli_inner_pretty.js:606236-606246) reads `CLAUDE_CLIENT_PRESENCE_FILE`; returns `false` if unset, false if the path fails a trust check (`_d(e) && !YA(e)`), else `fs.stat`s the file and returns `true` iff it exists (a missing file is a clean `false`, with `ENOENT` not logged as an error).

**Step 2 — Presence pulse.** The presence pulser (`m3l`, cli_inner_pretty.js:606247-606302) POSTs to `…/v1/code/sessions/<id>/client/presence` with a per-session `client_id` and a stable `connected_at` (cli_inner_pretty.js:606255-606263). Its `pulseIfClientPresent()` method (cli_inner_pretty.js:606296-606301) calls `ECf()` and only pulses when the marker is present and a debounce window (`kYn = 5000` ms, cli_inner_pretty.js:606305) has elapsed.

**Step 3 — Wiring to push triggers.** The query loop exposes an `onBeforePushTriggeringState` callback that delegates to `pulseIfClientPresent()` (cli_inner_pretty.js:608900). So immediately before reaching a state that would fire a mobile push (e.g. a waiting permission prompt — cf. the `inputNeededNotifEnabled` setting, *"Push to mobile when a permission prompt or question is waiting"*, cli_inner_pretty.js:56456-56458), Claude tells the backend the human is present, and the backend withholds the push.

## Sub-theme B — Streaming & retry resilience

### 5. Auto-retry on a connection drop mid-thinking (IMPROVED)

**Type:** improvement · **Modules:** LLM API, Streaming

#### TL;DR

When the API stream drops **after only thinking blocks have been yielded** (no visible answer yet), Claude now **silently retries the streaming request** instead of surfacing *"Connection closed while thinking, before producing a response. Try again."* The retry path is new: the telemetry flag `after_thinking_only` returns **0 hits in v2.1.156** and **1 in v2.1.183**, and the "Connection closed while thinking" string is also new.

#### How it works

In the stale-connection branch of the stream reader (cli_inner_pretty.js:583851-583890), when a recognized stale-connection error (`Ve`, `QCe.has(code)`) is hit and only thinking-type blocks were yielded (`gs`/`Ni` distinguish tool-use and non-thinking content), the reader checks `!cn && Tr === null && sr < An` — no final content, no stop reason yet, under the retry cap — and if so:

1. increments the retry counter `sr`,
2. logs *"…after thinking-only yield — retrying streaming (sr/An)"* (cli_inner_pretty.js:583860-583863),
3. emits `tengu_streaming_stale_connection_retry` with `after_thinking_only: !0` and the error code (cli_inner_pretty.js:583864-583870),
4. discards the partial (thinking-only) yield, backs off `100 * sr` ms, and `continue e`s the outer stream loop to re-issue the request (cli_inner_pretty.js:583889-583890).

Only if the cap is exhausted (or non-thinking content had already streamed) does the reader fall through to finalize and emit the user-visible *"Connection closed while thinking…"* message (cli_inner_pretty.js:583907-583912).

### 6. Line-by-line streaming of long paragraphs (IMPROVED)

**Type:** improvement · **Modules:** UI/rendering (markdown stream)

Long paragraphs now render **line by line** as text streams in, rather than buffering until the first hard line break. **Not isolated to a single decl** — this is a change in the incremental markdown/text renderer that flushes soft-wrapped visual rows (the layout engine's `softWrap` machinery, cli_inner_pretty.js:169144-169944) as content arrives, instead of waiting for a `\n`. There is no distinctive grep-able string and no single function that captures the before/after; the behavior is emergent from how the streaming renderer chunks partial text. (Confidence: medium — confirmed as a rendering-pipeline change by the absence of any standalone "buffer-until-newline" decl and the changelog description; the exact flush site is inside a React/Ink stream component.)

## Sub-theme C — Prompt caching & file-write correctness

### 7. Prompt caching now reads on custom `ANTHROPIC_BASE_URL` and on Foundry (FIX)

**Type:** fix · **Modules:** Prompt caching, API client, Bridge attestation

#### TL;DR

Prompt cache **reads** were silently failing on custom-`ANTHROPIC_BASE_URL` setups and on Foundry because a **per-request device-attestation token** was being folded into the cached request configuration and changed every turn — so the cache key never matched and every request was a cache miss. The fix is that the attestation token is treated as a per-request artifact and excluded from the cache-affecting request shape.

#### How it works

The bridge attestation path (cli_inner_pretty.js:299966-300070) computes a `device_attestation_status` and, when enforcement is off (`!ct("tengu_bridge_attestation_enforce", !1)`), accepts unverified events. The `cache_control` markers on request blocks (cli_inner_pretty.js:230220, 231359-231462) and the cache-bust reasons array (which records *"cache_control changed (scope or TTL)"*, cli_inner_pretty.js:231660) are what determine whether a cached prefix is reused. The regression was that a turn-varying attestation token participated in the request identity feeding that comparison; on first-party direct connections it was stable, but on a custom gateway / Foundry it rotated per request, so the cached prefix was invalidated every turn.

**Honest scoping:** the changelog describes a precise cause (a per-request attestation token changing every turn), and the attestation + `cache_control` machinery is verified verbatim at the cited lines, but the **exact 2.1.180→2.1.181 patch site** (the line that newly excludes the attestation token from the cache key) cannot be diffed from a single build. Attributed by structure to the bridge-attestation / cache-control boundary above. (Confidence: medium.)

| | |
|---|---|
| **Before** | On a custom `ANTHROPIC_BASE_URL` gateway or Foundry, a per-request attestation token rotated every turn and entered the cache-affecting request shape, so prompt-cache reads always missed — full re-process each turn, higher latency/cost. |
| **After** | The attestation token is per-request only; the cached prefix matches across turns and cache reads succeed on custom gateways and Foundry. |
| **Why** | A device-attestation token is intrinsically per-request (that's the point of attestation), so it must never be part of the cache key. First-party direct connections happened not to expose the bug; gateways/Foundry did. |

### 8. Write/Edit no longer produce 0-byte or truncated files on network drives (FIX)

**Type:** fix · **Modules:** Write/Edit tools, Atomic file write

#### TL;DR

After writing a file, Claude now **verifies the on-disk byte count** matches what it intended to write, and throws a clear error if a network drive or cloud-sync folder silently truncated it. The atomic-write path also `fsync`s the temp file before the rename, with a graceful fallback when `fsync` is unsupported. The verification is new (0 hits in v2.1.156).

#### How it works

**Verification (`writeTextContent`, cli_inner_pretty.js:48290-48298):** after `imr(e, o, …)` writes the content, it computes the expected byte length and `stat`s the file; on a size mismatch it throws *"Write verification failed: \<path\> is N bytes on disk, expected M. The filesystem may have silently truncated the write (network drive / cloud sync)."* (cli_inner_pretty.js:48293-48296).

**Durable atomic write (cli_inner_pretty.js:48460-48522):** the content is written to a temp file opened `O_WRONLY|O_CREAT|O_EXCL`, then **`fsyncSync`** is called to flush to disk (cli_inner_pretty.js:48475), with `fsync unsupported on this filesystem` logged and swallowed when the FS rejects it (cli_inner_pretty.js:48477-48478); the temp file is then `renameSync`d into place ("written atomically"). An in-place fallback (also fsync'd) handles `EACCES`/rename-rejection cases (cli_inner_pretty.js:48491-48522).

```javascript
// READABLE (for understanding):
await writeFile(path, content, { encoding });
let expectedBytes = Buffer.byteLength(content, encoding),
  stat = await fs().stat(path);
if (stat.size !== expectedBytes)
  throw new ToolError(
    `Write verification failed: ${path} is ${stat.size} bytes on disk, expected ${expectedBytes}. ` +
    `The filesystem may have silently truncated the write (network drive / cloud sync).`,
    "writeTextContent: on-disk size mismatch after write",
  );
return Math.floor(stat.mtimeMs);

// Mapping: imr→writeFile, o→content, s→expectedBytes, i→stat, Bl→ToolError, Ut→fs
```

| | |
|---|---|
| **Before** | A network/cloud filesystem could accept a write and persist a 0-byte or truncated file; Claude reported success and the user discovered the corruption later. |
| **After** | The post-write `stat` catches the mismatch immediately and raises a descriptive error; `fsync` before rename reduces the window for the truncation to occur. |
| **Why** | Network/cloud filesystems lie about durability — a successful `write()` syscall doesn't guarantee the bytes landed. The only reliable detection is to read back the size. Pairing the check with an `fsync`-before-rename atomic write both *prevents* (flush) and *detects* (verify) the failure, and the `fsync unsupported` swallow keeps it working on filesystems that don't support it. |

## Sub-theme E — AWS credentials

### 12. AWS `awsCredentialExport`: short-lived credentials no longer refresh every minute, and `aws configure export-credentials` JSON shape is accepted (FIX)

**Type:** fix · **Modules:** Auth (Bedrock/AWS), Credential cache

#### TL;DR

Two coupled AWS credential fixes: (a) the credential cache now honors the credential's own `Expiration` with a minimum-lifetime floor, so a short-remaining-lifetime credential no longer triggers a refresh **every minute**; and (b) the export parser now accepts both the `{ Credentials: {...} }` (STS) shape **and** the flat top-level shape emitted by `aws configure export-credentials`.

#### How it works

**Parser — both shapes (v2.1.183).** `parseExportedCredentials` (`QUs`, cli_inner_pretty.js:101445-101451) returns `t.Credentials` if that wrapped object validates, **else** the top-level object if *it* validates (the flat `aws configure export-credentials` shape). The validator `validateAwsCreds` (`XUs`, cli_inner_pretty.js:101433-101444) checks `AccessKeyId`/`SecretAccessKey`/`SessionToken` on whatever object it's handed. The export reader (cli_inner_pretty.js:135284-135295) then extracts `Expiration` and parses it to an epoch ms `expiration` field — **previously absent**.

**Cache TTL — min-lifetime floor (v2.1.183).** The AWS credential resolver is memoized by `j$e` (cli_inner_pretty.js:47367), which in v2.1.183 accepts a **function** TTL (`typeof t === "function" ? t(i) : t`, cli_inner_pretty.js:47368) and stores `lifetimeMs: n(p)` per cached value (cli_inner_pretty.js:47382). The AWS resolver passes a TTL function (cli_inner_pretty.js:136428-136433): remaining = `expiration - Date.now()`; if remaining is undefined or `<= Mti + G8u` (300000 + 60000), use the default 1-hour cache (`j8u = 3600000`); otherwise cache for `remaining - Mti` (expiration minus a 5-minute buffer). Constants: `j8u = 3600000`, `Mti = 300000`, `G8u = 60000` (cli_inner_pretty.js:136333-136335).

**v2.1.156 before-picture.** The validator `y3K` **required** the `Credentials` wrapper (`if (!$.Credentials …) return !1`, v2.1.156 cli_inner_pretty.js:97996-98008) — the flat shape was rejected. The reader returned `{ accessKeyId, secretAccessKey, sessionToken }` with **no `expiration`** (v2.1.156 cli_inner_pretty.js:131124-131135). And the cache used a **fixed** TTL constant `MH5 = 3600000` (v2.1.156 cli_inner_pretty.js:132017, passed positionally to `LGH` at 132102), whose memoize helper `LGH` took a *number* default (`function LGH(H, $ = 300000)`, v2.1.156 cli_inner_pretty.js:43263) — i.e. no per-value, expiration-aware lifetime.

```javascript
// ============================================
// awsCredentialCacheTtl - Expiration-aware cache lifetime for AWS credentials
// Location: cli_inner_pretty.js:136428-136433  (constants 136333-136335)
// ============================================

// ORIGINAL (for source lookup):
(e) => {
  let t = e?.expiration,
    n = t === void 0 ? void 0 : t - Date.now();
  if (n === void 0 || n <= Mti + G8u) return j8u;
  return n - Mti;
}
// j8u = 3600000, Mti = 300000, G8u = 60000

// READABLE (for understanding):
(creds) => {
  let expiresAt = creds?.expiration,
    remainingMs = expiresAt === undefined ? undefined : expiresAt - Date.now();
  // No expiration, or too little life left (< 5min buffer + 1min) → fall back to fixed 1h cache:
  if (remainingMs === undefined || remainingMs <= REFRESH_BUFFER_MS + MIN_REMAINING_MS) return DEFAULT_TTL_MS;
  // Otherwise cache until 5 minutes before the credential actually expires:
  return remainingMs - REFRESH_BUFFER_MS;
}
// DEFAULT_TTL_MS = 3600000 (1h), REFRESH_BUFFER_MS = 300000 (5m), MIN_REMAINING_MS = 60000 (1m)

// Mapping: j8u→DEFAULT_TTL_MS, Mti→REFRESH_BUFFER_MS, G8u→MIN_REMAINING_MS, e→creds, n→remainingMs
```

| | |
|---|---|
| **Before** | The parser required the wrapped `{ Credentials: {...} }` shape (rejecting `aws configure export-credentials` output) and carried **no expiration**. The cache used a fixed 1h TTL with no expiration awareness, so a credential with only a couple minutes of life left was repeatedly re-resolved (effectively every minute). |
| **After** | The parser accepts both shapes and extracts `Expiration`; the cache lifetime is `min(expiration − 5min, …)` with a floor — short-lived credentials are cached for their real remaining life instead of thrashing, and a genuinely short remaining lifetime falls back to the fixed 1h cache rather than refreshing constantly. |
| **Why** | The min-lifetime floor (`<= Mti + G8u` → fixed 1h) is the anti-thrash guard: without it, a credential expiring in 90s would compute a tiny TTL and re-resolve immediately, repeating forever. Accepting the flat shape removes friction for the very common `aws configure export-credentials` helper script. The expiration-aware TTL required generalizing `j$e` to take a **function** TTL — the structural enabler for this fix. |

## Summary

v2.1.181 is the **flagship maintenance release** of the late-2.1.18x line: three new surfaces, a streaming/retry hardening pass, and ~two dozen fixes spread across nearly every subsystem. The new surfaces all reuse existing machinery rather than building parallel paths — `/config key=value` drives the same setting registry the panel uses (including its `consentGated` boundary), `sandbox.allowAppleEvents` adds inert profile rules whose only enabling sources are the trusted tiers, and `CLAUDE_CLIENT_PRESENCE_FILE` is a single debounced presence pulse the backend reads to withhold push.

The correctness fixes carry the weight. The **mid-thinking auto-retry** transparently recovers from the one connection-drop case where retrying is provably safe (no visible output yet), tagged by the new `after_thinking_only` flag. The **Write 0-byte verification** finally catches network/cloud filesystems that lie about durable writes, paired with an `fsync`-before-rename atomic write. The **AWS credential** fix both stops short-lived credentials from thrashing the cache (expiration-aware TTL with a min-lifetime floor, enabled by generalizing the memoizer to a function TTL) and accepts the flat `aws configure export-credentials` shape. And three distinct **startup-latency** regressions — managed-settings fetch, account-settings fetch, null-project crash — get the fresh-environment launch back under budget.

The two focus-feature touches are linked, not re-derived: the auto-memory status line stops listing files outside verbose ([../31_auto_memory/status_line_and_misc_delta.md](../31_auto_memory/status_line_and_misc_delta.md)), and foreground subagents are folded into the same universal 5-level depth gate as background ([../36_background_agents/nested_subagent_depth_limit.md](../36_background_agents/nested_subagent_depth_limit.md)).
