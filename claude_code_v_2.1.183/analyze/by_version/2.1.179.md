## 1. Mid-stream connection drops preserve the partial response and unstick the spinner (FIX — substantive)

**Type:** fix (resilience) · **Modules:** LLM API streaming, Spinner/turn state, Telemetry

### TL;DR

When the model's streaming connection drops *after* it has already emitted some content blocks (a `ConnectionClosed`/`ECONNRESET`/`EPIPE` mid-response), Claude Code no longer throws the raw transport error up to the UI. Instead it **synthesizes a stop reason** for the blocks already received, finalizes them as a complete-enough turn, and yields a calm trailer — *"Connection closed mid-response. The response above may be incomplete."* Because the turn is finalized rather than left dangling, the spinner that was showing `running tool for …` transitions out of the running state instead of hanging there forever.

### How it works

The streaming loop's error handler (`cli_inner_pretty.js:583836-583924`) classifies the failure and branches:

1. **Classify the error.** `Ee = dG(ks)` extracts the error code; `Ve = Ee !== null && QCe.has(Ee.code)` tests it against the stale-connection set `QCe = new Set(["ECONNRESET", "EPIPE", "ConnectionClosed"])` (cli_inner_pretty.js:228839). If matched, the failure class is tagged `"stale_connection"` (cli_inner_pretty.js:583850).
2. **Only act when real content was yielded.** The guard `Lt.some(block => block.message.content.some(c => !p2(c)))` (cli_inner_pretty.js:583851) checks whether any *non-empty* block was already streamed (`Lt` is the accumulated yielded blocks). Empty/no-content drops fall through to the existing non-streaming fallback or rethrow.
3. **Thinking-only special case → retry.** If every yielded block was a thinking block, the loop *retries* the stream (up to `An` attempts) rather than finalizing, emitting `tengu_streaming_stale_connection_retry` with `after_thinking_only: true` (cli_inner_pretty.js:583857-583890) — a dropped stream that produced only reasoning is worth re-attempting because no user-visible answer was lost.
4. **Finalize the partial.** Otherwise it picks a synthesized `stop_reason` — `"tool_use"` if any yielded block was a `tool_use`, else `"end_turn"` (cli_inner_pretty.js:583892) — stamps it onto every accumulated block, logs `Stream connection closed (…) after N block(s) yielded — finalizing partial response`, emits `tengu_streaming_partial_finalized` (with `blocks_yielded`, `has_output`, `synthesized_stop_reason`), and yields a synthetic assistant trailer: *"Connection closed mid-response. The response above may be incomplete."* (cli_inner_pretty.js:583900-583924). It then `break`s out of the retry loop, ending the turn cleanly.

The spinner state lives in a separate renderer whose `P.kind === "tool-running"` produces the `running tool for ${ea(P.toolMs)}` string (cli_inner_pretty.js:354846-354847). It stays in `tool-running` only while the turn is in flight; finalizing the partial turn (step 4) is what lets `P.kind` advance, so the "running tool" spinner stops — this is the same fix, not a second code path.

By manufacturing a valid `stop_reason` and emitting a trailer block, v2.1.179 makes the partial response indistinguishable *structurally* from a normal completion — which is precisely what lets the spinner advance and the session stay usable.

## 2. `denyRead`/`allowRead` glob over a large tree no longer bloats the Bash tool description (FIX — substantive)

**Type:** fix (prompt size / Linux) · **Modules:** Sandbox (Linux), Bash tool description

### TL;DR

On Linux, a sandbox `denyRead` or `allowRead` glob is expanded to concrete paths before being applied. If the glob matched a large directory tree (thousands of entries), the **full expanded list** was being inlined into the Bash tool's `## Command sandbox` description block — making the tool description enormous, blowing up prompt size, and rendering the session effectively unusable. v2.1.179 caps each filesystem/network path list at 50 entries in the description, appending `… and N more (truncated for prompt size)`.

### How it works

The Bash description's sandbox section is assembled by `cJa` (cli_inner_pretty.js:449934-450002). It reads the sandbox read/write/network configs and builds a `Filesystem: …` / `Network: …` JSON blob. Two helpers do the trimming:

- **Dedupe** — `Wdt` (cli_inner_pretty.js:449925-449928) drops duplicate paths (`ms`). This existed before (it was `tH$` in v2.1.156).
- **Cap (new)** — `RWe` (cli_inner_pretty.js:449929-449933) is the v2.1.179 addition: if a list exceeds `_Ao` (`= 50`, cli_inner_pretty.js:450164), it keeps the first 50 and appends a single `… and ${count} more (truncated for prompt size)` sentinel. Every list in the description — `read.denyOnly`, `read.allowWithinDeny`, `write.allowOnly`, `write.denyWithinAllow`, `allowedHosts`, `deniedHosts`, `allowUnixSockets` — is wrapped in `RWe(Wdt(...))` (cli_inner_pretty.js:449946-449954).

The glob expansion that *produced* the giant list is in `lSd` (cli_inner_pretty.js:210138-210156): on Linux a glob pattern is expanded via `GDt(n)` and logged as `[Sandbox] Expanded allowRead glob pattern "${n}" to ${o.length} paths on Linux` (cli_inner_pretty.js:210153). That expansion is still needed for the actual seccomp/sandbox-profile (the kernel-level rule list must be concrete); the fix is purely to stop that concrete list from being copied verbatim into the *prompt*.

```javascript
// ============================================
// capPathListForPrompt - Truncate a path list before it is inlined into the Bash tool description
// Location: cli_inner_pretty.js:449929-449950, 450164 (v2.1.183)
// ============================================

// ORIGINAL (for source lookup):
function Wdt(e) { if (!e || e.length === 0) return e; return ms(e); }          // dedupe (was tH$ in v2.1.156)
function RWe(e) {                                                              // NEW cap
  if (!e || e.length <= _Ao) return e;
  let t = e.length - _Ao;
  return [...e.slice(0, _Ao), `... and ${t} more (truncated for prompt size)`];
}
// ... inside cJa():
l = {
  read: { denyOnly: RWe(Wdt(e.denyOnly)), ...(e.allowWithinDeny && { allowWithinDeny: RWe(Wdt(e.allowWithinDeny)) }) },
  write: { allowOnly: RWe(a(t.allowOnly)), denyWithinAllow: RWe(Wdt(t.denyWithinAllow)) },
};
var _Ao = 50;

// READABLE (for understanding):
function dedupePaths(list) { if (!list || list.length === 0) return list; return dedupe(list); }
function capPathListForPrompt(list) {
  if (!list || list.length <= PROMPT_PATH_CAP) return list;
  let overflow = list.length - PROMPT_PATH_CAP;
  return [...list.slice(0, PROMPT_PATH_CAP), `... and ${overflow} more (truncated for prompt size)`];
}
// in buildSandboxDescription():
fs = {
  read: { denyOnly: capPathListForPrompt(dedupePaths(readCfg.denyOnly)),
          ...(readCfg.allowWithinDeny && { allowWithinDeny: capPathListForPrompt(dedupePaths(readCfg.allowWithinDeny)) }) },
  write: { allowOnly: capPathListForPrompt(tmpdirSubst(writeCfg.allowOnly)),
           denyWithinAllow: capPathListForPrompt(dedupePaths(writeCfg.denyWithinAllow)) },
};
var PROMPT_PATH_CAP = 50;

// Mapping: RWe→capPathListForPrompt, Wdt→dedupePaths, _Ao→PROMPT_PATH_CAP, ms→dedupe, cJa→buildSandboxDescription
```

| | |
|---|---|
| **Type** | Fix (prompt-size / Linux sandbox) |
| **Modules touched** | Sandbox config → Bash tool description |
| **Before (v2.1.156)** | The description builder `g24` dedupes each list (`tH$`) but applies **no cap** (cli_inner_pretty.js:438963-438989, v2.1.156 before-picture). A `denyRead`/`allowRead` glob expanding to thousands of Linux paths dumped all of them into the `Filesystem:` blob, ballooning the Bash tool description sent on every request. |
| **After (v2.1.183)** | Each list is capped at 50 entries with a `… and N more (truncated for prompt size)` sentinel via `RWe`, so the description stays small regardless of how broadly a glob matched. |
| **Why** | The tool description is sent to the model on every turn — its size is multiplied across the whole session. The seccomp profile genuinely needs every expanded path, but the model does not need to see all of them to understand "reads under this tree are denied." Showing the first 50 plus a count preserves the *informational* purpose while bounding the *token* cost. The cap is per-list (not global) so an enormous deny list can't crowd out the network or write sections. |

**Key insight:** The split between "what the kernel rule needs" (concrete, exhaustive) and "what the prompt needs" (representative, bounded) is the design move. The expensive glob expansion still happens for the sandbox profile; v2.1.179 just inserts a presentation-layer cap right before the JSON is serialized into the prompt, so the fix is a two-function addition (`RWe` + wrapping the existing `Wdt` calls) rather than a rework of sandbox path handling.

## 3. Mouse-wheel scrolling fixed in WSL2 under Windows Terminal and VS Code (FIX — regression from 2.1.172)

**Type:** fix (input / terminal detection) · **Modules:** Mouse/wheel input, Terminal detection

### How it works

The wheel pipeline has three layers in v2.1.183:

- **SGR decode** — `oEi` (cli_inner_pretty.js:159894-159912) masks the SGR mouse button with `& 67` and maps `64 → wheelup`, `65 → wheeldown`. This decode is **byte-identical to v2.1.156** (cli_inner_pretty.js:153243-153247, before-picture), so the regression and its fix are *not* here.
- **Terminal-environment detection** — `MO` (cli_inner_pretty.js:159294-159327) computes a per-terminal wheel profile carrying `wtSession` (true when `WT_SESSION` is set → Windows Terminal, cli_inner_pretty.js:159299/159322) and `wheelFlood` (true for terminals known to flood duplicate wheel events). `wheelFlood` is computed by `vFr` (cli_inner_pretty.js:159329-159336), which now gates VS Code/Cursor on a **version window**: `TERM_PROGRAM === "vscode"` only counts as wheel-flooding when the parsed `TERM_PROGRAM_VERSION` is `>= 1092000 && < 1105000` (VS Code 1.92.0–1.104.x), plus explicit Cursor signals.
- **jediTerm corrective filter** — `YSi` (cli_inner_pretty.js:159389-159419) synthesizes/suppresses wheel events for JetBrains-style terminals; this block is carryover from v2.1.156 (it was `nlK`).

### Why this is the relevant code, with an honest caveat

In v2.1.156's before-picture the VS Code wheel-flood detector `PL` (cli_inner_pretty.js:152589-152593, before-picture) returned `true` for *any* `TERM_PROGRAM === "vscode"` terminal with no version gate. v2.1.183's `vFr` narrows that to a specific VS Code/Cursor version range and keys WSL2/Windows-Terminal handling off `wtSession`. That narrowing is exactly the shape of "we over-applied a wheel-flood workaround to terminal/version combos (WSL2 under Windows Terminal / current VS Code) where it broke normal scrolling."

**Confidence: medium, with a span caveat.** The changelog attributes the regression to **2.1.172** and the fix to **2.1.179**. The only two bundles available here are **2.1.156** (predates the regression) and **2.1.183** (postdates the fix), so the version window in `vFr` and the `wtSession` plumbing cannot be cleanly attributed to 2.1.179 alone versus the intervening 2.1.157–2.1.178 churn — the 2.1.156→2.1.183 diff contains *both* the regression and its fix. The relevant machine is `MO`/`vFr`/`YSi` at cli_inner_pretty.js:159294-159419; the precise 2.1.179 delta line is **not isolable** from these two builds.

## 4. Feedback survey no longer captures a single-digit reply as a session rating right after a turn (FIX)

**Type:** fix (input timing) · **Modules:** Feedback survey, Telemetry

### How it works

The terminal feedback survey's visibility is decided by the `useFeedbackSurvey` hook (`uZl`, cli_inner_pretty.js:667245+; the visibility memo is cli_inner_pretty.js:667417-667444). It gates appearance on a stack of conditions, the timing-relevant ones being:

- `X - m.current < c.minTimeBeforeFeedbackMs` → too soon after session start (cli_inner_pretty.js:667435)
- `n < A.current + c.minUserTurnsBeforeFeedback` → not enough user turns yet (cli_inner_pretty.js:667436)
- after a prior appearance: `minTimeBetweenFeedbackMs` and `minUserTurnsBetweenFeedback` (cli_inner_pretty.js:667431-667433)

The survey state machine itself is `fgt` (cli_inner_pretty.js:667126-667231): `state` advances `closed → open → pending → thanks/submitted`, and the response is recorded through `handleSelect` (`x`, cli_inner_pretty.js:667183-667192) with a `RFf = 3000`ms confirm/undo window. The bug — a single digit typed *immediately after a turn completes* being swallowed as a survey rating — is the survey arming and grabbing the keystroke before the user intended, governed by these `minTimeBeforeFeedbackMs` / `minUserTurnsBeforeFeedback` turn-completion gates.

**Confidence: medium.** The survey hook, its visibility gate (cli_inner_pretty.js:667417-667444), the state machine `fgt`, and the `feedbackSurveyRate` setting (cli_inner_pretty.js:56174) are verified verbatim. The exact line that previously routed a bare digit keypress into the survey response (the render component's key handler) does **not** carry a distinctive grep string in this build, and the two-build span includes intervening survey churn, so the precise patch site is attributed by structure (the appearance-timing gate) rather than by a captured before/after digit-handling line. The fix is a timing/eligibility tightening, not a new declaration.

## Summary

v2.1.179 is a **resilience + rough-edges** maintenance release with two substantive mechanisms and a tail of input/UI corrections. The headline is **mid-stream connection-drop recovery** (cli_inner_pretty.js:583836-583924): a stream that drops after yielding real content is now finalized with a synthesized `stop_reason` and a graceful "the response above may be incomplete" trailer (emitting `tengu_streaming_partial_finalized`) instead of throwing a raw error — and because the turn finalizes, the `running tool` spinner (cli_inner_pretty.js:354847) leaves its stuck state. The clean second fix caps each sandbox path list at 50 entries (`RWe`/`_Ao = 50`, cli_inner_pretty.js:449929-449933, 450164) before it is inlined into the Bash tool description, so a `denyRead`/`allowRead` glob that expands over a huge Linux tree no longer balloons the prompt — verified against the v2.1.156 before-picture (`g24`/`tH$`, cli_inner_pretty.js:438963-438989) where the dedupe existed but no cap did.

The remaining items are input/render/detection fixes of decreasing isolability: the WSL2/Windows-Terminal/VS-Code mouse-wheel fix lives in the `MO`/`vFr`/`YSi` wheel machine (cli_inner_pretty.js:159294-159419) but spans the 2.1.172 regression and 2.1.179 fix across the unavailable intermediate builds; the feedback-survey single-digit fix is a timing tightening in the survey-visibility gate (cli_inner_pretty.js:667417-667444); and the welcome-promo cap, prompt-input focus-return, Ctrl+O subagent transcript, and remote plugin-load perf are render/focus/remote fixes documented honestly with their surrounding anchors where the exact patch line is not grep-isolable from a single bundle. The remote background-tasks "still running" fix is a focus-feature item summarized here and linked to [`../36_background_agents/bg_command_surface_and_retire_delta.md`](../36_background_agents/bg_command_surface_and_retire_delta.md).
