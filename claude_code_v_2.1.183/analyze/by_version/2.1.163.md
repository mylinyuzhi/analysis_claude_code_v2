## 1. `requiredMinimumVersion` / `requiredMaximumVersion` managed settings (NEW)

**Type:** feature · **Modules:** Managed/policy settings, Startup gate, Version

### TL;DR

Two new **managed-settings-only** keys, `requiredMinimumVersion` and `requiredMaximumVersion`, let an organization pin a hard version window. At startup Claude Code compares its own version against the policy bounds; if it is older than the minimum or newer than the maximum, it **refuses to start** and prints organization-specific guidance toward an approved version. The bounds are enforced *only* from `policySettings` (the managed layer) — a user can't set them on themselves.

### How it works

**Step 1 — Schema.** Both keys are added to the settings Zod schema as optional strings (cli_inner_pretty.js:56277-56286), each `.describe()` spelling out the semantics and the "Only enforced from managed (policy) settings" constraint. They sit right after the pre-existing `minimumVersion` (which only prevented *channel-switch downgrades*) — this pair is the stricter, admin-imposed gate.

**Step 2 — The gate.** `evaluateVersionPolicy` (`UBl`, cli_inner_pretty.js:593560-593579) is the comparator. It short-circuits to `null` (allow) when neither bound is set, when the top-level command is one of the exempt `update`/`install`/`doctor` (so an out-of-window binary can still self-rescue, exempt set `OHf` at cli_inner_pretty.js:593629), or when the running version isn't parseable. Otherwise it parses each bound with semver; an **unparseable bound is logged and ignored** (defensive — a typo in policy must not brick startup, cli_inner_pretty.js:593566/593573). If the version is below the floor (`!bL(...)`) or above the ceiling (`!AQe(...)`), it returns a human-readable refusal string.

**Step 3 — Two call sites.** `evaluateVersionPolicyForCommand` (`jBl`, cli_inner_pretty.js:593580) walks to the root command and reads `policySettings`; `evaluateVersionPolicyGlobal` (`GBl`, cli_inner_pretty.js:593603) is the topLevelCommand-less variant. Both feed the policy's `requiredMinimumVersion`/`requiredMaximumVersion` into `UBl`. The same `requiredMaximumVersion` is also consulted in the "is an update available / should I block" path (cli_inner_pretty.js:341683-341687 returns the reason string `above your organization's requiredMaximumVersion (...)`, and cli_inner_pretty.js:692033 folds it into the upgrade decision).

```javascript
// ============================================
// evaluateVersionPolicy - Refuse startup outside the org-approved version window
// Location: cli_inner_pretty.js:593560-593579
// ============================================

// ORIGINAL (for source lookup):
function UBl({ currentVersion: e, requiredMinimumVersion: t, requiredMaximumVersion: n, topLevelCommand: r }) {
  if (!t && !n) return null;
  if (r !== void 0 && OHf.has(r)) return null;
  if (!U7n.parse(e)) return null;
  if (t) {
    let o = U7n.parse(t)?.version;
    if (!o) v(`requiredMinimumVersion '${t}' is not a valid semver version — ignoring`, { level: "error" });
    else if (!bL(e, o))
      return `Claude Code ${e} is older than the minimum version required by your organization (${t}).
Update Claude Code using your organization's approved method, then try again. If automatic updates are available, \`claude update\` may also work.`;
  }
  if (n) {
    let o = U7n.parse(n)?.version;
    if (!o) v(`requiredMaximumVersion '${n}' is not a valid semver version — ignoring`, { level: "error" });
    else if (!AQe(e, o))
      return `Claude Code ${e} is newer than the maximum version allowed by your organization (${n}).
Your organization requires version ${n} or older. Install an approved version using your organization's approved method. \`claude install <version>\` may also work.`;
  }
  return null;
}

// READABLE (for understanding):
function evaluateVersionPolicy({ currentVersion, requiredMinimumVersion, requiredMaximumVersion, topLevelCommand }) {
  if (!requiredMinimumVersion && !requiredMaximumVersion) return null;            // no policy -> allow
  if (topLevelCommand !== undefined && EXEMPT_COMMANDS.has(topLevelCommand)) return null; // update/install/doctor escape hatch
  if (!semverParse(currentVersion)) return null;                                  // unparseable self-version -> allow
  if (requiredMinimumVersion) {
    let floor = semverParse(requiredMinimumVersion)?.version;
    if (!floor) logError(`requiredMinimumVersion '${requiredMinimumVersion}' is not a valid semver version — ignoring`);
    else if (!gte(currentVersion, floor)) return /* refusal: older than org minimum */;
  }
  if (requiredMaximumVersion) {
    let ceiling = semverParse(requiredMaximumVersion)?.version;
    if (!ceiling) logError(`requiredMaximumVersion '${requiredMaximumVersion}' is not a valid semver version — ignoring`);
    else if (!lte(currentVersion, ceiling)) return /* refusal: newer than org maximum */;
  }
  return null;
}

// Mapping: UBl→evaluateVersionPolicy, OHf→EXEMPT_COMMANDS, U7n.parse→semverParse, bL→gte, AQe→lte, v→logError
```

**Type:** feature · **Modules:** Plugins, Slash commands

Previously the in-session `/plugin` surface offered install/manage/enable/disable/configure/uninstall but no plain *list* — you had to drop to the `claude plugin list` CLI subcommand. ## 3. `Stop` / `SubagentStop` hooks: `hookSpecificOutput.additionalContext` keeps the turn going (NEW)

**Type:** feature · **Modules:** Hooks, Agent loop

### TL;DR

`Stop` and `SubagentStop` hooks can now return `hookSpecificOutput.additionalContext` — non-error feedback that is delivered to the model (or subagent) so it can act on it, **without** being labeled a hook *error* and **without** forcing the turn to stop. This adds a sanctioned "here's more to do / here's some context" channel distinct from the existing "deny continuation" path.

### How it works

**Step 1 — Schema.** The `hookSpecificOutput` union for these two events gains the `additionalContext` shape: `{ hookEventName: "Stop", additionalContext: string? }` (cli_inner_pretty.js:364243-364245) and the `SubagentStop` twin (cli_inner_pretty.js:364247-364249). The describe text is explicit: *"additionalContext is non-error feedback delivered to the model; the conversation continues so the model can act on it."* The same pair appears again in the broader hook-output union (cli_inner_pretty.js:367573-367574).

**Step 2 — Kept out of the error channel.** The internal `stop_hook_summary` SystemMessage gains a `hook_additional_context: string[]` field, described as *"Non-error feedback from hookSpecificOutput.additionalContext — kept separate from hook_errors so the sanctioned feedback channel is not labeled an error"* (cli_inner_pretty.js:365022-365026). That separation is the whole point: the feedback rides alongside `hook_errors`/`prevented_continuation` but in its own array, so the UI and the model treat it as guidance, not a failure.

**Step 3 — Validator hint.** The hook-output validator already special-cases this key: an unrecognized `hookSpecificOutput.*` key triggers the suggestion *"Did you mean hookSpecificOutput.additionalContext (with a hookEventName)?"* (cli_inner_pretty.js:576548-576556).

## 4. Skills: `\$` escape for a literal `$` before a digit (NEW)

**Type:** feature · **Modules:** Skills, Command/argument substitution

### TL;DR

Skill (and single-file command) bodies do argument substitution — `$1`, `$2`, `$ARGUMENTS[0]`, `$ARGUMENTS`. That meant a body could not safely contain a literal `$` immediately before a digit (e.g. a price `$5`, a shell var `$1` you wanted verbatim) — it would be eaten as a positional-arg placeholder. v2.1.163 adds a `\$` escape: writing `\$` before a digit / `ARGUMENTS` / an arg name yields a literal `$`.

### How it works

The substitution function (`substituteSkillArgs` = `Mot`, cli_inner_pretty.js:289876-289914) gains an **escape pre-pass and post-pass** around the existing replacements:

1. **Pre-pass (new).** It builds an alternation `l` of the substitution targets (`\d`, `ARGUMENTS`, and each named arg). Then `c = e.replace(new RegExp(`(?<!\\\\)\\\\\\$(?=${l})`, "g"), mYr)` (cli_inner_pretty.js:289888) replaces every `\$` that is *(a)* not itself backslash-escaped and *(b)* immediately followed by a substitution target, with the sentinel `mYr` (`￿`, cli_inner_pretty.js:289915). This hides the escaped `$` from the substitution machinery.
2. **Substitution (unchanged).** Named args, `$ARGUMENTS[n]`, `$n`, and `$ARGUMENTS` are replaced as before (cli_inner_pretty.js:289892-289904).
3. **Post-pass (new).** If the pre-pass fired (`u`), `e = e.replaceAll(mYr, "$")` (cli_inner_pretty.js:289912) restores each sentinel to a single literal `$`.

The negative-lookbehind `(?<!\\)` means `\\$` (an escaped backslash followed by `$`) is *not* treated as an escape — only a lone `\$` is. The lookahead `(?=${l})` means `\$` is only escaped when it actually precedes a substitution target, so `\$` before ordinary text passes through untouched.

```javascript
// ============================================
// substituteSkillArgs - $-substitution with new \$ escape pre/post pass
// Location: cli_inner_pretty.js:289876-289914
// ============================================

// ORIGINAL (for source lookup):
let l = ["\\d", "ARGUMENTS", ...a.map(({ name: p }) => `${q0(p)}(?![\\[\\w])`)].join("|"),
  c = e.replace(new RegExp(`(?<!\\\\)\\\\\\$(?=${l})`, "g"), mYr),   // <-- NEW pre-pass
  u = c !== e;
e = c;
// ... named / $ARGUMENTS[n] / $n / $ARGUMENTS replacements (unchanged) ...
if (u) e = e.replaceAll(mYr, "$");                                    // <-- NEW post-pass
return e;

// READABLE (for understanding):
let targets = ["\\d", "ARGUMENTS", ...argNames.map(({ name }) => `${escapeRegex(name)}(?![\\[\\w])`)].join("|"),
  escaped = body.replace(new RegExp(`(?<!\\\\)\\\\\\$(?=${targets})`, "g"), ESCAPE_SENTINEL), // \$<target> -> ￿
  didEscape = escaped !== body;
body = escaped;
// ... run the normal $1 / $ARGUMENTS[n] / $ARGUMENTS substitutions ...
if (didEscape) body = body.replaceAll(ESCAPE_SENTINEL, "$");          // ￿ -> literal $
return body;

// Mapping: Mot→substituteSkillArgs, mYr→ESCAPE_SENTINEL("￿"), q0→escapeRegex, e→body, l→targets, c→escaped, u→didEscape
```

## 5. stdio MCP servers receive `CLAUDE_CODE_SESSION_ID` updated across `--resume` (FIX)

**Type:** fix · **Modules:** MCP (stdio transport), Session, `--resume`

### TL;DR

stdio MCP servers are spawned with `CLAUDE_CODE_SESSION_ID` in their env (this was already true). The bug was that a `--resume` **changes the session id**, but the new id wasn't being re-propagated, so stdio MCP servers (and other children) could carry the *old* session id — diverging from what hooks and Bash saw. 2.1.163 makes the resume path overwrite `process.env.CLAUDE_CODE_SESSION_ID` with the freshly minted id, so stdio MCP servers get the same id as hooks/Bash.

### How it works

**The spawn (already correct).** The stdio MCP transport builder stamps `CLAUDE_CODE_SESSION_ID: xt()` into the child env at construction (cli_inner_pretty.js:284653) — `xt()` reads the *current* session id. (In v2.1.156 this was likewise present: `CLAUDE_CODE_SESSION_ID: E$()` at v2.1.156 cli_inner_pretty.js:433127.)

**The resume fix.** On a conversation reset / resume, after minting a new conversation id, the code now refreshes the process-level env var: `if (process.env.CLAUDE_CODE_SESSION_ID) process.env.CLAUDE_CODE_SESSION_ID = xt();` (cli_inner_pretty.js:476576-476578). Because `xt()` now returns the resumed session's id, any stdio MCP server spawned after the resume (and any child reading the inherited env) sees the same id hooks and Bash already use (`CLAUDE_CODE_SESSION_ID` is part of the same passthrough set, cli_inner_pretty.js:233222, 595801).

```javascript
// Location: cli_inner_pretty.js:476574-476578
// On conversation reset/resume, re-stamp the process env so children inherit the *new* session id:
if (
  (/* ...conversation_reset emitted, new conversationId minted... */,
   process.env.CLAUDE_CODE_SESSION_ID)
)
  process.env.CLAUDE_CODE_SESSION_ID = xt();   // xt() = current (resumed) session id
```

## 7. `$TMPDIR` per-uid override now applies to sandboxed commands only (FIX — regression from 2.1.154)

**Type:** fix (regression) · **Modules:** Bash/command execution, Sandbox, TMPDIR

### TL;DR

2.1.154 introduced a per-uid temp dir (`/tmp/claude-{uid}`) for sandbox socket needs, but wired the `$TMPDIR` override onto **every** command rather than only sandboxed ones. That broke toolchains that are sensitive to `$TMPDIR` — notably bazel and EDR-protected Go workflows. 2.1.163 gates the override on `shouldUseSandbox`: non-sandboxed commands keep the inherited `$TMPDIR`.

### How it works — the before/after

The fix lives in the command-runner (`runShellCommand`, `Xae`, cli_inner_pretty.js:292544) and the per-shell `getEnvironmentOverrides`. The decisive change is how the sandbox temp dir is computed and whether it's pushed to the environment:

- **v2.1.156 (the buggy shape):** the per-uid temp dir was computed **unconditionally** — `X = VL()` (v2.1.156 cli_inner_pretty.js:341626, where `VL()` = the `claude-${process.getuid()}` dir, v2.1.156:176754) — and then `process.env.CLAUDE_TMPDIR = X` was set inside the sandbox block (v2.1.156:341693) with `X` always defined. The shell `getEnvironmentOverrides` likewise stamped `o.TMPDIR = $` whenever its captured dir was truthy (v2.1.156:341544). So the override rode onto every command's env.
- **v2.1.183 (the fix):** the temp dir is computed **only when sandboxing** — `A = a ? EQe() : void 0` where `a` is `shouldUseSandbox` (cli_inner_pretty.js:292560). The env push is guarded by `if (A && !process.env.CLAUDE_TMPDIR)` (cli_inner_pretty.js:292637), and `getEnvironmentOverrides` stamps `o.TMPDIR` only when its captured dir is non-null and that dir is now sourced from `r.useSandbox ? r.sandboxTmpDir : void 0` (cli_inner_pretty.js:292478, with the powershell variant's `t = r.useSandbox ? r.sandboxTmpDir : void 0`). When a command is **not** sandboxed, `A` is `undefined`, nothing is pushed, and the inherited `$TMPDIR` survives.

```javascript
// ============================================
// runShellCommand - sandbox tmpdir is now sandbox-gated (was unconditional)
// Location (183): cli_inner_pretty.js:292560, 292637
// ============================================

// ORIGINAL v2.1.156 (buggy — unconditional):
X = VL(),                                                   // per-uid dir computed for EVERY command
// ... later, inside the sandbox block ...
if (!process.env.CLAUDE_TMPDIR) process.env.CLAUDE_TMPDIR = X;   // X always defined

// ORIGINAL v2.1.183 (fixed — sandbox-gated):
A = a ? EQe() : void 0;                                     // a = shouldUseSandbox; undefined when not sandboxed
// ... later, inside the sandbox block ...
if (A && !process.env.CLAUDE_TMPDIR) process.env.CLAUDE_TMPDIR = A;   // pushed only when A (sandbox) exists

// READABLE (for understanding):
let sandboxTmpDir = shouldUseSandbox ? perUidSandboxTmpDir() : undefined;
// ...
if (sandboxTmpDir && !process.env.CLAUDE_TMPDIR) process.env.CLAUDE_TMPDIR = sandboxTmpDir;

// Mapping: a→shouldUseSandbox, A→sandboxTmpDir, EQe→perUidSandboxTmpDir (183), VL→perUidTmpDir (156)
```

|---|---|
| **Type** | Fix (regression introduced 2.1.154) |
| **Modules touched** | Command runner, shell `getEnvironmentOverrides`, sandbox |
| **Before** | Every command — sandboxed or not — got `$TMPDIR` overridden to `/tmp/claude-{uid}`. bazel (which keys its action cache / outputs off `$TMPDIR`) and EDR-protected Go workflows (which expect a stable system temp) broke. |

## 8. Background-agent sessions keep running tasks when reattached after an update; update in the background (FOCUS — link)

**Type:** fix + improvement · **Modules:** Background agents, daemon lifecycle

Two background-agents bullets land here. (1) **Reattach after update:** background sessions in `claude agents` previously lost their running background tasks when reattached after a Claude Code update. (2) **Background update:** background-agent sessions now update to a new Claude Code version *in the background*, so opening a session after an update no longer waits on a cold restart. Both are lifecycle refinements on the daemon-fleet / binary-takeover machinery whose structure is documented in the background module. The daemon's retire/respawn lifecycle (including the `cliVersion`-equality "not-stale" short-circuit, the `respawnIfIdleStale` `trigger` parameter with its new `prewarm` trigger, and the `gFl` "detritus" inflight allowlist) is the surface these fixes touch — see the full deep-dive. These reattach/update-timing fixes are **not isolated to a single distinctive decl** in this build (they are state-machine timing within the daemon lifecycle), so no standalone anchor is asserted here.

## Summary

v2.1.163 is a **managed-fleet + extensibility-ergonomics** release. The two new *capabilities* are policy- and discoverability-oriented: `requiredMinimumVersion`/`requiredMaximumVersion` give admins a hard startup version window (with `update`/`install`/`doctor` exempted so a blocked user can still self-rescue, and unparseable bounds tolerated so a typo can't brick the fleet), and `/plugin list [--enabled|--disabled]` finally makes the installed-plugin set inspectable from the prompt. The other new surfaces are small affordances welded onto existing machinery — a `\$` escape (sentinel roundtrip) so skill bodies can emit a literal `$5`, a sanctioned `additionalContext` feedback channel for `Stop`/`SubagentStop` hooks kept *out* of the error array, a `c`-to-copy chord on `/btw`, and a `--resume` re-stamp that keeps stdio MCP server session ids in sync with hooks/Bash.

The fix band carries the practical weight. The headline is the **`$TMPDIR` regression** from 2.1.154: a sandbox-socket implementation detail (the per-uid `/tmp/claude-{uid}` dir) had leaked onto every command's `$TMPDIR`, breaking bazel and EDR-protected Go; 2.1.163 re-gates it on `shouldUseSandbox`. Around it sit a cluster of correctness fixes — `claude -p` hang and Bedrock/Vertex/Foundry-under-CI auth, Windows session-env EEXIST, a managed-permission startup race, the hook-`if:`-Bash subshell over-match, and the `$HOME` deny-rule gap — most of which are logic/timing changes with no single isolable decl, plus two background-agents lifecycle fixes that link to the [background module](../36_background_agents/README.md).
