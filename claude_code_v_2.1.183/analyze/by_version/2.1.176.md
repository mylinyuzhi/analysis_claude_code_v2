## 1. Session titles are generated in the conversation's language (BEHAVIOR)

**Type:** behavior (localization) · **Modules:** Session title generation, Settings (`language`)

### TL;DR

The auto-generated session title (the 3–7-word label shown in session lists) is now written in the language of the conversation by default. If the `language` setting is set (e.g. `"japanese"`, `"spanish"`), the title is pinned to that language; otherwise the model is explicitly told to write the title *in the language the user wrote in*, overriding the (English) few-shot examples in the system prompt. The `language` setting itself already existed in v2.1.156 (cli_inner_pretty.js:51652 in the v2.1.156 bundle; the same schema lives at cli_inner_pretty.js:56167-56169 in v2.1.183) — what changed is the **default** title-generation behavior when `language` is *unset*.

### How it works

`generateSessionTitle` (`Eue`, cli_inner_pretty.js:516571-516617) reads `language` from settings and builds a per-call language directive `o`:

- **`language` set** → `Write the title in ${language}. Keep technical terms and code identifiers in their original form.`
- **`language` unset** → `Write the title in the language the user wrote in, regardless of the language of the examples above.`

The directive is then appended to the **user** prompt (after the `<session>…</session>` block, cli_inner_pretty.js:516581-516585), not the system prompt. The result is parsed as a single-field JSON `{ title }` (json_schema output, cli_inner_pretty.js:516586-516594) and the call emits `tengu_session_title_generated` (cli_inner_pretty.js:516609). `generateSessionTitle` is invoked from the transcript-title flows at cli_inner_pretty.js:608787, 624913, 675569, 689000, 689364.

## 2. `footerLinksRegexes` — regex-matched clickable footer badges (NEW)

**Type:** feature (footer UI / settings) · **Modules:** Footer link badges, Settings (user/flag/managed only)

### TL;DR

A new `footerLinksRegexes` setting lets you declare regexes that match against turn output (tool results + assistant text); on a match, a clickable **badge** appears in the footer row, with its URL and label built from the regex's named capture groups. At most **5** badges render; newer matches displace the oldest, and `/clear` removes them. The setting is read **only** from user, CLI-flag, and managed (policy) settings — it is deliberately ignored in project `.claude/settings.json` and `.claude/settings.local.json`.

### How it works

**Step 1 — Schema.** `footerLinksRegexes` is an optional array of a discriminated union (`nQc`, cli_inner_pretty.js:56649-56669). The understood variant is `{ type: "regex", pattern, url, label? }`:
- `pattern`: regex matched against turn output.
- `url`: `{name}` placeholders filled from named capture groups (`(?<id>…)` → `{id}`), URL-encoded; the scheme must be `https`/`http` or a recognized editor/workspace deep-link scheme (`vscode`, `cursor`, `windsurf`, `zed`, `jetbrains`, `slack`, `linear`, `notion`, `figma`, …).
- `label`: badge text (also `{name}`-templated; defaults to the full match).

Unknown `type` variants are *preserved but skipped at runtime* — forward-compatible config. Invalid entries are replaced by a sentinel (`Tns`) and filtered out (cli_inner_pretty.js:56084-56089).

**Step 2 — Restricted settings source.** `footerLinksRegexes` is read via `Ogr` (cli_inner_pretty.js:58162-58169), which only walks `["policySettings","flagSettings","userSettings"]` — *not* project/local. The schema's `describe` text states this explicitly.

**Step 3 — Match + cap.** On each turn, `mUl` (cli_inner_pretty.js:598469-598472) reads the patterns; `Rvf` (cli_inner_pretty.js:598513-598517) extracts a bounded tail of turn output via `hUl` (last few user/assistant text + tool-result messages, capped at `mDo` = 65536 chars and `Mvf` = 256 messages, cli_inner_pretty.js:598519-598543) and produces badges. The merge `fDo` (cli_inner_pretty.js:598365-598393) de-dupes against existing badges and applies the cap `A8t = 5` (cli_inner_pretty.js:598402) via `.slice(0, A8t)`, displacing oldest. Invalid regex patterns are compiled defensively (`Pvf`, cli_inner_pretty.js:598457-598467) and logged + telemetered (`repl_footer_links` / `invalid_pattern`) rather than crashing.

## 3. Bedrock `awsCredentialExport` credentials cached until their `Expiration` (IMPROVEMENT)

**Type:** improvement (credential caching) · **Modules:** AWS/Bedrock auth

### TL;DR

When AWS credentials come from a user `awsCredentialExport` script (a script that prints STS output), Claude Code now caches them **until the `Expiration` timestamp the script returns**, instead of a fixed 1-hour TTL. The export function parses `Expiration` into an epoch and the credential-resolve cache uses a *dynamic* lifetime derived from it.

### How it works

**Step 1 — Export returns expiry.** `z8u` (cli_inner_pretty.js:135265-135302), the export runner, now reads `r.Expiration`, parses it (`Date.parse`), and returns `expiration: Number.isFinite(s) ? s : void 0` alongside the access/secret/session keys (cli_inner_pretty.js:135288-135295).

**Step 2 — Dynamic cache lifetime.** The AWS credential resolver `n4` (cli_inner_pretty.js:136419-136434) is built with `j$e(producer, lifetimeFn)`. The memoizer `j$e` (cli_inner_pretty.js:47367-47403) supports a **function** as its second argument and stores a per-value `lifetimeMs = lifetimeFn(value)` (cli_inner_pretty.js:47382, 47394). The lifetime function computes `remaining = expiration - Date.now()`; if there's no expiration or it's already within `Mti + G8u` (300000 + 60000 = 6 minutes) of expiring, it falls back to `j8u` (3600000 = 1 hour); otherwise it caches for `remaining - Mti` (i.e., until ~5 minutes before the real expiry, cli_inner_pretty.js:136428-136433).


| **Before** (v2.1.156, cli_inner_pretty.js:131125-131132, 132095-132102) | The export runner returned only `{ accessKeyId, secretAccessKey, sessionToken }` (no expiration), and the resolve cache `Og = LGH(producer, MH5)` used a **fixed** `MH5 = 3600000` (1-hour) TTL. That one generalization is what lets the cache key its TTL off data the producer returns (the parsed `Expiration`) rather than a compile-time constant.

## 4. `availableModels` allowlist closes the alias / `ANTHROPIC_DEFAULT_*` / `/fast` bypasses (FIX)

**Type:** fix (managed-settings / model policy) · **Modules:** Model allowlist enforcement, `/fast`, model aliases

### TL;DR

Building on v2.1.175's `enforceAvailableModels` (see [`../by_version/2.1.175.md`](2.1.175.md)), 2.1.176 closes two ways the allowlist could be circumvented:

1. **Alias redirection via `ANTHROPIC_DEFAULT_*_MODEL`.** An alias pick (`sonnet`/`opus`/`haiku`/`fable`/…) that *appears* in the allowlist could previously resolve — through `ANTHROPIC_DEFAULT_SONNET_MODEL` / `…_OPUS_MODEL` / `…_HAIKU_MODEL` / `…_FABLE_MODEL` env vars — to a concrete model the admin had **blocked**. Now the allowlist check resolves the alias *with* those env vars and re-validates the resolved target.
2. **`/fast`.** The `/fast` toggle (whose model is Opus, `n1e()`) now **refuses** to toggle when Opus isn't in the allowlist, surfacing *"{model} is not in your organization's allowed models"* instead of silently switching to a non-allowlisted model.

### How it works

**Alias redirection.** `isModelAllowed` (`ul`, cli_inner_pretty.js:102242-102291) is the allowlist gate. The alias-aware predicate `PM` (cli_inner_pretty.js:102180-102182) recognizes `["sonnet","opus","haiku","fable","best","sonnet[1m]","opus[1m]","fable[1m]","opusplan"]`. When a candidate matches an allowlist entry, `ul` no longer accepts it unconditionally — it requires `t?.envFreeAliasResolution || !PM(s) || Dun(s, t)` (cli_inner_pretty.js:102256, mirrored at 102273). `Dun` (cli_inner_pretty.js:102235-102240) resolves the alias **respecting** the `ANTHROPIC_DEFAULT_*_MODEL` env vars and re-runs `ul` on the resolved concrete model. So an alias whose env-var target is blocked now fails the check; the `envFreeAliasResolution` flag is the explicit opt-out used by callers that want the *literal* alias judged (e.g. enforcement-state computation in `NN`/`isModelAllowedUnderActiveEnforcement`, cli_inner_pretty.js:102797-102806).

**`/fast` refusal.** `Uoe` (the "fast mode unavailable" reason, cli_inner_pretty.js:101665-101701) now includes:

```javascript
// Location: cli_inner_pretty.js:101672-101678
if (!ul(n1e())) {                       // n1e() = "opus" (or "opus[1m]") — the fast-mode model
  let n = Gs();                         // current resting model
  if (!(!jE() && TA(n) && ul(n))) {     // …and no allowed fallback already active
    let o = `${s4()} is not in your organization's allowed models`;  // s4() = "Opus 4.8"
    return (v(`Fast mode unavailable: ${o}`), o);
  }
}
```

When the fast-mode model (Opus) isn't allowed and there's no already-allowed fallback, `/fast` returns the refusal string and does not toggle.

## 5. Auto-mode classifier falls back to best-available Opus when Fable 5 lacks Opus 4.8 (FIX)

**Type:** fix (auto mode) · **Modules:** Auto-mode permission classifier, model resolution

### TL;DR

Auto mode (the model-classifier permission mode) was failing on **Fable 5** for organizations that don't have **Opus 4.8** enabled — the classifier hard-required Opus 4.8. The classifier-model resolver now walks an ordered Opus preference list and picks the **first Opus model the org actually has access to**, instead of unconditionally demanding Opus 4.8.

### How it works

The auto-mode classifier model is chosen by `DMa` (cli_inner_pretty.js:370244-370260). For a Fable-family (`pT`, cli_inner_pretty.js:102447-102449) or Mythos-family (`iwt`, cli_inner_pretty.js:102450-102452) main model, it routes through `awt` (cli_inner_pretty.js:102453-102461) — the "resolve the classifier's Opus model" helper:

## 6. Hook `if` conditions for Read/Edit/Write tool paths now match documented patterns (FIX)

**Type:** fix · **Modules:** Hooks (conditional `if`), tool path matching

**Before:** A hook with an `if` condition keyed on a tool path pattern — e.g. `Edit(src/**)`, `Read(~/.ssh/**)`, `Read(.env)` — did not match correctly for Read/Edit/Write tools, so path-scoped hooks silently failed to fire (or fired when they shouldn't).

**After:** The documented patterns — glob (`src/**`), home-relative (`~/.ssh/**`), and exact-file (`.env`) — now match the actual tool input path for Read/Edit/Write. The hook `if` matcher routes Read/Edit/Write through the same path-pattern matcher the permission rules use (the `Tool(pathPattern)` form), so the documented examples resolve consistently with permission rules.

**Why:** Hook `if` conditions and permission rules share the same documented `Tool(pattern)` syntax; users reasonably expect a pattern that works in `permissions` to work in a hook `if`. The mismatch made path-scoped hooks (a common "run a secret-scanner before any `.env` write" use case) unreliable. This is a matcher-routing fix with no single distinctive isolable declaration string in this build — it lives inside the shared hook-condition evaluator that delegates Read/Edit/Write to the path matcher; **not isolated to a single grep-able decl** (medium confidence on exact site).

## 7. Linux sandbox starts when `.claude/settings.json` is a symlink with an absolute target (FIX)

**Type:** fix (sandbox) · **Modules:** Linux sandbox (bubblewrap), settings resolution

**Before:** When `.claude/settings.json` was a **symlink whose target is an absolute path**, the Linux sandbox failed to start — the sandbox's filesystem allowlist resolved the symlink's absolute target outside the bind-mounted set, so reading settings inside the sandbox failed.

**After:** The sandbox accounts for the absolute symlink target (binding/allowing the resolved real path), so settings load and the sandbox starts normally.

**Why:** Dotfile managers (chezmoi, GNU stow, bare-repo dotfiles) routinely symlink `.claude/settings.json` to an absolute path in a managed store. A sandbox that refuses to start in that very common configuration is effectively broken for those users. This is a path-resolution fix inside the sandbox mount/allowlist setup with no isolable single-string anchor in this build — **not isolated to a single decl** (medium confidence).

## 8. Clipboard / tmux fixes for `/copy` and mouse-selection over SSH (FIX)

**Type:** fix (clipboard) · **Modules:** Clipboard (OSC 52 / tmux), copy-on-select

**Before:** Inside **tmux over SSH**, `/copy` and mouse-selection copy did not reach the system clipboard, and the tmux paste buffer failed to load on **tmux versions older than 3.2**.

**After:** `/copy` and copy-on-select now reach the system clipboard inside tmux over SSH (via the appropriate OSC 52 / `tmux load-buffer` path), with a fallback for tmux < 3.2 paste-buffer loading.

**Why:** tmux intercepts the terminal's clipboard escape sequences; over SSH there's no local clipboard daemon, so OSC 52 (or `tmux set-buffer`) is the only path to the user's real clipboard, and pre-3.2 tmux handles the paste buffer differently. Copy that silently no-ops is a frustrating, hard-to-diagnose failure. This is a terminal-capability/escape-sequence fix with no single isolable decl — **not isolated to a single decl**.

## 9. Remote Control fixes (FIX)

**Type:** fix · **Modules:** Remote Control (web/mobile)

Four Remote Control corrections, grouped:

- **Connecting from web/mobile no longer silently switches the session's model.** Previously, attaching a Remote Control client could override the running session's model selection without telling the user.
- **Disconnect notifications show a human-readable reason** instead of a bare numeric code, and a connection failure **no longer adds a duplicate line** to the conversation transcript.
- **Remote Control sessions disconnect when you sign in to a different account** — a session bound to account A no longer keeps a live Remote Control link after you switch to account B (a session-identity/auth-binding fix).

**Why:** Remote Control is a trust-sensitive bridge (a second device driving your local session). Silently changing the model, leaking raw protocol codes, double-logging failures, and keeping a link alive across an account switch are all correctness/trust gaps. These are protocol-handler and notification-rendering fixes spread across the Remote Control transport; no single decl isolates the batch — **not isolated to a single decl** for the group.

## 10. `/cd` and worktree moves no longer report the previous directory's git branch (FIX)

**Type:** fix · **Modules:** `/cd`, worktree move, git state

**Before:** After `/cd` or a worktree move, the session kept reporting the **previous** directory's git branch in its status — the cached git context wasn't invalidated on directory change.

**After:** Changing directory (`/cd`) or moving worktrees refreshes the git context so the reported branch matches the new working directory.

**Why:** The footer/status branch indicator is a frequent reference point; showing a stale branch after `/cd` is actively misleading (you might commit thinking you're on the wrong branch). This is a cache-invalidation fix on the directory-change handler — a timing/state fix with no isolable distinctive string — **not isolated to a single decl** (medium confidence).

## 11. `claude agents`: pressing back in one window no longer detaches sibling windows (FIX)

**Type:** fix · **Modules:** `claude agents` (multi-window attach), Background sessions

**Before:** When multiple windows were attached to the same background session, pressing **back** in one window detached the **other** windows too — the back action operated on shared session state instead of the per-window attachment.

**After:** Back detaches only the window that issued it; sibling windows attached to the same session stay attached.

**Why:** Multiple attached windows are an intended workflow (watch a long-running agent from two terminals). One window's navigation collapsing all of them is a state-scoping bug. This sits in the agent-view attach/detach state machine covered by `../36_background_agents/`; **not isolated to a single decl** here (medium confidence).

## 12. Background-session reliability batch (FIX) — FOCUS: background

**Type:** fix (background agents) · **Modules:** Background agents / `claude agents` / daemon

These touch the **background-agents focus feature**. They are deep daemon/respawn/Windows internals; the authoritative re-derivation of the `/bg` command surface and the daemon retire/respawn delta is [`../36_background_agents/bg_command_surface_and_retire_delta.md`](../36_background_agents/bg_command_surface_and_retire_delta.md), with worker env-isolation in [`../36_background_agents/worker_env_isolation_2181.md`](../36_background_agents/worker_env_isolation_2181.md). Summary + verified anchors:

- **`/bg` mid-turn "Working" forever with nothing to continue.** A session backgrounded mid-turn that had nothing left to continue could show "Working" indefinitely. *(Closely related to the 2.1.178 "Working forever" fix; the bg module doc carries the `/bg` fork flow in `sKn`/`iKn` — `spawnBackgroundFork` (`sKn`) at cli_inner_pretty.js:566835 and `deriveBackgroundSeed` (`iKn`) at cli_inner_pretty.js:566927. The exact mid-turn-with-nothing-to-continue guard is **not isolated to a single decl** — see the doc's open-questions note.)*
- **Background agent search by PR URL.** PRs opened during scheduled wakeups or while a job was blocked now appear in `claude agents` search (the PR/artifact index now ingests PRs created in those previously-missed states).
- **Agents-view input shows a text cursor on Windows.** The dispatch input was rendering with no caret on Windows; fixed (a TUI/Ink cursor-rendering fix specific to Windows input).
- **`claude --bg -cn <name>` now seeds the session name.** The `-cn`/custom-name flag was parsed but not threaded into the seeded session name. Per the module doc (cli_inner_pretty.js:794 note in `bg_command_surface_and_retire_delta.md`), the seed flows through the env-builder `_Fl` (`CLAUDE_CODE_SESSION_NAME: seed?.name || seed?.intent || short`); the fix lives in the `--bg` arg-parsing region near `XAf = ["--bg","--background"]` (cli_inner_pretty.js:566831) — **not isolated to a single decl**.
- **Windows network paths neutralized in persisted state before respawn.** Background sessions now sanitize Windows UNC/network paths in their persisted state before respawning the worker, so a respawn from a network-path working dir doesn't choke.
- **Respawn rejects malformed resume IDs from corrupted state files.** A corrupted state file with a malformed resume ID no longer crashes respawn; the malformed ID is rejected cleanly.
- **Windows background-service daemon starts when `~/.claude/daemon` has the ReadOnly attribute.** The Windows daemon failed to start if the daemon dir carried the ReadOnly file attribute; fixed.
- **Cloud sessions no longer fail with "Could not resolve authentication method" when idle too long before being claimed** (cli_inner_pretty.js:8415 carries the SDK error string). An idle-too-long cloud session re-resolves auth on claim instead of erroring.
- **Version-skew guidance.** A window left open across an auto-update that can't submit a reply now shows clearer guidance, and `claude daemon status` explains version-skew behavior. The daemon-status surface renders `claude daemon status` guidance (cli_inner_pretty.js:492226), and the daemon zombie/skew detector computes `version_skew` by comparing the running daemon's version against the current build's `VERSION` (cli_inner_pretty.js:564119-564140); the `[bg-pty] … host dropped input … (version skew; respawn the worker to re-key)` message at cli_inner_pretty.js:594357 is the worker-side skew signal.

**Why (group):** This is the by-now-familiar background-agents hardening arc — Windows path/attribute/IME quirks, respawn robustness against corrupted state, cloud-session auth re-resolution, and making version-skew (a daemon running an older binary than the foreground process) legible rather than mysterious. The daemon binary-takeover and retire/respawn machinery these ride on is documented in `../36_background_agents/`.

## Summary

v2.1.176 is a **localization + auth/credential-routing + background-stabilization** release. The one new *surface*, `footerLinksRegexes`, turns regex matches over turn output into up to five clickable footer badges, fenced by a fixed user/flag/managed settings source and an https/editor-deeplink scheme allowlist — a deliberately security-conscious design for a feature that builds clickable links from model/tool output. Session titles now read back in the user's own language by default (a one-line *else* branch plus moving the directive into the user prompt).

The two policy/credential items carry the weight. The **Bedrock `awsCredentialExport`** cache stops guessing with a fixed 1-hour TTL and instead honors the STS `Expiration` (refreshing ~5 minutes early), enabled by generalizing the memoizer to accept a per-value lifetime function. The **`availableModels`** work hardens the v2.1.175 allowlist into a real boundary: an allowlisted alias can no longer be re-pointed to a blocked model via `ANTHROPIC_DEFAULT_*_MODEL`, and `/fast` refuses to toggle to a non-allowlisted Opus. The **auto-mode classifier** stops hard-requiring Opus 4.8 and degrades gracefully down the Opus ladder (gated by the same allowlist), unblocking auto mode on Fable 5 for orgs a model behind.

Everything else is the familiar **background-agents + cross-cutting reliability** sweep — Windows network-path/ReadOnly-attribute/IME/cursor quirks, respawn robustness against corrupted state, cloud-session auth re-resolution, version-skew legibility (`claude daemon status`), plus Remote Control trust fixes, tmux-over-SSH clipboard, `/cd` branch staleness, hook `if` path matching, and an absolute-symlink Linux-sandbox fix.
