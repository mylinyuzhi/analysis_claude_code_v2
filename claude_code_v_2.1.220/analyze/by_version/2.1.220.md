## 1. Release narrative

**2.1.220 is a contentless release note, and that is a fact about the note, not about the build.** The
single bullet — *"Bug fixes and reliability improvements"* — makes no scoped claim, names no surface,
and cannot be falsified. There is no literal to grep, no gate to read, no settings key to trace.

The structural problem is sharper than "the bullet is vague". **`2.1.220` is the target bundle of this
entire analysis tree, and the nearest available baseline is `2.1.193`** — 25 published releases earlier
(`/lyz/codespace/claude-code-bomb/versions/` holds `2.1.132 2.1.142 2.1.156 2.1.183 2.1.193 2.1.220`
and nothing between). A `.219` bundle does not exist here. Therefore **anything `.220` changed relative
to `.219` is, by construction, invisible**: every delta a `193 → 220` diff can see is attributable to
*some* release in the window, and nothing in the diff carries a release stamp. Any claim of the form
"this line is the `.220` fix" would be invention. This file makes no such claim.

What `.220` *can* be documented as is an **endpoint**, and three things follow from that:

1. **Every anchor in this tree is a `.220` anchor.** The 24 bullets of
   [`2.1.219`](./2.1.219.md), the 47 of `.214`, the 48 of `.212` — all of them are verified against
   *this* build. Read the other `by_version/` files and you are reading `.220`'s contents; the release
   boundaries are changelog metadata layered over a single artefact.
2. **`.220` is the last build that can ever display the Opus 4.7 fast-mode sunset notice**, and its
   display window was **under two hours** (§4.2). That is the only piece of behaviour in this build
   whose lifetime is pinned to `.220` specifically.
3. **`.220` demonstrably did *not* fix several things the changelog claims are already fixed** (§4.3).
   For a release whose whole content is "bug fixes", the set of surviving changelog↔code contradictions
   is the most informative thing that can honestly be said about it.

**Position in the window.** This is the sixth single-bullet release of the 25 (`.197 .201 .204 .209
.215 .220`), and the only one whose bullet has no subject. The other five were each a specific, findable
thing — a model launch (`.197`), a hotfix that was later reverted (`.201`, see
[`../40_system_prompt/mid_conversation_system_role.md`](../40_system_prompt/mid_conversation_system_role.md)),
a headless hook-streaming fix (`.204`), a revert of an over-broad dialog guard (`.209`), and a
skill self-invocation stop (`.215`). `.220` is the pattern's degenerate case: a release cut roughly one
day after `.219` — which was a same-day model launch — with no user-visible surface worth naming. The
shape is consistent with a launch-follow-up build, but *consistent with* is as far as the evidence goes.

## 4. Deep dives

### 4.1 Build identity is the only first-party evidence — and it is inlined 226 times

**What it does:** stamps the binary with an immutable `{VERSION, BUILD_TIME, GIT_SHA}` triple and makes
it readable at runtime by the user, the SDK, telemetry, and the API.

**How it works:**

1. The build constants are a plain object literal, **not** a module-level variable. The bundler inlines
   the whole eight-key object at **every** reference site: `grep -c 'VERSION: "2.1.220"'` = **226**, and
   `GIT_SHA` matches at exactly the same count. That is why `2026-07-24` appears 226 times in the file.
2. The canonical declaration site is `:223-231`:

```javascript
// ============================================
// BUILD_CONSTANTS - the inlined build-identity object (one of 226 identical copies)
// Location: cli_inner_pretty.js:223-231
// ============================================

// ORIGINAL (for source lookup):
{
  ISSUES_EXPLAINER: "report the issue at https://github.com/anthropics/claude-code/issues",
  PACKAGE_URL: "@anthropic-ai/claude-code",
  README_URL: "https://code.claude.com/docs/en/overview",
  VERSION: "2.1.220",
  FEEDBACK_CHANNEL: "https://github.com/anthropics/claude-code/issues",
  BUILD_TIME: "2026-07-24T22:17:45Z",
  GIT_SHA: "4073f59596e272f39393db4f96abc5f4b10eff21",
  DD_SOURCEMAP_GROUP: "default",
}.BUILD_REF_NAME

// READABLE (for understanding):
BUILD_CONSTANTS.BUILD_REF_NAME     // note: BUILD_REF_NAME is NOT a key of the object -> undefined

// Mapping: (no obfuscation — a build-time constant fold, re-emitted at each use site)
```

   Note the tail: `.BUILD_REF_NAME` is read from an object that has no such key, so this particular
   site evaluates to `undefined` — a harmless artefact of the same constant-fold being applied to a key
   the build pipeline no longer emits.

3. **Where the identity actually surfaces**, each re-read in this build:
   - **User-agent strings** — `claude-code/${VERSION}` (`SS`, `:176-178`),
     `claude-cli/${VERSION} (external, …)` (`:108993`), `claude-code/${VERSION}${t}` (`:109001`), plus a
     dash-versioned artefact-name builder `claude-code_${VERSION.replace(/\./g, "-")}_${e}`
     (`tbi`, `:210-212`).
   - **The headless stream-json init event** — `claude_code_version: {…}.VERSION` at `:593603-593612`,
     inside the same `tAr()` builder that gained `mcp_server_errors` in `.219`.
   - **OpenTelemetry resource attributes** — `version: n.version, build_time: n.buildTime` at
     `:152382-152383`, populated from the inlined constants at `:152598` / `:152605-152613`.
   - **The `--remote` `/version` control request** — `get_binary_version` returns
     `{ version: string, buildTime?: string }` (`:838818-838823`), *"so the thin client can show both
     its own and the remote container's version"*.
   - **A version-floor gate** — `Nsu()` at `:164315-164348` refuses to enable error reporting unless
     `semver.gte(VERSION, qMg)` where `qMg = "2.1.193"` (`:164352`), then requires
     `bZi().startsWith("allowed")` and the gate `tengu_orford_ness` (`:164351`). A build older than
     2.1.193 self-excludes from crash reporting.

**Why this approach:** inlining the triple rather than importing a shared constant means no module in
the graph can be loaded without also carrying the identity — there is no code path that can report a
version and no path that can report the *wrong* version. The cost is 226 copies of a ~450-byte object,
about 100 KB of the 29 MB bundle. For a product whose entire support workflow starts with "what version
are you on", trading 0.3% of bundle size for an unspoofable, always-present stamp is a reasonable deal.

**Key insight for this tree:** `build_time` is an **OTel resource attribute**, not just a display
string. Anthropic can slice every metric by build. That is precisely the instrumentation a release whose
only claim is "reliability improvements" would be validated with — the release note is vague because the
*evidence* for it is a dashboard, not a feature.

### 4.2 The one behaviour whose lifetime is pinned to this build

`getOpus47FastModeSunsetDate` (`LIc`, `:109491-109498`) returns `null` once
`Date.now() >= Date.parse(getFeatureValue("tengu_sunset_penguin_opus47", "2026-07-25"))`. The gate
default is the date-only string `"2026-07-25"`, which ECMAScript parses as **UTC midnight** —
`2026-07-25T00:00:00.000Z`.

| | value |
|---|---|
| `BUILD_TIME` (`:228`) | `2026-07-24T22:17:45Z` |
| sunset threshold (`:109493`, default) | `2026-07-25T00:00:00Z` |
| **displayable window from build** | **1 h 42 min 15 s** |

Its caller `ZFo()` (`:499782-499790`) builds the banner
`{ key: "opus47-fast-mode-deprecation", text: "Opus 4.7 fast mode is deprecated and will be removed on <date>", priority: "immediate", color: "warning" }`.

So: **2.1.220 is the last build that can ever render this notice, and it could only do so for the first
~102 minutes of its existence** (absent a server override moving the gate date forward). Anyone reading
this build today sees nothing at all — which is the practical lesson: **reason from the constant, never
from observed behaviour.** Full analysis in [`2.1.219.md`](./2.1.219.md) §4.2, and a correction to
[`../_GROUND_TRUTH_verified_anchors.md`](../_GROUND_TRUTH_verified_anchors.md) §6.2b's "~26 hours"
figure is recorded there.

**Why this is the right framing:** a "bug fixes" release invites the reader to assume the ledger is
clean by now. It is not. Five of these six are claims made **before** `.220` that `.220` had the
opportunity to make true and did not — and the sixth (`.208`'s screen-reader mode) was never true in the
direction the bullet implies. Documenting the surviving set is the only way a contentless release note
can be held to account.

**Key insight:** the correct reading of "Bug fixes and reliability improvements" is *"no user-visible
surface changed enough to name"*, not *"the outstanding issues were resolved"*. Nothing in this build
supports the stronger reading.

## 5. What the changelog does not say

### 5.1 Three structural changes shipped in this window with no bullet at all

All three are visible in this build and none is mentioned anywhere in the 579 bullets:

- **The model registry was rewritten** from scattered camelCase per-model objects
  (`:95696-95702 (193)`) into a single build-validated declarative catalogue at `:14009-14496`, carrying
  its own doc comment at `:14009` and a `bun run generate:model-catalog` provenance note. New key
  families: `provider_ids` (22 sites), `knowledge_cutoff` (16), `advisor_rank` (12),
  `latest_per_family` (4), `supports_1m_suffix` (13) — all **193=0**. →
  [`../47_models/model_catalogue_rewrite.md`](../47_models/model_catalogue_rewrite.md)
- **`anthropic_google_cloud` is a whole new provider channel**, present in every catalogue entry and in
  `CLAUDE_CODE_USE_ANTHROPIC_GOOGLE_CLOUD`. →
  [`../47_models/anthropic_google_cloud_channel.md`](../47_models/anthropic_google_cloud_channel.md)
- **Two complete MCP runtime trees ship side by side** (`v1` default, `v2` opt-in), selected by
  `MCP_SDK_GENERATION` (220=3 / **193=0**, validator message at `:262852`) with the `MCP_TREE_ID`
  tripwire at `:302431` and the gate `tengu_brindle_causeway`. →
  [`../39_mcp/dual_mcp_runtime_trees.md`](../39_mcp/dual_mcp_runtime_trees.md)

A fourth candidate lives in the catalogue itself: `claude-mythos-5` at `:14439`, whose
`provider_ids` are `null` for **every third-party channel** (only `first_party` survives) with
`capabilities: []`, yet which is special-cased **by name** in `supportsMidConversationSystem` at
`:150524`. An unannounced family, shipped inert.

> ⚠ **But it is not NEW, so it does not belong with the three structural changes above.** `grep -cF`
> gives **220=25 / 193=31** — the count *fell*. 2.1.193 already carried the family **with third-party
> ids populated** (`firstParty`/`bedrock: "us.anthropic.claude-mythos-5"`/`vertex` at
> `:95716-95718 (193)`). This window therefore **de-provisioned** it rather than introducing it. The
> inertness is the finding; the novelty is not. See `_GROUND_TRUTH_verified_anchors.md` §1.

### 5.2 The final build carries an armed-but-empty migration slot

`applyModelAliasMigration` (`rTm`, `:833732-833744`) runs at every first-party startup (`:834073`) and
rewrites a pinned `userSettings.model` — preserving any `[1m]` suffix — for any id present in its
migration map. The map, `qlE`, is `{}` (`:833753`). The catalogue's matching `alias_migration` field is
also `{}` (`:14495`, schema default `:14640`) and **no code reads it**. A release that changed what
`opus` resolves to shipped the machinery to migrate pinned users, disarmed, in both halves. Detail in
[`2.1.219.md`](./2.1.219.md) §5.1.

### 5.3 The tree's own scale is the honest summary of what `.220` contains

Rather than guess at `.220`'s diff, the measurable statement is what the endpoint holds:
**+153,917 lines (+21.4%)** over 2.1.193 (718,679 → 872,596); **65** tool entries in
`assets/tools/_index.json` (was 50); **1,731** feature-gate/event names (326 net-new by the raw asset
diff); **578** bundled prompts; **17** catalogue model ids; **8** provider channels. That is the shape
of 25 releases, and the last of them added the line "Bug fixes and reliability improvements" to it.
