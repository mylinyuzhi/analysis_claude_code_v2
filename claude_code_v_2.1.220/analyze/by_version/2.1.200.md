## a) What this release was for

`2.1.200` is the release where **two defaults stopped being defaults**. `AskUserQuestion` no longer
auto-continues when the user does not answer, and the permission mode formerly displayed as `Default`
is now displayed as `Manual`. Both changes are about the same underlying discomfort: a coding agent that
had been quietly *proceeding* — past an unanswered question, and under a mode whose name implied
"nothing special is happening" — while the user believed they were still in control. Neither change
alters a wire value. `askUserQuestionTimeout` defaults to `"never"` (`cli_inner_pretty.js:61218-61225`),
and the permission mode's `external` field is still `"default"` on every row of the display table
(`:58502`). The release is a **relabelling and de-automating** release, deliberately implemented so that
no existing settings file, SDK client, or CI config breaks.

The second half of the release is the continuation of the background-agent repair queue that `.198`
opened and `.199` carried. Six of the seventeen bullets (`#4`–`#8`, `#10`) are daemon, roster, or worker
fixes, and three of them are *identity* fixes in the strict sense: a `daemon.lock` whose PID the OS
recycled (`#6`), a reinstalled older build taking over the daemon (`#7`), and a roster whose fields an
older binary silently dropped (`#8`). The common shape is that 2.1.193 answered "is this the right
process / build / record?" with a single weak signal (a live PID, a version string, a strict schema), and
2.1.220 answers it with a **composite identity check that fails closed**: PID + `/proc` cmdline +
process start time (`QH`, `:664794-664804`), a build-timestamp comparator that round-trips its own format
before trusting it (`rUt`, `:552453-552467`), and a loose roster schema that preserves unknown fields.

The third strand is accessibility and terminal correctness — `#10` (control bytes escaping into the
agent view), `#13` (`/mcp` list focus), `#15` (tmux synchronized output), `#16` (screen-reader table
reading). `#15` and `#16` are the two bullets in this release with real rendering substance, and `#15` is
the cleanest single-line delta in it: 2.1.193 refused synchronized output under tmux outright
(`if (process.env.TMUX) return !1;` `:160038 (193)`), 2.1.220 *probes* for DECRQM mode 2026 and answers
`tho === !0` (`:253386`) — three states instead of two, with an `undefined`-while-probing wrapper
(`f2u`, `:253380-253383`).

Relative to its neighbours: `.199` and `.200` are one continuous stabilisation queue, split at a release
boundary rather than a topic boundary — bullet `.199 #6` (Linux daemon suicide) and bullet `.200 #6`
(stale lock, reused PID) are the same class of bug in the same subsystem. `.201`, the next release, is a
single-bullet model hotfix with no connection to either.

**What it does:** turns "how long do we wait before answering the question ourselves" from a hardcoded
behaviour into a four-valued user setting whose default disables the behaviour entirely.

**How it works:**

1. `askUserQuestionTimeout` is **220=9 / 193=0**, so the entire surface — schema field, `/config` row,
   resolution, telemetry — is new. There is no 193 setting to compare against; in 193 the auto-continue
   was unconditional.
2. Resolution is a three-level fallback at `:451893`: **explicit project/user setting → policy default
   (`TCe()`) → `"never"`**. Note the policy hook sits *between* the user's choice and the hard default,
   so an organisation can turn auto-continue back on for its fleet without touching each user's settings,
   and a user can still override it locally.
3. `.catch(void 0)` on the zod field is the interesting defensive choice: a settings file containing
   `"askUserQuestionTimeout": "30s"` does not fail validation and does not abort settings loading — it
   collapses to `undefined`, which the `??` chain then resolves to `"never"`. **A malformed value fails
   toward the safe behaviour** (do not auto-answer), not toward a crash and not toward the old behaviour.
4. `onChange` writes optimistically to local state *before* awaiting the settings write, then bails with
   `{ error }` if the write fails. The event is emitted only on a successful write, so
   `tengu_ask_user_question_timeout_changed` (**220=1 / 193=0**) counts durable changes, not clicks.

**Why an enum of four discrete values rather than a number of seconds?** Three reasons are visible in the
code. (a) The `/config` panel row is `type: "enum"` — a numeric field would need validation UI that the
panel does not have. (b) `.catch(void 0)` only works cleanly on a closed set; an unbounded number would
need range checking with its own failure mode. (c) The values are coarse on purpose — `60s / 5m / 10m` are
"I stepped away for a moment / a coffee / a meeting", which is the actual decision the user is making.
The setting is a **policy choice, not a tuning parameter**, and the type reflects that.

**Why `never` is the default, stated as a trade-off:** auto-continuing costs the user a wrong answer they
did not give; not auto-continuing costs a background or headless session that stalls forever. Two
sibling gates in the same family — `tengu_ask_user_question_afk_auto_advance` (`:767111`) and
`tengu_ask_user_question_skipped` (`:766944`), both **220=1 / 193=0** — show the second cost was handled
separately, by an away-from-keyboard path in the remote/web surface rather than by a global timeout.
Splitting the problem that way is what made `"never"` affordable as the default.

**Key insight:** the changelog frames this as "changed a default". The code shows it is a *new subsystem*
— nine sites, three gates, a policy hook, and a settings row — built specifically so that the default
could be changed without stranding the headless and web surfaces that genuinely need auto-advance.

**What the two guards each answer:**

| guard | question | bullet |

| `callerSawTail` (`g`, `:320208-320209`) | "has the caller already seen this exact tail message?" | **#5** — the Esc case |

**How `#5` works.** When a user presses Esc, the turn is cancelled but the transcript tail does not
change. If the worker is then respawned by a stall detector, the deserialiser sees an
`interrupted_turn` and would helpfully re-submit it. The caller passes the uuid of the last
user/assistant message it already knew about; if that uuid still matches the tail, **nothing new
happened**, so the interruption is not a fresh one and no replay is warranted. Note it is compared
against `findLast(user || assistant)` — deliberately skipping `system` and `progress` entries, which the
harness writes without user involvement.

**How `#4` works.** `isInterruptedTurnTooOld` walks the transcript backwards and stops at the first entry
that is neither `system` nor `progress`, then compares its timestamp against the max-age. Three details
carry the design:

1. **Unset means disabled, not "use the default".** `if (!t) return !1` at `:320148` — with no
   `CLAUDE_CODE_RESUME_INTERRUPTED_TURN_MAX_AGE_MS` the age check never fires and the pre-`.200`
   behaviour is preserved exactly. The worker sets the variable explicitly, and only for
   `interactiveLineage` sessions — a human-driven session gets the 1-hour rule, a task-contract session
   does not.
2. **Garbage parses to one hour, not to disabled.** `Number.isFinite(r) && r > 0 ? r : 3600000` at
   `:320151`. A malformed value fails *toward* suppression, i.e. toward not replaying.
3. **No timestamped real message at all returns `true`** (`:320158`) — stale by default. An
   untimestamped transcript is unverifiable, so it is treated as unsafe to replay.

**Why two guards instead of one age check?** Because they fail in opposite directions. The age check
alone would still replay an Esc-cancelled turn that happened five seconds ago. The uuid check alone
would still replay a genuinely interrupted turn from yesterday's laptop-sleep, which is `#4`'s bug. Each
covers the other's blind spot, and the combination is `if (g || y) → { kind: "none" }` at `:320213`.

**Why `tooOld` is computed as `!callerSawTail && …`:** short-circuit ordering. The uuid comparison is a
single array scan and a string compare; the age check parses an env var and a date. Ordering the cheap,
more-specific test first also means `tengu_resume_stale_turn_suppressed` (`:320211`, **220=1 / 193=0**)
never fires for the Esc case — the two suppression reasons stay distinguishable in telemetry, which is
the only way to tell afterwards which of the two bugs a fleet is actually hitting.

**Key insight and the trap:** `CLAUDE_CODE_RESUME_INTERRUPTED_TURN` is **220=18 / 193=8** — the env var,
and the whole resume-the-interrupted-turn feature, are **carryover**. What `.200` adds is two ways to say
*no*. A count-based read of this bullet finds a big delta on the env var and attributes the feature to
`.200`; the honest reading is that `.200` fixed a pre-existing feature that was too eager.

**What broke in 2.1.193:** `:280996 (193)` read `(t.disabledMcpServers || []).includes(e)`. The `||`

during MCP server enumeration at startup, the throw becomes a startup crash.

when no change is needed, which is the standard "don't write" signal. But if the stored value was
`{"foo": true}`, `asArrayOrEmpty` produced a fresh `[]` and `toggleMembership` returned that same `[]` by
identity — so the "no change" test would pass and **the illegal value would stay on disk forever**,
crashing every older build that reads it. The extra clause `&& (a === void 0 || Array.isArray(a))` at
`:282798` says: treat "no membership change" as a no-op *only if the stored value was already legal*.
Otherwise write the coerced array, which repairs the file.

**Key insight:** the read-side coercer stops the crash; the write-side condition stops the *bad data*.
Only the second one makes the fix permanent, and it is the half a "just add `Array.isArray`" patch would
have missed.

## d) What the changelog does not say

**1. The "Manual" rename never touched the wire.** Every row of the display table keeps its `external`
field (`:58502` `external: "default"`), and `manual` is not an enum member — it is a **preprocessor**,
`fL(e) { return e === "manual" ? "default" : e }` at `:58323-58325`, wrapped around both zod schemas at
`:58492-58493` (`tc.preprocess(fL, tc.enum(...))`). The settings description says so out loud at
`:60599`: *"('manual' is accepted as an alias for 'default')"*. So a user who writes
`"defaultMode": "manual"` has their value rewritten to `"default"` before validation, and reading the
setting back gives `"default"`. The changelog's "accepted alongside `default`" is precise; the natural
misreading — that `manual` became a real mode — is wrong, and the internal mode key is still `default`
everywhere in the bundle.

**2. The permission-mode table gained a field the changelog never mentions.** `indicator:` is
**220=6 / 193=0** — a new lowercase prose phrase on all six rows, used in running text rather than as a
label. Its consumer is the shortcut hint at `:815406`: *"Hit shift+tab to cycle between manual mode,
auto-accept edit mode, and plan mode"*. Renaming a mode required a second, grammatically different name
for the same mode, and that is why the count of `manual mode` is 2 and not 1.

**3. Bullet 9 is unanchorable, and the `.199` code says why.** The bullet claims a subagent rate-limited
before producing text now "fails cleanly" instead of returning an empty result. Read `.199`'s recovery
path: `recoverPartialSubagentOutput` (`:345891`) returns `null` when
`lastNonErrorAssistantText(clean) === undefined` (`:345895`) — i.e. when there is no text — and
`finishSubagentAfterError` then takes the `throw` at `:345911`. So the behaviour the bullet describes is
implemented by the `.199` code, not by a `.200` change; `.200` is most plausibly the release in which the
`.199` mechanism reached the no-text case in practice. No 220-only literal supports a separate `.200`
delta, and none is claimed here.

**4. Bullet 15's headline mechanism is entirely carryover.** `DECRQM(2026)` **1/1**,
`SYNCHRONIZED_UPDATE` **4/4**, `XTVERSION` **3/3**. The probe existed; what changed is a single
consumer line, `if (process.env.TMUX) return !1;` (`:160038 (193)`) → `if (Z.TMUX) return tho === !0;`
(`:253386`), plus the tri-state wrapper `f2u` (`:253380-253383`) that returns `undefined` while the
probe is still outstanding so the renderer does not commit to a wrong answer during startup. tmux 3.4 is
never named in the code — it is implicit in *which tmux versions answer the DECRQM query at all*.

**5. Bullet 6's headline literal is not new either.** `daemon.lock` is **220=4 / 193=2**, and the
three-way liveness check (kill(0) + `/proc/<pid>/cmdline` + version) already existed. The delta is the
fourth signal: `procStart`, guarded by `Y0r` (`:664788-664790`) and retried through `cAa`
(`:664779-664786`) with `skipCache` on the second attempt. `QH` (`:664794-664804`) now returns `null`
unless all of PID-alive, cmdline-is-`claude daemon`, **and** process-start-time agree — and a lock
without a `procStart` field is refused with an explicit log at `:680348`
(`bg: skipping stale-daemon retire — lock pid … has no procStart identity`). A recycled PID passes the
first two checks and fails the third; that is the whole bug.

**6. Bullet 7's comparator validates its own parse before trusting it.** `rUt` (`:552453-552467`)
extracts `-dev.YYYYMMDD.tHHMMSS` (or `-engine.…`) with `matchAll` and keeps the **last** match, builds a
UTC epoch from it, and then **re-formats that epoch and compares it to the input** —
`new Date(o).toISOString().slice(0,19).replace(/[-:]/g,"").replace("T","t") === `${r}t${n}`` at `:552467`.
A version string containing `-dev.20261340.t999999` parses to a real `Date` (JS rolls over out-of-range
components) but does not round-trip, so it returns `null` and the whole comparison is skipped rather than
producing a confidently wrong ordering. Neither the round-trip nor the fail-to-null policy is in the
bullet.

**7. Three of seventeen bullets have no anchor in this bundle at all** (`#12` worktree-scoped plugins,
`#13` `/mcp` focus, `#17` the install script). For `#17` this is structural: the installer is a shell
artifact shipped separately and is not part of `cli_inner_pretty.js`, so no amount of grepping will
produce evidence. For `#12`, `grep 'plugin' | grep -i worktree` returns **zero lines in both bundles** —
the plugin discovery path and the worktree path do not textually intersect anywhere.
