## a) Release narrative

**2.1.195 is a maintenance release, not a feature release — and its shape tells you what the
2.1.193→2.1.220 window is going to be about.** Eleven of the twelve bullets are `Fixed`/`Improved`;
exactly one is `Added`, and that one is an accessibility escape hatch
(`CLAUDE_CODE_DISABLE_MOUSE_CLICKS`). Six of the twelve are background-agent or agent-view bullets.
That ratio holds for the next twenty-four releases: the window's real subject is **making the
background-agent fleet survive its own lifecycle** — daemons that restart, workers written by a newer
binary, transcripts probed by the wrong reader — and `.195` is where that campaign starts being
visible in the changelog.

The release has one genuinely interesting engineering artefact, and it is the smallest change in it.
Bullet 2 fixes hyphenated hook matchers by adding **one character** to a regular expression
(`/^[a-zA-Z0-9_|, ]+$/` → `/^[a-zA-Z0-9_|, -]+$/`, `cli_inner_pretty.js:520221` vs
`:589636 (193)`). That character moves matchers like `code-reviewer` and `mcp__brave-search` out of
the `new RegExp(matcher)` fallback and into the **exact-string list** branch — a semantic change, not
a parsing fix, because a regex `code-reviewer` substring-matches `my-code-reviewer-v2` while the list
branch does not. Anthropic evidently knew this would silently break configs, because the same release
ships a bespoke migration warning whose text **cites its own changelog entry**: *"…See CHANGELOG
v2.1.195."* (`:520215`, 220=1 / 193=0). That is the only self-referential changelog citation compiled
into the binary anywhere in this window.

The background-agent bullets (7, 8, 9, 11) are four separate symptoms of one architectural fact: the
background fleet has **two on-disk stores and several readers, and any of them can be newer or older
than the writer**. Bullet 7 (jobs disappearing when written by a newer version) is unknown-field
preservation in the roster schema; bullet 8 (five-second blank screen) is a transcript-probe rescue
path; bullet 9 (unreachable daemons) is a *persisted* `bgDisabled` flag written into the daemon record
when the control socket fails to bind; bullet 11 is agent-view layout. They are covered in depth by
[`../36_background_agents/`](../36_background_agents/README.md).

The weakest part of the release, from an analysis standpoint, is **voice**. Three of the twelve
bullets (3, 4, 10) are voice/audio, and only one of them (10, the Linux "no microphone" branch) has a
literal in this bundle at all. Bullets 3 and 4 live in the native audio addon and in a language-aware
auto-submit heuristic that leaves no distinguishing string — and the scoping pass's candidate anchor
for bullet 4 turns out to be a **false match** in unrelated OAuth text (§c.2). Recording that
elimination is the honest deliverable for those two rows.

## c) Deep-dives

I am deliberately **not** re-deriving bullet 1 (the mouse tri-state) or bullets 7/8/9/11: those are
covered thoroughly by `48_accessibility_ui` and `36_background_agents`. The three dives below are the
release's headline mechanism, plus two negative results that no module doc records.

### c.1 The one-character hook-matcher change, and the warning that cites its own changelog

**What it does:** it moves matchers containing `-` from the *regex* branch of hook matching to the
*exact-string list* branch, and warns once per matcher whose meaning changed.

**How it works:**

```javascript
// ============================================
// hookMatcherMatches - decide whether a hook matcher selects this tool name
// Location: cli_inner_pretty.js:520219-520232
// ============================================

// ORIGINAL (for source lookup):
function IF_(e, t, r, n) {
  if (!t || t === "*") return !0;
  if ((r ? /^[a-zA-Z0-9_|, -]+$/ : /^[a-zA-Z0-9_|]+$/).test(t))
    return t
      .split(r ? /[|,]/ : "|")
      .map((s) => s.trim())
      .filter(Boolean)
      .flatMap((s) => pWn(ij(s), n))
      .includes(e);
  try {
    let i = new RegExp(t);
    if (i.test(e)) return !0;
    ...

// READABLE (for understanding):
function hookMatcherMatches(toolName, matcher, allowExtendedListSyntax, expansionCtx) {
  if (!matcher || matcher === "*") return true;                 // wildcard
  const listShape = allowExtendedListSyntax
    ? /^[a-zA-Z0-9_|, -]+$/          // 2.1.195: '-' added here
    : /^[a-zA-Z0-9_|]+$/;
  if (listShape.test(matcher))                                  // LIST branch: exact string compare
    return matcher
      .split(allowExtendedListSyntax ? /[|,]/ : "|")
      .map((s) => s.trim())
      .filter(Boolean)
      .flatMap((s) => expandMatcherAlias(normalize(s), expansionCtx))
      .includes(toolName);                                      // <- exact, not substring
  try { if (new RegExp(matcher).test(toolName)) return true; }   // REGEX branch (unanchored!)
  ...
}

// Mapping: IF_→hookMatcherMatches, e→toolName, t→matcher, r→allowExtendedListSyntax,
//          n→expansionCtx, pWn→expandMatcherAlias, ij→normalize
```

1. The predicate is a **two-branch dispatcher**, and the char class is the dispatcher. If the matcher
   looks like a plain list (`A|B, C`), it is compared with `.includes(toolName)` — exact equality per
   element. Anything else falls through to `new RegExp(matcher).test(toolName)`.
2. The regex branch is **unanchored**. `new RegExp("code-reviewer").test("my-code-reviewer-2")` is
   `true`. Before `.195`, every hyphenated matcher took that branch, so every hyphenated matcher was a
   substring matcher by accident.
3. Adding `-` to the class routes those matchers into the exact branch, which is what a user writing
   `"matcher": "code-reviewer"` means.

**Why this approach:** the alternative — anchoring the regex branch with `^…$` — would have been a
one-token change too, and would have fixed substring bleed for *all* matchers. It was not taken,
because anchoring would break users who deliberately write partial-match regexes like
`mcp__github.*`. Confining the change to the *shape test* fixes the accidental-regex case while
leaving deliberate regexes untouched. The cost is that the matcher language now has a syntactic
cliff: `a-b` is a literal, `a-b.*` is a regex.

**The migration warning is the interesting half.** The change silently *narrows* matching, so a
config that previously matched now matches nothing. `.195` therefore ships a helper whose only job is
to say so:

```javascript
// ============================================
// warnIfBareMcpServerMatcher - one-shot warning for matchers the .195 change broke
// Location: cli_inner_pretty.js:520204-520218
// ============================================

// ORIGINAL (for source lookup):
function HF_(e, t) {
  if (!t || !kF_.has(e)) return;
  let r = JEi();
  if (r.has(t) || !Eip(t)) return;
  r.add(t);
  let n = t.split(/[|,]/).map((o) => o.trim())
        .find((o) => o.startsWith("mcp__") && !o.slice(5).includes("__")) ?? t;
  w(
    `Hook matcher \`${n}\` matches no tool (it is compared as an exact string). To match all tools from this server, use \`${n}__.*\`. See CHANGELOG v2.1.195.`,
    { level: "warn" },
  );
}

// READABLE (for understanding):
function warnIfBareMcpServerMatcher(hookEvent, matcher) {
  if (!matcher || !TOOL_MATCHED_EVENTS.has(hookEvent)) return;   // only events that match tool names
  const alreadyWarned = warnedMatcherSet();
  if (alreadyWarned.has(matcher) || !isBareMcpServerMatcher(matcher)) return;
  alreadyWarned.add(matcher);                                    // once per matcher per process
  const offending = matcher.split(/[|,]/).map(s => s.trim())
        .find(s => s.startsWith("mcp__") && !s.slice(5).includes("__")) ?? matcher;
  log(`Hook matcher \`${offending}\` matches no tool (it is compared as an exact string). ` +
      `To match all tools from this server, use \`${offending}__.*\`. See CHANGELOG v2.1.195.`,
      { level: "warn" });
}

// Mapping: HF_→warnIfBareMcpServerMatcher, kF_→TOOL_MATCHED_EVENTS, JEi→warnedMatcherSet,
//          Eip→isBareMcpServerMatcher, t→matcher, n→offending
```

**Key insight:** the guard `startsWith("mcp__") && !s.slice(5).includes("__")` selects **exactly the
set of matchers whose meaning the change altered** — a bare MCP *server* name like `mcp__brave-search`,
which under the old regex branch matched every `mcp__brave-search__<tool>` and under the new list
branch matches nothing (because no tool is *named* `mcp__brave-search`). The warning is not a generic
"your matcher matched nothing" message; it is a targeted migration notice with the exact replacement
(`${offending}__.*`) and a version pointer. It is also **once per matcher** (`warnedMatcherSet`), so a
long-running session does not spam. Shipping a changelog reference inside a binary is a strong signal
that the authors expected this to generate support load — and it is the only such citation in the
whole `.195`→`.220` window.

Full matcher FSM, the `if:` conditions, and the exit-code-2 attribution work live in
[`../41_hooks/matching_and_exit_codes.md`](../41_hooks/matching_and_exit_codes.md).

### c.2 NEGATIVE RESULT — the `auto-submit` anchor for bullet 4 is a false match

The scoping pass ([`../00_overview/_scope_v195_199.md`](../00_overview/_scope_v195_199.md), `.195` row
4) recorded `auto-submit` as 220=1 / 193=0 and graded the bullet *NET_NEW (literal only)*, explicitly
noting the site was not read. **I read it, and it is unrelated to voice.** The single occurrence is at
`cli_inner_pretty.js:863149`, inside OAuth device-flow guidance prose:

> `per-IP rate limit (RFC 8628 §5.1) and don't auto-submit a pre-filled code`

That is device-authorization documentation, not the dictation auto-submit path. `48_accessibility_ui`'s
README also flags the site as unread; this file closes the loop: the anchor is **eliminated**.

**Why it matters methodologically:** a 220=N/193=0 count is necessary but not sufficient. RFC-8628
prose was added to this bundle in this window for unrelated reasons, and it happens to contain the
bullet's keyword. The `.195` voice bullets 3 and 4 concern (a) a CoreAudio default-device change and
(b) a word-boundary heuristic for scriptio-continua languages — neither of which needs a new English
string. **Verdict for bullet 4: UNANCHORED**, and the `auto-submit` literal must not be cited for it
anywhere in this tree.

The one voice bullet that *is* anchorable is bullet 10, and its shape explains why: it added a new
**user-visible sentence**, not a new code path shape. The availability probe now has three arms
instead of two — SoX-missing-with-a-known-install-command, SoX-missing-generic, and (new)
SoX-present-but-no-capture-device — and only the third one needed new text:

> `Voice mode requires a microphone, but SoX could not open an audio capture device.` /
> `This usually means the host has no microphone (for example, a remote server).`
> (`cli_inner_pretty.js:496025-496027`, 220=1 / 193=0)

The rule this yields: **anchorability tracks whether a fix has to explain itself to a human.**

### c.3 Bullet 9 is not "a retry was added" — it is a *persisted* kill switch

The bullet reads *"daemons running unreachable when the control socket fails to start, blocking
restarts."* The naive expectation is a retry loop. The code does the opposite — on control-socket
failure the daemon **writes a flag into its own on-disk record** so that every subsequent reader knows
this daemon is useless:

```javascript
// ============================================
// markDaemonBackgroundDisabled - persist "this daemon has no control socket"
// Location: cli_inner_pretty.js:664718-664722
// ============================================

// ORIGINAL (for source lookup):
async function Nef(e) {
  let t = await jAe();
  if (!t || t.pid !== e.pid || t.startedAt !== e.startedAt) return;
  await mYo({ ...t, bgDisabled: !0 });
}

// READABLE (for understanding):
async function markDaemonBackgroundDisabled(self) {
  const record = await readDaemonRecord();
  if (!record || record.pid !== self.pid || record.startedAt !== self.startedAt) return;  // not us
  await writeDaemonRecord({ ...record, bgDisabled: true });
}

// Mapping: Nef→markDaemonBackgroundDisabled, jAe→readDaemonRecord, mYo→writeDaemonRecord, e→self
```

**How it works:** the identity guard (`pid` **and** `startedAt`) is the load-bearing part. A daemon
record is a shared file; between reading it and writing it, this process may have been superseded by a
newer daemon that rewrote the record. Comparing both the PID *and* the start timestamp means a
recycled PID cannot cause one daemon to stamp `bgDisabled` on a healthy successor. Without the
`startedAt` half this would be a classic PID-reuse corruption.

**Why this approach:** an unreachable daemon is not a transient error — if the socket path is
unwritable or the address is in use, retrying inside the same process will keep failing. Publishing
the failure in the shared record turns a *silent* stuck daemon into an *observable* one, so the
launcher's skip path (`tengu_bg_daemon_bg_disabled_skip`, 220=1 / 193=0) and the upgrade path
(`tengu_daemon_upgrade_respawn_unreachable`, `:871997`, 220=1 / 193=0) can route around it instead of
handing work to a corpse. That is why the verdict is **DELTA, not NET_NEW**: daemon records existed;
the `bgDisabled` field and the two skip paths reading it are the change.

Full daemon ladder in [`../36_background_agents/daemon_lifecycle.md`](../36_background_agents/daemon_lifecycle.md) §6.

## d) What the changelog does not say

1. **`CLAUDE_CODE_DISABLE_MOUSE_CLICKS` created a tri-state, and the bullet describes only one third
   of it.** The resolver at `:164997-165001` returns `"off" | "scroll" | "full"`, and
   `CLAUDE_CODE_DISABLE_MOUSE` (which is *carryover*, 220=6 / 193=2) takes precedence over the new
   variable. In 2.1.193 the same concept was a plain boolean with a single DECSET string; `.195`
   split it into two sequences — `DECSET 1000+1002+1003+1006` for `full` versus `DECSET 1000+1006`
   for `scroll` (`:253481-253482`). The new variable is therefore not an addition to an existing
   switch; it is the reason the switch stopped being a switch. See
   [`../48_accessibility_ui/terminal_rendering.md`](../48_accessibility_ui/terminal_rendering.md) §2.

2. **The new variable was added to a *settings* env allow-list, not just read from the environment.**
   `:58152` places it in a curated list next to `CLAUDE_AX_SCREEN_READER`,
   `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN` and `CLAUDE_CODE_NO_FLICKER` — i.e. it is settable through
   the settings `env` block, not only through the shell. No bullet says so.

3. **The binary cites its own changelog.** `:520215` contains the literal string
   `See CHANGELOG v2.1.195.` This is 220=1 / 193=0 and is unique in the window. Any future analyst
   grepping a version number in the bundle will hit this and should know it is a *migration notice*,
   not a build stamp.

4. **`tengu_left_arrow_gesture` disappears in this window** (193=2 → 220=0) and is replaced by
   `tengu_left_arrow_editing_guard` (220=1 / 193=0, `:559928`). The scoping pass noticed the swap
   while probing `.195` but the behaviour it controls belongs to **`.196` bullet 27** (single-`←`
   agents view) and `.198` bullet 19. Do not attribute the gate rename to `.195`.

5. **Two bullets in this release are not verifiable from this artefact at all.** Bullet 3 (macOS
   default-input-device change) is inside the bundled native audio addon; the JS-side entry points
   `startNativeRecording` / `isNativeRecordingActive` are 2/2. `_false_delta_ledger` register 1 does
   not list them, so this file is the record: **treat them as out-of-artefact, not as carryover.**

6. **No bullet mentions that the mouse work and the screen-reader work are the same programme.**
   `.195`'s mouse tri-state, `.200`'s `screenReader: l` renderer prop and `.208`'s screen-reader-mode
   promotion (which `_GROUND_TRUTH` §3 shows was **dark-launched in 2.1.193**) are one accessibility
   push spread over three releases with no cross-reference between the bullets.
