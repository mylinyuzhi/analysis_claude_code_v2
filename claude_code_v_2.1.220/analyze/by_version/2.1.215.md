## a) Release narrative

`2.1.215` has **exactly one changelog bullet**, and the whole window contains only five such releases
(`.201 .204 .209 .215 .220`). A one-bullet release is never "a small release" — it is a release whose
*shipping reason* is one thing. The four archetypes in this window are:

| Archetype | Example | Tell |
|---|---|---|
| model launch | `.197` (Sonnet 5) | a large block of new catalogue data, no fixes |
| hotfix | `.201` (Sonnet 5 mid-conversation system role) | reverts a behaviour shipped days earlier |
| revert | `.209` (overly broad dialog guard) | undoes a `.208` change |
| **policy decision** | **`.215`** | a *flag flipped on two objects*, nothing else |
| contentless | `.220` | "Bug fixes and reliability improvements" |

`.215` is the fourth kind, and it is the cheapest possible shape a release can have: **two source lines**.
It sits between `.214` — the 47-bullet security release (Bash/PowerShell permission hardening, the
`EndConversation` tool, OTel correlation attributes) — and `.216`, a 40-bullet bug sweep. Neither
neighbour is a plausible carrier for this change, which is the point: shipping it alone means it was
**not a bug fix but a decision**, made after `.214`'s security review and important enough not to wait
for `.216`'s bus.

**What the decision is.** `/verify` and `/code-review` stop being reachable through the `Skill` tool.
They remain fully available when the *user* types them. Mechanically this is `disableModelInvocation: !0`
added to two command objects — `cli_inner_pretty.js:774588` (`code-review`) and `:789551` (`verify`).

**Why it matters more than the bullet suggests.** These two skills are not arbitrary. They are the two
members of a hard-coded pair, `E$y = new Set([Mse, REe])` (`:340271`, where `Mse = "verify"` `:318664`
and `REe = "code-review"` `:318660`), and invoking either one is what the harness records as a
**verification event** on the session's attribution ledger:
`applyAttributionOp({ kind: "recordVerification", method: Spr(e.name) })` (`:344043`, `:340332`,
`:414370`; `Spr` at `:340263`; `recordVerification` **220=4 / 193=2**). A model that can call `/verify`
on its own initiative can mark its own work as verified. `.215` closes that loop.

**Where it sits in the window's arc.** This is step 3 of a five-step policy oscillation that
[`../52_code_review/manual_invocation_gating.md`](../52_code_review/manual_invocation_gating.md)
documents in full: `.202` cut `/review` back to a single pass, `.215` blocks model invocation of
`/verify` + `/code-review`, `.218` moves `/code-review` into a background fork (softening `.215`: still
manual, but no longer expensive in conversation context) and applies the same restraint to
`/deep-research`. `.215` is the only step of the five that is **not remotely reversible** — it is a
literal in a command object, not a gate read.

### c.3 What the flag actually does — and the escape hatch that makes the bullet's second half true

**What it does:** blocks the `Skill` tool from executing the command, *unless the user typed the
command's name during the current turn*.

**How it works:**

```javascript
// ============================================
// checkSkillInvocationBlocked - the model-invocation gate, extracted in 2.1.220
// Location: cli_inner_pretty.js:346456-346463 (first arm)
// ============================================

// ORIGINAL (for source lookup):
function oin(e, t) {
  let { commandName: r, userTypedThisTurn: n, isMainSession: o, permissionContext: i } = t;
  if (e.disableModelInvocation && !n)
    return {
      reason: "disable_model_invocation",
      message: `Skill ${r} cannot be used with ${Ph} tool due to disable-model-invocation`,
      errorCode: 4,
    };
  ...

// READABLE (for understanding):
function checkSkillInvocationBlocked(skill, ctx) {
  let { commandName, userTypedThisTurn, isMainSession, permissionContext } = ctx;
  if (skill.disableModelInvocation && !userTypedThisTurn)
    return { reason: "disable_model_invocation",
             message: `Skill ${commandName} cannot be used with ${SKILL_TOOL_NAME} tool due to disable-model-invocation`,
             errorCode: 4 };
  ...                                    // then: allowlist, skillOverrides, type, MCP, deny rules
}

// Mapping: oin→checkSkillInvocationBlocked, Ph→SKILL_TOOL_NAME, n→userTypedThisTurn,
//          zNy (:346566)→userTypedCommandThisTurn — 193 twin IZa (:399247 (193))
```

`userTypedThisTurn` comes from `zNy(name, ctx)` (`:346566`, called at `:346928`), whose 2.1.193 twin
`IZa` (`:399247-…(193)`) is the same regex scan back to `turnStartIndex` for a bare `/name` token in a
non-meta user message. **That predicate is why the changelog's second clause is literally true**: after
the user types `/code-review`, the `Skill` tool *may* run it for the rest of the turn — so a stacked or
argument-expanded invocation still works. The restraint is on *initiative*, not on the tool.

**Why a per-turn predicate rather than a per-session one?** A session flag would let one user
invocation unlock the skill forever, which defeats the point; a per-call flag would break the legitimate
routing paths (§c.4) where the harness re-enters the same command object after parsing arguments or
resolving a subcommand. The turn is the smallest unit that contains one user intention.

**Failure mode:** `errorCode: 4` is a *model-visible tool error*, not a silent no-op. The model is told
the reason, and the sibling helper `kpd` (`:346451-346455`) produces the user-facing half —
`Ask the user to run /${name} themselves — it cannot be invoked via the Skill tool.` — so the model's
next move is to suggest the command instead of retrying it.

### c.4 The 2.1.220 structural change the bullet does not mention: the gate was extracted

The **flag** is 2.1.193's. The **gate function** is not. In 2.1.193 the check was written inline inside
the `Skill` tool's `checkPermissions`, at `:399491 (193)`:

```javascript
if (l.disableModelInvocation && !IZa(o, t))
  return (Re("skill_invoke", "skill_invoke_model_disabled"),
          { result: !1, message: `Skill ${o} cannot be used with ${RS} tool due to disable-model-invocation`, errorCode: 4 });
```

— **one** call site, returning a `{result:false}` shape. 2.1.220 hoists the whole ladder into `oin`
(`:346456`) which returns a discriminated `{ reason, message, errorCode, … }`, and the caller
(`:346926-346950`) `switch`es on `reason` to pick the telemetry sub-event. Proof this shape is new:
`disable_model_invocation` (the reason token) is **220=2 / 193=0** and `userTypedThisTurn` is
**220=4 / 193=0**.

**Why extract?** Because 2.1.220 has **three** consumers, not one:

| Caller | `userTypedThisTurn` | What it is asking |
|---|---|---|
| `:346926` (Skill tool `checkPermissions`) | `zNy(name, ctx)` — the real answer | "may I run this now?" |
| `:652511` | hard-coded `!1` | "would the *model* be allowed to run this?" — prompt-routing preflight |
| `:652582` | hard-coded `!1` | same, passed as a predicate into the query pipeline |

The two `!1` sites ask a **counterfactual**: *if the model tried, would it be blocked?* They use it to
decide routing before any tool call exists. Passing `false` is deliberate — the answer must not depend
on what the user happened to type, or the routing decision would flip mid-turn.

**Key insight:** the 193 code could only *reject* a model invocation at the moment it happened. The 220
refactor makes "is this command model-invocable?" a **queryable property**, which is the prerequisite
for `.218` moving `/code-review` into a background fork: you cannot route a command you cannot classify
ahead of time. `.215` and `.218` are one piece of engineering delivered in two releases.

### c.5 Verdict rationale — why `DELTA`, not `NET_NEW`

- `disableModelInvocation` (any form) is **220=39 / 193=26**. The field, its zod plumbing
  (`:268349`, `:419667`), the frontmatter spelling `disable-model-invocation` (**220=11 / 193=7**,
  normalised by `otr()` at `:270599`), the menu filters (`:506822`, `:506848`, `:506854`) and the
  `/config` display (`:725243`, `:710986`) all pre-date the window.
- The 193→220 delta on the frontmatter spelling (7 → 11) is consistent with the scoping pass's read
  that *more skills* switched to user-invocable-only, but it is a **shared-mechanism** count and cannot
  be attributed to `.215` alone.
- **Anyone writing "2.1.215 introduced model-invocation gating" is wrong.** The correct sentence is
  *"2.1.215 applied an existing, pre-window gate to the two review skills."*

## d) What the changelog does not say

**1. Three more commands were gated in the same window, and none of them has a bullet.**
`__remote-workflow` (`:502380-502383`), `workflow-launch-exec` (`:502648-502651`) and `doctor`
(`:785859-785867`) also gained `disableModelInvocation: !0` between 193 and 220. The first two are
`isHidden: !0`, `type: "local"` server-launch plumbing whose descriptions say
*"server-launched sessions only"* / *"workflow_launch event sessions only"* — the model should never
call them for correctness reasons, not cost ones. `doctor` is a diagnostic. **These cannot be pinned to
`.215` specifically** — the two-point 193↔220 diff cannot separate them from `.207` or `.218` — so the
honest statement is: five commands were gated in the window, two of which `.215` names.

**2. `disableModelInvocation` and `userInvocable` are the two directions of one policy, and the
stacked-command parser enforces the other direction.** `.215` sets `disableModelInvocation: !0` while
*keeping* `userInvocable: !0`. The complementary rule lives in the stacked-slash-command peeler, which
refuses to stack any command with `p.userInvocable === !1` (`:343862`). So the policy matrix has four
cells and `.215` moves these two commands from *(user: yes, model: yes)* to *(user: yes, model: no)* —
not to *off*.

**3. The coordinator/worker path has its own, longer refusal.** In agent-team ("coordinator") mode the
same flag produces a different message at `:343966-343971`:
*"Skill `/code-review` is user-invocable only (disable-model-invocation) and cannot run in coordinator
mode: the coordinator does not load skill content, and workers cannot invoke it via the Skill tool."*
— and then it enumerates the command's *subcommands* that **are** still reachable
(`:343973-343978` filters `e.subcommands` for entries that are neither model-disabled nor MCP prompts).
For `/code-review` that surfaces `ultra` (`subcommands: { ultra: "ultrareview" }`, `:774584`). So in
coordinator mode the model is told what it *can* still do — a graceful-degradation detail with no
bullet.

**4. The two skills are paired in code for a reason the bullet never gives.** `E$y = new Set([Mse, REe])`
(`:340271`) is consumed only by `Spr` (`:340263`, `return E$y.has(e) ? "/" + e : null`), whose three
callers all do the same thing: record a **verification** attribution op. The set is *carryover* — 193
has `m9p = new Set([vqe, fre])` at `:397316 (193)` — but the number of `recordVerification` call sites
grew **2 → 4** (`:340332`, `:344043`, `:414370`, dispatcher arm `:229384`). The changelog frames `.215`
as a cost/annoyance change ("Claude no longer runs them on its own"); the code frames it as an
**integrity** change: self-invoked verification would be self-attested verification.

**5. Nothing else in `.215` is findable.** A single-bullet release two builds before the analysed build
leaves no other separable trace in a 193↔220 diff. I did not find, and do not claim, any other `.215`
content.
