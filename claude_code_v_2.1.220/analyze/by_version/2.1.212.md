## 1. Release narrative

**2.1.212 is where Claude Code decides that delegation needs a budget and a boundary.** Four of its
first five bullets are about *where work runs and how much of it you are allowed to start*: `/fork`
stops being an in-session subagent spawner and becomes a **conversation copier into a background
session**, the old behaviour is re-issued under a new name `/subtask`, a **per-session cap of 200
subagent spawns** and a **per-session cap of 200 WebSearch calls** land as refusal messages the model
reads as data, and MCP tool calls that run past **two minutes** are moved to the background
automatically. Read together, these are one design: the session is now a resource-managed scheduler
with hard ceilings, not an unbounded fan-out. The `.217` concurrency cap and the `.217`/`.219` spawn
depth gate are the same programme continued — `.212` is where the first *counters* appear.

**Its second centre of gravity is a real security fix in plan mode**, and it is the most completely
provable bullet in the whole release. Plan mode is supposed to be read-only, but two independent
permission fast paths — the sandboxed-Bash auto-allow and the `acceptEdits` short-circuit — never
asked which mode they were in. A one-line predicate `tcr(ctx) = ctx.mode === "plan"` (`:289037`,
220=5 / 193=0) was inserted into four otherwise byte-identical expressions, plus a fifth
`$ = u === "plan"` guard at `:513776`. The changelog's own examples (`touch`, `rm`) are literally the
first four entries of the auto-allowed write-command list `Lqy = ["mkdir","touch","rm","rmdir","mv","cp","sed"]`
at `:393515` — and the sandboxed path this reached **explicitly tolerated `rm`/`rmdir`** as long as the
sandbox would contain them. See §3.2.

**The third block is a long reliability tail with an unusually high anchor rate.** Four `/ultrareview`
bullets collapse into one 800-line precondition state machine (`:496639-497460`); two OTel bullets
land inside one ~80-line exporter/trace-context span; and the background-agent daemon, roster and
attach paths pick up six more fixes each backed by a net-new `tengu_bg_*` gate. Only **five** of the
48 bullets resist anchoring outright, and three of those are pure terminal-layout fixes that carry no
string at all.

**Relative to its neighbours:** `.211` (37 bullets) was a bugfix-dominated release whose UI half was
largely unanchorable; `.214` (47 bullets, `.213` was never published) is the security release, six
consecutive Bash/PowerShell analyzer hardenings plus the `EndConversation` tool. `.212` sits between
them and is the only one of the three that introduces *new user-facing surface area* — two commands,
three env vars, one CLI subcommand — rather than repairing existing surface. Where `.214`'s deltas are
single lines inside mature machinery, `.212`'s are whole new objects.

**One structural warning specific to this release:** four of its bullets are *label* changes whose
label is carryover (`Needs input`, `Cloud authentication`→`Authentication`, `Command timed out`,
the tmux release-note correction). A literal-count reading scores three of them wrong in *both*
directions. See §4.

### 3.1 `/fork` and `/subtask` are not a rename — they are a conditional swap

**What it does:** `.212` gives `/fork` a new meaning (copy this conversation into a background
session, keep working here) and re-issues the *old* meaning (spawn an in-session subagent that
inherits the conversation) as `/subtask`. The changelog reads like a rename. The code is a runtime
choice between two disjoint command sets.

**How it works:**

1. Three descriptor objects exist side by side in the bundle:
   - `pJd` `:500525` — the **old** `/fork`: *"Spawn a background agent that inherits the full
     conversation"*, `argumentHint: "<directive>"`, with a lazy `load:` pointing at the handler module.
   - `mJd` `:500537` — the **new** `/fork`: *"Copy this conversation into a new background session and
     keep working here"*, `argumentHint: "[prompt]"`, and **no `load:` at all**.
   - `_Jd` `:500572` — `/subtask`: *"Send a subagent off with your full context; its result comes back
     here"*, `argumentHint: "<task>"`, `load:` → `gJd`, whose `call` is `NL_` `:500547`.
2. The registry decides which pair ships, at `:507186`:
   `...(NP() && !Yt(Z.IS_DEMO) ? [mJd, _Jd] : [pJd])`.
   `NP()` `:157277` is `return !Zer()` — a build/environment predicate, not a feature flag.
3. `NL_` `:500547` is the old `/fork` body verbatim: it validates a non-empty argument
   (`Usage: /subtask \<task\>` `:500549`), calls the same spawner `Lpn` `:500337`, and — the tell —
   still prints **`forked ${o.name}`** on success.

```javascript
// ============================================
// forkSubtaskCommandRegistration - one gate selects {new /fork, /subtask} or {old /fork}
// Location: cli_inner_pretty.js:500525-500580 (descriptors) + :507186 (registry)
// ============================================

// ORIGINAL (for source lookup):
pJd = { type: "local-jsx", name: "fork",
        description: "Spawn a background agent that inherits the full conversation",
        argumentHint: "<directive>", isEnabled: () => !F_(),
        load: () => Promise.resolve().then(() => (dJd(), uJd)) };
mJd = { type: "local-jsx", name: "fork",
        description: "Copy this conversation into a new background session and keep working here",
        argumentHint: "[prompt]", isEnabled: () => !F_() };
_Jd = { type: "local-jsx", name: "subtask",
        description: "Send a subagent off with your full context; its result comes back here",
        argumentHint: "<task>", isEnabled: () => !F_(),
        load: () => Promise.resolve().then(() => (yJd(), gJd)) };
// registry:
...(NP() && !Yt(Z.IS_DEMO) ? [mJd, _Jd] : [pJd]),

// READABLE (for understanding):
legacyForkDescriptor = { name: "fork", description: "Spawn a background agent that inherits the full conversation",
                         argumentHint: "<directive>", isEnabled: () => !isCoordinatorSession(),
                         load: () => import("./legacy-fork-handler") };
backgroundForkDescriptor = { name: "fork", description: "Copy this conversation into a new background session and keep working here",
                             argumentHint: "[prompt]", isEnabled: () => !isCoordinatorSession() };  // no loader
subtaskDescriptor = { name: "subtask", description: "Send a subagent off with your full context; its result comes back here",
                      argumentHint: "<task>", isEnabled: () => !isCoordinatorSession(),
                      load: () => import("./subtask-handler") };
commands.push(...(backgroundSessionsSupported() && !isDemoBuild() ? [backgroundForkDescriptor, subtaskDescriptor]
                                                                 : [legacyForkDescriptor]));

// Mapping: pJd→legacyForkDescriptor, mJd→backgroundForkDescriptor, _Jd→subtaskDescriptor,
//          NL_→subtaskCall, Lpn→spawnInheritingSubagent, NP→backgroundSessionsSupported,
//          F_→isCoordinatorSession, Yt(Z.IS_DEMO)→isDemoBuild
```

**Why this approach:**

- **A rename would have broken every environment that cannot run background sessions.** The old
  `/fork` still exists, fully wired, for the `NP() === false` branch. Anthropic did not delete the
  behaviour; it moved it behind a name and kept the original reachable.
- **`mJd` has no `load:`.** Every other descriptor lazily imports its handler. The new `/fork` does
  not, because it does not run a JSX handler at all — it hands off to the background-session spawner
  `gGt` `:683672` through the ordinary fork path. The *absence* of a field is the strongest evidence
  that the new `/fork` is a different kind of object from the old one.
- **`argumentHint` went `"<directive>"` → `"[prompt]"`.** Angle brackets mean required, square
  brackets mean optional. The old `/fork` needed a directive because it had to give the subagent a
  task; the new one can copy the conversation with no prompt at all, and bullet #39 is what fills the
  resulting nameless row: `:683674-683676` derives a 60-character name from the prompt
  (`ma(mu(Uf(t ?? "")), 60)`) and tags it `nameSource: "auto"` — but **only when `keepParent` is set**,
  i.e. only on the fork path.

**Key insight:** the changelog says "the in-session subagent it used to launch is now `/subtask`", which
implies one command was renamed. What actually shipped is *three* descriptors and a runtime ternary, so
in a non-background-capable build **`/subtask` does not exist and `/fork` still means the old thing**.
The mechanism is derived line by line in
[../43_slash_commands/fork_and_subtask.md](../43_slash_commands/fork_and_subtask.md) §0.

### 3.2 The plan-mode Bash bypass: one predicate, four insertion points

**What it does:** In plan mode, Claude Code was auto-approving file-modifying Bash commands via two
permission fast paths that never checked the session mode. `.212` inserts a mode predicate into both.

**How it works:**

The predicate is three lines and does nothing else:

```javascript
// ============================================
// isPlanMode - the entire .212 plan-mode Bash security fix, as a predicate
// Location: cli_inner_pretty.js:289037-289039  (220=5 call sites / 193=0)
// ============================================

// ORIGINAL (for source lookup):
function tcr(e) {
  return e.mode === "plan";
}

// READABLE (for understanding):
function isPlanMode(permissionContext) {
  return permissionContext.mode === "plan";
}

// Mapping: tcr→isPlanMode, e→permissionContext
```

**Bypass A — the sandboxed-Bash auto-allow (`:393890`, `:393924`).** Two sibling functions, `cvd`
`:393889` and `Wqy` `:393923`, share an identical four-clause disqualifier chain. Compare them with
their 2.1.193 twins:

```javascript
// ============================================
// sandboxedBashAutoAllow - the disqualifier chain that gained the plan-mode guard
// Location: cli_inner_pretty.js:393890 (220)  ·  cli_inner_pretty.js:460181 (193)
// ============================================

// ORIGINAL (for source lookup):
// 220 :393890
if (!Oo.isSandboxingEnabled() || !Oo.isAutoAllowBashIfSandboxedEnabled() || !H4(e) || tcr(t)) return null;
// 193 :460181
if (!ko.isSandboxingEnabled() || !ko.isAutoAllowBashIfSandboxedEnabled() || !o$(e)) return null;

// READABLE (for understanding):
// 2.1.220
if (!sandboxingEnabled() || !autoAllowBashIfSandboxedEnabled() || !toolIsBash(tool) || isPlanMode(ctx))
  return null;                       // <- the added 4th clause
// 2.1.193
if (!sandboxingEnabled() || !autoAllowBashIfSandboxedEnabled() || !toolIsBash(tool))
  return null;                       // <- plan mode was never consulted

// Mapping: Oo/ko→sandboxRuntime, H4/o$→toolIsBash, tcr→isPlanMode, t→permissionContext
```

Everything *else* in `cvd` is byte-equivalent between the builds — including the loop at `:393911-393920`
that walks parsed commands and, for `rm` / `rmdir`, **allows them through** as long as the destructive-command
analyzer does not return `passthrough`. That is the whole shape of the bug: the path was designed to
tolerate `rm` because the sandbox would contain it, and plan mode was invisible to it.

**Bypass B — the `acceptEdits` fast path (`:513525`, `:513574`, `:513776`).** Two permission entry
points compute the same pair:

```javascript
let u = e.name === ri && Oo.isSandboxingEnabled() && Oo.isAutoAllowBashIfSandboxedEnabled() && H4(t),
    d = u && tcr(o);
if (!(u && !d)) return Mrp(e, t, r, a);        // :513525-513527
```

`u` is "this is a sandbox-auto-allowable Bash call"; `d` is "…and we are in plan mode". The rule
`u && !d` reads as *take the fast path only if sandbox-eligible **and not** planning*. The third guard,
`$ = u === "plan"` `:513776`, disables the fast permission re-check entirely in plan mode, which is
what stops the `acceptEdits` short-circuit from reaching `Lqy = ["mkdir","touch","rm","rmdir","mv","cp","sed"]`
`:393515` — the list whose first four entries are the changelog's own examples.

**Why this approach:**

- **The guard is placed in the disqualifier chain, not at the call site.** There are two auto-allow
  functions and two permission entry points; guarding at the four call sites would have required the
  callers to know about plan mode. Putting it in the shared prologue means any future caller inherits
  the fix. The trade-off is that the predicate is now evaluated on every Bash permission check, which
  is free — it is one property read.
- **`tcr` is a named function rather than an inline `ctx.mode === "plan"`.** Four inline copies would
  have been the same bytes; a named predicate is greppable, which is exactly why this bullet is
  verifiable at all (`tcr(` is 220=5 / 193=0 with no false positives).
- **`Lqy` is unchanged (1/1).** The fix did not narrow the auto-allow list. That is deliberate: the
  list is correct for `acceptEdits`, where writing files is the point. The bug was that plan mode
  reached it.

**Key insight:** this is a **fail-open-by-omission** bug, the hardest class to find by grep, because
the vulnerable code contains no wrong logic — it contains a missing question. The five-line diff is
the entire fix, and the only reason it is provable is that someone chose to name the predicate.
Full derivation: [../05_plan_mode/bash_bypass_and_classifier_212_218.md](../05_plan_mode/bash_bypass_and_classifier_212_218.md) §§1–2.

### 3.3 Two hard budgets, and the asymmetry with the depth cap

**What it does:** bullets #3 and #4 add the first *session-lifetime counters* in Claude Code:
200 subagent spawns and 200 WebSearch calls, both overridable by env var, both reset by `/clear`.

**How it works:** three readers sit next to each other, and all three are two lines long:

```javascript
// ============================================
// sessionBudgetReaders - the three caps, read with no gate and no validation
// Location: cli_inner_pretty.js:231399-231413
// ============================================

// ORIGINAL (for source lookup):
function gPu() { return Z.CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS ?? gty; }
function Q7r() { return Z.CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION ?? yty; }
function yPu() { return Z.CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION ?? _ty; }
var WVe, jpo, kir, gty = 20, yty = 200, _ty = 200, _Pu, Gpo;

// READABLE (for understanding):
function getMaxConcurrentSubagents()   { return env.CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS   ?? MAX_CONCURRENT_SUBAGENTS; }
function getMaxSubagentsPerSession()   { return env.CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION   ?? MAX_SUBAGENTS_PER_SESSION; }
function getMaxWebSearchesPerSession() { return env.CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION ?? MAX_WEB_SEARCHES_PER_SESSION; }
const MAX_CONCURRENT_SUBAGENTS = 20, MAX_SUBAGENTS_PER_SESSION = 200, MAX_WEB_SEARCHES_PER_SESSION = 200;

// Mapping: gPu→getMaxConcurrentSubagents, Q7r→getMaxSubagentsPerSession, yPu→getMaxWebSearchesPerSession,
//          gty/yty/_ty→the three default constants, Z→envAccessors
```

**Why this approach:**

- **The refusals are written for the model, not the user.** `:398397` reads
  *"Subagent spawn limit reached (N of M agents spawned). **Complete the remaining work directly with
  your tools instead of spawning more agents.** If more agents are genuinely needed, ask the user to
  raise `CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION`."* — a refusal, a substitute strategy, and an escalation
  path. `:398411` (concurrency) even adds **"Do not retry."** These are prompts, not error messages.
- **The WebSearch cap refuses *as data*.** `:403669` returns a normal `{ data: { query, results: [...],
  durationSeconds: 0, searchCount: 0 } }` whose single "result" is the refusal sentence. Throwing would
  have surfaced as a tool error the model might retry; a zero-cost successful result with a textual
  explanation cannot be retried into a loop. That is the design decision worth taking away.
- **The asymmetry with the depth cap is the real story.** These three read `Z.<ENV> ?? <const>` with
  **no feature gate and no validation**. The fourth member of the family — `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`,
  resolved by `hee` `:230896-230906` — is gate-backed (`tengu_hazel_trellis`), memoised, and validates
  `Number.isInteger(r) && r >= 1`. Anthropic shipped the *budgets* as constants and the *depth* as a
  remotely tunable value, because depth was the one they expected to change without a release — and it
  did, between `.217` and `.219` (see [`../_GROUND_TRUTH_verified_anchors.md`](../_GROUND_TRUTH_verified_anchors.md) §2).
- **Why 200 and not 50?** 200 is high enough that a legitimate long session never sees it and low enough
  that a runaway loop terminates in bounded time. The changelog says so explicitly for both: *"to stop
  runaway search loops"* / *"to stop runaway delegation loops"*. These are **loop breakers, not quotas**.

**Careful reading required on the "four caps" framing.** All four env vars are registered contiguously
in the accessor table at `:32122-32125`, and three of the constants share one `var` block at
`:231411-231413`. That adjacency is *suggestive* of common authorship but proves nothing about release
timing — the bundle is a single build with no per-declaration provenance. The changelog attributes
`MAX_CONCURRENT_SUBAGENTS` to `.217` and the depth cap to `.217`/`.219`; only **two** of the four are
`.212` bullets. Do not let the code layout override the release record.
Full derivation: [../53_subagent_limits/concurrency_and_session_caps.md](../53_subagent_limits/concurrency_and_session_caps.md).

### 3.4 MCP auto-backgrounding: a race that refuses to fire while a human is being asked

**What it does:** an MCP tool call still running after 2 minutes is converted into a registered
background task; the model gets a text result telling it the work continues, and the session stays usable.

**How it works:** `EEy` `:288862` races the tool promise against a timer, but the loop is the interesting
part:

```javascript
// ============================================
// callMcpToolWithAutoBackground - deadline race with an elicitation escape hatch
// Location: cli_inner_pretty.js:288862-288900
// ============================================

// ORIGINAL (for source lookup):
let c = new AbortController(), u = v9r(o, c), d = Date.now(), p = e(c.signal),
    f = p.then(() => "settled", () => "settled"),
    m = new AbortController();
try {
  while (!0) {
    if ((await Promise.race([f, vr(s, m.signal).then(() => "timeout")])) === "settled" || o.signal.aborted)
      return (u(), await p);
    if (a?.()) continue;
    break;
  }
} finally { m.abort(); }

// READABLE (for understanding):
const detachController = new AbortController(),
      unlink = linkAbortSignals(parentAbort, detachController),
      startedAt = Date.now(),
      toolPromise = runTool(detachController.signal),
      settled = toolPromise.then(() => "settled", () => "settled"),
      timerAbort = new AbortController();
try {
  while (true) {
    const winner = await Promise.race([settled, sleep(autoBackgroundMs, timerAbort.signal).then(() => "timeout")]);
    if (winner === "settled" || parentAbort.signal.aborted) { unlink(); return await toolPromise; }
    if (hasPendingElicitation?.()) continue;   // deadline expired, but a human is being asked -> re-arm
    break;                                     // deadline expired with nobody waiting -> promote
  }
} finally { timerAbort.abort(); }

// Mapping: EEy→callMcpToolWithAutoBackground, e→run, s→autoBackgroundMs, a→hasPendingElicitation,
//          o→parentAbortController, v9r→linkAbortSignals, vr→sleep, p→toolPromise
```

**Why this approach:**

- **`if (a?.()) continue;` is the whole design.** An MCP server that has issued an *elicitation* — a
  prompt back to the user — is slow because a human is reading it, not because the tool is stuck.
  Backgrounding it would move a dialog the user is currently looking at into a task list. So the
  deadline is *re-armed* rather than cancelled, which means an elicitation-heavy tool can exceed the
  2-minute budget indefinitely and never be promoted. That is intentional and correct.
- **The tool is never cancelled.** `detachController` is created but not aborted on the timeout path;
  `unlink()` only severs the parent's ability to cancel. The call keeps running and reports through the
  task registry. The model-facing text at `:288965` says so, and adds the honest caveat
  *"Note: it does not survive exiting this session."*
- **Four kill switches, checked in order** (`SEy` `:288854`): a per-type deny set (`bEy`), a global
  disable `LE()`, a non-interactive-session rule that requires `CLAUDE_AUTO_BACKGROUND_TASKS`, then
  the env override clamped `Math.min(Math.max(0, r), _Ey)` where `_Ey = 2147483647`, and finally the
  gate `tengu_mcp_auto_background` defaulting **on** with `yEy = 120000`. Returning `0` at any rung
  disables the feature for that call — the "off" value and the "no deadline" value are the same number,
  which is why the clamp floors at 0 rather than rejecting negatives.
- **Why 120,000 ms?** It is longer than any interactive tool a user will wait through and shorter than
  the pre-existing MCP idle-timeout of 300,000 ms (`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`, `:32119`). The
  two mechanisms are deliberately ordered: background first at 2 min, abort as dead at 5 min.

**Key insight:** every other "slow operation" mechanism in the codebase cancels or errors. This one
*promotes*. The promotion is possible only because MCP already had a task registry and a notification
channel — the feature is 40 lines because the plumbing was already there.
Full derivation: [../39_mcp/auto_background_tool_calls.md](../39_mcp/auto_background_tool_calls.md).

### 3.5 Deprecating Task `mode`: keep the field, empty the semantics

**What it does:** the Task tool's `mode` parameter is still accepted by the schema and is now ignored;
subagents inherit the parent session's permission mode.

**How it works:** the diff is one `.describe()` string and one deletion.

```javascript
// ============================================
// taskModeParameterDeprecation - the field survives, its meaning does not
// Location: cli_inner_pretty.js:398226-398230 (220)  ·  :430392-430394 (193)
// ============================================

// ORIGINAL (for source lookup):
// 220 :398226
mode: pWl()
  .optional()
  .describe(
    "Deprecated; ignored. Subagents inherit the parent session's permission mode; agent-definition frontmatter may override it.",
  ),
// 193 :430392
mode: Ihs()
  .optional()
  .describe('Permission mode for spawned teammate (e.g., "plan" to require plan approval).'),

// READABLE (for understanding):
// 2.1.220 — schema field retained so old callers still validate; semantics removed
mode: permissionModeEnum().optional().describe(
  "Deprecated; ignored. Subagents inherit the parent session's permission mode; agent-definition frontmatter may override it."),
// 2.1.193 — the field actually selected the child's permission mode
mode: permissionModeEnum().optional().describe(
  'Permission mode for spawned teammate (e.g., "plan" to require plan approval).'),

// Mapping: pWl/Ihs→permissionModeEnum
```

The proof that the removal is real, not cosmetic: `mode` is **gone from the handler's `call`
destructuring** (`:398314` vs `:430466 (193)`), and the literal `mode parameter` is **220=0 / 193=2** —
two prompt strings in 2.1.193 that told the model how to use it, both deleted.

**Why this approach:**

- **Keeping the field is a compatibility decision.** Removing it from the zod schema would make every
  stored agent definition, SDK caller and replayed transcript that still sets `mode` fail validation.
  Optional-and-ignored costs nothing and cannot break a caller.
- **Why deprecate at all?** `mode` let a *model* choose the permission mode of the agent it spawned.
  That is a privilege-escalation shape: a subagent asked to run in a laxer mode than its parent. Making
  inheritance the only rule closes it, and the `.describe()` text names the single sanctioned override —
  **agent-definition frontmatter**, which is authored by a human on disk, not by the model at call time.
- **This is the same programme as §3.2.** Both bullets remove a way for the permission mode of an
  operation to be something other than the session's own. `.212` is, quietly, a permission-mode
  integrity release.

Full derivation: [../53_subagent_limits/budget_and_delegation_hardening.md](../53_subagent_limits/budget_and_delegation_hardening.md) §6.
