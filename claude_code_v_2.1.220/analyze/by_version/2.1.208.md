## 1. Release narrative

**`.208` is where the window's feature work stops and its engineering debt gets paid.** Of its 46
bullets, exactly four are "Added" — screen reader mode, `vimInsertModeRemaps`,
`CLAUDE_CODE_PROCESS_WRAPPER`, and mouse clicks in multi-select menus — and one of those four
(screen reader mode) is not an addition at all. The remaining 42 bullets are fixes, and **eleven of
them are explicitly about resource consumption**: four memory leaks in one bullet, a 16 MiB read
cache, a 200-row table cap, a 50-document LSP LRU, a 79× transcript reduction, a long-single-line
read guard, two CPU bullets that turn out to be one three-line hoist, and a render-responsiveness
claim that carries no literal at all. Nothing in the window before or after it looks like this.
`.207` was a *trust-boundary* release (three privilege fixes); `.210` is a *containment* release
(worktree escape, prompt-injection scrubbing, human-origin gating). `.208` sits between them and is
about the process not falling over.

**The centre of gravity is "long sessions and long-lived processes".** Read the resource bullets
together and they describe one failure story: a Claude Code session that has been open for hours,
with MCP servers attached, LSP documents open, many permission rules, a large transcript, and a
background daemon behind it. Every one of the eleven fixes bounds something that previously grew
without limit — stderr buffers (`:294911`), LSP open documents (`zCy = 50`, `:307353`), the file-edit
read cache (`tky = 16777216`, `:310490`), rendered table rows (`_Up = 200`, `:636511`), the selected
byte range of a read (`maxSelectedBytes`, `:235122`), the transcript (delta records instead of
snapshots, `file-history-delta` 220=5 / 193=0), the fork-context cache (`bB_ = 16777216`, `:527424`).
The CPU half of the same story is a **loop-hoist**, not a cache: `nve` (`:425004-425007`) now builds
the deny-rule array once per turn instead of once per candidate tool, and threads it into `WB`
(`:513293-513299`) — three lines that satisfy two separate changelog bullets.

**The second theme is version skew between processes.** `CLAUDE_CODE_PROCESS_WRAPPER` (13 sites,
193=0) makes every Claude Code self-spawn go through a corporate launcher, and four new telemetry
gates (`tengu_bg_respawn_downgrade_refused` `:553647`, `tengu_daemon_upgrade_refused_stale_binary`
`:870704`, plus siblings registered at `:537417-537443`) exist because a daemon and the binary it was
launched from can now diverge in *three* independent ways: the binary was replaced by an auto-update,
the daemon is older than the workers it supervises, or the daemon predates the launcher config. The
bundle even ships a message for the third case (`:680396`) that *retires* the offending daemon
outright — behaviour the changelog never mentions.

**The trap in this release is its first bullet.** "Added screen reader mode" is the single most
over-claimed line in the whole window. `--ax-screen-reader`, `CLAUDE_AX_SCREEN_READER`,
`axScreenReader`, the settings group that wraps it, the group's `buildGate: () => !0`, and the
byte-identical description string **all exist in 2.1.193**. See §3.1 — and note that even the
correction recorded in [`../00_overview/_scope_v206_210.md`](../00_overview/_scope_v206_210.md) and
[`../00_overview/_false_delta_ledger.md`](../00_overview/_false_delta_ledger.md) (which says the
*settings group* is the new part) is itself wrong, and is corrected below with both line numbers.

**Two bullets that every prior pass filed as unanchored are anchored here.** `.208` #12
(`CLAUDE_CODE_MAX_OUTPUT_TOKENS` using the mantissa of `1e6`) resolves cleanly to a **new numeric
parser**, `Fd` / `fUm` at `:4431-4444`, replacing 193's bare `parseInt(t, 10)` at `:234885 (193)` —
§3.3. And `.208` #17's Bedrock message bullet is not the flat CARRYOVER the ledger records: the old
message survives untouched at 2/2 but has been made *mostly unreachable* by a new pre-emptive
content-type guard at `:149991-149999` — §3.5.

### 3.1 Bullet #1 — screen reader mode was *promoted*, and even the recorded correction is wrong

**What it does:** the bullet claims `.208` introduced screen reader mode via three surfaces. All
three predate it, and so does a fourth surface the tree's existing correction credits to `.208`.

**How it works:**

1. **The flag, env var and setting.** 2.1.220's zod field is at `:60191` inside a group at
   `:60188-60197`. 2.1.193's is at `:55849 (193)` inside a group at `:55846-55855 (193)`. The
   `.describe(...)` string is **byte-identical** in both.
2. **⚠ The "settings group" story recorded in
   [`_GROUND_TRUTH`](../_GROUND_TRUTH_verified_anchors.md) §3, `_scope_v206_210.md` (`.208` note) and
   `_false_delta_ledger.md` register 1 is itself incorrect.** Those files say the delta is the group
   wrapper `screenReader: { buildGate: () => !0, … }` plus `"screenReader"` joining the group list at
   `:60112`. I read both bundles: 193 already has `buildGate: () => !0` at `:55847 (193)`, and 193's
   group list at `:55780 (193)` is `["autoMode", "deepLink", "voice", "briefView", "screenReader"]` —
   **byte-identical to 220's `XHh` at `:60112`.** So the settings group is *also* carryover. The
   literal-count bump (`screenReader` 220=9 / 193=3) comes from the renderer, not the settings layer.

### 3.2 Bullet #3 — `CLAUDE_CODE_PROCESS_WRAPPER`: an enterprise launcher with a contract

**What it does:** lets an administrator interpose a wrapper executable in front of *every* Claude Code
process that Claude Code itself spawns — the background-agent supervisor, the sessions and workers it
hosts, and self-exec on upgrade. 13 sites, 193=0.

**How it works:**

1. **Two configuration surfaces with an explicit precedence.** The env var `CLAUDE_CODE_PROCESS_WRAPPER`
   (named at `:267645`) takes precedence; the settings key `processWrapper` (`:60628-60632`) is
   resolved from exactly three scopes, in this order (`:267852-267854`):
   `policySettings` → `flagSettings` → `userSettings` (and the last only when `pg("userSettings")`
   permits). **`projectSettings` and `localSettings` are not consulted at all** — the description
   string at `:60632` says so in as many words. That is the same trust-boundary reasoning as `.207`'s
   `pluginConfigs` and `autoMode` fixes: a repo must never be able to name the binary that wraps your
   shell.
2. **A failure taxonomy, not a boolean.** The bundle distinguishes *misconfigured* (`:679805`,
   `"CLAUDE_CODE_PROCESS_WRAPPER is misconfigured"`), *not runnable* (`:501792`, `:679812`), and
   *deleted or moved* (`:554414`, `:870277` — ENOENT gets its own message telling you to fix the
   variable and rerun). An upgrade that cannot use the launcher is **deferred, not skipped**:
   `:870716` logs `binary at ${g} changed but CLAUDE_CODE_PROCESS_WRAPPER cannot be used (${te}) —
   deferring the upgrade restart until it is fixed (re-checked every poll)`.
3. **The daemon can be retired for predating the launcher.** `:680370-680396` decides to kill a
   running supervisor when either (a) it runs an older version than this binary, or (b)
   `a.origin === "transient" && !a.processWrapper && a.version === "2.1.220"` — i.e. **a same-version
   daemon that was started before the wrapper was configured**. The log line at `:680396` reads
   `bg: <daemon> pid <n> predates CLAUDE_CODE_PROCESS_WRAPPER and spawns sessions unwrapped — retired
   it so the replacement runs through the configured launcher`.
4. **A numbered launcher contract.** `:680415` is the most unusual string in the release: when a raw
   (unwrapped) daemon reappears after a launcher-driven restart, the message enumerates the two
   indistinguishable causes and names the rule that was broken —
   *"the launcher does not pass that variable through in the environment it hands to `exec`
   (launcher contract #3)"*. A numbered contract implies external documentation for wrapper authors,
   which is exactly what the settings description at `:60632` points at
   ("the Claude Code corporate-launcher documentation").

**Why this approach:**

- **Why wrap self-spawns rather than the entry point?** An administrator can already control the
  entry point. What they cannot control is the daemon that Claude Code re-spawns hours later, after an
  auto-update, in a different environment. Hooking self-spawn is the only place that catches all of
  them.
- **Why retire an unwrapped same-version daemon?** Because a daemon started before deployment looks
  perfectly healthy. Every session it dispatches escapes the launcher silently, which is precisely the
  audit hole the feature exists to close. Fail-loud (kill and log at `warn`) is the only posture that
  makes the control trustworthy.
- **Trade-off taken:** three of the four failure paths *defer* rather than *degrade*. Claude Code
  would rather stop upgrading than run outside the launcher.

**Key insight:** this is not an env var, it is a **process-lineage policy** with a documented contract,
a per-scope trust boundary, a four-way failure taxonomy and a self-healing retirement rule. Full
treatment: [36_background_agents/daemon_lifecycle.md](../36_background_agents/daemon_lifecycle.md) §3.
