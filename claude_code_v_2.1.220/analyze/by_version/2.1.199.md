## a) What this release was for

`2.1.199` is the **hardening tail of the `.198` autonomy push**. `.198` had just flipped subagents to
run in the background by default, made background agents ship draft PRs on their own, and put the
Explore agent on the session model. `.199` is the bill for that: eleven of its twenty-four bullets are
background-agent or subagent bugfixes, and every one of them is about *an autonomous unit dying badly*
— a daemon that suicides every fifty seconds, a subagent that reports a rate limit as success, a
`claude stop` that a respawn quietly undoes, a cold start over SSH that cannot reach an Aqua session.
There is no new user-facing feature except stacked slash-skills; this is a release whose purpose is to
make the previous release survivable.

The second, smaller centre of gravity is the **API retry policy**, and it is where `.199` does its most
consequential work. Four bullets (`#2`, `#3`, `#22`, `#23`) all land inside one file region —
`cli_inner_pretty.js:227948-228060` and `:534940-534991` — and together they change what "the request
failed" means. Before `.199` an SSL misconfiguration burned the entire retry budget before showing the
user anything useful, a mid-stream `overloaded` threw away a half-written assistant turn, a 429 that had
nothing to do with your usage limit ended the turn for a subscriber, and `CLAUDE_CODE_MAX_RETRIES` was
hard-clamped at 15 no matter what. After `.199`: fail fast on non-retryable transport errors, keep the
partial, retry the *transient* 429s, and let a watchdog-mode operator ask for 300 retries. The retry
budget change is the single most-cited `.199` bullet in this tree and also its most-misread one — the
two env-var names in the bullet are **carryover**, and only the numbers and the branch shape moved
(§c.3).

Third: `.199` contains two changes that read as trivia and are not. `_Al()` at `cli_inner_pretty.js:130`
is a four-line argv peeler that fixes an entire *class* of "global flag placed before a subcommand" bugs
— it is the third function in the whole bundle, running before anything else. And `a4o()` at
`cli_inner_pretty.js:536559` reorders a `throw` so that a corrupted `.claude.json` is copied to a
timestamped backup *before* the startup recovery dialog is allowed to reset it. That one is a data-loss
fix, has no module doc in this tree, and is derived in full in §c.1.

Relative to its neighbours: `.198` was the behaviour change, `.199` is its repair, `.200` (the very next
release) continues the same background-agent repair queue with the daemon lock and the roster, and
`.201` is a single-bullet model hotfix that has nothing to do with either. Read `.198`→`.199`→`.200` as
one continuous background-agent stabilisation arc.

### c.1 Bullet 19 — the corrupted-config reset destroyed the file because the `throw` came first

**No module doc in this tree covers this bullet.** It is derived here in full.

**What it does:** when `.claude.json` fails to parse, Claude Code copies it to a timestamped
`<name>.corrupted.<epoch>` file in the backup directory before anything else touches it. In 2.1.193 the
*caller that resets the file* — the startup recovery dialog — was the one caller that skipped the backup
entirely, so choosing "reset" from that dialog destroyed the only copy of the corrupt config.

**How it works:**

1. Both builds classify a read failure into `ENOENT` (missing file → print the restore hint, return
   defaults) and `ConfigParseError` (corrupt → recover).
2. Both builds then run the identical five-step backup: `mkdir` the backup dir, list existing
   `<base>.corrupted.*` snapshots, read the current file, compare byte-for-byte against each snapshot,
   and copy only if no snapshot already matches. The **dedupe is why re-launching after a crash does
   not fill the disk with identical snapshots** — and it also produces the distinct message
   `The corrupted file has already been backed up.` (220 `:536615` / 193 `:604619`).
3. **The only structural difference is where the strict-caller `throw` sits.** 193 puts it at
   `:604587 (193)`, *ahead* of the whole recovery block: `if (o instanceof IN && n) throw o;`. 220 moves
   it to `:536629-536641`, *after* the backup has completed, and adds a `tengu_config_parse_error` event
   carrying `has_timestamped_backup` so the outcome is observable.

**Why the bullet reads as a data-loss fix:** the third argument is the "I will handle corruption myself"
flag, and the startup recovery dialog is exactly the caller that sets it — it wants the raw error so it
can offer "reset". In 193 that flag short-circuited past the backup, so the one code path whose *next
action was to overwrite the file* was the one path that had not preserved it.

**Why this approach:** the alternative — teaching the recovery dialog to call a `backupCorruptedConfig()`
helper itself — was available and was not taken. `backupCorruptedConfig` greps **0/0** in both bundles;
there is no such helper. Moving the `throw` puts the invariant *"nothing observes a corrupt config
without a snapshot existing"* inside the single function that can enforce it, rather than inside every
caller. That is a fail-safe-by-construction choice, and it costs one `await fs.copyFile` on a path that
was already about to show a modal dialog.

**Key insight and the trap:** every string in this block is **220=1 / 193=1**
(`Corrupted config backed up to:`, `Could not back up corrupted config`,
`The corrupted file has already been backed up.`, `.corrupted.` 3/3). A literal-counting pass scores this
bullet as pure carryover and moves on. The delta is a **statement reordered across an early return** —
invisible to grep, visible only by reading both functions end to end. It is the cheapest possible
illustration of `_CONVENTIONS.md` §4 trap 7.

**Undocumented, in the same function:** 2.1.220's config reader is **`async`** (`await n.readFile`,
`await n.mkdir`, `await n.readdir`, `await n.copyFile`); 2.1.193's was fully synchronous
(`readFileSync`, `mkdirSync`, `copyFileSync`, `readdirStringSync`). The config load moved off the
synchronous filesystem path entirely, and no bullet in this window mentions it.

### c.2 Bullets 4 + 5 — one code change: a subagent that dies to a rate limit now says so, and hands back what it wrote

**How it works, step by step:**

1. The subagent loop now **throws** `AgentApiErrorTerminationError` when the inner API call fails, instead
   of returning whatever it had. That is bullet 5 in one sentence: the failure becomes a control-flow
   event with a typed `errorKind` rather than an empty-but-successful return value.
2. `finishSubagentAfterError` runs `recoverPartialSubagentOutput` **first**, so the happy-ish path
   (transient error, some text written) is checked before the rethrow.
3. `recoverPartialSubagentOutput` applies four independent filters in increasing cost order: the error
   class check (free), the `errorKind` whitelist (a `Set` probe), the error-turn filter (one array pass),
   and the "is there any non-error assistant text at all" scan (a backwards walk that stops at the first
   hit).
4. Filter 3 is doing real work: the transcript at the point of failure contains an assistant message with
   `isApiErrorMessage: true` — the rendered API error itself. If it were handed to the parent, the parent
   would read a rate-limit banner as if it were the subagent's finding. Both the filter and
   `lastNonErrorAssistantText`'s skip clause exist to make sure the *only* thing the parent sees is text
   the subagent actually produced.
5. The `cutoffNote` prepends the sanitised error message and then the fixed notice at `:345902`. Note
   `prependMarker: !1` — the error message is deliberately *not* given the harness marker prefix that the
   sanitiser normally adds, because it is already inside a note the parent is being told to distrust.

**Why the whitelist has exactly three members:** `rate_limit`, `overloaded`, `server_error` are the
error kinds where *the work already done is still valid* — the subagent was reasoning correctly and the
server ran out of capacity. Anything else (a 400 from a malformed request, an auth failure, a refusal)
means the run itself was ill-formed, and returning half of it to the parent would launder a broken run
into a "partial finding". Those cases take the `throw` at `:345911`, and the parent gets an error.

**Why this is not simply "always return the history":** look at the two counters. `api_error_partial`
(`:345907`) and `sync_error_partial` (`:345913`) are *different* events for what is superficially the
same outcome. The first means "an upstream transient failure truncated a valid run"; the second means "a
local exception happened but there was still text". Collapsing them would make the fleet-level question
*"how often does capacity cost us subagent work?"* unanswerable.

**Key insight:** the pre-`.199` behaviour was worse than a crash. A rate-limited subagent returned a
*successful* result containing nothing, and the parent agent — which cannot see the subagent's
transcript — had no way to distinguish "explored the codebase and found nothing" from "never ran". The
fix's real content is not the partial recovery; it is that **the absence of output stopped being
ambiguous**. Everything else (the whitelist, the note, the two counters) is refinement on top of that
one distinction.

### c.3 Bullet 23 — the retry-count bullet is a numeric delta wearing two carryover env vars

`57_api_reliability/retry_policy.md` §1 derives the mechanism. This section exists to nail the *framing*,
because the bullet is listed in [`../00_overview/_false_delta_ledger.md`](../00_overview/_false_delta_ledger.md)
register 1 and must never be written up as "added `CLAUDE_CODE_RETRY_WATCHDOG`".

| Anchor | 2.1.220 | 2.1.193 | Reading |
|---|---|---|---|
| `CLAUDE_CODE_RETRY_WATCHDOG` | **2** | **2** | carryover — the env var already existed |
| `CLAUDE_CODE_MAX_RETRIES` | **5** | **4** | carryover — one extra unrelated site |
| resolver | `Pqs` `:534954-534967` | `O5f` `:603209-603221 (193)` | rewritten |
| watchdog reader | `WUe` `:534513-534515` (`Yt(process.env.CLAUDE_CODE_RETRY_WATCHDOG)`) | *absent from the resolver* | the delta |
| default | `e ? NU_ : $U_` = 300 or 10 (`:534966`, `:534989-534990`) | `_5f` = 10 (`:603220`, `:603243 (193)`) | 10 → 10-or-300 |
| clamp | `if (t > X9s && !e)` with `X9s = 15` (`:534959`, `:534991`) | `if (e > Ujo)` with `Ujo = 15` (`:603213`, `:603244 (193)`) | unconditional → watchdog-conditional |

Both the constant `15` and the warning `CLAUDE_CODE_MAX_RETRIES=${…} clamped to 15` survive verbatim
(`:534960` vs `:603214 (193)`). What moved is the guard on that clamp: 193 clamped *always*, 220 clamps
only `&& !e` — only when the watchdog is off.

**Why the clamp survives at all rather than being deleted:** a retry budget is a denial-of-service
control on the *user's own bill and terminal*. Without the watchdog there is no upper bound on how long a
retried request can take, so an operator typing `CLAUDE_CODE_MAX_RETRIES=10000` would hang the session
silently. The watchdog is precisely the component that *does* bound wall-clock time independently, so
when it is on the count limit becomes redundant and the clamp is dropped. **The two flags are not
independent knobs — one is the precondition for the other**, and that dependency is exactly what the
changelog bullet's phrasing ("`CLAUDE_CODE_RETRY_WATCHDOG` … lifts the cap of 15 on
`CLAUDE_CODE_MAX_RETRIES`") is describing.

**Why 300 and not "unlimited":** `NU_ = 300` (`:534990`) is a *default* that only applies under the
watchdog, and it is 30× the normal default of 10. Combined with a wall-clock watchdog, 300 is
"effectively unlimited for any request that is actually making progress" while still terminating a
pathological loop. `300` is also the count *after* the clamp was removed — an operator can raise it
further, which is what "lifts the cap" means.

Bullet 22 rides in the same file region and is a one-disjunct change to the retryability predicate:
`:603205 (193)` `if (e.status === 429) return !Eo() || pnt();` becomes `:534947`
`if (e.status === 429) return !ii() || zer() || $lp(e);`, with `$lp` (`:534951-534953`) returning true
for a 429 that is **neither** a usage-limit error **nor** carries the unified-rate-limit header. That is
a *header-absence* test — see [57_api_reliability/retry_policy.md](../57_api_reliability/retry_policy.md)
§2 for why absence rather than a status sub-code.

### c.4 Bullet 21 — the browser auto-allow list did not grow; it acquired a gate

Short, because [05_plan_mode/readonly_auto_allow_198_199.md](../05_plan_mode/readonly_auto_allow_198_199.md)
§1 derives it fully. Stated here because the bullet invites the wrong verdict.

The 9-name browser tool set is **carryover**: `OKt` at `:34675-34684` is the same nine names as
`Kvt` at `:12536-12546 (193)`. In 193 the plan-mode permission sweep skipped *every* member of that set
unconditionally. In 220 the same sweep at `:289063` reads:

```javascript
if (n.name === "browser_batch" || (OKt.has(n.name) && cOt(n.name, o))) continue;
```

`cOt` (`:288994-288999`, **220=4 / 193=0**) is the new gate: an unconditional read-only set `vEy`
(`list_connected_browsers`, `resize_window`, `shortcuts_list`, `switch_browser`, `tabs_close_mcp`,
`:289007-289013`) plus a table of per-tool *argument* predicates `len` (`:289002-289006`) —
`read_console_messages` and `read_network_requests` are read-only only when `input.clear` is falsy
(`z9u`, `:288991-288993`), and `tabs_context_mcp` has its own predicate.

So the change is a **tightening**, not a widening: three of the nine tools moved from
"always auto-allowed" to "auto-allowed only when their arguments prove they mutate nothing". `BEy`
(`:289288-289293`, 2/0) applies the same predicate *inside* a `browser_batch`, and its default is
fail-closed — a sub-action that is not a recognisable object returns `true` (needs a prompt) at
`:289291`. The changelog's "read-only `browser_batch` calls are now correctly auto-allowed" is the
visible half; the invisible half is that non-read-only ones stopped being auto-allowed.

## d) What the changelog does not say

**1. The `#14` hook fix is a wrapper, not a new attachment type.** `hook_non_blocking_error` is
**220=24 / 193=23** — the attachment already existed and 23 tool-hook sites already used it. `Pur`
(`:520551-520562`) is the one new thing: it re-shapes a *blocking* error from a non-tool hook into a
non-blocking attachment with a **synthetic** `exitCode: 2` (`:520559`) — synthetic because
`SessionStart`/`Setup`/`SubagentStart` have no tool-use to attach to and the real exit code has already
been consumed by the blocking path. Anyone citing the 24-count as proof of a new feature is wrong.

**2. Bullet 1's cap of 5 has five undocumented disqualifiers.** `epd = 5` (`:344087`) is the number in
the changelog. What the bullet omits is that a leading `/command` is silently excluded from stacking when
it is `context: "fork"`, defines `getContext`, or sets `argsMayContainSlashCommands` — the check is
inline at `:343681-343683` and short-circuits the peeler entirely with `{ stacked: [], capped: !1 }`.
So `/fork-ish-skill /other do X` does not stack and gives no feedback about why.

**3. Bullet 15's peeler accepts a flag the bullet never names.** `_Al` (`:130-134`) skips **both**
`--dangerously-skip-permissions` *and* `--allow-dangerously-skip-permissions` before testing for
`daemon`. The changelog names only the first. It also loops (`while`), so any number of repetitions of
either flag are peeled — the fix is general over the flag prefix, not a special case for one spelling.

**4. Bullet 24 is carryover and the "PR" label did not disappear from the bundle.** The row builder at
`:160555` emits `` `#${e.prNumber}` `` (or `` `${repo}#${n}` `` when a repository is known) and is
byte-identical to `:11182 (193)`. A `PR #`-prefixed renderer is still live at `:722854`
(`LgS`, a URL→label rewriter used elsewhere in the UI). Whatever row-level label the bullet describes
removing is not visible as a string delta in this build.

**5. Bullet 17's stated fix shipped switched off.** The bullet promises transcripts stop growing when a
resume has no new messages. The mechanism the scoping pass points at is `tengu_transcript_local_gc`
(`:840678`), and it resolves as `Z.CLAUDE_CODE_TRANSCRIPT_LOCAL_GC ?? Ke("tengu_transcript_local_gc", !1)`
— **default `false`**, with an env override. The user-visible fix therefore comes from the dedup path
described in [50_performance/disk_and_transcript.md](../50_performance/disk_and_transcript.md) §3, not
from the GC, and the GC is a dark-launched second mechanism with no bullet of its own.

**6. Bullet 11's headline literal moved the wrong way.** `Reconnecting` is **220=41 / 193=42** — the
count went *down*. There is no new flapping-related string; the only 220-only anchor in the region is a
gate, `tengu_remote_bootstrap_cycle_hidden` (`:757247`, 1/0), and reading its site does not connect it to
a Working/Idle transition. Recorded as `UNANCHORED` rather than dressed up.

**7. Two of the release's bugfixes have no source anchor at all in the JS bundle** (`#9` progress
indicators, `#18` `/color` on backgrounded rows). For `#18` the scoping candidate is wrong outright: the
literal `"/color` is **0/0** in both bundles. These are honest gaps, listed in the ledger as such.

**8. The undocumented change inside bullet 19's function: the config loader became asynchronous.**
See §c.1. 193's `AEt` used `readFileSync`/`copyFileSync`/`mkdirSync`/`readdirStringSync`; 220's `a4o`
is `async` throughout. That removes four synchronous filesystem calls from a path that runs before the
first frame is drawn, and it is not mentioned by any bullet in this window.
