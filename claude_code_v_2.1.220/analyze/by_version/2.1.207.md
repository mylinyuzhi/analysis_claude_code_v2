## 1. Release narrative

**2.1.207 is where auto mode stopped being an experiment.** The headline bullet reads like a
provider-availability tweak — *"Auto mode is now available without `CLAUDE_CODE_ENABLE_AUTO_MODE`
opt-in on Bedrock, Vertex AI, and Foundry"* — and it is implemented as a **single-line deletion of an
env-var read**: `Eer` (`:150416-150419`) is now `if (e === "firstParty" || iW(e)) return !0; return !0;`,
where 2.1.193's counterpart `ont` (`:135186-135189 (193)`) ended in
`return at(process.env.CLAUDE_CODE_ENABLE_AUTO_MODE)`. Everything else in the release orbits that
decision. Once a model-driven approver runs by default on every provider, three questions become
urgent: *whose* rules does it obey, *whose* settings can turn it on, and *what* can a repository put in
front of it. `.207` answers all three, and that is the release's centre of gravity.

**Four of its 24 bullets move the same trust boundary in the same direction — repository files lose
authority.** Auto-mode classifier rules may no longer come from `.claude/settings.local.json`
(`tengu_settings_auto_mode_rules_untrusted_source_ignored`, `:63563`, 220=1/193=0); plugin option
values may no longer come from project-level `.claude/settings.json`
(`a5g = ["userSettings", "flagSettings", "policySettings"]`, `:191083`); plugin hooks, monitors and MCP
`headersHelper` may no longer interpolate `${user_config.*}` into a **shell-form** command
(`:519965-519972`, `:764145-764149`, `:268206-268212`); and remote managed settings may no longer be
silently recorded as consented by a non-interactive run (`deferred_non_interactive`, `:455663`,
220=3/193=0). None of these four bullets names auto mode, and all four are consequences of it. Reading
`.207` bullet-by-bullet hides that; reading it as one change makes it obvious.

**The second half of the release is AWS, and it is the only release in this window whose successor
explicitly blames it for a regression.** `.207` #16 replaced a per-request AWS SSO credential
resolution with a memoised, expiry-aware, stale-while-revalidate cache keyed on
`${AWS_PROFILE}\0${region}` (`oW`/`Qeu`, `:156097-156121`, `:154821-154823`), and `.207` #21 wrapped the
default provider chain in a 60-second stall guard (`Jeu`, `:154799-154820`). Six bullets later, `.208`
#46 reads *"Fixed Bedrock auth failing with 'Session token not found or invalid' for AWS SSO profiles
whose `sso_region` differs from the Bedrock region (**2.1.207 regression**)"*. Caching a credential
under the wrong region key is exactly the failure mode a per-(profile, region) cache introduces, and the
next release paid for it. That closed loop — new cache in `.207`, region-keying bug surfaced in `.208` —
is the most instructive engineering story in this release.

**The third strand is agent-view and Remote Control polish**, and it is unusually rich for a
maintenance batch: a genuine crash-loop fix in the agent-team mailbox (~90 lines of net-new validation
bolted onto an otherwise byte-identical module, `:325091-325284`), `rosterName` for plan-auto-named
background sessions (`:683848`), a worded staleness clock on blocked peeks (`:803995`), and two Remote
Control transport fixes (`tengu_remote_active_goal_adopted` `:757214`; the SDK-host
`background_tasks_changed` emit at `:848974`).

**Where `.207` sits in the window.** It is the hinge between `.206`'s `/doctor`-era diagnostics work and
`.208`'s 46-bullet performance blowout. Two of its bullets are already **stale in the 2.1.220 bundle**:
#19's "default to Claude Opus 4.8" was overwritten by `.219` (the alias table at `:14461-14486` reads
`claude-opus-5` for bedrock/vertex/anthropic_aws), and #1's `CLAUDE_CODE_ENABLE_AUTO_MODE` messages at
`:529606` and `:529652` are now **unreachable strings**. A reader who reconstructs `.207` from the
changelog alone will state two things the bundle contradicts.

### 3.1 Bullet 3 — remote managed settings recorded as consented from `claude -p`

**What it does:** an enterprise's remote managed settings are fetched over the network. When the new
payload changes something security-relevant, the user must approve it in a dialog before it is applied
*and* before the payload is written to the on-disk cache as the new consented baseline. In 2.1.193 a
non-interactive run (`claude -p`, the SDK) **skipped the check and still advanced the baseline**, so the
dialog never appeared again on any later interactive run. 2.1.207 splits "may I apply this now?" from
"may I record this as consented?".

**How it works.**

```javascript
// ============================================
// runManagedSettingsSecurityCheck - four-way consent outcome (2.1.220) vs three-way (2.1.193)
// Location: cli_inner_pretty.js:455660-455670  (2.1.193 counterpart: :311944-311948 (193))
```

`Nka` (`:53944-53957 (193)` region; decl at `:53944 (193)` neighbourhood, body read at the `writeFile` +
`datasync` block) **writes `remote-settings.json` to disk**. So a `-p` run reached `Nka(...)` with no
dialog and the file on disk became the consented baseline — permanently. 2.1.220 (`:456810-456826`)
replaces the boolean with a four-arm switch:


`applied_consent_deferred` is **220=1 (`:456822`) / 193=0**. The non-interactive arm calls neither
`FPi` nor `TBd` — the settings take effect for this process and nothing is written.

**The state model changed to make this possible.** 2.1.193's remote-settings module declared exactly
three module variables (`:53966-53970 (193)`): `Cxt` (the settings), `Cwr` (an override-path memo) and
`Iwr` (a boolean). 2.1.220's declares five (`:58241-58248`) and two of them are new roles:

- `vxt` — current settings (`getRemoteSettings`, `BPi` `:58229-58235`)
- `B5n` — the **verified** baseline, set only by `o7t(e, { verified: !0 })` (`:58189-58192`), read by
  `J5l()` (`:58193-58195`) as `vxt !== null && vxt === B5n`
- `U5n` — the **consented** baseline, written by `FPi` (`:58186-58188`), read by `X5l()` (`:58183-58185`)

The consent comparison at `:456794-456796` is `pBd(wBd(X5l()), wBd(s), …)` — new payload against the
**consented** baseline, not against whatever happens to be cached. That separation is the whole fix;
without a third state slot there is no way to apply settings without consenting to them.

**Why this approach.** The obvious alternative — *refuse to apply managed settings in non-interactive
runs* — would break every CI and SDK deployment the moment an administrator changed a policy. The
chosen design keeps headless runs working (`fBd` at `:455691-455702` maps `deferred_non_interactive` to
`true`, i.e. "proceed") while making the deferral **non-durable**, so the first interactive session
still gets its dialog. Note the asymmetry with the sibling outcome: `deferred_no_consent_surface` maps to
`false` (`:455696`) and the caller returns `{ settings: r, fetchSucceeded: !1 }` (`:456802`) — an
*interactive* session that somehow has no dialog surface is treated as a **failure**, not a deferral,
and keeps the previously consented settings. Two deferrals, two opposite fail directions, chosen by
whether a human could in principle have been asked.

**Key insight:** the bug was not a missing check — 2.1.193 *had* a check and deliberately short-circuited
it for non-interactive runs. The bug was that the short-circuit returned the same token
(`"no_check_needed"`) as "there is nothing security-relevant here", and the caller could not tell the
two apart. **The fix is a widened return type, not new logic**, which is why the literal count moves
(3/0 and 4/0) while the control flow barely does.

### 3.2 Bullet 6 — the `/dev/null` exemption for compound `cd` redirects

Both [`../00_overview/_false_delta_ledger.md`](../00_overview/_false_delta_ledger.md) and
[`../38_permissions/README.md`](../38_permissions/README.md) record this bullet as *"the `bashMissKind`
label pre-exists; the `/dev/null` exemption lives inside the predicate"* and leave it there. It is
findable, and it is **one line**.

**What it does:** when Claude proposes a compound command that both changes directory and redirects
output (`cd build && make > log.txt`), Claude Code cannot statically determine the final working
directory, so it cannot know which file the redirect writes. It asks. 2.1.193 asked for **any** redirect;
2.1.220 asks only when at least one redirect target is something other than `/dev/null`.

```javascript
// ============================================
// checkCompoundCdRedirects - the .207 one-line change
// Location: cli_inner_pretty.js:391014-391028  (2.1.193 counterpart: :304515-304529 (193))
// ============================================

// ORIGINAL 2.1.193 (for source lookup):
function ehp(e, t, n, r) {
  if (r && e.length > 0)
    return { behavior: "ask", message: "Commands that change directories and write via output redirection require explicit approval …",
      decisionReason: { type: "other", reason: "Compound command contains cd with output redirection - manual approval required to prevent path resolution bypass", bashMissKind: "cd-compound-redirect" } };
  for (let { target: o } of e) { if (o === "/dev/null") continue; ... }

// ORIGINAL 2.1.220 (for source lookup):
function eqy(e, t, r, n) {
  if (n && e.some((o) => o.target !== "/dev/null"))
    return { behavior: "ask", message: "Commands that change directories and write via output redirection require explicit approval …",
      decisionReason: { type: "other", reason: "Compound command contains cd with output redirection - manual approval required to prevent path resolution bypass", bashMissKind: "cd-compound-redirect" } };
  for (let { target: o } of e) { if (o === "/dev/null") continue; ... }

// READABLE (for understanding):
function checkCompoundCdRedirects(redirects, permissionContext, sessionState, commandContainsCd) {
  if (commandContainsCd && redirects.some((r) => r.target !== "/dev/null"))
    return { behavior: "ask", message: COMPOUND_CD_REDIRECT_MESSAGE,
             decisionReason: { type: "other", reason: COMPOUND_CD_REDIRECT_REASON, bashMissKind: "cd-compound-redirect" } };
  for (let { target } of redirects) {
    if (target === "/dev/null") continue;                     // already present in BOTH builds
    ...
  }
}

// Mapping: ehp(193)/eqy(220)→checkCompoundCdRedirects, e→redirects, r(193)/n(220)→commandContainsCd
```

The diff is `e.length > 0` → `e.some((o) => o.target !== "/dev/null")`. Everything else in the
function — both message strings, the `decisionReason` shape, the `bashMissKind` label, and the
path-validation loop below — is byte-equivalent.

**Why this is the interesting shape.** The `/dev/null` exemption **already existed one line below**, at
`:391028` / `:304529 (193)`: `if (o === "/dev/null") continue;`. The per-target validation loop had
always known that `/dev/null` is not a path worth checking. The early return simply never asked. So the
bug was a **guard that was coarser than the logic it guarded** — a very common and very hard-to-spot
class, because reading either half in isolation looks correct. The fix aligns the guard's predicate with
the loop's, and after it the two are provably consistent: if every target is `/dev/null`, the guard
falls through and the loop skips every target, so the command is allowed with no further checks.

**Trade-off accepted.** `some(target !== "/dev/null")` is still conservative — one real redirect in a
ten-redirect command re-arms the prompt for all of them. The alternative (validate each target
independently and only prompt for the un-resolvable ones) is unsound here, because the whole reason for
the prompt is that the *working directory* is unknown, which makes every relative target unresolvable at
once. `/dev/null` is exemptible precisely because it is the one target whose meaning does not depend on
the working directory. **That is the whole rule: absolute, well-known, non-file sink → safe; anything
else → the cwd ambiguity applies.** No other target could have been added to this exemption without
resolving the cwd first.

**Why it matters more after `.207` #1.** `bashMissKind` values feed the auto-mode classifier's miss
taxonomy ([`../38_permissions/classifier_adjudication.md`](../38_permissions/classifier_adjudication.md)).
With auto mode now default-available on three more providers, a spurious `cd-compound-redirect` prompt
is no longer a rare annoyance — `2>/dev/null` and `>/dev/null` are ubiquitous in generated shell — so a
false prompt rate that was tolerable under opt-in became a visible defect under default-on. The two
bullets are the same release for a reason.

### 3.3 Bullet 24 — `/usage-credits` amount parsing and the $1,000 floor

**What it does:** the monthly-spend-limit input in `/usage-credits` used to normalise whatever you typed
by keeping its digits, so pasting a timestamp like `2026-07-24` silently became a limit. 2.1.207 replaces
normalisation with **full-string validation**, and adds a typed confirmation above $1,000.

```javascript
// ============================================
// parseUsageCreditsAmount - full-string amount validation, returning cents
// Location: cli_inner_pretty.js:692875-692884  (constants :695080-695082)

// READABLE (for understanding):
function parseUsageCreditsAmount(input) {
  let text = input.trim();
  if (text === "") return { ok: false, error: "Enter an amount" };
  let m = /^([0-9]+)(?:\.([0-9]{1,2}))?$/.exec(text);          // ANCHORED: no partial acceptance

// Mapping: hEt→parseUsageCreditsAmount, Xyf→MAX_SPEND_LIMIT_CENTS (1e6 = $10,000, :695081),
//          Yyf→TYPED_CONFIRM_THRESHOLD_CENTS (1e5 = $1,000, :695080), Lkr→CONFIRM_WORD ("yes", :695082)
```

**How the pieces fit.**

1. **`^…$` anchoring is the fix.** A digit-stripping normaliser accepts every string; an anchored regex
   rejects everything that is not exactly a decimal amount. `2026-07-24` no longer becomes `20260724`
   cents — it produces `"Enter an amount like 20 or 20.50"`.
2. **Cents are computed as integers.** `Number(whole) * 100 + Number(frac.padEnd(2,"0"))` never runs
   floating-point arithmetic on the money value, so `20.10` is exactly `2010` and not `2009.9999…`.
   `padEnd` is what makes `20.5` mean `$20.50` rather than `$20.05`.
3. **Two thresholds, two different responses.** `Xyf = 1e6` ($10,000) is a **hard rejection** with a
   message; `Yyf = 1e5` ($1,000) is a **soft gate** that routes into a confirmation component. The
   confirm branch at `:694102-694106` reads `if (VJe.cents > Yyf) { HKb(!0); return; }` — it does not
   submit, it flips a state flag, and `:694129-694139` then renders `GGt` (`:693953`) with
   `question: "Set your monthly spend limit to"` and `amountCents`, whose body requires typing the word
   `Lkr = "yes"` (`:695082`) — `["Type ", Lkr, " to confirm."]`.
4. **Error text is suppressed while typing.** `:694095` reads
   `IZo = !VJe.ok && (vkr.trim() !== "" || hje === 1) ? VJe.error : ""` — the error only shows once the
   field is non-empty *or* the user has advanced to the confirm step, so a half-typed `2` is not
   flagged as invalid mid-keystroke.

**Why a typed confirmation rather than a second Yes/No prompt.** A Yes/No dialog is dismissed by the
same Enter keystroke that submitted the amount — the exact input the user is already holding down.
Requiring a *different* token (`yes`) breaks keystroke momentum, which is the only reliable defence
against a mistyped order of magnitude. It is the same reasoning as the 500 ms input debounce on the
auto-mode onboarding prompt (`F4f = 500`,
[`../38_permissions/auto_mode_availability_and_gating.md`](../38_permissions/auto_mode_availability_and_gating.md) §7):
the risk is not that the user disagrees, it is that they never saw the question.

**Why $1,000 and $10,000.** $10,000 is a hard ceiling on a self-service monthly limit — beyond it the
flow is an admin request, which is the separate surface at `:692740-692742`
(`tengu_usage_credits_admin_request_confirm_shown`, 220=1/193=0). $1,000 is an order of magnitude below
it, i.e. the boundary at which a single mistyped digit ($100 → $1000) becomes expensive rather than
merely wrong. The two constants are adjacent in the same declaration block (`:695080-695081`), which
makes the intended relationship — confirm at 10% of the ceiling — explicit in the source.
