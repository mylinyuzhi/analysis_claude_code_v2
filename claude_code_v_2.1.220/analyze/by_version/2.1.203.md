## a) Release narrative

**2.1.203 is the release where background agents stopped being a feature and started being
infrastructure.** Twenty-two of its thirty-seven bullets touch the background daemon, its workers, its
worktrees, its environment, or the `claude agents` view. That is not a grab-bag: read them together and
they describe a system that had been shipped optimistically and was now being made survivable. A worker
whose session token went stale was **permanently** unreachable (#5). A daemon whose auto-upgrade failed
took **every running session** with it (#14). A worker whose working directory had been deleted
**crash-looped** instead of failing once (#13). A worktree-isolated subagent could run shell commands in
the **parent checkout** (#11). Each of those is the same category of defect: a distributed system with
no failure semantics for its own control plane.

The fixes have a common shape, and it is worth naming because it recurs eleven times in this ledger:
**replace a silent, unbounded retry with a bounded, instrumented, one-shot failure.** `settleCwdGone`
(`:554674`) fails a spawn once with `tengu_bg_spawn_cwd_gone` rather than respawning forever;
`tengu_daemon_refuse_stale_upgrade` (`:870697`) refuses to hand a session to a binary older than the one
running it; `rekeyForAuthMismatch` (`:554730`) re-keys instead of wedging; the worktree escape guard
(`:314164`, `:314192`, `:314210`) **refuses** rather than falling back to the shared checkout. In every
case the new behaviour is *less* forgiving and *more* observable — the trade the team makes over and
over in this release is availability for diagnosability.

The second thread is **environment hygiene at the daemon boundary**, and it is subtler than its two
bullets suggest. A background worker does not inherit the shell you typed in; it inherits the daemon's
environment, which was captured whenever the daemon started — possibly days ago, possibly under a
different `PATH`, possibly without your `ANTHROPIC_BASE_URL`. #8 and #9 are the same block of code
(`:553404-553428`) fixing two symptoms: a Windows `PATH` that arrived under the wrong letter case, and
a gateway URL whose absence sent your API key to `api.anthropic.com` and got a 401. That block is one of
the highest-value twenty lines in the whole bundle and neither bullet hints at its shape.

Third: `.203` contains the release's only **deep systems fix that is not about agents at all** — the
macOS false-low-memory stall (#4), where a shedder that 2.1.193 had *disabled on macOS by returning a
zero threshold* was re-enabled in `.196` using `os.freemem()`, which on macOS reports near-zero because
of the unified buffer cache. The fix replaces the measurement with a `bun:ffi` `dlopen` of
`libSystem.B.dylib` and a `sysctlbyname("kern.memorystatus_vm_pressure_level")` read. It is the only
place in this window where the client reaches into a platform kernel interface, and the changelog gives
it one line.

Finally, `.203` is where **the ← key stopped being a "close" gesture** (#33) and where the empty
`claude agents` view learned to explain itself (#34) — two small interaction changes that, together
with #6 ("your subagents keep running"), turn the agents view from a screen you back out of into a
place you can leave and return to. `.204`, a single-bullet release, and `.205` continue that repair;
see [`2.1.204.md`](2.1.204.md).

## c) Deep dives

`.203`'s four richest fixes all have module owners, so this section deliberately picks the parts the
module docs under-served: the *reasoning* behind the macOS probe's threshold (§c.1), the three-reason
structure of the worktree guard and why it refuses rather than falls back (§c.2), and the twenty-line
environment block that two separate bullets share (§c.3). §c.4 covers the ← state machine, which is the
only interaction change in this release with real depth.

### c.1 `#4` — the macOS low-memory probe, and why `>= 4`

**What it does:** decides whether the machine is under memory pressure, so the background daemon can
shed (retire) idle worker processes. Getting it wrong in the *false-positive* direction makes every
`claude agents` open stall 15–20 seconds while the daemon retires and re-spawns a worker it should have
kept.

**How it works — the three-point history matters here.**

```javascript
// ============================================
// getBackgroundLowMemoryState - macOS now reads kernel VM pressure instead of free RAM
// Location: cli_inner_pretty.js:552597-552603  (was Gnr, :575136-575139 (193))
// ============================================

// ORIGINAL 2.1.193 (for source lookup) - :575136-575139 (193):
function Gnr() {
  if (Wt() === "macos") return 0;
  return it("tengu_bg_low_mem_mb", 1024) * 1024 * 1024;
}

// ORIGINAL 2.1.220 (for source lookup) - :552597-552603:
function t7s() {
  let e = Ke("tengu_bg_low_mem_mb", 1024) * 1024 * 1024;
  if (e <= 0) return { lowMem: !1, level: void 0 };
  if (Mt() !== "macos") return { lowMem: Shp.freemem() < e, level: void 0 };
  let t = oq_();
  return { lowMem: t !== void 0 && t >= rq_, level: t };
}

// READABLE (for understanding):
function getBackgroundLowMemoryState() {
  const thresholdBytes = getFeatureValue("tengu_bg_low_mem_mb", 1024) * 1024 * 1024;
  if (thresholdBytes <= 0) return { lowMem: false, level: undefined };      // gate can disable entirely
  if (platform() !== "macos")
    return { lowMem: os.freemem() < thresholdBytes, level: undefined };     // free-RAM heuristic
  const pressureLevel = readMacVmPressureLevel();                          // kernel's own verdict
  return { lowMem: pressureLevel !== undefined && pressureLevel >= MAC_VM_PRESSURE_CRITICAL, level: pressureLevel };
}

// Mapping: Gnr→(193 threshold-only form), t7s→getBackgroundLowMemoryState, Ke/it→getFeatureValue,
//          Mt/Wt→platform, Shp→os, oq_→readMacVmPressureLevel (:552608), rq_→MAC_VM_PRESSURE_CRITICAL (:552630)
```

1. **2.1.193 returned a threshold of `0` on macOS**, and the caller `i7t()` (`:575140-575143 (193)`)
   tested `e > 0 && freemem() < e` — so on macOS the shedder was *structurally disabled*.
2. **2.1.196 evidently enabled it** using the same `os.freemem()` path. On macOS `freemem()` reports
   only the truly free page count; the unified buffer cache legitimately holds most of RAM, so the
   number sits near zero on a healthy machine. Every check reported "low memory". The changelog names
   `.196` as the regression source and the code corroborates the mechanism.
3. **2.1.220 splits the measurement by platform.** `oq_()` (`:552608-552621`) `dlopen`s
   `/usr/lib/libSystem.B.dylib` through `bun:ffi`, binds `sysctlbyname`, and reads the OID
   `kern.memorystatus_vm_pressure_level` (`:552638`) into an `Int32Array(1)`.

**Why `>= rq_` where `rq_ = 4` (`:552630`).** macOS publishes VM pressure as a bitfield-shaped enum:
`1` = normal, `2` = warn, `4` = critical. Testing `>= 4` therefore means **critical only** — warn-level
pressure, which a laptop with a browser open reaches routinely, does not shed workers. That single
constant is the entire difference between "shed aggressively" and "shed when the kernel is about to
start killing processes", and it is the reason the fix is a *measurement* change rather than a
*threshold* change: no value of `tengu_bg_low_mem_mb` could have made `freemem()` mean the right thing.

**Failure modes are handled by omission, deliberately.** The `dlopen` is wrapped in `try/catch` and
memoises `yhn = null` on failure (`:552615-552617`); `oq_()` then returns `undefined`, and
`t !== void 0 && t >= rq_` evaluates to `false`. **A machine where the FFI probe fails never sheds** —
fail-open rather than fail-closed, which is correct here because a missed shed costs memory while a
false shed costs a 15-second user-visible stall.

**The trap this bullet sets.** `tengu_bg_low_mem_mb` and `tengu_bg_retire_pinned_low_mem` are both
**1/1**. A gate-name diff reports "no change" for the most consequential fix in the release. Only
`sysctlbyname` (**2/0**) and `kern.memorystatus_vm_pressure_level` (**1/0**) expose it.

### c.2 `#11` / `#13` — one guard, three refusal reasons, and a deliberate refusal to fall back

The two bullets read as unrelated (one is a containment bug, one is a crash-loop) and are the same
enforcement block in the Bash pre-exec path. `tengu_agent_worktree_cwd_escape_blocked` is **220=4 /
193=0** and fires with three distinct `reason` values:

| Line | `reason` | Situation | Message gist |
|---|---|---|---|
| `:314164` | `context_lost` | the agent's isolation context is gone | *"…this command would run in the parent session's directory instead of this agent's worktree"* |
| `:314192` | `worktree_gone` | cwd deleted **and** the only recovery target is the shared checkout | refuse rather than silently recover into the parent |
| `:314210` | `shared_checkout` | cwd resolves outside the isolation worktree | refuse |

**Why refuse instead of recovering?** There *is* a generic recovery path — `:314185` returns
*"Working directory "X" no longer exists. Please restart Claude from an existing directory."* — and in
a non-isolated session that is the right answer. For a worktree-isolated subagent it is not: recovering
into the nearest valid directory means recovering into the **shared checkout**, which is exactly the
boundary the isolation exists to enforce. A "helpful" fallback would silently convert a containment
failure into a *successful* command run against the wrong tree, and the user would have no signal at
all. So the guard treats "I cannot prove I am in my worktree" as fatal.

That decision is what turns #13's crash-loop into one clean failure, because the refusal is paired with
`settleCwdGone` (`:554674`) on the spawn side, which emits `tengu_bg_spawn_cwd_gone` and **settles** the
job instead of returning it to the respawn queue. Refuse at exec-time, settle at spawn-time: one
policy, two layers.

**Honesty note carried from the module doc.** Because the entire shell guard is `193=0`, `.203` #11,
`.210` #11 and `.216`'s worktree bullets **all landed in-window on this one guard**, and no literal
separates `.203`'s "sometimes running shell commands in the parent checkout" from `.210`'s
"git-mutating commands on the main repo". Only `.216` is separable (its reason string differs). See
[`../53_subagent_limits/budget_and_delegation_hardening.md`](../53_subagent_limits/budget_and_delegation_hardening.md)
§4 — it states this rather than guessing, and so does this ledger.

**Why step 3 deletes every case-variant before re-adding one.** On Windows the environment is
case-insensitive but the JS object holding it is not. Merging a daemon env that contains `Path` with a
dispatch env that contains `PATH` produces an object with *both*, and which one the OS honours when
spawning is not defined by anything the CLI controls. Deleting all variants and writing exactly one —
**under the daemon's own key spelling**, `s[a ?? "PATH"]`, so the child's env keeps the platform's
native casing — makes the outcome deterministic. `toUpperCase() === "PATH"` is **220=6 / 193=3**; the
three new occurrences are precisely lines 1, 3 and the `find` in this block.

**Why step 4 deletes credentials rather than the URL.** The failure the bullet describes is a 401: the
worker sent an API key to `api.anthropic.com` because it had lost the `ANTHROPIC_BASE_URL` the user
exported in their shell. The fix is *not* "propagate the URL" — the URL propagates already, as part of
the dispatch env. The fix is to notice that **the child's endpoint and the daemon's endpoint disagree**
and to stop shipping the daemon's endpoint-scoped credentials along with it, because a token minted for
gateway A is at best useless and at worst a leak when sent to endpoint B. `s.ANTHROPIC_BASE_URL !==
i.ANTHROPIC_BASE_URL` is **220=1 / 193=0** — a single comparison, and the whole of bullet #9.

**Key insight:** the changelog presents #9 as "the variable was dropped". The code says the variable was
never dropped; what was missing was the *consequence* of it differing. That is why grepping
`ANTHROPIC_BASE_URL` (47/40) finds nothing useful and grepping the comparison finds everything.

### c.4 `#33` — ← becomes a four-outcome state machine

> *"Changed left arrow to no longer close the background tasks, diff, and workflow detail views —
> press Esc instead."*

`Nyp` (`:559650`) is called at `:559928` as
`Nyp(j, nt, Me.soloKeypress, Ke("tengu_left_arrow_editing_guard", !0))` and returns one of
`fire | arm | absorb | attach-arm`. The gate (**220=1 / 193=0**) replaces 193's
`tengu_left_arrow_gesture`, which is in the GONE-gate list.

**Why four outcomes and not a boolean.** The ← key has to serve three constituencies simultaneously:
cursor movement inside a composer, "go back" in a view stack, and "background this turn" in the main
REPL. A boolean "does ← close things" flag cannot express *"the user was typing three keystrokes ago,
so treat this ← as cursor movement, but tell them ← again will go back"* — which is the `arm` outcome,
and which surfaces a transient *"Press ← again"* hint plus `tengu_left_arrow_blocked` with
`reason: "editing-quiet"`. `absorb` swallows the key with no hint (mid-word), `attach-arm` handles the
attached-background-session case, and `fire` is the old unconditional behaviour.

**It is the same interaction as #6.** When ← fires while subagents are running, the session does not
tear them down — it prints *"Still backgrounding after the current tool — waiting for N running
subagent(s) so the work carries over. Press ← again to skip ahead and restart them from the
beginning."* (`:413946`, **220=1 / 193=0**). So the escalation ladder is: first ← arms, second ←
backgrounds-but-waits, third ← abandons. Three presses, three increasingly destructive meanings, each
one announced before it happens. The changelog splits this across bullets #6 and #33 and never says
they are the same gesture.
