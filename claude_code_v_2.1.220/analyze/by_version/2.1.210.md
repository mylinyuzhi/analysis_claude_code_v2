# 2.1.210 — agent view, the auto-mode classifier model, and `isolation: 'worktree'` containment

**Bullets: 33.** **Centre of gravity: three security containments, an agent-view/background-session
polish sweep, and the first release where the auto-mode classifier gets a model of its own.**

---

## 1. Release narrative

`2.1.210` is the release that follows a revert (`.209`) and precedes the `--forward-subagent-text`
release (`.211`), and its shape reflects that position: it is a **consolidation** release. Nothing in it
is a new user-facing capability of any size. What it does contain is an unusual density of *containment*
work — three separate bullets (#3, #4, #25) each close a path by which content the model produced, or
content the model read, could reach a privileged surface it was never supposed to reach. Read together
they are the most coherent security story in the `.206`–`.210` stretch:

- **#3** — a subagent declared `isolation: 'worktree'` could run `git` against the *parent* checkout.
  Four independent detectors now block it, each with its own reason code (`:314164` `context_lost`,
  `:314192` `worktree_gone`, `:314210` `shared_checkout`, `:314220` `command_redirect`).
- **#4** — the `ultracode` keyword could be triggered by text that no human typed (a webhook body, a
  relayed PR comment). The keyword scanner is untouched; a single new conjunct, `isHumanTypedPrompt`
  (`:516671`, 220=2/193=0), gates the call site.
- **#25** — text a subagent *read* could contain harness-shaped markup that the parent would then treat
  as instructions. A flag/neutralize/neutralize-silent pattern pipeline now rewrites it, and what
  survives is announced with `[harness: subagent output matched instruction-shaped pattern(s): `
  (`:345393`, 220=1/193=0).

The second cluster — ten bullets (#7, #17, #18, #19, #20, #21, #23, #31, #32, and half of #13) — is
`claude agents` and background-session hygiene. This is the same subsystem that dominates `.206`–`.208`;
`_scope_v206_210.md`'s roll-up puts `background_agents` at 21% of the whole five-release range. `.210`'s
contribution is mostly *state that survives a transition*: a task list that follows the session into its
background fork (#19), a worktree lock released when its owner dies (#21), an attach that waits for the
daemon to settle (#7), a selection marker that survives hover (#32).

The third thread is the one the changelog buries in an "Improved" bullet: **#27 gives the auto-mode
permission classifier its own model story** — a default, a first-request validation, and a per-session
pin. That is the release in which the classifier stops being "whatever model the session is on" and
becomes an independently-versioned component; `.218` later moves three more permission dialogs onto it.

Two bullets in this release are register-1 carryover traps (#12 `(edited by user)`, #32
`keepInPlaceIds`) and one is server-side (#33 Fable in the advisor picker). Six more (#1, #5, #6 in part,
#8, #16, #20) have no isolable client anchor at all — an unusually high UNANCHORED rate, which is what a
consolidation release looks like: the deltas are single lines inside mature machinery, exactly as
`_GROUND_TRUTH` §6.4 predicts for this stretch of the window.

## 3. Deep dive A — `.210` #18: why `--effort ultracode` vanished, and the one-line fix

*No module doc covers this bullet — `47_models/README.md` records it as "not covered" and
`36_background_agents/README.md` forwards it to `47_models/`. This is the primary analysis.*

**What it does:** `claude agents --effort ultracode` sets the default effort for every session the agent
view dispatches. Before `.210` the value was accepted by the CLI parser, stored in `dispatchDefaults`,
and then silently dropped on the way into the dispatch record — so dispatched sessions ran at the
account default.

**How it works:**

1. `EL = ["low", "medium", "high", "xhigh", "max"]` (`:119650`) is the canonical effort ladder. It is
   **byte-identical to 193's `lD` at `:149908 (193)`**, so the level set is not the delta.
2. `"ultracode"` is deliberately **not** in that ladder. It lives in a separate alias table:
   `hBc = { ultracode: "xhigh" }` (`:119651`). A second table `mBc = { med: "medium" }` holds the
   abbreviation aliases.
3. Two resolvers sit on top. `uHt` (`:119472`, *parseCanonicalEffortLevel*) applies `mBc` and then
   requires membership in `EL`. `AWr` (`:119460`, *resolveEffortAliasKey*) checks membership in `hBc` and
   returns **the alias key itself**, not its expansion.
4. `uJn` (`:119477`, *parseEffortFlagValue*) composes them: canonical first, alias second, and only then
   a warning. This is what the session-level `--effort` flag has always used (`:851248`).

```javascript
// ============================================
// parseEffortFlagValue - two-stage effort parse: canonical ladder, then the ultracode alias
// Location: cli_inner_pretty.js:119460-119487
// ============================================

// ORIGINAL (for source lookup):
function AWr(e) { if (typeof e !== "string") return; let t = e.trim().toLowerCase(); return Object.hasOwn(hBc, t) ? t : void 0; }
function uHt(e) { let t = e.trim().toLowerCase(), r = mBc[t] ?? t; return q1e(r) ? r : void 0; }
function uJn(e) {
  let t = uHt(e);
  if (t !== void 0) return { level: t, warning: void 0 };
  let r = AWr(e);
  if (r !== void 0) return { level: r, warning: void 0 };
  return { level: void 0, warning: `Unknown --effort value '${e}' — ignoring it and using the default effort. Valid values: ${EL.join(", ")}.` };
}
// with:  EL = ["low","medium","high","xhigh","max"];  mBc = { med: "medium" };  hBc = { ultracode: "xhigh" };
// and:   function q1e(e) { return EL.includes(e); }

// READABLE (for understanding):
function resolveEffortAliasKey(raw) {
  if (typeof raw !== "string") return undefined;
  const key = raw.trim().toLowerCase();
  return Object.hasOwn(EFFORT_ALIASES, key) ? key : undefined;   // returns "ultracode", NOT "xhigh"
}
function parseCanonicalEffortLevel(raw) {
  const key = raw.trim().toLowerCase();
  const expanded = EFFORT_ABBREVIATIONS[key] ?? key;             // "med" -> "medium"
  return EFFORT_LEVELS.includes(expanded) ? expanded : undefined;
}
function parseEffortFlagValue(raw) {
  const canonical = parseCanonicalEffortLevel(raw);
  if (canonical !== undefined) return { level: canonical, warning: undefined };
  const alias = resolveEffortAliasKey(raw);
  if (alias !== undefined) return { level: alias, warning: undefined };
  return { level: undefined, warning: `Unknown --effort value '${raw}' — ignoring it and using the default effort. Valid values: ${EFFORT_LEVELS.join(", ")}.` };
}

// Mapping: AWr→resolveEffortAliasKey, uHt→parseCanonicalEffortLevel, uJn→parseEffortFlagValue,
//          q1e→isCanonicalEffortLevel, EL→EFFORT_LEVELS, mBc→EFFORT_ABBREVIATIONS, hBc→EFFORT_ALIASES
```

**The bug, and the fix, in one pair of lines.** The agent-view dispatch-defaults builder did not use
`uJn`. It re-implemented step 3 with the canonical validator only:

```javascript
// ============================================
// buildAgentViewDispatchDefaults - normalises `claude agents` flag defaults for dispatched sessions
// Location: cli_inner_pretty.js:802156-802166   (2.1.193 twin: Wbc, :674078-674089 (193))
// ============================================

// ORIGINAL (for source lookup):
// --- 2.1.193 :674085-674086 ---
    s = e?.allowBypass && r ? !0 : void 0,
    i = e?.effort?.toLowerCase(),
    a = i && cje(i) ? i : void 0;                 // cje(e) { return lD.includes(e); }  -> "ultracode" fails
  if (!o && !e?.model && !a && !t && !s) return;
  return { permissionMode: o, model: e?.model, effort: a, agent: t, allowBypass: s };

// --- 2.1.220 :802162-802165 ---
    i = e?.allowBypass && n ? !0 : void 0,
    s = e?.effort ? uJn(e.effort).level : void 0;  // the SAME parser the --effort flag uses
  if (!o && !e?.model && !s && !t && !i) return;
  return { permissionMode: o, model: e?.model, effort: s, agent: t, allowBypass: i };

// READABLE (for understanding):
  const effort = flags?.effort ? parseEffortFlagValue(flags.effort).level : undefined;
  if (!permissionMode && !flags?.model && !effort && !agent && !allowBypass) return undefined;
  return { permissionMode, model: flags?.model, effort, agent, allowBypass };

// Mapping: Wbc/Mum→buildAgentViewDispatchDefaults, cje/q1e→isCanonicalEffortLevel, uJn→parseEffortFlagValue
```

193's `cje(i)` returns `false` for `"ultracode"`, so `a` becomes `undefined`, the `effort` key is empty,
and `$Tn` (`:681406-681416`) — which builds the worker argv as
`...(e.effort ? ["--effort", e.effort] : [])` — emits nothing. **The value was validated out of
existence between the CLI and the dispatch record.** The user saw no warning, because the warning lives
in `uJn`, which was never called on this path.

**Why the fix returns `"ultracode"` and not `"xhigh"`.** `AWr` deliberately returns the alias *key*.
Downstream, `:683746` re-emits `["--effort", m]` into the worker's argv, and the receiving session's own
effort machinery treats `ultracode` as a distinct mode: `:667275` computes
`gWi(iwn === "ultracode" ? "xhigh" : iwn, …)` — xhigh *for the effort number* — while `:667272-667273`
branches on `iwn === "ultracode"` to call `yW()`, which sets the standing dynamic-workflow orchestration
flags (the same latch `dJn` at `:119501` uses). Eagerly resolving
`ultracode → xhigh` at dispatch time would have delivered the token budget and dropped the orchestration
behaviour, i.e. half the feature. Keeping the alias key alive until the leaf is what makes the argv
round-trip lossless.

**Why this was easy to get wrong.** The alias table is one line away from the ladder it is not part of
(`:119650` vs `:119651`), and there are five separate places in the bundle that ask "is this a valid
effort?" — `q1e` (`:119420`, set membership), `Q6e` (`:119497`, the four-level subset that excludes `max`), `gW`
(`:119487`, which also accepts integers), `uHt`, and `uJn`. Only the last knows about `ultracode`. The
`.210` fix is the removal of the fifth-hand re-implementation in favour of the one resolver that is
complete.

**Key insight:** the changelog says "the value was silently dropped", and the code says exactly why —
a **validator** was used where a **parser** was needed. A validator answers *is this in my set*; a
parser answers *what does this mean*. Any alias system that grows a second table will produce this bug
wherever a validator survives.

fleet view and the session view paint into the *same* scrollback. A fix for that is a clear/reflow
ordering change in the renderer teardown — no string, no constant, no gate. `terminal_rendering.md` §0
independently establishes that **the Ink renderer core did not change in this window**, which bounds
where the fix can be and simultaneously explains why it leaves no trace.

**The generalisable rule.** A count delta on an env-var *name* is worthless as evidence, because names
appear in accessor tables, allow-lists, `dropEnv` lists and settings schemas — four places that have
nothing to do with behaviour. Before quoting `220=N / 193=M` on an env var, enumerate the sites and
classify each one. Here, 3 of the 4 sites are registration and 1 is a list.

**Key insight:** this bullet and `.210` #1 / #5 / #8 / #16 / #20 share a signature — *pure control-flow
or lifetime fixes in code whose vocabulary did not change*. Twelve of thirty-three bullets in this
release are in that class. Reporting them as UNANCHORED with the disproof attached is the finding; the
alternative is six invented deltas.

## 5. Deep dive C — the release's structural signature: one new predicate on a mature mechanism

**What it does:** three of `.210`'s four most substantial bullets change *nothing* about the mechanism
they fix. Each adds exactly one predicate to a call site.

**How it works — the three instances, side by side:**

| Bullet | Mature mechanism (carryover) | The one new thing |
|---|---|---|
| #4 `ultracode` on non-human input | `LWs` word-boundary keyword scanner (`:498250-498290`), shared with `ultraplan`/`ultrareview`; `ultracodeKeywordTrigger` 1/1; `suppressWorkflowKeyword` 7/8; `preExpansionInput` 4/4 | `s?.isHumanTypedPrompt &&` — one conjunct at `:516671`, **220=2 / 193=0** |
| #3 worktree isolation | shell exec path, cwd recovery, `git` redirect analysis | four `tengu_agent_worktree_cwd_escape_blocked` emissions with distinct reason codes, **220=4 / 193=0** |
| #18 `--effort ultracode` | the entire effort ladder, alias tables, and `uJn` parser | swapping a validator call for a parser call at `:802163` |

```javascript
// ============================================
// buildWorkflowKeywordReminders (call site) - the ultracode keyword now requires human origin
// Location: cli_inner_pretty.js:516667-516673
// ============================================

// ORIGINAL (for source lookup):
K_("workflow_keyword_request", () =>
  Promise.resolve(
    s?.isHumanTypedPrompt && !s.suppressWorkflowKeyword && aJn() ? DN_(s.preExpansionInput ?? e) : [],
  ),
),
K_("ultra_effort_enter", () => Promise.resolve(s?.isRegularUserPrompt ? PN_(o, t) : [])),

// READABLE (for understanding):
namedReminder("workflow_keyword_request", async () =>
  origin?.isHumanTypedPrompt              // NEW in .210 — provenance, not content
  && !origin.suppressWorkflowKeyword      // carryover — explicit suppression
  && isWorkflowKeywordFeatureOn()         // carryover — feature gate
    ? scanForWorkflowKeywords(origin.preExpansionInput ?? text)
    : [],
),
namedReminder("ultra_effort_enter", async () => origin?.isRegularUserPrompt ? buildUltraEffortReminder(...) : []),

// Mapping: K_→namedReminder, s→origin, aJn→isWorkflowKeywordFeatureOn, DN_→scanForWorkflowKeywords,
//          PN_→buildUltraEffortReminder
```

**Why this shape, and what it costs.** Adding a conjunct is the smallest possible change with the
largest possible blast radius reduction: the scanner keeps working identically for every input that *is*
human-typed, and stops entirely for every input that is not. The alternative — teaching the scanner
about origins — would have required threading provenance into a pure text function used by three
keywords. The cost is that the invariant now lives at the call site, so a *fourth* call site added later
inherits nothing. Note the neighbouring reminder on the very next line uses a **different** origin
predicate (`isRegularUserPrompt`), which is precisely the hazard: two provenance concepts, adjacent,
easy to confuse.

**The two traps this shape sets for an analyst, both realised in this release.** When the mechanism is
carryover and the delta is one predicate, the *literal you would naturally grep is the mechanism's*, and
it will read as carryover:

- #12 — `(edited by user)` is **220=2 / 193=2** (`:326160`, `:498208`) and `planWasEdited` is
  **3/3**. Register 1 of [`_false_delta_ledger.md`](../00_overview/_false_delta_ledger.md) records both.
  The `.210` plan-dialog change is only *partially* anchored, by the new instrumentation
  `tengu_plan_exit_dialog_shown` (`:761290`) / `tengu_plan_review_step` (`:761415`), and
  [`05_plan_mode/README.md`](../05_plan_mode/README.md) §3.1 says so rather than inventing an anchor.
  **Do not construct one.**
- #32 — `keepInPlaceIds` is **220=2 / 193=2**, and worse, both sites (`:710562`, `:711140`) are in the
  **plugin/skills manager**, a different screen entirely. The agent view's real marker is
  `r8t(...)` at `:802689` returning `"session you came from"` / `"current session"`, **220=1 / 193=0**.
  A label string is the worst possible anchor for a UI bullet because UI vocabulary is shared.

**Key insight:** in a consolidation release the correct default hypothesis is *"the mechanism is old and
one predicate is new"*. That hypothesis tells you to grep for **guards** — `&&` conjuncts, reason codes,
new gate names — and never for the feature's own vocabulary.

## 6. Deep dive D — `.210` #29 and `.211`, read backwards

*Read `.211`'s memory bullet **before** `.210`'s: they interlock, and the changelog order hides it.*

`.211`: *"Improved the memory index over-limit warning to measure only loaded content, excluding
frontmatter and HTML comments."*
`.210`: *"Memory writes that leave a MEMORY.md index over its read limit now produce an explicit error
instead of silent truncation."*

Taken in changelog order, `.210` looks like the substantive change and `.211` like polish. Taken in
dependency order it is the reverse: **`.210` raised the stakes, and `.211` paid the bill.**

**What `.210` actually changed — and what the word "error" means here.** `aLo` (`:434055-434079`)
returns `{ text, overCap }`; `FPd` (`:436637-436642`) emits the gate with `over_cap` and returns
`{ hookSpecificOutput: { hookEventName: "PostToolUse", additionalContext: t.text } }`. There is **no
block, no non-zero exit, and no refusal — the write always succeeds.** The `Error:` prefix is a
*prompt-level classification*: text spliced into the model's context, weighted more heavily because of
how it starts. A reader expecting the Write tool to fail will not find that code path, because it does
not exist. The message deliberately disambiguates itself in its own second clause — *"The write
succeeded, but everything past the limit is silently dropped…"* — so the raised salience does not cause
the model to retry the write or report a failure to the user.

**The undocumented half: a `>=` → `>` off-by-one.** In the same release the over-cap test moved from
`>=` to `>`:

```javascript
// 220 :434059 / :434068          (aLo, the reporter)
over: e.sizeBytes > e.byteCap
over: e.lineCount > e.lineCap
// 220 :161588-161589            (Htr, the enforcer that actually truncates)
let i = n > cie, s = o > Ixe;
// 193 :455234 / :455243 (193)   (lKn, the reporter)
over: … >= byteCap ;  over: … >= lineCap
```

`Htr` — the function that performs the truncation — has always used strict `>`; a file of exactly
25,000 bytes or exactly 200 lines loses nothing. 193's *reporter* used `>=`, so a file sitting precisely
on the cap was told it was over. While the message was a soft warning that was harmless. Once the
message became `Error: … entries at the end are already invisible to readers`, a false positive
actively instructs the model to rewrite a file that is fine. **The two changes belong in the same
release for that reason, and only one of them is in the changelog.**

**Why `.211` had to follow.** `.210` made the message assert a *present fact about data*. But the
measurement it was based on was the whole file — including frontmatter and HTML comments that
`Lp(...)`/`NPu(...)` strip before the index is spliced into context. So `.210` could tell a user their
index was over a limit that the loaded content never approached, in the most alarming possible wording.
`.211` splits the measurement in two (`splicedSizeBytes` / `spliceActive`, `:434116`, 220=3/193=0) and
adds a chooser. In other words: **`.210` is the change that made `.211` mandatory**, and neither bullet
mentions the other.

Full derivation — including `chooseBindingSizeBasis`, the `ht_ = 0.8` warn fraction, the `tPd = 0.7`
shrink target (the writer is told to shrink to 70% so the next write does not immediately re-trip the
80% warning), and the team-index twin — is in
[`31_auto_memory/memory_index_size_budget.md`](../31_auto_memory/memory_index_size_budget.md) §2–§3.

**Key insight:** changelog order is publication order, not causal order. When two consecutive releases
touch the same function, read them backwards first; the later bullet usually names the cost of the
earlier one.

## 7. What the changelog does not say

**7.1 — The `ultracode` scanner is byte-identical carryover, and the bullet's wording invites the
opposite conclusion.** *"Fixed the `ultracode` keyword opt-in firing on non-human-originated input"*
reads as a change to keyword detection. `LWs` (`:498275`) is **identical** to `:472958 (193)`, and
`ultracodeKeywordTrigger` is 1/1. The entire delta is `isHumanTypedPrompt` at the call site. Anyone
who greps `ultracode` (220=83 / 193=70) will find seventy carryover sites and conclude wrongly.

**7.2 — `.210` #22's scope-file anchor is wrong, and the module caught it.** `tengu_mcp_sdk_generation`
(`:262859`) is the **MCP v1/v2 runtime-arm probe** — `MCP_SDK_GENERATION`, gate `tengu_brindle_causeway`,
the dual runtime trees documented in [`39_mcp/dual_mcp_runtime_trees.md`](../39_mcp/dual_mcp_runtime_trees.md).
It has nothing to do with SDK MCP servers connecting a turn late. The real fix is one added call, `It()`
at `:847530`, inside the `initialize` handler's `sdkMcpServers` branch; the 193 twin at
`:707046-707047 (193)` populates the config map and never syncs. This is a good illustration of the
scope files being **leads, not conclusions**.

**7.3 — `advisor_rank` is a catalogue field, and it cannot express "unavailable".** `.210` #33 says
Fable "temporarily shows as unavailable in the advisor picker". `advisor_rank` is **220=12 / 193=0**
and is a plain integer per model (`:14067` = 1 for Haiku 4.5, `:14174`, `:14212`, `:14301`, `:14327`,
`:14362`…). It ranks; it does not gate. Combined with `best: "fable"` (`:14488`) this answers
`_GROUND_TRUTH` §7 question 5 **in the negative**: neither field encodes availability, so the Fable
outage is entitlement/flag-driven and has no client anchor. Verdict SERVER_SIDE, and the *interesting*
finding is that a brand-new catalogue field arrived in this window with no bullet of its own.

**7.4 — the worktree-containment bullet under-reports its own scope.** #3 names one symptom
("git-mutating commands against the main repo checkout"). The code implements **four** independent
detectors with distinct reason codes and, separately, two *path-shape* refusals in `ied`
(`:312384-312396`) covering raw dot segments stored inside symlinks and UNC/`/net` automount spellings
used while the protected checkout is local. The `command_redirect` arm (`:314220`) is the only one the
bullet describes; `context_lost` (`:314164`) fires when the cwd-override mechanism itself failed, and
`worktree_gone` (`:314192`) when the isolation worktree has been deleted underneath the agent. Three of
the four are about *losing* isolation, not about escaping it.

**7.5 — `.210` #6's real anchor is two escape sequences, not a paste marker.** The bullet blames "paste
markers … stray È/É". Those bytes are what a terminal emits when **bracketed paste mode is still on**
and a child process receives `ESC[200~` / `ESC[201~` it does not understand. The fix is that
`enterAlternateScreen` (`:258035-258047`) now writes `Usr` (DECRST 2004, bracketed paste off) and `jsr`
(DECRST 2031) before handing the terminal over; 193's version (`:175117-175127 (193)`) wrote neither,
while its `exitAlternateScreen` unconditionally re-*enabled* 2004 — an asymmetry visible in one glance
once you know where to look. Grepping for `È`, `É` or `pasteMarker` returns 0/0 in both builds.

**7.6 — twelve of thirty-three bullets are honestly unanchored, and that is the release's real
signature.** #1, #2, #5, #8, #11, #16, #17, #20, #23 have no client-side literal in either build; #12,
#27, #30 are only partially anchored. `.210` is a release of behavioural corrections inside code whose
vocabulary was already complete. Reporting the disproofs — `Write(path)` 0/0 in *both* builds, `bigint`
125/114 dominated by vendored zod/React, `renameWithRetry` 0/0 with the retry set byte-identical to
`:46613 (193)`, `dropEnv` identical to `:545902 (193)` — is more useful than any of the deltas that could
have been fabricated from those counts.
