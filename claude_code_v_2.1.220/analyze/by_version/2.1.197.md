## 1. Release narrative

`2.1.197` is one of six single-bullet releases in the `.195`→`.220` window, and it is the only one of
them that is a **launch** rather than a hotfix or a revert. Its whole changelog is:

> *Introducing Claude Sonnet 5: now the default model in Claude Code, with a native 1M-token context
> window and promotional pricing of $2/$10 per Mtok through August 31. Update to version 2.1.197 for
> access.*

**What a one-bullet launch release means, mechanically.** A model launch is normally the *loudest*
kind of release and the *quietest* kind of diff. The client is not where a model lives: weights,
routing and billing are all server-side. The client's job is to (a) know the id exists, (b) know what
the id can do, (c) know what to call it in the picker, and (d) decide what the bare word `sonnet`
resolves to. In 2.1.193 those four jobs were spread across imperative branch-on-model-id code. In
2.1.220 they are **one object literal plus one alias-table edit**, because the model registry was
rewritten into a declarative catalogue somewhere in this window — see
[`../47_models/model_catalogue_rewrite.md`](../47_models/model_catalogue_rewrite.md). The catalogue
carries its own contract comment at `:14009` telling maintainers exactly that: *"On model launch add
one entry to `models` below."* `.197` is the first release in this window to exercise that contract,
and `.219` (Opus 5) is the second. **The one-bullet shape of `.197` is therefore evidence of the
undocumented rewrite, not evidence that little changed.**

**Where it sits in the window.** `.196` (27 bullets) had just landed org-default models and the
`/model` attribution ladder; `.198` (33 bullets) immediately follows with the autonomy batch. `.197`
slips between two large releases as a same-day model drop — the classic "ship the client the moment
the server flips on" pattern, confirmed by the bullet's own *"Update to version 2.1.197 for access"*.
Two releases later, `.201` shipped a second single-bullet hotfix that was *also* about Sonnet 5
(the mid-conversation system role), so `.197` is best read as the opening move of a three-release
Sonnet-5 arc: `.197` launch → `.201` behavioural hotfix → a later, unannounced re-shaping of that
hotfix that survives into `.220` (§5).

**Do not attribute the 1M machinery to this release.** `1M context` is **220=42 / 193=40** and
`context-1m` is **220=3 / 193=2** — the plumbing predates `.197` by a long way. What is genuinely new
is the *`native_1m` classification* (§3), and it is new because the catalogue schema is new.

## 3. Deep-dive A — the anatomy of a one-bullet model launch

### What one bullet costs in code

**What it does:** turns a server-side model id into a fully-wired client model — selectable, priced,
labelled, aliasable, and capability-gated.

**How it works.** Five edits, and only the first is large:

1. **One catalogue entry** — `:14177-14213`, 37 lines. Read verbatim, the fields that matter:

   ```javascript
   // ============================================
   // sonnet5CatalogueEntry - the entire client-side definition of Claude Sonnet 5
   // Location: cli_inner_pretty.js:14177-14213
   // ============================================

   // ORIGINAL (for source lookup):
   { id: "claude-sonnet-5", family: "sonnet", display_name: "Sonnet 5",
     knowledge_cutoff: "January 2026",
   ```

2. **Two alias-table lines** — `sonnet: { default: "claude-sonnet-5", … }` at `:14473-14474`, and
   `latest_per_family.sonnet: "claude-sonnet-5"` at `:14492`. This is what "now the default model"
   actually is, and §4 shows it is narrower than the sentence.
3. **One short-name map row** — `"claude-sonnet-5": "sonnet5"` at `:100226`, inside `OZh`
   (`:100218-100235`), whose keys are validated at load time by `NZh` (`:100186-100198`): a missing
   catalogue entry for any key in the map **throws** *"model catalog missing entry for '<id>'"*
   (`:100192`). The short-name map is therefore a build-time-ish integrity check on the catalogue.
4. **Two picker rows** — the plain `Sonnet` row `AJn` (`:120055-120064`) and the 1M row `CWi`
   (`:120166-120175`), both of which call the pricing-suffix builder rather than hard-coding a price.
5. **Zero prompt edits.** Sonnet 5 ships with no `.197`-specific system-prompt text.

**Why this approach.** The alternative — the 2.1.193 shape — was per-model `if`/ternary chains spread
over provider-id resolution, 1M handling, pricing, and picker construction. Adding a model then meant
touching every one of those sites and hoping none was missed. The catalogue centralises the *data*
and leaves the *code* untouched, which is why `.197` and `.219` are both one-bullet releases while
older model launches were not.

**The trade-off is visible in this very release.** Centralisation is incomplete. `$Zh`
(`:100171-100184`) exists solely to translate the catalogue's snake_case `provider_ids` back into the
legacy camelCase runtime shape (`first_party`→`firstParty`, `anthropic_aws`→`anthropicAws`,
`anthropic_google_cloud`→`anthropicGoogleCloud`), and `ybc` at `:100253-100261` is a *hand-written*
camelCase provider map for `claude-mythos-5` that bypasses the catalogue entirely. So the build ships
both shapes at once, and any grep that assumes one naming convention will miss half the sites. (This
is the mechanism behind the `.198` `anthropicAws` false delta — see
[`2.1.198.md`](2.1.198.md) §5.)

**Key insight:** the single bullet is not a measure of how little changed; it is a measure of how much
the *previous, undocumented* refactor paid off. Read `.197` as the acceptance test for the catalogue
rewrite.

## 4. Deep-dive B — "now the default model" is provider-conditional

**What it does:** resolves the bare alias `sonnet` (and the implicit session default) to a concrete
model id, per provider.

**How it works.** The alias table at `:14461-14486` has a `default` and a `per_provider` override map
for each alias. Read verbatim for `sonnet` (`:14473-14483`):

```
default: "claude-sonnet-5"
per_provider: { bedrock: "claude-sonnet-4-5", vertex: "claude-sonnet-4-5",
                foundry: "claude-sonnet-4-5", mantle: "claude-sonnet-4-5",
                anthropic_aws: "claude-sonnet-4-6", gateway: "claude-sonnet-4-6" }
```

So in the shipped 2.1.220 bundle, **`sonnet` resolves to Sonnet 5 only on first-party**. Bedrock,
Vertex, Foundry and Mantle still get Sonnet 4.5 — two generations back — and Claude Platform on AWS
and the gateway get Sonnet 4.6. `latest_per_family.sonnet` (`:14492`) says `claude-sonnet-5`
unconditionally, but that is the *newest known* model, not the *resolved alias*; the two fields
disagree by design.

**Why this approach.** A first-party launch and a Bedrock/Vertex launch are different events with
different dates. Encoding the lag as data means a server-side flag flip or a one-line catalogue edit
retires it, instead of a release. The cost is that the client can truthfully claim one default while
delivering another, which is exactly what the `.197` bullet does.

**Edge case worth stating:** `.207` later claimed *"Changed Bedrock, Vertex, and Claude Platform on
AWS to default to Claude Opus 4.8"* and `.219` overwrote that value again — the `opus` row at
`:14462-14471` now reads `bedrock/vertex/mantle/anthropic_aws → "claude-opus-5"` with only `foundry`
(4-6) and `gateway` (4-7) lagging. The *sonnet* row was never given the same treatment. So by
`.220`, third-party Opus users are on the newest Opus while third-party Sonnet users are still on
4.5. That asymmetry has no bullet anywhere in the window.

**Key insight:** verdict for this half of the bullet is **DELTA, not NET_NEW** — the default did
change, but only for one of eight provider channels, and the code says so in a table you can read.

## 5. Deep-dive C — the promo price is baked, the promo *window* is not

**What it does:** renders `$2/$10 per Mtok · promo through <date>` in the `/model` picker for
Sonnet 5, with `$3/$15` struck through beside it — and silently reverts to the standard rate when the
promotion ends, with no client update.

**How it works:**

```javascript
// ============================================
// buildSonnet5PromoPricing / getActivePromoEndDate - a price that expires itself
// Location: cli_inner_pretty.js:119957-119962, :120043-120054
// ============================================

// ORIGINAL (for source lookup):
function kBc() {
  let e = Jx()?.cedar_basin;
  if (typeof e !== "string" || e.trim() === "") return;
  let t = bJn(e);
  return Date.now() < t ? e : void 0;
}
function wug() {
  let e = vBc(kBc());
  if (e === void 0) return;
  return { pricing: `$2/$10 per Mtok \xB7 promo through ${e}`, promoListPrice: "$3/$15" };
}
function Goe(e, t) {
  if (!t && uGr()) {
    let r = YO(e) === "claude-sonnet-5" ? wug() : void 0;
    if (r !== void 0) return { pricingSuffix: ` \xB7 ${r.pricing}`, promoListPrice: r.promoListPrice };
  }
  return { pricingSuffix: _5r(t, e) };
}

// READABLE (for understanding):
function getActivePromoEndDate() {
  const raw = getFeatureFlagPayload()?.cedar_basin;          // server-supplied date string
  if (typeof raw !== "string" || raw.trim() === "") return undefined;
  const endMs = parseLenientIsoDate(raw);
  return Date.now() < endMs ? raw : undefined;               // self-expiring
}
function buildSonnet5PromoPricing() {
  const endDate = formatPromoDate(getActivePromoEndDate());
  if (endDate === undefined) return undefined;
  return { pricing: `$2/$10 per Mtok · promo through ${endDate}`, promoListPrice: "$3/$15" };
}
function buildPricingSuffix(modelId, isFastMode) {
  if (!isFastMode && usesFirstPartyPricing()) {              // promo never shows on 3P or in fast mode
    const promo = normaliseToCatalogueId(modelId) === "claude-sonnet-5"
      ? buildSonnet5PromoPricing() : undefined;
    if (promo) return { pricingSuffix: ` · ${promo.pricing}`, promoListPrice: promo.promoListPrice };
  }
  return { pricingSuffix: buildRatePricingSuffix(isFastMode, modelId) };   // catalogue tier path
}

// Mapping: kBc→getActivePromoEndDate, wug→buildSonnet5PromoPricing, Goe→buildPricingSuffix,
//          Jx→getFeatureFlagPayload, bJn→parseLenientIsoDate, vBc→formatPromoDate,
//          uGr→usesFirstPartyPricing, YO→normaliseToCatalogueId, _5r→buildRatePricingSuffix
```

**Why this approach.** Three separate decisions, each defensible and each with a cost:

- **The numbers are hard-coded, the deadline is not.** `$2/$10 per Mtok` is **220=1 / 193=0** and
  lives only at `:120046`; `$3/$15` is a sibling literal on the same line. But the *date* comes from
  the `cedar_basin` feature-flag payload (**220=1 / 193=0**, its only occurrence is the read at
  `:119958`). **`August 31` appears nowhere in the bundle — grep count 0.** So the changelog's most
  concrete-sounding claim is the one the client cannot corroborate.
- **Expiry is checked at render time, not at build time.** `Date.now() < t` at `:119961` means the
  promo row disappears the instant the flagged date passes, on a client that was never updated. This
  is the same self-expiring-announcement pattern as `.219`'s Opus 4.7 fast-mode sunset notice (see
  [`../_GROUND_TRUTH_verified_anchors.md`](../_GROUND_TRUTH_verified_anchors.md) §6.2b) — Anthropic
  uses date-gated strings in preference to shipping a follow-up release.
- **The guard `!t && uGr()` is a fix disguised as a condition.** The promo is suppressed in fast mode
  and whenever the session is not on first-party pricing. Every pricing suffix in the picker now
  routes through this single function, which is why `.206`'s *"the `/model` picker printed a price
  for a different model than the row named"* bullet lands here too.
- **`promoListPrice: "$3/$15"` duplicates the catalogue.** The entry already says
  `pricing: "tier_3_15"` at `:14201`, i.e. $3/$15. The strikethrough price is a hand-written string
  that could drift from the tier it mirrors — a residue of the pre-catalogue imperative style, in the
  same function that consumes the catalogue.

**Key insight:** classify the promo as **SERVER_SIDE for the window, NET_NEW for the price string**.
Prior scoping passes marked the whole promo SERVER_SIDE; that is half right, and the half that is
wrong (`$2/$10` *is* baked at `:120046`) is the half you can grep.

## 6. Deep-dive D — `native_1m` and the one field only Sonnet 5 has

**What it does:** distinguishes a model whose 1M window is *intrinsic* from one whose 1M window is a
*beta opt-in*, and further distinguishes which third-party channels honour it natively.

**How it works.** Sonnet 5's `context` block (`:14194-14199`) sets four things:

| Field | Value | Meaning |
|---|---|---|
| `window` | `1e6` | the window the client budgets against |
| `native_1m` | `!0` | 1M without a beta header |
| `native_1m_3p` | `{ bedrock: !0, vertex: !0, foundry: !0 }` | **unique to this entry** |
| `supports_1m_beta` | `!0` | back-compat: the beta path still works |

`native_1m_3p` is **220=3 / 193=0** and Sonnet 5 is the only model that carries it. Every other 1M
model in the catalogue — including Opus 5 at `:14382` — has `native_1m` but no `native_1m_3p`.
Sonnet 5 is also the only `native_1m` model that does **not** set `supports_1m_suffix`, so the
`[1m]` picker row it gets (`CWi`, `:120166-120175`, `label: "Sonnet 5 (1M context)"`) is built by
hand rather than derived from the catalogue.

**Why this approach.** Native-versus-beta is a *request-shape* decision (does the client send a
`context-1m` beta header?) and it is not uniform across providers: a model can be native on
first-party and beta-only on Bedrock. Encoding the exception as a per-provider sub-map keeps one
boolean for the common case and admits the messy case without a second code path.

**Edge case:** because `supports_1m_beta` is *also* true, a Sonnet 5 session that still sends the
beta header is not broken — the fields are additive, not exclusive. That belt-and-braces choice is
why the pre-existing 1M plumbing (`1M context` 220=42 / **193=40**) needed no changes at all for
`.197`.

**Key insight:** the only genuinely new 1M *machinery* in `.197` is a classification field. Any doc
that credits `.197` with "adding 1M context support" is reading the changelog, not the bundle.

## 7. What the changelog does not say

### 7.1 The registry rewrite that made this a one-bullet release is unmentioned

The single largest structural change in the whole `.193`→`.220` window is that the model registry
became a declarative, schema-validated catalogue (`provider_ids` 220=22/193=0, `knowledge_cutoff`
220=16/193=0, `advisor_rank` 220=12/193=0, `latest_per_family` 220=4/193=0 at `:14489-14494`,
`alias_migration` 220=4/193=0 at `:14495`). No bullet in any of the 25 releases mentions it.
`.197` is where its payoff first shows. Full treatment:
[`../47_models/model_catalogue_rewrite.md`](../47_models/model_catalogue_rewrite.md).

### 7.2 Sonnet 5 shipped alongside two models that have no bullet at all

The catalogue's tail holds `claude-fable-5` and `claude-mythos-5`. Mythos 5's entry ends at
`:14455-14458` with `pricing: "tier_10_50"`, **`capabilities: []`**, and `advisor_rank: 5`, and its
provider ids come from a hand-written camelCase map at `:100253-100261` rather than the catalogue
adapter — an unannounced family carried in the same data file as the announced one. And `best:
"fable"` at `:14488` names *Fable*, not Sonnet 5 or Opus 5, as the catalogue's "best" model. None of
this is in any changelog bullet.

### 7.3 `.197`'s launch created a Sonnet-5-shaped hole in the prompt layer that is still open at `.220`

`.201` — the next single-bullet release — said *"Claude Sonnet 5 sessions no longer use the
mid-conversation system role for harness reminders."* In the shipped 2.1.220 bundle that role-level
exclusion is **gone**: Sonnet 5's `capabilities` array declares `"mid_conv_system"` at `:14207`, and
the exclusion list inside `Ser` (`:150505-150526`) names `claude-3-*`, opus-4-0/4-1/4-5/4-6/4-7 and
sonnet-4-0/4-5/4-6 and haiku-4-5 — **but not `claude-sonnet-5`** — so control reaches
`if (M$(r, "mid_conv_system") || r === "claude-mythos-5") return !0;` at `:150524` and returns true.

But the carve-out did not vanish; it **moved to the presentation layer**. A dedicated one-line
predicate exists solely for this model:

```javascript
// ============================================
// isSonnet5 - a model-specific predicate that exists only to shape Sonnet 5's reminder framing
// Location: cli_inner_pretty.js:150395-150397
// ============================================

// ORIGINAL (for source lookup):
function mro(e) {
  return lo(e) === "claude-sonnet-5";
}

// READABLE (for understanding):
function isSonnet5(model) {
  return normalizeModelId(model) === "claude-sonnet-5";
}

// Mapping: mro→isSonnet5, lo→normalizeModelId
```

Its two consumers, both re-read here:

- `:508117` — `Jep = Vr((e) => (…, Ser(e) && !mro(e) && !$Fc(lo(e))), …)`: Sonnet 5 never receives the
  new mid-conversation framing sentence. `$Fc` excludes Opus 4.8 on the same line, so there are
  **three** framing states, not two.
- `:531422` — `i = r !== void 0 && o && mro(r)` inside `NN` (`:531420`): on Sonnet 5, harness
  reminders are individually `<system-reminder>`-wrapped before entering the system turn.

**Correct statement: `.201`'s role-level exclusion was reverted and replaced by a presentation-level
shim.** Neither the reversion nor the shim has a changelog bullet. Analysis:
[`../40_system_prompt/mid_conversation_system_role.md`](../40_system_prompt/mid_conversation_system_role.md).

### 7.4 The bullet's own instruction is the tell

*"Update to version 2.1.197 for access"* is unusual phrasing for a changelog and marks this as a
coordinated launch note rather than an engineering summary. It is the only bullet in the 579 that
tells the reader to upgrade, and the only one carrying an external URL.
