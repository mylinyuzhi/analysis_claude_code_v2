## 1. Release narrative

**2.1.219 is a model launch wearing a settings-surface release as a coat.** Its centre of gravity is
`claude-opus-5` — a full 17-field catalogue entry at `cli_inner_pretty.js:14365-14400` with
`context: { window: 1e6, native_1m: !0, supports_1m_beta: !0, supports_1m_suffix: !0 }`, a ten-token
`capabilities` array, `advisor_rank: 4`, and eight `provider_ids` including the otherwise-undocumented
`anthropic_google_cloud` channel. Around it sits a cluster of consequences: the `/model` picker's merged
Opus row (bullets 10, 20), the Fable "Requires usage credits" row (bullet 9), the bundled `claude-api`
skill's default id (bullet 23), Remote Control's fast-mode wire state (bullet 12), and — supposedly —
Opus 4.7's removal from fast mode (bullet 22). **Five of the 24 bullets are Opus-5 blast radius.**

The second, quieter half of the release is **settings-surface promotion**: three things that already
worked internally were given public keys. `sandbox.network.strictAllowlist` (bullet 2) got a zod field,
a merge rule and an effective-settings projection around an enforcement branch that had been shipping —
as dead code — since 2.1.193. `workflowSizeGuideline` (bullet 5) turned `.202`'s `/config` row into a
settings key with a documented precedence chain and a **default** (`medium`). `DirectoryAdded`
(bullet 3) is the one genuinely net-new event surface, and even it splits: the hook is new (220=20 /
193=0) but the SDK `register_repo_root` control request it fires from is not (220=15 / **193=3**).

Third, `.219` **closes the nesting flip-flop**. `.217` had switched nested subagents off by default;
`.219` puts them back at depth 3 (bullet 24). The code shows this was never two changes — it is one
resolver, `hee()` at `:230896-230905`, whose default constant `ZDu = 3` sits behind the remote gate
`tengu_hazel_trellis`. The flip-flop happened server-side; the client constant is the *floor* the gate
falls back to. That is why `.217` could disable nesting and `.219` re-enable it at a different value
without either release touching the enforcement path.

**Relative to its neighbours:** `.218` was a background-execution release (`/code-review` and
`context: fork` skills moved off the main conversation); `.219` is the model release that `.218`'s
concurrency work made safe to ship; `.220` is a single "Bug fixes and reliability improvements" line —
so `.219` is effectively the last release in this window with content, and **the 2.1.220 bundle is the
first and only place any of it can be verified**.

Finally, the release contains this tree's cleanest changelog↔code contradiction. Bullet 22 says Opus 4.7
was removed from fast mode. In the shipped build **it was not** — Opus 4.7 passes the eligibility
predicate twice over — and what actually shipped is a **warning banner announcing a future removal**
whose default date is `2026-07-25`, i.e. **1 h 42 min after this build's own `BUILD_TIME`**. See §4.2.

## 4. Deep dives

### 4.1 The Opus 5 entry, and why "now the default Opus model" is only true first-party

**What it does:** adds `claude-opus-5` to the declarative catalogue and re-points the `opus` alias at it.

**How it works:**

1. The entry (`:14365-14400`) is pure data — no code branches on Opus 5 by id at registration time.
   Eight `provider_ids` are populated (including `anthropic_google_cloud`, which no bullet in the whole
   25-release window mentions), `fallback_3p: "claude-opus-4-8"`, and
   `vertex_region_env_var: "VERTEX_REGION_CLAUDE_5_OPUS"`.
2. Selection goes through the `aliases` table at `:14461-14486`, and that table is **per-provider**:

3. So `opus` resolves to Opus 5 on first-party, Bedrock, Vertex, `anthropic_aws` and Mantle — but to

   third-party channel still resolves to 4.5 or 4.6, three releases after `.197` announced Sonnet 5 as

**Why this approach:** per-provider aliasing lets one shipped binary serve channels whose model rollout
schedules are outside Anthropic's control (a Bedrock/Foundry region gets the weights when the cloud
vendor publishes them). The alternative — a single `default` plus runtime availability probing — would
add a network round-trip to model selection and would fail closed on a cold start.

**Key insight:** the changelog's "now the default Opus model" is a **first-party statement rendered as a
universal one**. The catalogue is the only place the asymmetry is visible, and it also silently
overwrites `.207`'s bullet ("Changed Bedrock, Vertex, and Claude Platform on AWS to default to Claude
Opus 4.8") — those three rows now read `claude-opus-5`. Two changelog entries describing the same field,
twelve releases apart, and only the later one is true in the shipped build.

### 4.2 Bullet 22 is premature: what actually shipped is a countdown

**What it does (per the changelog):** removes Opus 4.7 from fast mode.
**What the code does:** keeps Opus 4.7 fast-mode eligible and renders a deprecation banner.

**How it works:**

1. Eligibility is `mv()` at `:109467-109474`. Opus 4.7 passes on the **capability** branch —
   `capabilities: [..., "fast_mode"]` at `:14324` — *and* on the **substring fallback**,
   `n.includes("opus-4-7")` at `:109473`. Two independent paths, neither removed.
2. The 2.1.193 fallback (`Fm`, `:102320-102325 (193)`) read
   `opus-4-6 || opus-4-7 || opus-4-8`. The **real** window-scale delta is therefore **4-6 out, 5 in** —
   4.7 never moved.
3. What is new is the notice. `LIc()` (`:109491-109498`) returns a formatted date, or `null`:

```javascript
// ============================================
// getOpus47FastModeSunsetDate - formats the sunset date, or null once it has passed
// Location: cli_inner_pretty.js:109491-109498
// ============================================

// ORIGINAL (for source lookup):
function LIc() {
  if (lo(Oi()) !== "claude-opus-4-7") return null;
  let e = Ke("tengu_sunset_penguin_opus47", "2026-07-25"), t = Date.parse(e);
  if (Number.isNaN(t) || Date.now() >= t) return null;
  return new Date(t).toLocaleDateString("en-US", { month: "short", day: "numeric", timeZone: "UTC" });
}

// READABLE (for understanding):
function getOpus47FastModeSunsetDate() {
  if (normalizeModelId(getCurrentModel()) !== "claude-opus-4-7") return null;      // hardcoded to ONE model
  const dateStr = getFeatureValue("tengu_sunset_penguin_opus47", "2026-07-25");    // remotely tunable
  const sunsetMs = Date.parse(dateStr);                                            // date-only ⇒ parsed as UTC
  if (Number.isNaN(sunsetMs) || Date.now() >= sunsetMs) return null;               // silently disappears
  return new Date(sunsetMs).toLocaleDateString("en-US", { month: "short", day: "numeric", timeZone: "UTC" });
}

// Mapping: LIc→getOpus47FastModeSunsetDate, lo→normalizeModelId, Oi→getCurrentModel, Ke→getFeatureValue
```

Its only caller, `ZFo()` at `:499782-499790`, builds
`{ key: "opus47-fast-mode-deprecation", text: "Opus 4.7 fast mode is deprecated and will be removed on <date>", priority: "immediate", color: "warning" }`.

**The timing is the punchline — and it is tighter than previously recorded.**
`Date.parse("2026-07-25")` is a date-only form, which ECMAScript parses as **UTC midnight**, i.e.
`2026-07-25T00:00:00Z`. This build's `BUILD_TIME` is `2026-07-24T22:17:45Z` (`:228`). The notice is
therefore displayable for **1 hour 42 minutes 15 seconds** after the build was cut, not ~26 hours.

> ⚠ **Correction to [`../_GROUND_TRUTH_verified_anchors.md`](../_GROUND_TRUTH_verified_anchors.md)
> §6.2b.** That section states the build shipped "~26 hours before its own announced sunset". Working
> from `Date.parse("2026-07-25") = 2026-07-25T00:00:00Z` and `BUILD_TIME = 2026-07-24T22:17:45Z`, the
> true interval is **1 h 42 min 15 s**. The ~26 h figure is consistent with treating the sunset as the
> *end* of 2026-07-25, but `Date.now() >= t` fires at the *start* of that day. **The conclusion §6.2b
> draws is unchanged and in fact strengthened:** 2.1.220 is the last build that can ever display this
> notice, and its display window was under two hours.

**Why this approach:** a date-gated banner lets the client tell users about a change that will be made
**server-side** without shipping the enforcement client-side, and the gate (`tengu_sunset_penguin_opus47`)
lets the date slip without a release. The cost is exactly what the changelog did: someone wrote the
bullet as if the client change had landed.

### 4.3 `workflowSizeGuideline`: a settings key, a default, and a row that hides itself

**What it does:** turns `.202`'s `/config`-only "Dynamic workflow size" choice into a settings key with
a documented precedence chain, and gives it a default (`medium`).

**How it works:**

1. **The data** (`:389142-389147`): `nMs = ["unrestricted","small","medium","large"]`,
   `cEd = "medium"`, `tko = { small: 5, medium: 15, large: 50 }`. The map is the agent-count target the
   prose quotes ("fewer than 15 agents").
2. **Resolution** (`Dft`, `:389152-389155`): `settings.workflowSizeGuideline` first, then the passed
   value (the `/config` choice), then `{ size: cEd, isDefault: true }`. `Nsn` (`:389157-389160`)
   memoises the first resolution per process.
3. **Row hiding** (`Q$t`, `:389149-389151`): `SI()?.settings.workflowSizeGuideline !== void 0` — a pure
   *presence* test, not a value test, so setting the key to `"unrestricted"` still hides the row. Four
   consumers: `!Q$t()` at `:452357` and `:668331` (the two `/config` row lists), and
   `Q$t() || !Dft(...).isDefault` at `:814921` (the spinner-tip suppressor).
4. **Model-facing prose** (`fEd`, `:389131-389137`) branches on `isDefault`, and *only* the default
   branch appends `' The user can raise or remove it with "Dynamic workflow size" in /config.'`
5. **Status line** (`kya`, `:651528-651549`, bullet 21) returns `null` unless
   `isDefault && size !== "unrestricted"`.

**Why this approach:** points 4 and 5 encode the same rule from opposite directions — *advertise the
guideline only when the user did not choose it*. If the user set `large` in `/config`, re-printing
"large size (/config)" in the status line and re-telling the model where to change it is noise; if the
guideline is an unrequested default, the user needs to know it exists and how to escape it. The
`/config` row disappearing when a settings file supplies the key follows the same logic from the third
direction: never offer a control that a higher-precedence source will override.

**Key insight:** three separate surfaces (prose, status line, `/config` row) are all gated on
`isDefault`/`Q$t()`, and the settings-schema `describe` string at `:60918` is the only place the full
precedence chain — including "managed settings takes precedence over the `/config` choice" — is written
down. The schema doc *is* the spec.

### 4.4 Bullet 17 is a carryover trap nobody caught — and the real delta is a new status arm

**Both candidate modules defer this bullet to each other**
([`../36_background_agents/README.md`](../36_background_agents/README.md) `.219` table → `43_slash_commands`;
[`../43_slash_commands/README.md`](../43_slash_commands/README.md) → `36_background_agents`), so it is
analysed here.

**The trap.** The bullet reads as if "This repo is …" is new. It is not:

```javascript
// ============================================
// teleport repo-mismatch error - the 2.1.193 site the .219 bullet reads as new
// Location: cli_inner_pretty.js:372436-372440 (193)
// ============================================

// ORIGINAL (for source lookup):
throw new Tb(
  `You must run claude --teleport ${e} from a checkout of ${l}.
This repo is ${c}.`,
  Et.red(`You must run claude --teleport ${e} from a checkout of ${Et.bold(l)}.
This repo is ${Et.bold(c)}.
`),

throw new TeleportError(
  `You must run claude --teleport ${sessionId} from a checkout of ${sessionDisplay}.\nThis repo is ${currentDisplay}.`,
  red(`… ${bold(sessionDisplay)}.\nThis repo is ${bold(currentDisplay)}.\n`),
);

// Mapping: Tb→TeleportError, e→sessionId, l→sessionDisplay, c→currentDisplay
```

`This repo is ` is **220=3 / 193=2**. The `resume_validate` mismatch branch is byte-equivalent between
builds (220 `:321226-321235` ↔ 193 `:372427-372441`); the only change there is that 193's inline
host-comparison was extracted into a named helper, `zvo` (`:321176-321182`), which returns
`{ sessionDisplay, currentDisplay }`.

**The three genuine deltas:**

1. **A new `host_unverified` status** (`:321154`, 220=4 / 193=0). The validator now distinguishes
   "different repo" from "same `owner/name`, host not verifiable". `:321154` returns
   `{ status: "host_unverified", sessionRepo, sessionHost, currentRepo, rawRemoteUrl }` when
   `d.toLowerCase() === i.toLowerCase()`. In the resume path (`:321210-321211`) that arm emits
   `tengu_teleport_repo_host_unverified` and **breaks without throwing** — the teleport proceeds. In the
   direct-argument path (`:868461-868464`) it instead asks for confirmation (`Uwm`) and exits 0 on
   refusal. A case that previously would have been a hard "mismatch" error is now a soft prompt.
2. **`rawRemoteUrl` capture and sanitisation** (`:321146-321150`): the raw remote is
   `stripVTControlCharacters(...)`-ed, has `[\r\n]+` collapsed, and is `.slice(0, 200)`-truncated before
   being attached to every non-match status. It surfaces as
   `Couldn't parse your git remote: ${s.rawRemoteUrl}` (`:321216-321218`, 220=2 / **193=0**) — this is
   the literal "show which repo your current checkout points at" for the *unparseable-remote* case,
   which 193 could not report at all.
3. **The message reached the direct-argument path.** The third `This repo is` site is `:868489`, inside
   the `claude --teleport <id>` argument handler, with `stage: Ee("direct_arg_detect")`. 193 had the
   message only on `resume_validate`.

**Why this matters methodologically:** grepping the bullet's own words (`This repo is`) returns a 193
hit and would have produced a `CARRYOVER` verdict and a dead end. Grepping the *status enum* around the
message produced the delta. **When a bullet describes an output string, probe the state machine that
selects it.**

### 4.5 Bullet 24: one gate explains the `.217` → `.219` flip-flop

**What it does:** restores nested subagent spawning at depth 3.

**How it works:** `hee()` (`:230896-230905`) resolves in three tiers — `Z.CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`
→ memoised `getFeatureValue_CACHED_MAY_BE_STALE(sty, ZDu)` → `ZDu = 3`, with
`sty = "tengu_hazel_trellis"` and the memo cell `Dus = null` (`:230908`). Validation is
`typeof r === "number" && Number.isInteger(r) && r >= 1`, and anything else silently falls back to 3.
The enforcement site (`:398325-398330`) throws when `DI(agentContext) >= hee()`.

**Why this approach:** compare with the three sibling caps. `gty = 20` / `yty = 200` / `_ty = 200`
(`:231411-231413`) are read as bare `Z.<ENV> ?? const` with **no gate and no validation**. Depth is the
only one of the four that is gate-backed — because it is the only one Anthropic expected to change
without a release, and it did: `.217` said "no longer spawn nested subagents by default", `.219` says
"up to depth 3 by default (was 1)". Neither release needed to touch the enforcement path; the server
moved the gate value, and `.219`'s bullet documents where the value settled.

**Key insight:** `.219`'s parenthetical "(was 1)" describes the **gate's runtime value at the time of
writing**, not the previous build's constant — 2.1.193's shipped default was **5**
(see [`../53_subagent_limits/spawn_depth_gate.md`](../53_subagent_limits/spawn_depth_gate.md) §1). The
refusal message at `:398328` also gained a line 193 lacked —
*"If the user explicitly requested deeper nesting, ask them to raise CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH."*
— which turns a dead end into an actionable instruction for the model.

## 5. What the changelog does not say

### 5.1 An alias-migration mechanism shipped, fully wired and completely disarmed

Changing what `opus` resolves to strands anyone who pinned `"model": "claude-opus-4-8"` in
`userSettings`. 2.1.220 contains the machinery to fix that — and it is empty:

```javascript
// ============================================
// applyModelAliasMigration - rewrites a pinned userSettings.model, [1m] suffix preserved
// Location: cli_inner_pretty.js:833732-833744
// ============================================

// ORIGINAL (for source lookup):
async function rTm(e = qlE) {
  if (Hn() !== "firstParty") return !0;
  let t = Pr("userSettings")?.model;
  if (!t) return !0;
  let r = Qs(t);
  if (!Object.hasOwn(e, r)) return !0;
  let n = e[r];
  if (n === void 0) return !0;
  let o = r !== t,
    { error: i } = await yi("userSettings", { model: o ? `${n}[1m]` : n });
  if (i) return (w(`Failed to apply model alias migration: ${i}`, { level: "error" }), !1);
  return (O("tengu_alias_migration", { from_model: Bu(r), to_model: Bu(n), has_1m: o }), !0);
}

// READABLE (for understanding):
async function applyModelAliasMigration(migrationMap = ALIAS_MIGRATION_MAP) {
  if (getProvider() !== "firstParty") return true;               // first-party only
  const pinned = readSettings("userSettings")?.model;
  if (!pinned) return true;
  const base = stripOneMSuffix(pinned);                          // "claude-opus-4-8[1m]" -> "claude-opus-4-8"
  if (!Object.hasOwn(migrationMap, base)) return true;
  const target = migrationMap[base];
  if (target === undefined) return true;
  const had1m = base !== pinned;
  const { error } = await writeSettings("userSettings", { model: had1m ? `${target}[1m]` : target });
  if (error) { log(`Failed to apply model alias migration: ${error}`, { level: "error" }); return false; }
  emitTelemetry("tengu_alias_migration", { from_model: redact(base), to_model: redact(target), has_1m: had1m });
  return true;
}

// Mapping: rTm→applyModelAliasMigration, qlE→ALIAS_MIGRATION_MAP, Hn→getProvider, Pr→readSettings,
//          Qs→stripOneMSuffix, yi→writeSettings, O→emitTelemetry, Bu→redact
```

It is called at startup (`:834073`). `qlE` is assigned `{}` at `:833753`. The catalogue has a matching
`alias_migration: {}` at `:14495` with a zod default at `:14640` — and **no code reads it**: the four
occurrences of `alias_migration` in the bundle are the catalogue literal, the schema, the schema default
and the telemetry event name. So there are two independently empty slots and no wire between them. The
mechanism runs on every first-party startup and always returns early. Ground-truth open question 4
("`alias_migration: {}` is empty — what consumes it?") answers: **nothing does, in this build.**

### 5.2 The `strictAllowlist` merge is deliberately one-way

`:62415` reads `if (o.strictAllowlist === !0) l.strictAllowlist = !0;` — a lower-scope settings file can
turn the flag **on** but can never turn it **off**, and the aggregation at `:205177` is
`YLt().some((K) => K?.sandbox?.network?.strictAllowlist === !0) || void 0` — an OR across trusted
sources, again with no way down. The schema string (`:49648-49656`) spells out the companion rule that
the bullet omits: the key is honoured **only** from user, managed/policy or `--settings` scope, and
project-level `.claude/settings.json` is ignored outright — otherwise a cloned repo could disable an
enterprise's deny-by-default network posture. A ratchet, not a toggle.

### 5.3 The picker highlight changed arity, not just target

Bullet 20 says the picker now highlights "only the newest model's name … rather than an arbitrary
subset". The code supports this more literally than
[`../47_models/README.md`](../47_models/README.md) records. 2.1.193 chained **two** highlighters at
`:490616-490617 (193)` — `.replaceAll("Fable 5", …).replaceAll("Mythos 5", …)` — while 2.1.220 has
**one**, `.replaceAll("Opus 5", …)` at `:667097`, followed by an unrelated promo-price
`.replace(/\$[\d.]+\/\$[\d.]+ per Mtok/, …)`. So the "arbitrary subset" is real and had size 2; it now
has size 1. (The mechanism itself — description-string `replaceAll` with an accent colour — is
carryover, so the row remains `DELTA`, and there is still no `isNew` flag anywhere.)

### 5.4 `/add-dir`'s `DirectoryAdded` failure handling is asymmetric by design

`:655138-655165` treats three failure classes differently: a hook that runs and fails logs to the debug
log at `level: "error"` and the user is told only *"N DirectoryAdded hooks failed; output is in the
debug log, not shown here"*; hook `systemMessage`s are surfaced as task notifications prefixed
`DirectoryAdded hook:`; and a `.catch` on the whole promise reports
`DirectoryAdded hook execution failed: …` inline. Crucially the whole thing is fire-and-forget — the
directory is added and the confirmation printed *before* `a2t(a, "slash_command")` is invoked, so a slow
or failing hook can never block or reverse `/add-dir`. The changelog says the hook "fires after"; the
code makes "after" load-bearing.

### 5.5 The bullet count understates the release

Three of the largest structural changes visible in the 2.1.220 build have **no bullet in `.219` or
anywhere in the 25-release window**: the model-registry rewrite itself
([`../47_models/model_catalogue_rewrite.md`](../47_models/model_catalogue_rewrite.md)), the
`anthropic_google_cloud` provider channel that appears in every catalogue entry
([`../47_models/anthropic_google_cloud_channel.md`](../47_models/anthropic_google_cloud_channel.md)),
and the dual MCP runtime trees
([`../39_mcp/dual_mcp_runtime_trees.md`](../39_mcp/dual_mcp_runtime_trees.md)). `.219` is where the
first two become *visible* — Opus 5 is the entry that makes the catalogue worth reading — but the
changelog frames the launch as adding a model, not as the payoff of a registry rewrite.
