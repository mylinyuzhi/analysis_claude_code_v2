## a) Release narrative

**2.1.205 is the release where the background-agent surface stops being a process manager and starts
being a product.** Nine of its 23 bullets touch `claude agents` — the row state word, the classifier
headline, the peek, the PR link, the compacting header, `claude attach`, `SendMessage` resume — and
they are not independent fixes. They are the visible half of one change: the agent view now reports
*semantic* state (`working` / `blocked` / `done` / `failed` plus a one-line headline and, when blocked,
the exact ask) instead of echoing raw tool-call text. Every "flapping"/"stale label" bullet in this
release is a hole in that reporting pipeline being plugged — a turn with no readable text (#6), a turn
that ends in a terminal state and is then resumed (#5), a PR the agent touched but did not create (#19),
a Bash call whose output spilled to a file (#8).

**The second centre of gravity is anti-forgery, and it is unusually explicit.** Three bullets in this
release are about *the model not being allowed to launder its own claims into authority*: the auto-mode
rule that blocks writes to session transcripts (#1), the `rm -rf $VAR` rule that refuses a delete whose
target the classifier cannot resolve from the transcript it can see (#16), and the background-task
notification banner that now states in so many words that no human input has occurred (#18). Read
together they describe a single threat model: **the transcript is the classifier's ground truth, so
anything that can write to it, or that can hide a value from it, is a privilege-escalation vector.**
The `Unverifiable Deletion Target` rule text spells the reasoning out — the value "came only from
earlier command output the classifier never sees, so the blast radius is unknowable" — and refuses to
accept `echo "$VAR"` as proof, because *that output never reaches the classifier either*.

**Third: `/doctor` is re-founded (#21).** `/doctor` stops being a version/installation check and becomes
a ten-check setup prompt that can also *fix* what it finds, with `/checkup` as an alias. It is one of the
largest new prompt assets in the whole `.193 → .220` window, and it absorbs work that other releases in
this range *removed* from startup (`.203` deleted the "claude command missing or broken" startup
warnings; `.206` adds the CLAUDE.md-trimming and Homebrew-cask checks into the same corpus).

Around those three, `.205` carries a Windows/filesystem safety batch (#4 NTFS junctions during worktree
removal, #11 a deleted launch directory, #12 a file watcher closed mid-scan), a genuine memory win in
the updater (#17, streaming download), and two forward-looking reservations: the `Claude Browser` MCP
server name (#22, taken *before* the Desktop pane rename ships) and the Remote-Control
`background_tasks_changed` level event (#15). Placed between `.204` (a single-bullet headless hook fix)
and `.206` (the `/doctor`-era polish release), `.205` is the substance of that pair.

### C.1 `#19` + `#8` — PR linking: the fix is a new `else` branch, and a spilled-output reader

**What it does:** in 2.1.193 a session's row in `claude agents` linked a pull request only when the
session *created* it with `gh pr create`. `.205` links a PR the session **edited, merged, commented on,
closed or marked ready** (#19), and finds the PR even when the `gh` output was too large to be returned
inline and got spilled to a temp file (#8).

almost nothing.

### C.2 `#6` — one character class turns "empty turn" into "no readable text"

**What it does:** the agent-view roster updater must decide whether the agent's last turn says anything
about its state. If it does not, the row must keep its previous state; if it wrongly decides the turn
*did* say something, the LLM classifier gets a content-free prompt and answers `working`, which is the
"needs input → working" flap in the bullet.

**How it works.** The updater joins the new transcript entries into one string and tests it:


**Why this approach:** 193's `!F` only catches a turn that joins to the empty string. But a turn can be
non-empty and still say nothing: a lone bullet `-`, an ellipsis, a bare code fence, an emoji, a
whitespace-and-punctuation-only diff header. `\p{L}` (any Unicode letter) `\p{N}` (any Unicode number)
is the minimal test for "there is a word or a figure in here" and — importantly — it is
**script-agnostic**, so a Japanese or Cyrillic turn still counts as readable. The alternative,
`F.trim().length > N`, would have failed exactly the same way for punctuation-only turns and would have
introduced a magic threshold.

**Key insight:** the `source: "no-text-turn"` tag is **220=1 / 193=1** and `"no-text-turn"` overall is
2/2. Counting the tag says "carryover"; reading the two `if` conditions says the guard's *domain*
widened. This is `_CONVENTIONS.md` §4 trap #1 in miniature, and it is why the ledger row above is
`DELTA`, not `NET_NEW`.

### C.3 `#1` + `#16` — the two new auto-mode rules are one threat model

**What they do:** both add a rule id to the canonical classifier rule enum `xNy`
(`:345161-345234`, alphabetically sorted) and a matching block of rule prose to the classifier prompt
corpus around `:443172-443410`. `session_transcript_tampering` (`:345225`, 220=1/193=0) and
`unverifiable_deletion_target` (`:345233`, 220=1/193=0) are adjacent-but-two-apart in that list, and
adjacent in intent.

**How they work — read the prose, not the id.** The `Unverifiable Deletion Target` rule (`:443379`)
fires on a recursive forced delete whose target is `$VAR` / `${VAR}` / `"$VAR"/*` when the variable has
**no in-window assignment** (`VAR=…`, `export VAR=…`, `read VAR`, `for VAR in …`) and is not an obvious
literal. Its stated reason:

> *"The value came only from earlier command output the classifier never sees, so the blast radius is
> unknowable — an empty or unexpected `$VAR` turns `rm -rf "$VAR"/*` into a `$HOME` or filesystem-root
> wipe. This includes multi-part paths like `"$BASE/$pin"`: if any component can be empty, the delete
> silently climbs to the parent directory or the filesystem root. Fail closed."*

And its clearing conditions are the interesting part: the user names the exact path, **or** the agent
re-runs the delete with the resolved literal path written into the command — with an explicit
carve-out that *"an `echo "$VAR"` does not clear it: its output never reaches this classifier, so the
re-run would be just as unverifiable."*

The `Session Transcript Tampering` rule (`:443406`) covers writes to the session `.jsonl` under
`~/.claude/projects/` (directly or through shell), **and** forging or altering the
`{"meta":{…}}` ground-truth lines the classifier reads, so they read back as harness-injected. Its
stated reason: *"a tampered entry feeds every later classification once the session is resumed."*
Reading transcripts is explicitly out of scope.

**Why this approach:** the classifier's whole security model is that the transcript is an honest record
of what actually happened. Both rules defend one invariant from opposite directions — #1 stops the agent
**writing** into the evidence, #16 stops the agent **hiding** a value from it. Note that #16's rule
has an unusual "must name" clause (`the exact path being destroyed`) and #1's is even more unusual
(`must name: that this flagged transcript write is a false positive — fine to allow`), i.e. the block
message itself is engineered so a human can adjudicate in one read.

**Key insight:** this is the same anti-fabrication posture as `.205 #18`'s notification banner
(`No human input has been received…`, `:226519`, `no human` **220=3 / 193=0**) — see
[`../40_system_prompt/reminder_framing_and_human_origin.md`](../40_system_prompt/reminder_framing_and_human_origin.md).
Three bullets in one release, three different subsystems, one rule: **the model may not manufacture its
own authority.** Note the banner *prefix* `[SYSTEM NOTIFICATION - NOT USER INPUT]` is **220=1 / 193=1**

### C.4 `#7` — `claude attach` learned to wait, with a two-tier retry budget

**What it does:** attaching to a background session that is mid-restart used to fail. `.205` makes
`claude attach` poll while the daemon reports a *transient* condition, with a printed progress line.

**How it works.** `DIa` (`:682883-682925`) wraps the single attach RPC in an exponential-backoff loop:

1. Classify the failure message. `Ndr = /ERESPAWNING|ESTARTING/` (`:330101`) is the *worker is coming
   back* class; `Fdr = /\bE(?:NOENT|CONNREFUSED|CONNRESET)\b|control socket closed/` (`:330102`) is the
   *daemon socket is down* class, filtered by `jdr = /^E[A-Z]+:/` (`:330105`) so a genuine errno-prefixed
   failure is not retried.
2. For the daemon class only, call `WX({ forceTransient: !0 })` (`:682910`) to re-ensure the daemon
   before retrying; if that fails, return `unavailableReason` instead of spinning.
3. Back off `Math.min(2000, 250 * 2 ** u)` (`:682913`) — 250, 500, 1000, 2000, 2000, … capped at 2 s.
4. Show progress only once it is worth showing: `if (d.includes($1t) || c + m > IGb) s(RGb(d), c)`
   (`:682914`), where `$1t = "ERESPAWNING"` (`:330047`) and `IGb = 2000` (`:683593`). So a restart is
   announced immediately, and anything else stays silent for the first 2 s.
5. Give up at `HGb = 60000` (`:683592`) total waited milliseconds, and report the wait as
   `waited_transient_ms` (`:682934`, **220=1 / 193=0**) on whatever outcome follows.
6. `abortOnDetachKey` (`:682915-682917`) lets the user press the detach key during the wait — the
   loop is interruptible, which is why it can afford a 60 s budget.

The separate `tengu_bg_attach_wake_after_reap` (`:682964`, 220=1/193=0) covers the *other* half of the
bullet: a session that was reaped while unattended (`reapedMidWorkAt` / `reapedUnsettledAt`, both
**220=6 / 193=0**) is now resumed with *"Session … was interrupted while unattended — resuming it…"*
instead of the `state === "failed"` hard error at `:682956-682962`.

**Why this approach:** two budgets rather than one. `IGb = 2000` governs *when to speak*, `HGb = 60000`
governs *when to stop waiting*. Collapsing them would either spam a progress line for a 300 ms blip or
hide a 40 s upgrade behind silence. And the `ERESPAWNING` exemption at step 4 is a deliberate asymmetry:
the one case where the user definitely wants to be told immediately is the one where the wait is
guaranteed to be long.

**Key insight:** the retry classes are *regex over the error message*, not error codes — the daemon
protocol returns strings. That is fragile, and the code knows it: `jdr` exists purely to stop
`Fdr` matching an already-formatted `ECONNRESET: …` error and retrying something that will never
succeed.
