## a) Release narrative

**2.1.217 is the subagent-governor release**, and it is the first release in this window whose centre of
gravity is *restraint* rather than capability. Two of its twenty bullets introduce
`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (default 20) and `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, and
together they finish a governor family that `.212` started with the two per-session budgets
(`CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION`, `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION`). The pairing is
deliberate and the ordering matters: `.212` bounded *how much* a session may spend in total, `.217` bounds
*how much may be in flight at once* and *how deep the tree may go*. Read against `.219` — which re-opens
nesting to depth 3 — `.217` looks like the safety half of a two-step: switch nesting off, ship a fan-out
cap, then switch nesting back on once the fan-out is bounded.

Its second thread is **failure visibility**. Four bullets (2, 4, 8, 11) are all of the same shape: a
failure that used to be silent now produces a message. Transcript writes that fail on a full disk used to
lose messages quietly; an inherited `CLAUDE_CODE_CHILD_SESSION` marker used to disable session saving
without saying so; a Windows update that lost `claude.exe` used to leave a broken install; a permission
prompt raised before a Remote Control viewer joined used to be invisible to that viewer. Each of these is
now a banner, a telemetry event, or a self-heal path, and three of the four are **220>0 / 193=0** on their
own strings.

The third thread is **accessibility and input polish** — the emoji shortcode engine (a 1,567-entry table
plus two trigger regexes), the screen-reader startup quiet window, and forced hyperlinks in the footer PR
badge. Emoji completion is the only bullet in the whole `.215`–`.220` sub-range where *every* component is
net-new; the other two are narrow deltas on machinery that already existed in 2.1.193.

Around those three threads sit six repair bullets whose value is a single deleted or added conditional: the
Bedrock auto-compact fix (three predicates lose a model-pinned conjunct), the Claude Desktop mTLS fix (one
added conjunct), the managed-OTel fix (a gateway push, not a client change), the brace-expansion budget, the
`maxLifetimeShows` property, and the login-expiry multiplier. This is characteristic of the late window: the
mechanisms are mature, so the deltas are one line wide and the analytical work is locating that line rather
than describing a new subsystem.

Two bullets in the release are honestly **unanchored** (#10 the `--resume` TypeError, #12 background shells
that cannot be stopped) and one is layout-only with no literal (#14). They are marked as such below rather
than attached to a plausible-looking neighbour.

### c.1 Bullet 2 — the two silent-transcript-loss failure modes, and the two banners that ended them

**What it does:** the client now tells you, in the footer, when (a) transcript *writes* are failing at the
filesystem level, or (b) transcript *saving* was never on in this process because an environment marker was
inherited from a parent. Both were previously silent, and both make `--resume` fail later with no
explanation.

**How it works.**

The two halves are independent machines that happen to share a bullet.

**Half A — the degraded-writer latch.** Every failed transcript write updates a per-file failure record and
emits `tengu_transcript_write_failed`. The *latch* into degraded state is deliberately conservative:

```javascript

1. Only three write *sources* can latch — `drain`, `materialize`, `adopt` (`:522839`). An ad-hoc write
   failing does not degrade the session.
2. The generic path needs **3 consecutive failures spanning at least 60 seconds**. Both terms are required:
   three failures inside one burst (a transient `EMFILE` spike) does not latch, and one failure an hour
   apart does not either. The banner therefore means "sustained", not "flaky".
3. A Linux-fatal errno class (`zF_(o, "linux")`) latches **immediately**, bypassing both terms — the disk-full
   case the bullet names, where waiting 60 seconds only loses more messages.
4. Recovery is symmetric and equally explicit: `Yip` (`:522794-522798`) deletes the record, clears the store
   and emits `tengu_transcript_writer_recovered` — so the banner disappears on its own and the telemetry can
   measure how long degradation lasted.

The banner text (`:749644-749645`, id `transcript-writer-degraded` `:749648`) is
*"Transcript writes are failing (`<code>`) · recent messages may not be saved for resume"*, and a second,
louder copy is written to the log at process exit (`:523307-523309`, "entries since the failure window may
be missing from the transcript").

`rHt` (`:112566-112570`) is the bullet's "inherited environment variable": it fires when
`CLAUDE_CODE_CHILD_SESSION` is set *and* the process looks like a nested child, with
`CLAUDE_CODE_FORCE_SESSION_PERSISTENCE` as the first-checked escape hatch. Only **two** of the four causes
raise a banner (`:749601`): `skip_prompt_history` and `nested_marker` — the two the user did not choose for
*this* process. `test_env` and `explicit_disable` are intentional, so they stay silent. Each banner names its
own remedy (`:749616-749619`):

> *Transcript saving is off — inherited `CLAUDE_CODE_CHILD_SESSION` marker*
> *· restart with `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1` to keep future transcripts*

**Why this approach:**

- *Why a latch instead of warning on the first failure?* Transcript writes are on the hot path of every
  message; a per-failure banner would flap. Requiring 3-in-60s converts "noisy" into "actionable" while the
  Linux-fatal carve-out keeps the one case where latency costs data.
- *Why suppress the banner for `explicit_disable`?* The design rule visible here is **warn only about state
  the user did not ask for in this process**. An inherited marker is exactly that — it arrives from a parent
  process the user may not know about.
- *Why fire `tengu_persistence_suppressed` through a once-latch* (`pVs` `:522758`, a `dVs` boolean)? The
  React effect it lives in re-runs on every state change; the latch makes the event a per-process fact rather
  than a per-render count, so fleet numbers mean "sessions", not "renders".

**Key insight:** the bullet reads like one logging improvement but it is two independent detectors joined by
a shared consequence — *`--resume` will not find this session*. Both banners lead with that consequence
rather than with the cause, which is why the strings are `220=2 / 193=0` while the underlying
`CLAUDE_CODE_CHILD_SESSION` plumbing (14/11) is mostly carryover. **This bullet has no module doc; the
anchors above are its primary analysis in this tree.**

### c.2 Bullet 4 — the Windows auto-update self-heal (`update_apply_heal`)

**What it does:** before attempting an update, the updater checks whether `process.execPath` is *missing*
(the state a failed Windows update leaves behind, because the install is a rename-then-write) and, if so,
restores the newest `claude.exe.old.<ts>` copy it preserved in a retired directory.

1. Candidates are gathered from **retired directories** — the per-version folders the updater leaves behind
   — and each is *probed* (`Xzs`) rather than trusted to exist, because a half-finished update can leave a
   zero-byte or locked file.
2. Selection is `reduce` on `a.ts > s.ts`: newest wins. Not "the version we were on" — newest — which is the
   right choice when the goal is *have a working binary at all*, not *roll back precisely*.
3. Both outcomes are telemetered under a single event name with a `heal_kind` discriminator
   (`"sweep"`), so the fleet can measure how often the heal path is taken and how often it itself fails.
4. The no-candidate branch logs the *number of directories searched*, which is what turns a support report
   into a diagnosable one.

**Why this approach:** the alternative — make the Windows install atomic — is not available, because Windows
cannot replace a running executable, so the updater must rename-then-write and there is necessarily a window
where `process.execPath` does not exist. Given an unavoidable window, the design choice is to make the *next*
run self-heal rather than to shrink the window. The preserved `.old.<ts>` copies were already being written
(that is why the sweep has something to find); `.217` adds only the consumer.

### c.3 Bullets 18 + 19 — why the cap and the nesting switch shipped in the same release

The mechanisms are documented in
[`../53_subagent_limits/concurrency_and_session_caps.md`](../53_subagent_limits/concurrency_and_session_caps.md)
and [`../53_subagent_limits/spawn_depth_gate.md`](../53_subagent_limits/spawn_depth_gate.md); what follows is
the release-level reading that spans both, and one detail neither doc frames as a `.217` decision.

**The two limits attack the same failure from opposite ends.** Depth bounds the *height* of the agent tree;
concurrency bounds its *width*. Either alone is insufficient: depth 1 with unlimited width still lets one
model turn open fifty streams, and width 20 with unlimited depth still lets a chain of re-delegations run
forever. Shipping only one of them would have been a half-measure, which is why they are one release.

**They are enforced at different layers, and the asymmetry is the design.** The depth cap is refused at three
tiers — the Agent tool is removed from the child's *schema*, the fan-out instructions are removed from the
child's *prompt*, and the call is refused at *runtime* — so a capped child usually never tries. The
concurrency cap has only the runtime tier, because concurrency is a live gauge that cannot be known when the
prompt is built. Read the runtime closure:

          let concurrencyCapGuard = () => {
            let cap = getMaxConcurrentSubagents();                       // env ?? 20   :231400/:231411
            if (taskRegistry.getConcurrentSubagents() < cap) return;     // under cap: allow
            if (getFeatureValue("tengu_amber_kestrel", false)) return;   // remote kill switch for the cap
            let appState = getAppState();
            if (isCapExemptSurface(mainLoopModel, appState.effortValue, appState.ultracode)) return;
            emitFailure("subagent_launch", "subagent_concurrency_cap");
            return new AgentLaunchError(`Concurrent subagent limit reached. You can run ${cap} subagents at once. Do not retry. …`);

// Mapping: D→concurrencyCapGuard, gPu→getMaxConcurrentSubagents, Ke→getFeatureValue,
//          bY→isCapExemptSurface (:119417), wIe→AgentLaunchError, pe→emitFailure
```

**The detail worth calling out:** the cap ships with **two escape hatches that are invisible in the
changelog** — a remote gate `tengu_amber_kestrel` (`:398405`, 220=1 / **193=0**) that disables the cap
fleet-wide, and a capability predicate `bY` (`:398407`, declared `:119417`) that exempts certain
model/effort surfaces entirely. So the "default 20" the bullet advertises is the *floor* of a three-way
decision, not a hard constant, and a session can legitimately exceed it without any env var being set.

**And the refusal is addressed to the model, not the user.** *"Do not retry. If the user wants more
concurrent subagents, ask them to increase `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`."* The depth refusal
(`:398328`) gained the same shape in this window: 2.1.193's text stopped at *"Complete this task directly
using your tools instead of spawning another agent."*; 2.1.220 appends *"If the user explicitly requested
deeper nesting, ask them to raise `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`."* Both sentences exist because the
model cannot raise the limit itself — the env vars are read from the process environment — so the only
correct model behaviour is to escalate. Treating a resource limit as a *prompt-engineering surface* is the
non-obvious idea in this release.

## d) What the changelog does not say

**1. `.217`'s headline nesting claim is not provable from this bundle, and the shipped constant contradicts
it.** The bullet says nesting is off by default. 2.1.220 ships `ZDu = 3` (`:230906`) and resolves depth
through `hee` (`:230896`) as *env → gate `tengu_hazel_trellis` → 3*. Because the `.217` build is not in this
tree, the bundle cannot distinguish "`.217` shipped `ZDu = 1` and `.219` changed it" from "`.217` shipped 3
and pushed `tengu_hazel_trellis = 1` remotely". What it *does* prove is that a remote gate is authoritative
over the constant — which is exactly the machinery that makes a `.217`→`.219` flip-flop cheap. See
[`../_GROUND_TRUTH_verified_anchors.md`](../_GROUND_TRUTH_verified_anchors.md) §2 and
[`../53_subagent_limits/spawn_depth_gate.md`](../53_subagent_limits/spawn_depth_gate.md) §2's honesty note.

**2. Depth limiting is not new — 2.1.193 already refused nested spawns at 5.** `FBt = 5` at `:229871 (193)`,
with no env override and no gate, and the refusal at `:430482 (193)` is otherwise the same sentence. A
`grep -c 'Subagent nesting limit reached'` returns **1/1**. The delta is the *limit's source* (constant →
three-tier resolver) and one appended sentence, not the existence of a cap.

**3. Only two of the four subagent governors can be set from `settings.json`.** The settings-`env`
allow-list at `:57993-58175` contains `CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION` (`:58164`) and
`CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` (`:58166`) — and **not** the two `.217` introduces. The
concurrency and depth caps are process-environment-only, so a repo cannot raise a machine-level resource
limit or a safety limit by committing a settings file. The changelog presents all four as symmetric env
overrides.

**4. The concurrency cap has a remote kill switch and a capability exemption.** `tengu_amber_kestrel`
(`:398405`, 220=1 / 193=0) and `bY` (`:398407`) — see §c.3. Neither appears in any bullet.

**5. The Bedrock auto-compact fix is a deletion in three places, plus a fourth rewrite.** The bullet names a
symptom ("auto-compact never triggering for Opus 4.8 on Bedrock"). The change is the removal of a
model-pinned experiment conjunct (`P7`/`PZr = "claude-opus-4-8"`) from the trigger predicate (`:441107`), the
blocking-limit predicate (`:237072`) and the `/context` buffer decision (`:441639`), **plus** the rewrite of
its companion from a four-name source enumeration to its complement (`zVe` `:237008-237010`:
`o7(e, t).source !== "auto"`). The second edit was mandatory: 193's enumeration omitted `"experiment"`, so
deleting the conjunct alone would have broken the experiment cohort. Two edits, one change. See
[`../07_compact/dispatcher_and_failure_breakers.md`](../07_compact/dispatcher_and_failure_breakers.md) §3.

**6. `.217` #9 is implemented in the gateway, not in the client.** The bullet reads as a client settings-
precedence fix. `OTEL_EXPORTER_OTLP_ENDPOINT` is 220=9 / 193=7, and the two new sites are in the enterprise
gateway's `/managed/settings` response (`:861015-861021`), which pushes `OTEL_METRICS_EXPORTER`,
`OTEL_LOGS_EXPORTER`, `OTEL_TRACES_EXPORTER` and the endpoint together. The *client-side* resolution is
carryover, and the signal-specific-override half of the bullet is not implemented client-side at all —
`44_telemetry` records this as an over-claim.

**7. The login-expiry "5 → 3" change is invisible from this baseline.** `run /login to renew` is
**220=2 / 193=0**: the entire warning post-dates 2.1.193. So `tff = 3 * rff` (`:687512`) is the *first*
threshold this tree can observe, not a change from 5. Reporting it as a threshold delta would be inventing a
before-picture.

**8. `.217` #3's fix is a general string-representation breaker, not an MCP change.** `_Il` (`:20687`) is
`Buffer.from(e, "utf16le").toString("utf16le")` — a round-trip that forces a JS engine `SlicedString` to
materialise as a standalone string, releasing its parent. MCP truncation is one caller; the bullet names the
symptom rather than the mechanism, and the mechanism applies to every truncation site that reaches it.

**9. Two bullets stay unanchored, and that is the finding.** #10 (`--resume` TypeError on a malformed
attachment) is currently a *circular* gap in this tree — `07_compact` files it under the slash-command side
and `43_slash_commands` files it back under compaction — and #12 (background shells impossible to stop) has
`tengu_bg_stdin_unreadable` as a neighbour but no stop-path anchor. Neither is attached here to a
plausible-looking literal.
