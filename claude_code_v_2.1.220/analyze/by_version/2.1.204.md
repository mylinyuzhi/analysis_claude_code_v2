## a) Release narrative — what a one-bullet release means

There are **five single-bullet releases** in the `.195 → .220` window: `.201`, `.204`, `.209`, `.215`
and `.220`, plus `.197`'s single-bullet Sonnet 5 launch. They are not one kind of release. `.197` and
`.219` are **model launches** with one headline and a large body of unlisted plumbing. `.201` and
`.209` are **behavioural retractions** — `.201` narrowed a model's use of the mid-conversation system
role, `.209` reverted an overly broad dialog guard. `.220` is a **release-note placeholder**
("Bug fixes and reliability improvements").

`2.1.204` is the fourth kind, and the rarest: **an out-of-band hotfix for a production incident**. It
lands one day after `.203`'s thirty-seven-bullet background-agent batch and one day before `.205`'s
twenty-three, with exactly one bullet between them:

> *"Fixed hook events not streaming during SessionStart hooks in headless sessions, which could cause
> remote workers to be idle-reaped mid-hook."*

The shape of a one-bullet hotfix is diagnostic in itself. Nobody cuts a release for one UI polish item;
they wait for the next batch. A release is cut for one item when **the item is losing sessions in
production** and the fix cannot wait for the next train. Read the bullet's second clause: *remote
workers idle-reaped mid-hook.* A remote worker (a Claude Code session running in a cloud environment,
driven over the SDK's stream-json protocol) is watched by a supervisor that reaps it if it appears
idle. A `SessionStart` hook can legitimately run for minutes — installing dependencies, warming a
cache, waiting on a network call. If nothing is written to the protocol stream while that hook runs,
the supervisor concludes the worker is dead and kills it **during its own initialisation**. Every
session on a slow `SessionStart` hook dies before it ever reaches the model. That is an outage, and it
is caused by `.203`'s own expansion of what background/remote sessions do.

The fix has two halves, and this is where the by-version view adds something the module docs did not.
[`../41_hooks/README.md`](../41_hooks/README.md) routes this bullet to `51_headless_sdk`;
[`../51_headless_sdk/README.md`](../51_headless_sdk/README.md) routes it back to `41_hooks`. Neither
module performed the primary analysis, so it is done here — and it turns out the *first* half of the
bullet, the "hook events not streaming" clause, has an anchor that neither doc found: a **temporary
event-queue drain pump installed around `SessionStart`**, at `:845211-845212` and `:845235`, with the
predicate literal `outputFormat === "stream-json" && Boolean(` measuring **220=1 / 193=0**.

## c) Deep dive — the whole of 2.1.204

### c.0 The pipeline the bullet is about

Four components, in order. Only the last two changed.

1. **The hook-event emitters.** `$uo` (`hook_started`, `:216586`), `mKg` (`hook_progress`, `:216590`),
   `Nuo` (a 1-second `setInterval` poller that re-emits `hook_progress` when a running hook's captured
   output grows, `:216603`), and `TN` (`hook_response`, `:216615`). All four push a `{type: "system",
   subtype: "hook_*"}` object into a queue via `lA`.
2. **The streaming gate** `Ouo` (`:216582`), which decides *which* hook events are streamable at all.
3. **The queue** — a per-session array behind `dKg()` (`:216511`), capped at `cKg = 1000` (`:216566`),
   pushed by `lA` (`:216523`), drained by `hDt()` (`:216541`), and with a **single module-level
   change callback** `cxu` installed by `pVe(e)` (`:216520`) and invoked at the end of every `lA` push.
4. **The consumer** — whoever most recently called `pVe`, which forwards drained events onto the
   stream-json output.

The queue holds events; the callback is what makes them *stream*. If no callback is installed, events
accumulate silently until someone drains — which is exactly the failure the bullet names.

the hooks subsystem at all, which is why `41_hooks` had nothing to own and punted.

### c.2 Half (a) — a temporary drain pump wrapped around `SessionStart`

**What it does:** installs a queue-change callback that writes hook events straight to the stream-json
output *before* `SessionStart` hooks run, and removes it the moment the real turn loop is ready to take
over.

**How it works:**

```javascript
// ============================================
// pumpTaskEventsToOutput + the SessionStart window that uses it
// Location: cli_inner_pretty.js:845049-845053 (pump), 845211-845212 (install), 845235 (teardown)
// ============================================

// ORIGINAL (for source lookup) - :845049-845053:
function Kkm(e) {
  let t = () => {
    for (let r of hDt()) e.write(r).catch(() => {});
  };
  (pVe(t), t());
}

// ORIGINAL (for source lookup) - :845211-845212 and :845230, :845235:
  let T = l.outputFormat === "stream-json" && Boolean(l.verbose);
  if (T) Kkm(_);
  if (l.setupTrigger) await KGe({ kind: "setup", trigger: l.setupTrigger });
  ...
  } = await sHm(r, { ..., sessionStartHooksPromise: l.sessionStartHooksPromise, ... });
  if (((E.current = I), T)) pVe(null);

// READABLE (for understanding):

//          pVe→setTaskEventQueueListener (:216520), sHm→loadInitialMessages,
//          KGe→runSetupHooks, _→io (from gfE, :850004), l→options, T→streamingHookEvents
```

**The 2.1.193 shape, and why it dropped the events.** In 2.1.193 the same entrypoint went straight from
sandbox initialisation to `if (l.setupTrigger) await yAe(...)` and then `loadInitialMessages`
(`:705303-705322 (193)`), with **no queue listener installed**. The only `sGe(...)` registration on the
headless path was inside the turn loop `JRc`, at `:705629-705631 (193)`:

```javascript
// ORIGINAL 2.1.193 (for source lookup) - :705629-705631 (193):
    (sGe(() => {
      for (let jn of V7()) R.enqueue(jn);
    }),
```

`JRc` runs *after* `loadInitialMessages` has resolved — that is, **after** the `SessionStart` hooks
have finished. So for the whole duration of a `SessionStart` hook, `bv` (193's `lA`, `:242514 (193)`)
pushed events into the array and then called `Fea?.()`, where `Fea` was still `null`. The events were
not lost — they surfaced in a burst once the turn loop registered — but they did not **stream**, and
the output was silent for the entire hook. Both clauses of the bullet follow from that one fact.

**Why this design, and what the alternatives were.**

- *Alternative 1: register the turn loop's listener earlier.* Not possible — the turn loop's listener
  closes over `R`/`j`, the outbound queue object that does not exist until the loop is constructed.
- *Alternative 2: drain the queue once, after the hooks finish.* That is precisely 2.1.193's behaviour
  and it does not solve the reaping half: a supervisor watching for traffic sees nothing until the
  hooks end, which is exactly when it has already killed the worker.
- *Alternative 3: make `lA` write through unconditionally.* This would couple the queue to an output
  transport that may not exist (interactive sessions have no stream-json writer) and would break the
  queue's other consumers at `:738752` and `:738769`.

The shipped design — a *scoped, temporary* listener that is installed for exactly one window and then
handed back — is the smallest change that satisfies both halves. **`pVe` holds exactly one callback**,
so install/teardown is a strict handover: `Kkm` claims it, `pVe(null)` releases it, `JRc` claims it
next. Getting the teardown wrong in either direction is a real bug (leak the pump → double-write every
task event; tear down too early → re-open the silent window), which is why the teardown is fused into
the same statement that stores the loaded messages, `if (((E.current = I), T)) pVe(null);`.

**Why gated on `verbose`.** `T` requires *both* `outputFormat === "stream-json"` **and** `verbose`.
`hook_started`/`hook_progress`/`hook_response` are `type: "system"` frames; a non-verbose stream-json
consumer does not expect them and some parsers reject unknown system subtypes. Restricting the pump to
verbose mode means the fix cannot change the output shape of any existing non-verbose integration.
Note the *cost* of that decision: **a non-verbose remote worker still gets no hook events during
`SessionStart`** — which is why half (b) exists and why it is a *separate* channel rather than more
events on the same one.

**One more property worth naming:** `e.write(r).catch(() => {})`. The pump swallows write failures
silently. During `SessionStart` the transport may not be fully connected; a rejected write here must
not become an unhandled rejection that kills the session the fix exists to keep alive.

### c.3 Half (b) — `CLAUDE_RUNNER_ACTIVITY_FD`, a liveness channel that is not the protocol stream

**What it does:** lets the harness that supervises a remote worker hand it a dedicated file descriptor.
The worker writes activity lines to that fd instead of stdout, so the supervisor can distinguish
*"alive and working"* from *"producing protocol output"* — two things that are the same channel in
2.1.193 and are the root cause of mid-hook reaping.

The env var is **220=3 / 193=0**: declared in the env accessor table at `:32017`
(`CLAUDE_RUNNER_ACTIVITY_FD: () => vuh`), consumed in the `RemoteIO` constructor at `:840835`, and
listed at `:869258` in the spare-worker env scrub list.

```javascript
// ============================================
// RemoteIO activity-fd adoption - validate, open, and fall back to stdout
// Location: cli_inner_pretty.js:840835-840849
// ============================================

// ORIGINAL (for source lookup):

        u = c ? Number.parseInt(c, 10) : NaN;

          let y = ggi.fstatSync(u);

          let _ = ggi.createWriteStream("", { fd: u, autoClose: !1 });
          (_.on("error", (E) => {
            (w(`[remote-io] activity fd ${u} write error (${le(E)}); falling back to stdout`),
              (this.activityFd = void 0));
          }),
            (this.activityFd = _));
        } catch (y) {
          w(`[remote-io] activity fd ${u} unavailable (${le(y)}); falling back to stdout`);
        }

      const raw = process.env.CLAUDE_RUNNER_ACTIVITY_FD;
      const fd = raw ? Number.parseInt(raw, 10) : NaN;
      if (Number.isInteger(fd) && fd > 2) {          // never 0/1/2 - stdin/stdout/stderr are off-limits
        try {
          const st = fs.fstatSync(fd);
          if (!st.isFIFO() && !st.isSocket()) throw new Error("not a pipe");   // refuse a regular file
          const stream = fs.createWriteStream("", { fd, autoClose: false });   // never close the harness's fd
          stream.on("error", (err) => {                                        // demote on first write error
            log(`[remote-io] activity fd ${fd} write error (${fmt(err)}); falling back to stdout`);
            this.activityFd = undefined;
          });
          this.activityFd = stream;
        } catch (err) {
          log(`[remote-io] activity fd ${fd} unavailable (${fmt(err)}); falling back to stdout`);
        }
      }

// Mapping: ggi→fs, u→fd, _→stream, this.activityFd→(:840807 class field), w→logForDebugging, le→formatError
```

**Every clause of that validation is load-bearing.**

- `Number.isInteger(u) && u > 2` — an fd of 0/1/2 would make "activity" writes collide with
  stdin/stdout/stderr, i.e. with the protocol stream, which is the exact confusion being fixed.
- `!isFIFO() && !isSocket()` → **refuse**. A regular file would accept writes and grow unboundedly
  while signalling liveness to nobody. Only a pipe or socket has a reader on the other end.
- `autoClose: !1` — the fd belongs to the *harness*, inherited across `exec`. Closing it on stream
  teardown would break the supervisor's read end for any subsequent process.
- The `error` handler sets `this.activityFd = void 0` rather than throwing, so a broken side channel
  degrades to stdout instead of taking the session down. Same fail-open instinct as the pump's
  `.catch(() => {})`.

**Where activity is written.** `teeActivity` (`:841036-841042`) is the single funnel — `activityFd` if
present, else `Js(e)` (stdout) — and `writeActivityLine` (`:841043-841045`) delegates to it. The base
structured-IO class defines `writeActivityLine(e) { Js(e); }` at `:840260-840262`, so the method is a
**polymorphic seam**: shared control-plane code at `:840107` and `:840137` (the
`update_environment_variables` control-response paths) calls `this.writeActivityLine(...)` and lands on
stdout in a local headless session and on the activity fd in a remote worker, with no branching at the
call site. The other producers are session-state transitions (`:840957`), `turn_starting`
(`:840978`), and the stdout tee inside `write()` (`:841052`).

`writeActivityLine` is **220=4 / 193=0** and `teeActivity` is **220=5 / 193=0** — the whole seam is new.
Which IO class you get is decided by `gfE` (`:850004-850014`): `new Iet(sdkUrl, …)` (RemoteIO, the class
carrying `activityFd`) when an SDK URL is present, `new JOn(…)` otherwise.

**The `oSE` scrub is the subtle third site.** `CLAUDE_RUNNER_ACTIVITY_FD` is the last entry
(`:869258`) of the session-scoped env list at `:869240-869259`, deleted wholesale by
`for (let c of oSE) delete process.env[c];` at `:869196` inside the **pre-warm spare** path. A spare
worker is started ahead of time and later *claimed* by a session; it must not inherit the previous
session's activity fd, or it would write liveness for a session it is no longer serving — a
worse-than-useless signal. Adding a new inherited fd to a process-reuse architecture forces you to add
it to the scrub list too, and `.204` did.

### c.4 Why the two halves are one fix

They solve the same problem at two levels, and the bullet's *"which could cause"* is the causal link:

| | Half (a) — the pump | Half (b) — the activity fd |
|---|---|---|
| Fixes | hook events not **streaming** | workers **idle-reaped** mid-hook |
| Audience | the SDK client reading stream-json | the harness supervising the worker process |
| Scope | `stream-json` **+ `verbose`** only | any remote worker with the env var set |
| Channel | the protocol stream | a separate FIFO/socket |
| Failure mode | swallowed write rejection | demote to stdout |

Half (a) alone would fix reaping only for verbose stream-json consumers. Half (b) alone would keep the
worker alive but leave the client blind. Together: the client sees hook progress, and the supervisor
sees a heartbeat *even when the client is not asking for one*.

**Key insight:** the deepest thing `.204` says is architectural, not tactical. In 2.1.193, "is this
worker alive?" and "is this worker producing protocol output?" were **the same question**, because both
were answered by bytes on stdout. A long-running `SessionStart` hook is the first situation where those
two questions have different answers, and the only correct fix is to give them different channels. The
same lesson is applied prophylactically fifteen releases later: `.219`'s `DirectoryAdded` hook wraps its
dispatch in `startKeepAlive` (`bs`, `:847193-847203`) from the very first commit, because a hook set
with a ten-minute budget is exactly the window in which a reaper strikes. See
[`../41_hooks/directory_added_hook.md`](../41_hooks/directory_added_hook.md) §"`startKeepAlive` around
the hook dispatch — the `.204` lesson, applied".

## d) What the changelog does not say

**1. The bullet names `SessionStart`; the fix is not `SessionStart`-specific.** `Kkm` pumps the *whole*
task-event queue, so `Setup` hooks (`:845213`, which run inside the same window) and any `task_started`
/ `task_notification` produced during initialisation stream too. The changelog names the symptom the
incident report contained; the code fixes the window.

**2. The obvious anchor is a carryover, and it is a good one to fall for.** `fKg = ["SessionStart",
"Setup"]` (`:216643`) reads like the fix and is byte-identical to `Qcf` at `:472749 (193)`. Whole-module
diffing (§c.1) is what rules it out. This is the same failure mode as
[`../00_overview/_false_delta_ledger.md`](../00_overview/_false_delta_ledger.md) register 1 — a literal
that matches the bullet's vocabulary and predates it.

**3. Undocumented in `.204`, and sitting in the same function: the queue's eviction policy changed.**
When the 1000-event cap (`cKg`, `:216566`) is hit, 2.1.193's `bv` did `if (t.length >= hKd) t.shift()`
(`:242517 (193)`) — drop the oldest, unconditionally. 2.1.220's `lA` (`:216525-216537`) instead
searches for the first event that is **not** a `task_started` or `task_notification` and evicts *that*,
falling back to `shift()` only when the queue is entirely bookends, and emits
`task_event_queue` dead-probes tagged `bookend_evicted` / `nonbookend_evicted`. The intent is to
preserve task **start** and **completion** frames — the ones a client needs to keep its task list
consistent — at the expense of progress frames. Nothing in this window's changelog mentions it, and it
is the second-order consequence of half (a): once you stream from a queue that is being filled during
initialisation, *what you drop when it overflows* becomes a product decision. Note the *direction*:
hook events are non-bookends, so under overflow the new policy sheds them **first**.

**4. The `keep_alive` frame is not this fix, and citing it would be wrong.** `keep_alive` is
**220=14 / 193=15** — it went *down*. The 30-second bridge keep-alive interval at `:840996-841003`
(gated on `session_keepalive_interval_v2_ms` and `this.isBridge`) is carryover and only runs on the
bridge path, which is not the headless remote-worker path this bullet describes. `startKeepAlive` is
**3/3**.

**5. Two module docs each believed the other owned this bullet.** `41_hooks` files it as
*"OTHER-MODULE (`../51_headless_sdk/`)"*; `51_headless_sdk` files it as *"OTHER-MODULE (`41_hooks`)"*
and adds *"Headless-side surface only"*. Both correctly identified `CLAUDE_RUNNER_ACTIVITY_FD`; neither
found the pump. **This is the one genuine `module_gaps` entry in this slice**, and the reason it opened
is structural rather than careless: the bullet's two halves sit in two modules, so each module saw the
half it owned as the *other* module's fix.
