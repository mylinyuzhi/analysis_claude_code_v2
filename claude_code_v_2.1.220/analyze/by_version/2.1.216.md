## a) Release narrative

`2.1.216` is the **largest release of the `.215`–`.220` tail** (40 bullets, ahead of `.218`'s 36,
`.219`'s 24 and `.217`'s 20) and it is overwhelmingly **BUGFIX**: **29 of the 40** bullets begin with
"Fixed", 5 with "Improved", and only one announces a setting. Its shape is the opposite of its
neighbours — `.215` shipped one policy decision, `.219` shipped a model launch. `.216` shipped a *sweep*.

**Its centre of gravity is path containment.** Read the bullets in code order rather than changelog
order and five of them turn out to be the same class of defect, each on a different surface:

| Bullet | Surface | The escape |
|---|---|---|
| 8 | worktree-isolated subagents | `git -C`, `--git-dir`, `GIT_DIR` / `GIT_WORK_TREE` redirect git out of the worktree |
| 9 | worktree session start | a *leftover* worktree from another project is entered |
| 11 | `claude daemon stop --any` | a stale **legacy lockfile** names a PID that is now someone else |
| 18 | workflow saves / scheduled tasks | a symlink planted at `.claude` redirects the write outside the project |
| 36 | `/rewind` | restore/delete follows a symlink or **hard link** at a tracked path |

All five are TOCTOU-shaped: something the harness resolved earlier is different by the time it is used.
Two of them (11, 18) are labelled as ordinary bugfixes in the changelog and are structurally security
fixes; `.216` never uses the word "security" once.

**Its second theme is the boundary between "invisible" and "meaningful" text.** Bullets 21 and 22 are
about non-ASCII and invisible Unicode reaching a permission decision — the same family as `.214`'s
bidi/zero-width work and `.207`'s deep-research chip labels. The window has been steadily working the
same seam: *a permission dialog shows the human one string and the shell executes another.*

**And its loudest bullet is its narrowest.** Bullet 1 announces `sandbox.filesystem.disabled` as an
addition. `grep -c 'filesystem.disabled'` is **220=7 / 193=6** — six of the seven sites have byte-level
193 twins, and the *enforcement* of the setting shipped before this window opened. This is a confirmed
register-1 carryover trap ([`../00_overview/_false_delta_ledger.md`](../00_overview/_false_delta_ledger.md),
§2.1.215-2.1.220 row 2) and it must not be written up as an introduction. The real delta is a **settings
resolver with a managed-settings pin** plus a **platform veto**, and it is genuinely interesting — see §c.1.

**Relative to its neighbours:** `.214` hardened the Bash/PowerShell *analyzer*; `.216` hardens the
*filesystem*; `.217` adds the subagent *governors*; `.218` moves expensive work to the background. Read
as a run, `.214`→`.218` is one containment programme delivered in four instalments, and `.216` is the
filesystem instalment.

**Honesty note up front:** 12 of the 40 bullets are TUI, roster or perf fixes with no distinguishing
literal in either bundle. I mark them `UNANCHORED` and record what was eliminated rather than attaching
a plausible-looking but unproven anchor. Two more are `CARRYOVER` — the literal the bullet implies is
new already exists in 2.1.193.

### c.1 Bullet 1 — `sandbox.filesystem.disabled`: what actually changed, in one paragraph plus the pin

**Full analysis lives in [`../49_sandbox/filesystem_disabled_and_paths.md`](../49_sandbox/filesystem_disabled_and_paths.md).**
The by-version job here is only to state the delta correctly, because the bullet is a register-1 trap.

**What it does:** lets an operator turn off the sandbox's filesystem layer while keeping network and
seccomp isolation.

**What is NOT new:** every enforcement branch. `getSandboxFsReadConfig`'s early-out (`:195430`),
`getSandboxFsWriteConfig`'s (`:195452`), the argv-builder skip (`:195572`), the Linux glob-warning
early-out (`:195845`), and the two facade overrides (`:205758`, `:205764`) all have 2.1.193 twins
(`:211676`, `:211698`, `:211782`, `:211991`, `:219869`, `:219875` — all `(193)`). **Six of the seven
`filesystem.disabled` sites are carryover.** The one new site, `:195477`, is not enforcement at all: it
is a field in the Windows ACL **change-detection snapshot**.

**What IS new — a resolver and a veto**, neither of which the grep finds:

**Why the pin is the interesting part.** Step 2 makes the setting's *authority* depend on what the
admin happened to configure elsewhere: if managed settings touch `sandbox.filesystem` at all — even
just a `denyWrite` list — or list a single `sandbox.credentials.files` entry, then no user-writable file
may turn isolation off. The schema string at `:49737` states the rationale verbatim: *"an admin who
deployed filesystem restrictions must not have them switched off by a user-writable file."* And the
exclusion is equally deliberate — `:49738`: *"(sandbox.credentials.envVars does not pin it — env
scrubbing is independent of the filesystem layer and survives this setting.)"*

**Why the Windows veto is checked *before* the settings read, not after.** Because the setting is not
merely ignored on Windows, it is never resolved. On Windows the sandbox runs as a separate low-privilege
user and access is granted by stamping ACLs, so an empty filesystem plan means **no grants at all** —
"skip the rules" would be a total lockout, not freedom. The schema says exactly that at `:49733-49734`,
and placing the veto upstream makes the sentence *"Ignored on native Windows"* literally true rather
than approximately true.

**Key insight:** the delta is a **new input edge into an existing two-state function**, plus a veto
placed upstream of it. Nothing about how `"relaxed"` is *enforced* changed at all — which is precisely
why the naive literal count under-reports the release and over-reports the feature.

**How the two-level cache is designed, and why each level is shaped that way:**

1. **Outer level is a `WeakMap` keyed by the rules *object*.** Not by a serialised rule list — by
   identity. The permission context is rebuilt whenever rules change, so a new object *is* the
   invalidation signal. No versioning, no manual bust, and no leak: when the old context is collected,
   its cache entry goes with it. A `Map` keyed by a hash would have needed both a bust path and an
   eviction policy for dead contexts.
2. **Inner level is a `Map` keyed by a NUL-joined tuple of everything else the compilation depends on** —
   tool kind, behavior, platform, `homedir()`, cwd, original cwd, repo root. `\x00` is the separator
   because it cannot appear in any of those values, so `["a\0b","c"]` and `["a","b\0c"]` cannot collide.
   The cwd terms are in the key because rule patterns are resolved *relative to* the current directory —
   a `cd` must invalidate.
3. **16 entries, LRU by insertion order.** `Map` preserves insertion order, so `keys().next().value` is
   the oldest and `delete`-then-`set` on a hit is a move-to-end. That is an LRU in three lines with no
   auxiliary structure. Why 16? One entry per (tool kind × behavior × directory) combination a session
   actually visits; a session that touches more than ~16 distinct directory contexts is thrashing
   anyway, and 16 bounds the retained matcher sets to something trivially small.
4. **A third, inner budget:** `getIg()` rebuilds the `ignore()` matcher after `E2_ = 1e4` (`:528889`)
   reuses. The `ignore` library accumulates internal state per test; rebuilding every 10,000 checks
   trades one rebuild for bounded growth. This is a *reuse* budget, not a correctness one — note it
   resets `y = 1`, not `0`, because the rebuild itself counts as the first use.

**The claim this does NOT support.** The session-level correction is exact and worth repeating:
**the caching is partial, not global.** The tool-name glob matcher `SMi` (`:60306-60313`) still compiles
a **fresh `RegExp` on every comparison**:


## d) What the changelog does not say

**1. Bullet 1's setting cannot be set from project settings, and the bullet does not mention it.**
`:49736-49737` restricts `sandbox.filesystem.disabled` to *"user, managed/policy, or CLI (`--settings`)
settings — project settings (.claude/settings.json and .claude/settings.local.json) are ignored."* A
setting that weakens sandboxing must not be reachable from a file a cloned repository can carry. The
changelog presents it as a plain new key.

**2. Turning filesystem isolation off does NOT stop the harness telling the model about the deny paths.**

`disabled` is set, so `isPathWritableUnderSandbox`, the system-prompt sandbox section, and the

The schema explains the intent (`:49735`: deployments *"whose goal is egress control rather than
filesystem containment"*), but the divergence between what the model is told and what is enforced has no
bullet at all.

deny paths into `denyRead` at `:195431` *before* the `disabled` early-out at `:195430`, so both are

unaffected because env scrubbing happens in the argv/env builder (`:205530-205531`), never through the
FS layer.

**4. Three bullets that read as ordinary bugfixes are security fixes in effect.** Bullet 11 (`claude

redirecting workflow writes outside the project) and bullet 36 (`/rewind` writing through a hard link).

repeatedly. The classification is editorial, not technical.

**5. The `.216` worktree-escape work is one guard with four named reasons, and only one of them is this

one feature and three bullets.
