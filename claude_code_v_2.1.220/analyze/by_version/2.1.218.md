## a) Release narrative

**2.1.218 is a 36-bullet sweep with two real designs hidden inside it**, and both designs are split across
several bullets, which is why the release reads as a bug list and is not one.

**Design one: one predicate now decides "does this run in the background?" for everything.** Bullet 1 moves
`/code-review` into a background subagent; bullet 34 makes `context: fork` skills background by default;
bullet 35 makes frontmatter booleans permissive. These are not three changes. A slash command's execution
context became a *function* — `getContext(args, ctx)` (`:774594`) instead of a static `context` field — a
generic resolver `RAo` (`:326547`) reads it, and one shared predicate `qTo` (`:342396`) answers *background
or blocking* with `return e.background ?? !0`. `/code-review` is simply the first command to use the new
field, and the skill frontmatter's new `background` key is the opt-out for the same default. The changelog
describes the two visible consequences and never mentions the mechanism that produced both.

**Design two: the auto-mode classifier absorbed three permission dialogs and plan mode's Bash floor.**
Bullets 26 and 30 are the same eight lines of code. `circuitBreaker` — **220=12 / 193=0** — is a named tag on
a non-approvable decision reason that says *"non-approvable by default, but the classifier may adjudicate
this one"*. Exactly three breakers exist (`dangerousRemoval` `:390684`, `backgroundOperator` `:394435`,
`suspiciousWindowsPath` `:528321`), matching bullet 26's three checks one-for-one, and the gate that consumes
them (`gnn` `:325872`) has a second disjunct for plan mode, which is bullet 30. This is the cleanest
bullet→code chain in the permissions theme in this whole window.

Underneath those two, `.218` is a **correctness release for long-running and resumed sessions**. Four
separate bullets (12, 21, 23, 24) all repair state that survives across a boundary: an interrupt marker that
was not pinned to the message it cancelled, a retry loop that could not terminate after a context overflow,
a fork lineage that could not be followed across a compaction, and a resumed transcript whose chain was
broken by a malformed delta attachment. Three of the four are provable single-anchor net-news; the doomed-retry
one is the sharpest, because 2.1.193's arithmetic (`U = Math.max(FLOOR, availableContext, thinkingBudget+1)`)
is a *provably* non-converging loop and `.218` both deletes the offending term and adds a monotonic-progress
breaker.

The remaining ~20 bullets are the sweep: five accessibility/input fixes (two of which share the same 20-line
function), an MCP over-count, a Bedrock wizard, a gateway rate table, agent-name validation, and a heartbeat
that outlived its worker. Six bullets (5's sibling cases aside: 11, 14, 16, 18, 20, 27, 32) resist anchoring;
they are marked UNANCHORED rather than pinned to a plausible neighbour, and three of them are true module
gaps.

## c) Deep-dives

Modules cover the mechanisms of bullets 1, 26, 30 and 34 well individually. What no module doc can do is
show that **1+34+35 are one design** and **26+30 are one design**, because each of those spans two module
boundaries. §c.1 and §c.2 do that. §c.3 takes bullet 12, which is only a method note anywhere else.

### c.1 Bullets 1 + 34 + 35 — a static field became a function, and "fork" started meaning "background"

**What it does:** in 2.1.193 a slash command declared *where* it runs with a constant string
(`context: "fork"`), read at exactly one dispatch site. In 2.1.220 it may instead declare a *function* of
`(args, ctx)`, a generic resolver calls it, and the fork dispatcher decides on its own whether the fork is
backgrounded. Three changelog bullets are three views of that one chain.

**How it works — the chain, top to bottom.**

**Step 1: the command may compute its own context.** `/code-review` is the first user
(`:774594-774600`):

```javascript
// ============================================
// codeReviewGetContext - the first getContext() implementation in the product
// Location: cli_inner_pretty.js:774594-774600
// ============================================

// ORIGINAL (for source lookup):
    getContext(e, t) {
      if (F_()) return "inline";
      if (acl(t)) return "inline";
      let r = icl(e);
      if (!r.ultraFallback && znm(Vnm(r, t), t)) return "inline";
      return "fork";
    },

// READABLE (for understanding):
    getContext(args, ctx) {
      if (isCoordinatorMode()) return "inline";                 // :231441 — the coordinator owns the turn
      if (isReportFindingsForceEnabled(ctx)) return "inline";    // structured findings must land in-conversation
      let parsed = parseCodeReviewArgs(args);
      if (!parsed.ultraFallback && shouldRouteToWorkflow(resolveEffort(parsed, ctx), ctx))
        return "inline";                                        // the workflow pipeline is its own runner
      return "fork";                                            // default: a (background) subagent
    },

// Mapping: F_→isCoordinatorMode, acl→isReportFindingsForceEnabled (:774313),
//          icl→parseCodeReviewArgs (:774350), Vnm→resolveEffort (:774520), znm→shouldRouteToWorkflow (:774526)
```

Three `inline` escapes, then `fork`. Each escape names a case where a background agent would *lose* something:
the coordinator's turn ownership, the `ReportFindings` structured sink, or the workflow runner's own
orchestration.

**Step 2: a generic resolver, with the static field as fallback.** `RAo` (`:326547-326549`) is
`e.getContext?.(t, r) ?? e.context ?? "inline"`. The `?.` and the two `??`s mean every command that predates
the change keeps working unchanged — this is a strictly additive schema evolution. `context ?? "inline"` is
**220=1 / 193=0**; 2.1.193 read the static field directly at its one dispatch site (`if (c.context === "fork")`,
`:398210 (193)`).

**Step 3: the fork dispatcher decides background-vs-blocking.** This is the shared predicate:

```javascript
// ============================================
// resolveForkBackgroundMode - the single decision behind bullets 1, 34 and /code-review's behaviour
// Location: cli_inner_pretty.js:342396-342399
// ============================================

// ORIGINAL (for source lookup):
function qTo(e, t) {
  if (t || LE() || yn()) return !1;
  return e.background ?? !0;
}

// READABLE (for understanding):
function resolveForkBackgroundMode(command, callerForcesForeground) {
  if (callerForcesForeground) return false;        // already inside a subagent: do not nest a bg agent
  if (isBackgroundTasksDisabled()) return false;   // CLAUDE_CODE_DISABLE_BACKGROUND_TASKS  (:230330)
  if (isNonInteractiveSession()) return false;     // -p / SDK: nothing to notify, so block instead (:3286)
  return command.background ?? true;               // DEFAULT TRUE — the .218 flip
}

// Mapping: qTo→resolveForkBackgroundMode, LE→isBackgroundTasksDisabled, yn→isNonInteractiveSession
```

**Step 4: the declaration side — the skill frontmatter `background` field** (`:157794-157798`), whose
description states the semantics precisely:

> *"Only for `context: fork`. Forks run as background agents that report back as a task notification instead
> of blocking the turn; set `false` to keep the caller waiting for the result in-line."*

**Step 5: the coercion — bullet 35.** The field is parsed through `qde` (`:158204-158211`):
`boolean` passes through; `string | number` goes through the shared `Yt`/`su` word lists
(`["1","true","yes","on"]` / `["0","false","no","off"]`); anything else returns `undefined`, which falls into
`?? true`.

**Why this approach:**

- *Why a function rather than a second static field?* Because `/code-review`'s three escapes depend on
  runtime state (`isCoordinatorMode`, a ctx flag, and a parsed argument). A static enum cannot express "fork
  unless the coordinator owns this turn", and adding three more boolean fields to the command schema would
  push the same logic into the dispatcher for every future command.
- *Why default `true` for backgrounding, when the identically-named **agent** frontmatter field defaults to
  `false`?* Because the two fields answer different questions. `agent.background` asks "should this agent
  type usually be launched detached?", which is opt-in because most agents are called to produce an answer
  the caller needs now. `skill.background` only exists for `context: fork`, i.e. a skill that *already*
  decided to leave the conversation — so the caller has already accepted an out-of-band result, and blocking
  is the exception. Note the trap: `background:` in the frontmatter block greps **220=2 / 193=1** across the
  two schemas, so a count-only reader can attribute the hit to the wrong one.
- *Why does `qde` return `undefined` rather than `false` on garbage?* Because `undefined` is what makes
  `?? true` fire. Coercing a typo to `false` would silently *disable* backgrounding, i.e. a typo would change
  behaviour; returning `undefined` makes a typo a no-op. That is the correct polarity for a permissive parser.

**Key insight:** the changelog presents `/code-review` backgrounding and `context: fork` backgrounding as
unrelated bullets in different themes. They are the *same* `return e.background ?? !0` — bullet 1 reaches it
because `getContext` now returns `"fork"`, bullet 34 reaches it because the frontmatter says `fork`, and
bullet 35 is what makes the opt-out survive a YAML `no` instead of `false`. One predicate, three bullets.

### c.2 Bullets 26 + 30 — `circuitBreaker`, and the two-predicate gate that reads it

**What it does:** three static safety heuristics used to force a modal permission dialog even in auto mode.
They now carry a named tag that lets the auto-mode classifier adjudicate them instead — and the same tag,
through a second disjunct in one predicate, does the same job for plan mode's Bash floor.

**How it works.**

The flag being modified is **carryover**: every safety-check decision reason has carried
`classifierApprovable: boolean` since 2.1.193 (220=57 / 193=29 — more sites, same concept), and
`classifierApprovable: false` means *"escalate to the human; the classifier may not wave this through"*.
That rule is sound but blunt: a heuristic with false positives turns every false positive into a mandatory
dialog.

`.218` adds `circuitBreaker: "<name>"` — **220=12 / 193=0** — meaning *"non-approvable by default, but
eligible for classifier adjudication in a classifier-adjudicating mode"*. Exactly three exist, and they are
exactly the bullet's three checks:

| breaker | line | bullet 26's wording |
|---|---|---|
| `dangerousRemoval` | `:390684` | "dangerous-rm" |
| `backgroundOperator` | `:394435` | "background-`&`" |
| `suspiciousWindowsPath` | `:528321` | "suspicious-Windows-path" |

The consumer is one line (`:513745`):

```javascript
A = sG(a.decisionReason, (V) => !V.classifierApprovable && !(V.circuitBreaker !== void 0 && gnn(c))),
```

— *find the first safety-check reason that is non-approvable **and** is not an adjudicable breaker in an
adjudicating mode*. If that search returns nothing, no dialog is opened.

And the mode predicate is where bullet 30 lives:

```javascript
// ============================================
// isClassifierAdjudicating - the mode gate; its second disjunct IS the .218 plan-mode bullet
// Location: cli_inner_pretty.js:325872-325874
// ============================================

// ORIGINAL (for source lookup):
function gnn(e) {
  return e.mode === "auto" || (e.mode === "plan" && A9() && !e.isBypassPermissionsModeAvailable);
}

// READABLE (for understanding):
function isClassifierAdjudicating(ctx) {
  return ctx.mode === "auto"                                   // bullet 26
      || (ctx.mode === "plan"                                  // bullet 30
          && isAutoModeCarouselActive()                        // A9() :325869, `return vfe.active`
          && !ctx.isBypassPermissionsModeAvailable);           // never a silent substitute for bypass mode
}

// Mapping: gnn→isClassifierAdjudicating, A9→isAutoModeCarouselActive
```

**Why this approach:**

- *Why a named tag rather than flipping `classifierApprovable` to `true`?* Because the two facts are
  different. `classifierApprovable: false` records *"the harness computed this itself and the model must not
  overrule it"* — that must stay true, or a model could argue its way past `rm -rf`. `circuitBreaker` records
  *"this specific heuristic is known to over-trigger"*. Keeping both lets the escape be **per-check and
  named**, so adding a fourth breaker is a one-word change and removing one is auditable.
- *Why is the plan-mode disjunct guarded by `!isBypassPermissionsModeAvailable`?* Without it, a session that
  *could* have used bypass mode would get classifier adjudication for free — a strictly weaker check reached
  without the user ever choosing it. The conjunct forces plan-mode adjudication to be the *fallback* path,
  not a shortcut.
- *Why two predicates?* `Qqs` (`:513122-513124`) is the same shape minus the bypass conjunct and takes a mode
  *string*; it gates entry to the whole classifier block at `:513733`. `gnn` takes the whole *context* and
  gates only the breaker escape. Permissive outer gate, strict inner gate — so a session can use the
  classifier for ordinary decisions without thereby unlocking the breaker escape.
- *And the user's own rules still win.* `pvd` (`:394411-394423`) re-attaches a user-authored `ask` rule
  before the decision reaches the gate, so an explicit `ask` in settings still produces a dialog. The
  telemetry `tengu_auto_mode_fallback_to_ask` (220=6 / 193=5 — one new arm) records which of
  `safety_check` / `ask_rule` / `plan_mode_floor` / `org_ask_ceiling` re-imposed it.

**Key insight:** bullets 26 and 30 are not two features; they are the two disjuncts of `gnn`. Anyone reading
them as separate work will look for a plan-mode change in the plan-mode code and find nothing but a
`mode === "plan"` term inside a permissions predicate.

### c.3 Bullet 12 — a fix whose proof literal went *down*, and the field that is the real answer

This bullet is the release's best methodological trap, and no module doc analyses it beyond a method note.

**The trap.** `[Request interrupted by user]` is **220=3 / 193=4**. A count-only pass concludes "fewer
occurrences, so something was removed" or "no change". Both are wrong. 2.1.193 duplicated the marker strings
inline at several construction sites; 2.1.220 hoists them into three module constants and builds the set from
those (`:162840-162842`):

```javascript
var SV = "[Request interrupted by user]",
  jI = "[Request interrupted by user for tool use]",
  MY = …
```

The count fell because of a **constant hoist**, which is a refactor, not a behaviour change. Nothing about
the spurious-marker bug can be read from that number.

**⚠ CORRECTION (orchestrator, both bundles re-read): the field is NOT new either — it is carryover.**
`interrupted_message_id` is **220=2 / 193=2**. 2.1.193 already carries both sites, with a
**byte-identical `describe` string**:

```
193:617477      ...(h && { interrupted_message_id: Ar(h) }),
193:699322      interrupted_message_id: A.string()
193:699324        .describe("@internal For [Request interrupted by user] markers only: the API msg_* id that Esc cancelled."),
```

mirrored in 2.1.220 at `:593785` and `:836616-836618`. So **both** candidate anchors for this bullet are
eliminated: the literal-count fall is a constant hoist (a refactor), and the schema field pre-exists.

**Revised verdict: UNANCHORED**, with two disproven candidates rather than a missing one. The fix is
real per the changelog but is not isolable from a 2-point diff — it most likely lives in *when* the
existing field is populated, which leaves no distinguishing literal. This row is a worked example of
`_CONVENTIONS.md` §4 trap 7: a plausible mechanism plus a matching `@internal` description is **not**
proof of novelty until the baseline is grepped.

The field, for reference (`:836616-836618`) — carryover, shown because it is what the fix operates on:

```javascript
// ============================================
// interruptedMessageIdField - pins an interrupt marker to the exact API message Esc cancelled
// Location: cli_inner_pretty.js:836617-836620
// ============================================

// ORIGINAL (for source lookup):
        interrupted_message_id: v
          .string()
          .optional()
          .describe("@internal For [Request interrupted by user] markers only: the API msg_* id that Esc cancelled."),

// READABLE (for understanding):
        interrupted_message_id: zod.string().optional()
          .describe("@internal For [Request interrupted by user] markers only: the API msg_* id that Esc cancelled."),

// Mapping: v→zod
```

**Why this fixes both halves of the bullet.** Without an id, an interrupt marker is a free-floating
transcript entry: the writer knows *that* something was cancelled but not *which* assistant message. That
produces exactly the two reported symptoms — a marker attributed to a turn that was not the cancelled one
("spurious"), and a `tool_use` block whose partner `tool_result` is never written because the abort could not
be matched back to the block that was in flight. Pinning the marker to the `msg_*` id makes both operations
*joins* instead of *guesses*: the marker attaches to one message, and the unpaired `tool_use` is
identifiable and repairable.

**Key insight:** the bullet's own words ("spurious messages", "an unpaired `tool_use` block") name two
symptoms of one missing key. The `@internal` comment is the bundle explaining its own fix — and it is the
only place in this release where that happens.

## d) What the changelog does not say

**1. Bullets 1, 34 and 35 are one predicate; bullets 26 and 30 are one predicate.** Five of the release's
thirty-six bullets reduce to two lines of code (`return e.background ?? !0` at `:342399`, and the
`circuitBreaker && gnn(c)` term at `:513745`). See §c.1 and §c.2. The changelog files them under five
different themes.

**2. `getContext` is a general slash-command capability that only one command uses.** `RAo`
(`:326547-326549`) resolves `getContext?.() ?? context ?? "inline"` for *every* command; `/code-review` is
its sole implementor in 2.1.220. This is infrastructure shipped ahead of its consumers, and no bullet
mentions it.

**3. The doomed-retry fix is two changes; the bullet describes one.** `.218` deletes the
`thinkingBudget + 1` term from the `max_tokens` recomputation *and* adds a monotonic-progress breaker
(`:534721`, **220=1 / 193=0**). The deletion fixes the reported bug (193's
`U = Math.max(jjo, D, thinkingBudget+1)` at `:603001 (193)` recomputed an identical, still-doomed value when
the budget was large). The breaker fixes a *class*: it makes the adjustment loop provably terminating
regardless of what the server returns. That matters much more after `.199` raised the retry budget to 300 —
a non-converging loop became 30× more expensive. See
[`../57_api_reliability/retry_policy.md`](../57_api_reliability/retry_policy.md) §4.

**4. The `/context` stale-usage bullet (#6) has no anchor, and two plausible ones are decoys.** The scoping
file's `originalMessages` (3/0) is a positional→named-parameter refactor of the message slicer, and the
`lineage` literal at `:846491` is a `print.ts` agent-swarm teardown log — *"Input closed with active swarm,
injected shutdown prompt — teardown handed to its lineage"* — with nothing to do with sessions. Both would be
wrong citations. The fork-lineage bullet (#23) *does* have real anchors, and they are different ones:
`:841759`, `:842259` and the self-documenting schema comment at `:837055`.

**5. `.218` #9's real fix is in a server that does not exist in the baseline.** `application-inference-profile`
is 6/6 and the ARN detector at `:111144` has a 193 twin, so nothing about ARN *support* is new. The changed
code is the gateway rate lookup `BMm` (`:862658-862663`), inside the enterprise gateway module — a component
absent from the 2.1.193 bundle entirely, which is why a client-side literal diff finds nothing.

**6. A register correction, confirmed here.** `_false_delta_ledger.md`'s `agent_team` row records
`reserved for plugin namespacing` as **220=3 / 193=1**. Grepping both bundles for that phrase returns
**two** 2.1.220 hits (`:269872`, `:269957`) and **zero** in 2.1.193. The `30_agent_team` module pass
re-measured it the same way. Bullet 33 is therefore a *cleaner* net-new than the register implies, and the
193 "hit" was most likely the unrelated marketplace-name message.

**7. Two `.218` bullets are pure carryover at the literal level and should not be re-litigated.**
`phantom` is 8/8 (#11) and `aws-us-gov` is 9/9 with `assume-role` 0/0 in both (#17). For #17 the wizard *did*
gain `invalidateAuth` hooks (6/0, `:861706`), which is the proxy-only half of the bullet; for #11 nothing
was isolable and it stays a module gap.

**8. A tree-internal numbering slip worth flagging.** The IDE-selection mojibake bullet is `.218` #10 in
`CHANGELOG.md` and in [`../00_overview/_scope_v215_220.md`](../00_overview/_scope_v215_220.md), but
[`../56_chrome_ide/README.md`](../56_chrome_ide/README.md) files it (row 20) under `.217`. The *analysis*
there is correct — including its finding that the scoping anchor `:424599` is wrong — only the release label

**9. Three bullets have no owner anywhere in the tree.** #11 (engine teardown / phantom turn), #16 (PR events
lost on immediate exit) and #32 (benign server-managed toggles skipping the approval prompt). For #32 I
