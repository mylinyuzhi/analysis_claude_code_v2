# 2.1.147 — Source Diff Analysis

**Theme:** Three real features land — **pinned background sessions** (`Ctrl+T`) that survive idle, self-update in place, and shed last under memory pressure; the `/simplify` → **`/code-review`** rename with **effort levels** and **`--comment`** inline-PR posting; and a **resilient auto-updater** (transient-failure retries + categorized error reporting). ## 1. Pinned background sessions stay alive, self-update in place, shed last (NEW)

**Type:** feature · **Modules:** Background agents (worker state machine + daemon sweep)

`Ctrl+T` in `claude agents` pins a background session. Pinning was already a UI affordance (sort-to-top), but 2.1.147 makes it a *lifecycle* guarantee with three coordinated behaviors, all driven by a persisted pin-set.

The pin-set lives in `pins.json` under the daemon job dir. `loadPinnedSessions` (`Qw$`) reads it, falling back to scanning per-job `pinned` marker files and re-persisting (`LL5` → `u$7`) when the JSON is absent (cli_inner_pretty.js:184012-184050). The daemon's idle-sweep interval loads this set every tick and threads it into both the respawn and retire decisions (cli_inner_pretty.js:647994-648017).

### Behavior 1 — pinned idle sessions restart in place to apply updates

`respawnIfIdleStale` (`SF.respawnIfIdleStale`) compares the worker's recorded `cliVersion` against the running daemon's version; if they differ AND the worker is idle, it SIGTERMs the old worker and respawns it on the new binary — without the user re-dispatching (cli_inner_pretty.js:560029-560060). It is gated so it never disrupts work in progress: returns early if transitioning, attached, or `tempo !== "idle"`.

### Behavior 2 — pinned sessions are not retired on idle

`retireIfSettled` (`SF.retireIfSettled`) now takes the pin-set as its second argument and short-circuits with `reason: "pinned"` before any idle-grace math (cli_inner_pretty.js:560062-560066). A non-pinned idle session still retires after the grace period; a pinned one does not.

### Behavior 3 — under memory pressure, pinned sessions shed last

The sweep loop first retires all *non-pinned* settled workers. Only if the low-memory predicate (`By$`) still reports pressure and *zero* sessions were shed does it retire pinned settled workers "as a last resort," emitting `tengu_bg_retire_pinned_low_mem` (cli_inner_pretty.js:648008-648016).

| | |
|---|---|
| **Type** | Feature (lifecycle policy) |
| **Modules touched** | Background worker state machine, daemon idle-sweep, pin persistence |
| **Before** | Pinning was cosmetic (sort order). Idle pinned sessions were retired by the same grace timer as everything else; after a Claude Code update the session kept running the old binary until it happened to retire; memory pressure shed sessions without regard to pin status. |
| **After** | Pinned sessions (a) survive idle indefinitely, (b) are SIGTERM-and-respawned in place onto the new binary when the daemon detects a version mismatch, and (c) are retired only after every non-pinned session under sustained memory pressure. |
| **Why** | A pinned session is the user's declaration "keep this warm." Without (a) it died silently; without (b) a pinned session would keep running a stale binary for hours after `brew upgrade`; without (c) the OS could reap your one important session before a dozen throwaway ones. |

## 2. `/simplify` renamed to `/code-review` — effort levels + `--comment` (feature)

**Type:** feature · **Modules:** Slash commands, Code review (45_code_review)

The user-invocable command is now `code-review` (`Y18 = "code-review"`, cli_inner_pretty.js:211646). It is a **bug-hunting** reviewer with a per-invocation **effort level** and two flags:

- effort levels `low|medium|high|...|max` (and `ultra` when the cloud review is available) — the syntax string is `[low|medium|high|...|ultra] [--fix] [--comment] [<target>]` (cli_inner_pretty.js:600561-600562). The level resolver `_kH` (cli_inner_pretty.js:184865) maps `high`/`medium`/etc. and an unrecognized level falls back with an "Ignoring unrecognized effort" notice (cli_inner_pretty.js:600606-600609).
- `--comment` — after producing findings, posts each one as an inline GitHub PR comment via `mcp__github_inline_comment__create_inline_comment`, falling back to `gh api .../pulls/{pr}/comments` or printing if the tool is unavailable; ignored (with a note) when the target is not a PR (cli_inner_pretty.js:600628-600636).
- `--fix` — applies the findings to the working tree (this is the 2.1.152 addition; co-resident in the bundle).

The arg parser `_O9` (cli_inner_pretty.js:600530-600556) extracts `comment`/`fix` boolean flags and the effort token; the command description `eyz` (cli_inner_pretty.js:600558-600559) reads: *"Review the current diff for correctness bugs and reuse/simplification/efficiency cleanups at the given effort level (low/medium: fewer, high-confidence findings; high→max: broader coverage…). Pass --comment to post findings as inline PR comments, or --fix to apply the findings…"*

## 3. Resilient auto-updater: transient retries + categorized errors + current-version reporting

**Type:** behavior/fix · **Modules:** Auto-updater

The updater gains three robustness behaviors:

**(a) Transient-network retries on the version check.** `WZ$` (the GCS version fetch) now wraps the HTTP GET in a retry helper with `attempts: ql7` and a per-attempt timeout, logging each retry and emitting `update_check_gcs_retry` when it took more than one attempt (cli_inner_pretty.js:607-style retry — verified at cli_inner_pretty.js:322607-322632). A genuine failure after all attempts emits `update_check_gcs_failed` and returns null rather than hard-failing the session.

**(b) Categorized error reporting.** The install-failure classifier `z3_` buckets npm/bun stderr into specific categories — `eacces_eperm`, `enotempty`, `etarget`, `e403_forbidden`, `enoent`, `registry_5xx`, `network_timeout`, `disk_full`, `warning_only`, `unknown` (cli_inner_pretty.js:322879-322896). The category is attached to `tengu_auto_updater_npm_failure` (with `npm_exit_code`, `platform`, `windows_self_rename`, `stderr_signature`, cli_inner_pretty.js:322823-322830), so a failed update no longer reports a generic error — it reports an OS-recognizable signature.

**(c) Current version shown on failure.** Every updater telemetry/log path carries the `VERSION` constant (`2.1.156`) so a failed update tells you what version you're still on (e.g. cli_inner_pretty.js:322666-322674), and the orchestrator records the last attempt's outcome via `nyH` with `version_from`/`version_to`/`status`/`error_code` (cli_inner_pretty.js:574958-574973) — which `claude doctor` surfaces.

| | |
|---|---|
| **Type** | Behavior + reliability |
| **Modules touched** | Auto-updater (version check, npm install, telemetry) |
| **Before** | A flaky network blip during the version check aborted the update; install failures produced a generic message; a failed update didn't say what you were left on. |
| **After** | Version-check fetches retry transient failures; install failures are classified into OS-level categories (EACCES/EPERM, 403, registry 5xx, timeout, ENOSPC…); the current version is reported on failure. |
| **Why** | Auto-update runs unattended (every 30 min — `h9(D, 1800000)`, cli_inner_pretty.js:575001). A single timeout shouldn't permanently skip updates; and when an update *does* fail, the user needs to know whether it's a permissions problem they can fix vs. a transient registry outage to ignore. |

```javascript
  if (/\bENOSPC\b/i.test(H)) return "disk_full";

    q = /npm err/i.test(H) || /\b(EACCES|EPERM|ETARGET)\b/i.test(H) || /code E/i.test(H);

function classifyUpdateFailure(stderr) {
  if (/\b(EACCES|EPERM|permission denied)\b/i.test(stderr)) return "eacces_eperm";
  if (/\bENOTEMPTY\b/i.test(stderr))                        return "enotempty";
  if (/\bETARGET\b/i.test(stderr))                          return "etarget";
  if (/\bE403\b/i.test(stderr) || /\b403 forbidden\b/i.test(stderr)) return "e403_forbidden";
  if (/\bENOENT\b/i.test(stderr))                           return "enoent";
  if (/\bE5\d\d\b/i.test(stderr) || /\b5\d\d\s+(internal server error|bad gateway|service unavailable|gateway time-?out)\b/i.test(stderr)) return "registry_5xx";
  if (/\b(ETIMEDOUT|ESOCKETTIMEDOUT)\b/i.test(stderr) || /\btimed[\s-]?out\b/i.test(stderr) || /\btimeout\b/i.test(stderr)) return "network_timeout";
  if (/\bENOSPC\b/i.test(stderr))                           return "disk_full";
  // npm "warn/notice" with no real error → install probably landed despite a nonzero exit
  let warningOnly = /npm warn/i.test(stderr) || /unknown user config/i.test(stderr) || /npm notice/i.test(stderr),
    realError   = /npm err/i.test(stderr) || /\b(EACCES|EPERM|ETARGET)\b/i.test(stderr) || /code E/i.test(stderr);
  if (warningOnly && !realError) return "warning_only";
  return "unknown";
}

// Mapping: z3_→classifyUpdateFailure, H→stderr, $→warningOnly, q→realError
```

**Key insight:** the `warning_only` bucket is the clever part — npm/bun frequently exit nonzero on pure deprecation *warnings*. Rather than declare the update failed, the updater re-probes the install prefix's `--version` (cli_inner_pretty.js:322781-322820) and, if the version actually advanced, reports `success`. The classifier turns "nonzero exit code" from a binary fail-signal into a nuanced one.

> Confidence **high** for (b)/(c) (classifier + telemetry verbatim); **high** for (a) (retry wrapper present at the version-fetch site). No v2.1.88 precursor for the categorized classifier.

## 4. Enterprise login enforcement now rejects third-party / API-key sessions (security fix)

**Type:** fix (security) · **Modules:** Auth, managed settings

`forceLoginOrgUUID` and `forceLoginMethod` managed-settings were previously enforced only against first-party OAuth logins. A machine pinned to an org could be bypassed by configuring a third-party provider, an API key, an auth token, or an `apiKeyHelper` — none of which the org-pin checked.

`enforceManagedLoginPolicy` (`L9H`, cli_inner_pretty.js:131921) is the validator. When the policy sets either field, it computes `q = forceLoginOrgUUID !== undefined || forceLoginMethod !== undefined`, and if the session is **not** first-party OAuth (`!Gj()`, where `isFirstPartyOAuth` is `Gj` at cli_inner_pretty.js:130831), it now returns `valid:false` with an explicit message naming the offending auth methods (cli_inner_pretty.js:131933-131945). For OAuth sessions it goes on to verify the token's org UUID is in the allow-list (cli_inner_pretty.js:131962-132005).

Crucially this is enforced at **startup**, not just at login: the boot path awaits `L9H()` behind the `before_validateForceLoginOrg` marker and aborts the session when invalid (cli_inner_pretty.js:645512-645514), and the `claude auth login` flows call it too (cli_inner_pretty.js:325099, 325158).

| | |
|---|---|
| **Type** | Fix (enterprise security) |
| **Modules touched** | Auth validation, managed-settings policy, startup |
| **Before** | `forceLoginOrgUUID`/`forceLoginMethod` were enforced only for first-party OAuth. A user could sidestep org pinning with a third-party provider (Bedrock/Vertex/gateway), `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, or `apiKeyHelper`. |
| **After** | If the policy requires a first-party login and any non-OAuth method is active, the session is refused at startup with: *"This machine's managed settings require a first-party login, but a non-OAuth authentication method is active… Remove the non-OAuth configuration and run: claude auth login."* |
| **Why** | The whole point of `forceLoginOrgUUID` is to guarantee a managed machine only talks to a permitted org's first-party endpoint. The pre-fix gap meant the strongest enterprise control was trivially bypassable — a real compliance hole. |

## Summary

2.1.147 is a substantive release sandwiched between the agent-view stabilization of 2.1.142–2.1.145 and the Opus-4.8/workflows flagship of 2.1.154. Its three headline items are genuine functionality, not polish: **pinned background sessions** finally become a lifecycle contract (survive idle, self-update in place, shed last) implemented cleanly by threading a single pin-set through the existing retire/respawn paths; the **`/simplify` → `/code-review` rename** turns a vague "cleanup" command into a recall-tunable bug reviewer that can post inline GitHub PR comments; and the **auto-updater** stops being brittle — it retries transient network failures and classifies install errors into actionable OS-level categories. The quiet but important one is the **enterprise login enforcement** fix (#4): a real security hole where `forceLoginOrgUUID`/`forceLoginMethod` could be bypassed with a third-party provider or API key is now closed at startup. The remaining ~25 bullets are a broad PowerShell/Windows, headless-mode, and rendering cleanup pass — including the regression that immediately required the 2.1.148 hotfix (Bash exit code 127).
