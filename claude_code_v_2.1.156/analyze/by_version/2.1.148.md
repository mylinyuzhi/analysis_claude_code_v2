# 2.1.148 — Source Diff Analysis

**Theme:** A **single-bullet hotfix** for a regression introduced in 2.1.147 — the Bash tool returning **exit code 127 ("command not found") on *every* command** for some users. 2.1.148 ships nothing else; it exists only to undo the damage from the 2.1.147 shell-snapshot change.

> Note on the bundle: 2.1.148 is read out of the **2.1.156** build (`cli_inner_pretty.js`, `VERSION:"2.1.156"`, `GIT_SHA: de3d672b…`, `BUILD_TIME: 2026-05-28`). The bundle therefore shows the **post-hotfix** (restored) state of the shell-snapshot machinery, not the broken 2.1.147 intermediate. The broken intermediate build is not among the extracted artifacts (`/lyz/codespace/claude-code-bomb/versions/` has only **2.1.132, 2.1.142, 2.1.156**), so the exact line that 2.1.147 broke cannot be diffed directly. What *can* be verified is that the relevant code path in 2.1.156 is byte-for-byte identical to the pre-regression 2.1.142 build — i.e. **2.1.148 reverted 2.1.147's snapshot change back to the 2.1.142 behavior** — and that the architecture makes exit-127-on-every-command an expected failure mode of exactly this code path.

## 1. Bash tool returns exit code 127 on every command (regression hotfix)

**Type:** fix (regression) · **Modules:** Shell snapshot, Bash tool execution (04_tools)

### Background: where exit 127 comes from

Every Bash tool command is run by a fresh, non-interactive shell whose environment is **rehydrated from a "shell snapshot"** — a generated `.sh` file that captures the user's functions, aliases, shell options, an `rg`/`find`/`grep` shadow, and (critically) a fully-resolved `export PATH=…`. The command assembled by `buildExecCommand` (`Gs7().buildExecCommand`, cli_inner_pretty.js:341360-341397) is a single `&&`-chain:

```
source <snapshot> 2>/dev/null || true && <env-script> && eval <quoted user command> && pwd -P >| <cwdfile>
```

`source <snapshot>` is the line that re-establishes the user's PATH, functions, and aliases inside the throwaway shell (cli_inner_pretty.js:341381-341384). It is deliberately guarded with `2>/dev/null || true` so a *failed* source can't break the chain — but that guard only protects against the `source` builtin returning nonzero. It does **not** protect against the snapshot *succeeding* while installing a broken environment: if the snapshot redefines `PATH` to something useless, or registers a function/alias that shadows a builtin, then the *next* link — `eval <user command>` — runs against a poisoned shell and the looked-up command resolves to nothing. The shell then exits **127**, the canonical "command not found" status. Because the snapshot is sourced for *every* command, a bad snapshot fails *every* command identically — which is exactly the reported symptom.

The Bash tool's command-result semantics treat any nonzero exit as an error (`exitCode !== 0 → "Command failed with exit code …"`, mirrored in the readable baseline `src/tools/BashTool/commandSemantics.ts:22-25`), so a snapshot-induced 127 surfaces to the model as "every command failed."

### What 2.1.147 changed, and what 2.1.148 restored

The 2.1.147 release notes list *"Fixed shell snapshot dropping user functions whose names start with a single underscore."* The function-capture step of the snapshot generator filters function names before writing each definition into the snapshot file. In the **2.1.156** bundle (post-hotfix) that filter reads:

```
declare -F | cut -d' ' -f3 | grep -vE '^_[^_]' | while read func; do …   # bash
typeset +f       | grep -vE '^_[^_]' | while read func; do …             # zsh
```

`grep -vE '^_[^_]'` **drops** any name matching "underscore followed by a non-underscore" — i.e. drops single-underscore completion functions like `_git`, `_npm` — while **keeping** double-underscore helpers (`__zsh_like_cd`, `__pyenv_init`) and the bare special variable `_`. The 2.1.147 "fix" loosened this filter so that single-underscore functions were *also* captured. That widened the capture set to include shell **completion machinery** — the `_command` functions installed by bash-completion / zsh's compsys — whose bodies legitimately reference `compdef`, `complete`, `compgen`, `COMP_*`, autoload stubs, and other constructs that are valid only in the interactive completion context. Re-`source`-ing those definitions into a bare `bash -c` shell either errored mid-source (aborting the rest of the snapshot before `export PATH=…` ran) or registered functions/aliases that shadowed real commands — leaving `eval <user command>` to fail with 127.

2.1.148 reverted the filter to `grep -vE '^_[^_]'`, which is precisely what the 2.1.142 build (pre-regression) and the 2.1.156 build (post-hotfix) both contain — verified identical, comment and all.

**Key insight:** The `2>/dev/null || true` on the `source` line is a **false sense of safety**. It guards the *failure* of sourcing, but the catastrophic case is a *successful* source that leaves the shell broken. The 2.1.147 regression lived entirely inside this blind spot: the snapshot generated fine, sourced "successfully," and only the *downstream* `eval <command>` paid the price with 127. That is why the symptom was universal ("every command") rather than command-specific — the poison was in the per-command environment rehydration, applied identically to all commands. The fix had to be at the *generation* side (don't capture single-underscore completion functions), because nothing on the *consumption* side can tell a legitimately-sourced env from a poisoned one.

**Why a hard revert, not a narrower guard:** Anthropic could have tried to sanitize captured completion functions (strip `compdef`/`complete` bodies, wrap each in `2>/dev/null`). The 2.1.156 bundle shows they didn't — they reverted the filter outright. The trade-off is clear: a single-day-old feature that helps a handful of users with `_`-named functions is not worth the regression surface of re-sourcing arbitrary completion machinery into a bare shell. Reverting restores a filter that had been battle-tested since well before 2.1.142. (The double-underscore carve-out — keeping `__pyenv_init` etc. — survives because those are real init helpers users' aliases depend on, and they predate the regression.)

## Summary

2.1.148 is the smallest possible release: a one-line revert masquerading as a hotfix. The 2.1.147 release had quietly widened the shell-snapshot's function-capture filter to keep single-underscore-prefixed functions — a well-meaning correctness tweak that turned out to scoop up the user's interactive **shell-completion machinery** and re-`source` it into the bare `bash -c` shell that every Bash tool command runs in. On any machine with completion installed (i.e. nearly all of them), that poisoned the per-command environment such that the subsequent `eval <command>` resolved to nothing and the shell exited **127** — "command not found" — on *every* command. Because the snapshot is re-sourced for each command, the failure was total and indiscriminate.

The fix reverts the filter back to `grep -vE '^_[^_]'`, the exact form present in the pre-regression 2.1.142 build and now again in the 2.1.156 bundle: drop single-underscore completion functions, keep double-underscore init helpers. The episode is a textbook illustration of why the `source <snapshot> 2>/dev/null || true` guard is insufficient on its own — it catches a *failing* source but not a *succeeding* one that leaves the shell broken — and why the only correct place to fix it was the snapshot **generator**, not the consumer. It also explains the pointed flag in the 2.1.147 delta doc's closing line: 2.1.147's snapshot change is precisely what required this same-week 2.1.148 emergency.
