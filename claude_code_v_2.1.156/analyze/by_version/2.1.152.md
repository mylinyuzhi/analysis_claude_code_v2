# v2.1.152 — Source Diff Analysis

**Theme:** **Hooks and skills become a session-mutation surface, `/code-review --fix` learns to apply its own findings, and auto mode stops asking permission to exist.** The headline cluster is a set of *extensibility* changes — three new ways for a `SessionStart` hook to reshape the live session (`reloadSkills`, `sessionTitle`), a brand-new `MessageDisplay` hook that can transform or hide assistant text *as it streams*, and skill/slash-command frontmatter that can `disallowed-tools` away from the model while active. Alongside that: `/code-review --fix` now writes its findings back into the working tree (and `/simplify` was rewired to call it), `/reload-skills` re-scans skill dirs without a restart, **auto mode no longer requires opt-in consent**, the primary→`--fallback-model` switch becomes permanent on `model_not_found`, and a long tail of display/render fixes. The Workflow tool's inline progress was simplified to a single persistent status row, and the post-response timer learned to wait for backgrounded agents *and* workflows.

> **Note on the source bundle.** This delta is read against the **2.1.156** bundle (`cli_inner_pretty.js`). Where 2.1.154 later changed a 2.1.152 behavior — most notably `/simplify` (2.1.152 made it call `/code-review --fix`; 2.1.154 made it cleanup-only) — the code you see in the bundle is the *post-2.1.154* form. Those cases are called out explicitly with confidence levels.

## 1. `MessageDisplay` hook — transform or hide assistant text as it streams (NEW)

**Type:** feature · **Modules:** Hooks, Renderer, Streaming

### TL;DR

A new `MessageDisplay` hook event fires once per *batch of newly completed lines* while an assistant message streams. The hook can return `displayContent` to **replace** the on-screen delta — but it is **display-only**: the stored transcript message and what the model itself sees are untouched. If the hook errors or times out, the original delta is shown. This is the first hook that intercepts the *render path* rather than the *data path*.

### How it works

**Step 1 — Streaming flush loop.** As an assistant message streams, the renderer accumulates raw text and flushes *whole completed lines* on a timer. Each flush is assigned a monotonically-increasing `index`, and exactly one flush per message carries `final: true`. The `MessageDisplay` hook is invoked per-flush with `{turnId, messageId, index, final, delta}` (cli_inner_pretty.js:337027-337045).

**Step 2 — Display substitution.** The flush dispatcher `streamDisplayController` (`OW9`) runs the hook for each delta; if the hook yields a `displayContent`, that string replaces the delta on screen. The substituted text is appended to the running `output` and forwarded to `onMessageDisplay`/`onStreamingDisplay` (cli_inner_pretty.js:626944-626975).

**Step 3 — Fail-open.** If the hook throws, the error is logged, an error stat is incremented, and the *original* delta is displayed — the model output is never lost behind a broken hook (cli_inner_pretty.js:626958-626963, 627108).

**Step 4 — Gate + telemetry.** Before any flush work, `begin()` checks whether a `MessageDisplay` hook is even registered (`wk("MessageDisplay", …)`); if not, it short-circuits to the plain streaming path with zero overhead (cli_inner_pretty.js:627042). On finalize it emits `tengu_message_display_hooks` with `{flushCount, errorCount, totalDurationMs, maxDurationMs}` (cli_inner_pretty.js:626983-626988).

## 2. `SessionStart` hooks gain `reloadSkills` and `sessionTitle` (NEW)

**Type:** feature · **Modules:** Hooks, Skills, Session lifecycle

### TL;DR

A `SessionStart` hook can now return two new fields in `hookSpecificOutput`:
- `reloadSkills: true` → re-scan skill **and command** directories *after* the hook completes, so skills the hook just installed are usable **in the same session** (no restart).
- `sessionTitle: "<string>"` → set the session title on startup and resume (same effect as `/rename`).

### How it works

**Step 1 — Hook output schema.** The `SessionStart` hook-specific output now declares `sessionTitle` (337117) and `reloadSkills` with the doc "Re-scan skill and command directories after SessionStart hooks complete, so skills installed by the hook are available in the same session" (cli_inner_pretty.js:337119-337124).

**Step 2 — Aggregation.** When SessionStart hook results are merged, both fields are pulled into the merged result `M`: `M.sessionTitle = H.hookSpecificOutput.sessionTitle` and `M.reloadSkills = H.hookSpecificOutput.reloadSkills` (cli_inner_pretty.js:552519-552527).

**Step 3 — Skill re-scan.** Downstream, if any hook requested `reloadSkills`, a flag `M` is raised (cli_inner_pretty.js:270669: `if (w.reloadSkills) M = !0;`) and the session re-runs the skill discovery pass, after which newly-installed skills are available without a restart. The generator path also yields `{ reloadSkills: !0 }` and `{ sessionTitle }` per hook (cli_inner_pretty.js:553933-553936).

## 4. Skills/slash commands can `disallowed-tools` in frontmatter (NEW for skills/commands)

**Type:** feature · **Modules:** Tools, Skills, Slash commands, Permissions

### TL;DR

Skill and slash-command frontmatter can now set `disallowed-tools` (canonical alias `disallowedTools`) to **remove** tools from the model while that skill/command is active. The removal is scoped: it is *"Cleared when the user sends the next message."*

### How it works

**Step 1 — Frontmatter schema.** The frontmatter zod schema adds `"disallowed-tools"` ("Tools removed from the model while this file is active. Comma-separated string or YAML list. Cleared when the user sends the next message.") plus a normalized alias `disallowedTools` (cli_inner_pretty.js:184492-184497). The agent-definition schema separately notes disallowedTools is *"Ignored if `tools` is set"* (184566).

**Step 2 — Parse + normalize.** When a command/skill file is loaded, `disallowedTools` is parsed from either spelling via `fc(...)` (cli_inner_pretty.js:414132) and stored on the command record (`disallowedTools: P.length > 0 ? P : void 0`, 414164).

**Step 3 — Activation merges into deny rules.** When the skill/command activates, its disallowed tools are merged into the live tool-permission context as a **union** of `alwaysDenyRules.command` (cli_inner_pretty.js:396621-396622):

## 6. Auto mode no longer requires opt-in consent

**Type:** behavior · **Modules:** Permissions, Auto mode

### TL;DR

The auto-mode availability gate is now unconditionally on, and the path that previously *required* explicit consent before auto mode could be used has been loosened — auto mode is reachable in the permission-mode cycle without first accepting an opt-in dialog.

### How it works

## 7. Permanent switch to `--fallback-model` on `model_not_found`

**Type:** behavior · **Modules:** Model, LLM API

### TL;DR

When the primary model fails permanently with `model_not_found` (the API reports the requested model doesn't exist or is retired) and a `--fallback-model` is configured, Claude Code now **permanently** switches the session to the fallback for the rest of the session, instead of failing every request.

### How it works

In the request retry loop, on a `model_not_found`-class error with a configured fallback that differs from the current model, it emits `tengu_api_model_not_found_fallback_triggered` and throws a typed `$PH(model, fallbackModel, "model_not_found")` that the session catches and uses to permanently re-route to the fallback (cli_inner_pretty.js:446875-446882). A new internal SDK message documents this: *"Emitted when the session is permanently switched to the configured fallback model because the primary model failed with a permanent API error (currently trigger 'model_not_found')"* (cli_inner_pretty.js:337855).

```javascript
// ============================================
// modelNotFoundFallback - Permanently switch to fallback model on model_not_found
// Location: cli_inner_pretty.js:446875-446883
// ============================================

// ORIGINAL (for source lookup):
if (Hg_(P) && q.fallbackModel && q.fallbackModel !== q.model)
  throw (
    d("tengu_api_model_not_found_fallback_triggered", { original_model: q.model, fallback_model: q.fallbackModel, provider: Mg() }),
    new $PH(q.model, q.fallbackModel, "model_not_found")
  );

// READABLE (for understanding):
if (isModelNotFound(err) && reqCfg.fallbackModel && reqCfg.fallbackModel !== reqCfg.model)
  throw (
    emit("tengu_api_model_not_found_fallback_triggered",
         { original_model: reqCfg.model, fallback_model: reqCfg.fallbackModel, provider: currentProvider() }),
    new PermanentFallbackSwitch(reqCfg.model, reqCfg.fallbackModel, "model_not_found")
  );

// Mapping: Hg_→isModelNotFound, $PH→PermanentFallbackSwitch, q→reqCfg, Mg→currentProvider, d→emit
```

| | |
|---|---|
| **Type** | Behavior change |
| **Modules touched** | Model, LLM API |
| **Before** | If the primary model was unknown/retired, *every* request failed — `--fallback-model` only kicked in on overload (5xx), not on `model_not_found`. |
| **After** | `model_not_found` permanently re-routes the session to `--fallback-model` (distinct from the existing 5xx-overload fallback, which is transient). |
| **Why** | A retired or mistyped model id is *permanent* — retrying it is pointless. Treating it like the transient overload fallback would re-attempt the dead model each turn. The new typed error makes the switch sticky for the session, so the user gets working responses instead of a wall of 4xx errors. |

**Confidence: high.** The 5xx/overload fallback path is separate (446910-446920). See `43_model_opus48/` and core LLM-API coverage.

## 8. Workflow inline progress simplified + post-response timer waits for workflows

**Type:** UX · **Modules:** Workflow tool, Renderer

### TL;DR

Two related workflow-UI changes: (a) the Workflow tool's *inline* progress was trimmed — live agent counts now show only in the persistent workflow status row below the prompt, not inline in the tool block; (b) the post-response timer now says "Waiting for N background agents/workflows to finish" when backgrounded agents *or* dynamic workflows are still running.

### How it works

The post-response "Waiting for … to finish" component composes a background-agents clause and a dynamic-workflows clause from `pendingBackgroundAgentCount` and `pendingWorkflowCount`, joined with " and" when both are nonzero (cli_inner_pretty.js:393613-393647):

```javascript
// ============================================
// pendingWorkComposer - "Waiting for N agents and M dynamic workflows to finish"
// Location: cli_inner_pretty.js:393613-393647
// ============================================

// ORIGINAL (for source lookup):
let G = O ? (q.pendingBackgroundAgentCount ?? 0) : 0,
  V = M ? (q.pendingWorkflowCount ?? 0) : 0,
  v = G > 0 || V > 0;
// ... E = G>0 && <Text> N background agent(s) </Text>
// ... h = V>0 && <Text> M dynamic workflow(s) </Text>
let S = G > 0 && V > 0 && " and";
// I = <Text dim> "Waiting for" E S h " to finish" </Text>

// READABLE (for understanding):
let pendingAgents    = backgroundAgentsEnabled ? (ctx.pendingBackgroundAgentCount ?? 0) : 0;
let pendingWorkflows = workflowsEnabled        ? (ctx.pendingWorkflowCount ?? 0)        : 0;
let agentsClause    = pendingAgents    > 0 && ` ${pendingAgents} background ${plural(pendingAgents, "agent")}`;
let workflowsClause = pendingWorkflows > 0 && ` ${pendingWorkflows} dynamic ${plural(pendingWorkflows, "workflow")}`;
let conjunction = pendingAgents > 0 && pendingWorkflows > 0 && " and";
let line = <Text dim>{"Waiting for"}{agentsClause}{conjunction}{workflowsClause}{" to finish"}</Text>;

// Mapping: G→pendingAgents, V→pendingWorkflows, S→conjunction, q→ctx
```

The Workflow tool's *completion* line (now the place agent counts live) renders `· N agents · K tokens · in TIME` from `agentCount`/`totalTokens` (cli_inner_pretty.js:378001-378017). The inline-progress simplification itself is a Workflow-tool renderer change — its persistent status-row component lives in the **42_workflow** module.

| | |
|---|---|
| **Type** | UX |
| **Modules touched** | Workflow tool, Renderer |
| **Before** | Live agent counts appeared *inline* in the streaming Workflow tool block, duplicating the persistent status row below the prompt and adding churn. The post-response timer only counted background agents. |

## Summary

v2.1.152 is the release where **extensibility surfaces grow teeth**. The marquee additions are all about giving hooks and skills more control over the *live* session: a `MessageDisplay` hook that can rewrite or hide assistant text on the render path (without ever touching the transcript or the model's context — a deliberately narrow, fail-open contract); `SessionStart` hooks that can re-scan skills and name the session; a `/reload-skills` command exposing that same re-scan to users; and `disallowed-tools` frontmatter that lets a skill take tools off the table via the existing deny-rule channel. On the workflow/quality axis, `/code-review --fix` closes the report→apply gap (and `/simplify` briefly re-acquired its "fix it" behavior by aliasing to it, before 2.1.154 split them again), and the post-response timer learns about dynamic workflows. The behavior changes — auto mode dropping its consent gate and `model_not_found` permanently re-routing to `--fallback-model` — are both "this experiment is now a first-class feature" graduations. The rest is a healthy maintenance tail of thinking-display, markdown, plugin, and MCP fixes.

Read against the 2.1.156 bundle, two 2.1.152 behaviors are already *past their 2.1.152 form* — `/simplify` (de-aliased from `--fix` in 2.1.154) and the auto-mode consent UX (softened further in 2.1.156). Both are flagged inline; the underlying mechanisms (`--fix` flag, always-on auto-mode gate) are intact and verifiable in source.
