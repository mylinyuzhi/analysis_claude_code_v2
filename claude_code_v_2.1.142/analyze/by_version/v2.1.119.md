# v2.1.119 — Source Diff Analysis

**Theme:** `/config` settings now persist to `~/.claude/settings.json`, **`prUrlTemplate`** for custom code-review URLs, **`CLAUDE_CODE_HIDE_CWD`**, `--from-pr` accepts GitLab/Bitbucket/GHE, PowerShell auto-approve, `PostToolUse` hooks gain `duration_ms`, plugin version pinning via cross-plugin constraint.

---

## 1. `/config` settings persist to `~/.claude/settings.json`

**Type:** Behavior · **Modules:** /config

### v2.1.88 baseline

`/config` settings (theme, editor mode, verbose, etc.) lived only in the current session. They didn't write to a settings file. A user setting `editorMode: "vim"` had to redo it next session.

### v2.1.119 change

`/config` now writes to `~/.claude/settings.json` and participates in the standard project/local/policy override precedence.

### Why this approach

**Persistence is the obvious expectation.** Users who change a setting via `/config` think they're configuring their CLI — not just this session. Per-session-only was the foot-gun.

**Why join the override stack:** Project settings (`./.claude/settings.json`) should still be able to override `/config` values; managed settings should still be able to enforce. The stack semantics are preserved — `/config` just writes to the user level.

**Trade-off:** A user who set something experimentally now has to *unset* it explicitly. Mitigated by `/config reset` (existing).

## 2. `prUrlTemplate` — custom code-review URL

**Type:** feature · **Modules:** Footer, PR linking

### v2.1.88 baseline

The footer PR badge always pointed at `github.com/<owner>/<repo>/pull/<n>`. Users with Phabricator, Gerrit, or other code-review systems had no way to link.

### v2.1.119 state

```javascript
// ============================================
// prUrlTemplate setting — custom URL format
// Location: cli_inner_pretty.js:50609, used at 347884
// ============================================

prUrlTemplate: y...

// Usage in footer:
z = DM()?.prUrlTemplate,
// ... interpolate ${owner}, ${repo}, ${number} (or similar)

// Mapping: DM→getCurrentSettings
```

The template supports placeholders (e.g. `https://phab.mycompany.com/D${number}`).

### Why this approach

**Heterogeneous code-review tooling.** Many teams don't use GitHub. The previous footer was actively misleading — pointed users at a URL that didn't exist.

**Why a template (not an enum):** No fixed list could cover all systems. Templates with placeholders let any URL shape work.

## 3. `CLAUDE_CODE_HIDE_CWD` env var

**Type:** Privacy · **Modules:** Startup logo

```javascript
// Location: cli_inner_pretty.js:467644
K = bH(process.env.CLAUDE_CODE_HIDE_CWD) ? "" : $ ? `${q} in ${$.replace(/^https?:\/\//, "")}` : q,

// Mapping: bH→parseBoolean
```

Setting `CLAUDE_CODE_HIDE_CWD=1` removes the working directory from the startup logo (e.g. screencasts where the cwd would expose paths).

### Why this approach

**Screencast hygiene.** Many users record their sessions. The startup logo printed the cwd verbatim — leaking absolute paths to whoever watches. The opt-out is one env var.

**Why an env var (not a setting):** Screencast contexts are often *temporary*. Env-var-per-session is the right granularity. A persistent setting would be too sticky.

## 4. `--from-pr` accepts GitLab, Bitbucket, GitHub Enterprise

**Type:** Feature · **Modules:** /resume, PR loading

### v2.1.88 baseline

`--from-pr <url>` only accepted `github.com` URLs.

### v2.1.119 change

```javascript
// Location: cli_inner_pretty.js:40121, 606183
q.includes("--from-pr") || q.some((K) => K.startsWith("--resume=") || K.startsWith("--from-pr="))
"--from-pr [value]"
```

GitLab merge requests, Bitbucket pull requests, and GitHub Enterprise PRs are now accepted.

### Why this approach

**Provider parity.** GitLab and Bitbucket users were second-class. The fix is shape-detection on the URL (host + path pattern) — no auth-specific code.

## 5. `--print` honors agent `tools:`/`disallowedTools:` frontmatter

**Type:** UX · **Modules:** Headless, Agents

### v2.1.88 baseline

In headless `claude -p` / `--print` mode, the agent definition's tool restrictions weren't being applied. The agent ran with the full toolset.

### v2.1.119 change

`--print` now honors the agent frontmatter's tool restrictions, matching interactive-mode behavior.

### Why this approach

**Agent semantics are not interactive-only.** The frontmatter's tool restrictions are part of the agent's safety contract. Skipping them in `--print` mode broke the principle of least surprise — and was a real security gap (a headless run of a code-review agent could be told to write files, contra its definition).

## 7. PowerShell auto-approve matching Bash behavior

**Type:** UX · **Modules:** PowerShell, Permissions

```javascript
// Location: cli_inner_pretty.js:422162
isDangerousPowerShellPermission: () => $q4,
findOverlyBroadPowerShellPermissions: () => _q4,
```

PowerShell tool commands can now be auto-approved in permission mode, matching Bash's classifier. The dangerous-permission and overly-broad detectors are parallel to the Bash ones.

### Why this approach

**Windows parity.** PowerShell users on Windows were getting more permission prompts than Bash users on Linux for equivalent commands. The auto-approve treats read-only PowerShell commands the same way.

## 8. `PostToolUse` / `PostToolUseFailure` hooks gain `duration_ms`

**Type:** feature · **Modules:** Hooks

```javascript
// ============================================
// Hook duration_ms attribute
// Location: cli_inner_pretty.js:388085-388130, 521369, 522142
// ============================================

c_H()?.observe("pre_tool_hook_duration_ms", Date.now() - E);
// ...
c_H()?.observe("hook_duration_ms", c)
c_H()?.observe("hook_duration_ms", F)
```

`duration_ms` (tool execution time, *excluding* permission prompts and PreToolUse hook time) is now in `PostToolUse` and `PostToolUseFailure` hook input.

### Why this approach

**Tool-runtime observability.** Hooks doing slow-tool detection / cost accounting / SLA enforcement need the actual tool runtime — not the wall-clock from request-to-result (which includes prompt time). The exclusion is the precision that makes the metric useful.

**Why two separate hook observations:** `pre_tool_hook_duration_ms` (the pre-tool hook itself) and `hook_duration_ms` (the post-tool hook itself) are different metrics. Both are observable.

## 10. Plugin pinning by cross-plugin version constraint

**Type:** feature · **Modules:** Plugins

Plugins constrained by another plugin's version range now auto-update to the *highest* satisfying git tag — not stay at the originally-pinned version.

### Why this approach

**Composability.** Plugin authors often pin to a range (e.g. `^1.2.3`). Auto-updating *within* the range lets dependent users get bug fixes; the constraint still prevents major-version drift.

## 11. Vim Esc not pulling queued message back

**Type:** UX · **Modules:** Vim mode

### v2.1.88 baseline

Vim mode INSERT: pressing Esc was bringing a queued message back into the input box (vim-like "restore the buffer to its earlier state"). But it conflicted with the in-flight interrupt semantics.

### v2.1.119 change

Esc in INSERT no longer pulls the queued message back. Pressing Esc again interrupts the running turn.

### Why this approach

**Two presses, two behaviors.** First Esc switches mode (vim semantic). Second Esc interrupts (Claude semantic). This composes naturally and removes the surprising "my queue restored."

## 16. OTEL `tool_result` / `tool_decision` carry `tool_use_id`

**Type:** observability · **Modules:** OTEL

```javascript
// Location: cli_inner_pretty.js:6472-6481, 10947-10954
{ type: "tool_result", tool_use_id: A.id, content: f }
tool_use_id: z,
j = { type: "tool_call", tool_use_id: z, ... }
```

`tool_result` and `tool_decision` events now include `tool_use_id` (the canonical correlation handle). `tool_result` also includes `tool_input_size_bytes`.

### Why this approach

**Correlation across spans.** Without `tool_use_id`, you can't join `tool_call` → `tool_result` in OTEL data. The fix makes the correlation possible.

**`tool_input_size_bytes`:** Lets enterprises monitor for input bloat (large tool inputs are a token-cost signal).

## Summary

v2.1.119 is the **"persist what users assume is persisted"** release:

- **`/config` writes through to `settings.json`** — closes the most common "wait, my settings vanished" surprise.
- **`prUrlTemplate`** — the footer was actively misleading for non-GitHub teams; now configurable.
- **`CLAUDE_CODE_HIDE_CWD`** — small privacy knob for screencast contexts.
- **`--from-pr` multi-provider** — provider parity catches up.
- **`PostToolUse` `duration_ms`** — finally lets hooks observe the tool's runtime separately from prompt/decision time.

The fix tail (50 items in CHANGELOG) is unusually long but follows the v2.1.118 OAuth fix pattern: **dozens of small bugs that individually wouldn't ship a release, but together earn one.** The persistence change (§1) is the headline; the rest is the cleanup that lets persistence not have hidden gaps.
