**Theme:** Single-fix patch release. Restores OAuth login when the experimental-betas gate is turned off.

## 1. OAuth 401 retry loop when `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1`

**Type:** fix · **Modules:** Auth, LLM API headers

### Symptom

Setting `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` (introduced to strip non-GA beta headers/fields from API requests) was causing every OAuth-authenticated request to come back as **401**, which kicked off the retry loop that ends in re-login. The CLI appeared "logged out" even though credentials on disk were fine.

### Root cause

The betas-gate logic deliberately strips beta strings from the `anthropic-beta` header so that gateways and stricter deployments don't reject the request. But the stripping was applied uniformly — including for **OAuth-specific beta strings** such as `oauth-2025-04-20` that are *not* experimental at all; they are how the server identifies the request as OAuth-authenticated rather than API-key-authenticated.

Stripping that string makes the server treat the request as an unrecognized OAuth flow and reject with 401. The retry path then tries the access token, gets another 401, refreshes, retries again — endless loop.

### Fix

When `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1`, only **truly experimental** beta names are filtered out. The OAuth identification betas (and a small allowlist of stable betas like `prompt-caching`, `interleaved-thinking`, `fine-grained-tool-streaming` when enabled) are preserved.

Concretely:

```javascript
// ============================================
// allowedBetasOnGate - allowlist of non-experimental betas
// Location: cli_inner_pretty.js:128855-128858, 128925
// ============================================

// ORIGINAL (for source lookup):
function aMK(H) {
  if (c$6()) return H;
  return H.filter(($) => oMK.has($));
}
// ...
oMK = new Set([KWH, PxH, EU, _WH, wa, T4$, WxH, V4$]);

// READABLE (for understanding):
function filterBetasFor3p(allBetas) {
  if (isFirstPartyOrAwsOrFoundry()) return allBetas;       // 1P passes everything
  return allBetas.filter((beta) => STABLE_BETAS.has(beta)); // 3P keeps only stable
}

const STABLE_BETAS = new Set([
  /* prompt-caching */ "prompt-caching-2024-07-31",
  /* interleaved thinking */ "interleaved-thinking-2025-05-14",
  /* tool-output-format */ "extended-output-format-2025-05-14",
  /* api-context-management */ "context-management-2025-04-22",
  /* tool-format */ "tool-format-2025-04-22",
  /* vertex tool format */ "vertex-tool-format-2025-04-22",
  /* effort header */ "effort-2025-05-14",
  /* fine-grained streaming */ "fine-grained-tool-streaming-2024-12-20",
]);

// Mapping: aMK→filterBetasFor3p, c$6→isFirstPartyOrAwsOrFoundry, oMK→STABLE_BETAS
```

The OAuth beta string sits in the always-passed `anthropic-beta` header path; the *user-controlled* `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` gate now strips only the model-experimental ones (e.g. `task-budget-2025-09-30`, mid-conversation system), not the auth-identifying ones.

### Why this approach

- **Symptom vs cause:** The user-visible symptom was "I can't log in." The cause was "betas were over-stripped." Fixing only the symptom (retry less aggressively, show better error) would have masked the issue and still left OAuth broken.
- **Allowlist over blocklist:** Adding the OAuth beta to a "never strip" allowlist is more conservative than scanning every header for an OAuth marker. Future OAuth beta versions just need a one-line allowlist update.
- **Why the env var exists at all:** Some enterprise gateways reject requests with any unrecognized beta — `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` is the escape hatch for those deployments. The bug made the escape hatch unusable for OAuth users.

## Summary

v2.1.123 ships exactly one fix: restore OAuth login when `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` is set. The deeper lesson: **kill-switches need allowlists**. A flag that strips "all betas" must be defined narrowly enough to leave authentication intact.
