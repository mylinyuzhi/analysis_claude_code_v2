# v2.1.139 — Source Diff Analysis

**Theme:** **Agent view** (`claude agents`) + **`/goal`** (Stop-hook driven loop-until-condition) as headline features, plus `/scroll-speed`, `claude plugin details`, transcript-view nav, hook `args[]` exec form, hook `continueOnBlock`, plugin `${CLAUDE_PROJECT_DIR}`, agent-id headers in API requests, plus a long list of UX/renderer fixes.

This release introduces the **persistent multi-session "all your Claude sessions" surface** (agent view) that v2.1.140+ keeps polishing.

## 1. Agent view — `claude agents` (NEW, Research Preview)

**Type:** feature · **Modules:** Agent view, Daemon

### v2.1.139 state

```javascript
// CLI route detection (cli_inner_pretty.js:509152)
if (H[0] === "agents") return "claude agents";

// Detached message (cli_inner_pretty.js:431077)
return `Detached — ${H} ${S8(H, "task")} still running. Run \`claude agents\` to see your background sessions.`;

// Daemon installation pitch (cli_inner_pretty.js:509194)
"Installing it as a service keeps the background daemon running across reboot so 'claude agents' stays available."
```

### Why this approach

**What it does:** A single list (dashboard) of every Claude Code session — *running*, *blocked on you*, or *done*. You can:
- Dispatch a new session from inside agent view.
- Attach to a running one.
- See completed sessions and their results.

**Why this is a big deal:** Pre-2.1.139, multi-session workflows meant running `claude` in separate terminals and remembering which was which. Background-mode (`--bg`) sessions had a similar issue — fire-and-forget but no UX for "where did that go?" Agent view unifies this. It surfaces what was previously implicit.

**Why "Research Preview":** The feature is new and the daemon/dashboard interaction model isn't yet final. The "Research Preview" tag signals to enterprise users that internals can change. See https://code.claude.com/docs/en/agent-view.

**The daemon-as-service pitch:** Agent view depends on a persistent daemon. The CLI nudges users to install it as a service so the daemon survives reboot — otherwise reboot kills background sessions.

**Disabling:** `disableAgentView` setting (cli_inner_pretty.js:50527) or `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` env var. Typically set in managed settings for environments that don't want the daemon running.

## 2. `/goal` command (NEW)

**Type:** feature · **Modules:** Slash commands, Hooks, Goal-loop

### v2.1.139 state

```javascript
// ============================================
// goalCommandSessionStopHook - block stop until condition met
// Location: cli_inner_pretty.js:486759-486762
// ============================================

// ORIGINAL (for source lookup):
`A session-scoped Stop hook is now active with condition: "${H}". Briefly acknowledge the goal, then immediately start (or continue) working toward it — treat the condition itself as your directive and do not pause to ask the user what to do. The hook will block stopping until the condition holds. It auto-clears once the condition is met — do not tell the user to run \`/goal clear\` after success; that's only for clearing a goal early.`

// Error messages:
"/goal is only available in trusted workspaces. Restart, accept the trust dialog, and try again."
"/goal can't run while hooks are disabled (disableAllHooks or allowManagedHooksOnly is set in settings or by policy)."

// READABLE (for understanding):
// /goal <condition> sets a session-scoped Stop hook with:
//   - Condition fed into the agent loop on each Stop-attempt
//   - "ok=false" → loop continues
//   - "ok=true"  → hook clears, session exits naturally
```

### Why this approach

**The "Stop hook" lever:** `/goal` doesn't write its own loop control — it sets a session-scoped Stop hook. When the agent tries to Stop (end the turn), the hook is invoked. If the hook's condition isn't met (the model determines that based on context), the hook returns `decision: "block"` and the agent continues working.

**Why use the existing Stop-hook mechanism:** A separate loop-control system would duplicate `decision: "block"` semantics. By layering on Stop hooks, `/goal` slots into the existing observability (transcript, logs) and policy (`disableAllHooks`).

**The system prompt nudge:** When `/goal` is active, the model is told (in the Stop hook's reason text): "Briefly acknowledge the goal, then immediately start working toward it — *treat the condition itself as your directive*." This is critical — without the nudge, the model might pause to ask "what do you want me to do?" and waste turns on confirmation.

**Auto-clear after success:** When the condition becomes true, the Stop hook self-removes. The user doesn't have to run `/goal clear` (which is reserved for *early* termination).

**Trust gate:** `/goal` only works in trusted workspaces. The reason: it auto-loops Claude based on a user-provided condition. Untrusted workspaces could have prompt-injected goals.

**Disabled-hooks check:** `/goal` requires hooks; if `disableAllHooks` or `allowManagedHooksOnly` is set, `/goal` is unavailable (with a clear message — v2.1.140 fixes the case where this was a silent hang).

**Surfaces:** Works in interactive (`claude`), `-p` (non-interactive), and Remote Control. Shows an overlay panel with live elapsed time/turns/tokens.

## 6. Hook `args: string[]` (exec form) (NEW)

**Type:** feature · **Modules:** Hooks

### v2.1.139 state

```javascript
// Hook schema (cli_inner_pretty.js:48371)
.object({ command: y.string(), args: y.array(y.string()).optional() })

// Default empty array (cli_inner_pretty.js:48885)
args: y.array(y.string()).default([])
```

| | |
|---|---|
| **Type** | Feature (hook config) |
| **Modules touched** | Hooks |
| **Before** | Hook config supported only a single `command: "..."` string. Path placeholders like `$CLAUDE_PROJECT_DIR/some path with spaces/script.sh` needed careful quoting inside the shell. |
| **After** | `args: string[]` exec form spawns the command directly without a shell. Placeholders are passed as discrete arguments — quoting is moot. |
| **Why** | The shell form is convenient but fragile for paths with spaces. The exec form is the bulletproof option for production hooks. |

**Key insight:** This mirrors Node's `spawn(command, args, opts)` API. The shell form (`command: "..."`) is kept for simple one-liners; `args[]` adds the safer alternative.

## 7. Hook `continueOnBlock` config (NEW for PostToolUse)

**Type:** feature · **Modules:** Hooks

### v2.1.139 state

```javascript
// ============================================
// continueOnBlockSetting - feed PostToolUse rejection back to Claude
// Location: cli_inner_pretty.js:48783-48788
// ============================================

continueOnBlock: y
  .boolean()
  .optional()
  .describe(
    `Sets the continue value for the decision:"block" produced when ok is false. Default false (turn ends). Whether continue:true lets the turn proceed depends on the event's decision:"block" semantics. On PostToolUse, the reason is fed back to Claude and the turn continues.`,
  )
```

| | |
|---|---|
| **Type** | Feature (hook config) |
| **Modules touched** | Hooks, PostToolUse |
| **Before** | When a PostToolUse hook returned `ok: false`, the turn would end with `decision: "block"`. No way to feed the rejection reason back to Claude. |
| **After** | `continueOnBlock: true` on a PostToolUse hook makes the rejection feed back as additional context — Claude sees "the hook rejected your tool call because [reason]" and continues the turn. |
| **Why** | Common pattern: a lint hook says "you wrote a file with bad indentation." Pre-2.1.139, the turn ended. Now Claude can read the rejection and try again, automatically. |

## 16. `x-claude-code-agent-id` / `x-claude-code-parent-agent-id` headers

## 17. Remote Control / `/schedule` / claude.ai connectors disabled when API key set

**Type:** safety · **Modules:** Remote Control, Auth

When `ANTHROPIC_API_KEY`, `apiKeyHelper`, or `ANTHROPIC_AUTH_TOKEN` is set, even with a Claude.ai login also present, these features are disabled:
- Remote Control
- `/schedule`
- claude.ai MCP connectors
- Notification preferences

**Why:** These features assume Claude.ai session-based auth. Running them with an API key creates account-confusion (which auth identity does the remote action belong to?). Unset the API key to use them.

## Summary

v2.1.139 is the version that introduces **persistent multi-session UX** (agent view) and the **loop-until-condition** pattern (`/goal`). Both build on existing primitives — agent view on `--bg` + daemon, `/goal` on Stop hooks — but the surface is new. The "Research Preview" tag signals these are not yet stable APIs.

The remaining 32 fixes are the usual mix of renderer edge cases and platform-specific issues, but two stand out:
- **Hook stdout corrupting interactive prompts** (#3) — hooks were writing directly to the controlling terminal, breaking the input line. Now hooks have no terminal access. This is the kind of "loud bug" that hits anyone running hooks.
- **MCP 16 MB SSE body cap** (#4) — an MCP server streaming non-protocol garbage would OOM the client. Hard cap added.
