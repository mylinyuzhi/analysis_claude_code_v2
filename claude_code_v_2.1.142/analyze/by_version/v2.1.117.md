## 1. Forked subagents on external builds (`CLAUDE_CODE_FORK_SUBAGENT=1`)

**Type:** feature · **Modules:** Agents, Subagent

### v2.1.88 baseline

Forked subagents (a subagent that inherits the parent's conversation context rather than starting fresh) were an internal Anthropic experiment. The feature only worked on Anthropic-internal builds (gated by a build-time flag).

### v2.1.117 state

System-prompt augmentation (when fork is enabled):

> Fork yourself (omit `subagent_type`) when the intermediate tool output isn't worth keeping in your context. The criterion is qualitative — "will I need this output again" — not task size. Fork open-ended questions. If research can be broken into independent questions, launch parallel forks in one message. A fork beats a fresh subagent for this — it inherits context and shares your cache.

### Why this approach

**Fork vs. fresh subagent:**
- Fresh subagent (`subagent_type: "..."`) → starts with system prompt + the spawning user message. No parent context.
- Fork (omit `subagent_type`) → inherits the *full* parent conversation. Cache hits on the parent's prompt tokens.

**Why expose to external builds:** Forks save tokens (cache reuse) and time (no context handoff). The feature was ready for general use; the internal-only gate was historical.

**Why omit-`subagent_type` as the trigger:** It's the natural shape. The model already chooses between `subagent_type` and "general-purpose" via parameter; "omit it to fork" is one more cognitively cheap rule.

**Trade-off:** A fork "leaks" the parent's full context to the child. For tasks that should have a clean context (privacy, scoped tooling), a fresh subagent is still the right call. The system prompt's "intermediate tool output isn't worth keeping" framing helps the model choose.

## 2. Agent frontmatter `mcpServers` for `--agent` main-thread

**Type:** feature · **Modules:** MCP, Agents

### v2.1.88 baseline

`mcpServers:` frontmatter in `.claude/agents/<name>.md` was honored when the agent ran as a subagent (Agent tool dispatch). But running it as a *main-thread* agent via `--agent` ignored the frontmatter MCP servers — only the global ones connected.

### v2.1.117 state

```javascript
// ============================================
// Agent mcpServers schema (now honored in both dispatch and main-thread)
// Location: cli_inner_pretty.js:198731, connect at 393037
// ============================================

mcpServers: y.unknown().optional().describe("MCP servers to connect when this agent runs.")

if (!H.mcpServers?.length) return { clients: $, agentClients: [], tools: [], cleanup: async () => {} };
```

The connect path now wires up `mcpServers` from frontmatter when the agent is run with `--agent`.

### Why this approach

**Symmetry.** An agent's tooling needs are part of its definition. Whether the agent is invoked as a subagent or directly via `--agent`, its declared MCP servers should connect.

**Why not just connect everything globally:** Agents are scoped; declaring `mcpServers` in frontmatter says "this agent needs these — not the world." Per-agent MCP cuts startup time, reduces tool-search noise, and lets agents declare hard dependencies that fail loudly when missing.

## 3. `/model` persistence across restarts + pinned-model startup header

**Type:** UX · **Modules:** /model

### v2.1.88 baseline

Selecting a model via `/model` persisted *only for that session*. Project-pinned model (in `~/.claude/projects/<sanitized>/settings.json`) was the override. If the user wanted to *change* the pinned model, they'd `/model` and lose it on restart.

### v2.1.117 change

`/model` selections now persist across restarts even when the project pins a different model. The startup header shows when the active model comes from project or managed-settings pin.

### Why this approach

**The annoyance:** "Why does my model keep getting reset?" had a non-obvious answer (project pin). Now the UI surfaces it, and `/model` can override even a project pin.

**Pin precedence is preserved in spirit:** A managed-settings (org policy) pin still shows in the header. The fix is about user-clarity, not policy bypass.

## 8. `blockedMarketplaces` / `strictKnownMarketplaces` enforced on all plugin paths

**Type:** security · **Modules:** Plugins, Managed settings

### v2.1.88 baseline

These managed-settings allowlist/denylists were enforced on `plugin install` but not on `plugin update`, `plugin refresh`, or background autoupdate. An org admin who blocked a marketplace could still see plugins from it auto-updating.

### v2.1.117 state

```javascript
// ============================================
// blockedMarketplaces enforcement (now at all install/update paths)
// Location: cli_inner_pretty.js:219120-219133
// ============================================

if (!H?.strictKnownMarketplaces) return null;
return H.strictKnownMarketplaces;

`Plugins from ${H}/ are blocked by your organization's managed settings (strictKnownMarketplaces or blockedMarketplaces). Ask your administrator to add {"source":"skills-dir"} to strictKnownMarketplaces, or remove it from blockedMarketplaces.`
```

### Why this approach

**Defense in depth.** Install/update/refresh/autoupdate are all paths plugins can enter the system. Gating only the user-initiated install left a backdoor through background autoupdate.

**Why a clear error message:** Without it, the user sees "couldn't install" and blames the network. The org-policy framing tells them who to ask.

## 12. Native `bfs` + `ugrep` shadow `find`/`grep` (macOS/Linux native builds)

**Type:** Performance · **Modules:** Bash tool, Glob, Grep

### v2.1.88 baseline

`Glob` and `Grep` were separate JS-implemented tools, called via the standard tool round-trip. They were correctness-faithful but slow for large repos.

### v2.1.117 state

```javascript
// ============================================
// nativeFindGrepWrappers - shadow installed find/grep
// Location: cli_inner_pretty.js:360521, 360635
// ============================================

Iv6("find", "bfs", ["-regextype", "findutils-default"]),
"ugrep",

// Snapshot file augmentation:
"# Shadow find/grep with embedded bfs/ugrep (ant-native only)\n"
"echo \"# Shadow find/grep with embedded bfs/ugrep\" >> \"$SNAPSHOT_FILE\""

// Mapping: Iv6→createCommandShadow
```

On native macOS/Linux builds, the Bash tool exposes embedded `bfs` (a faster `find`) and `ugrep` (a faster `grep`). They're shadowed *into the Bash environment* — the model can call them directly. The standalone `Glob`/`Grep` tools are kept as thin wrappers but no longer pay the tool round-trip.

### Why this approach

**Tool round-trip is expensive.** Each `Glob` call serializes inputs, validates, runs JS-side search, serializes results. Embedded native binaries skip JS work entirely.

**Why shadow rather than supplement:** The model already knows `find` and `grep`. Shadowing means the model's existing instincts work *and* are fast. No new tool to teach the model.

**Why ant-native only:** The embedded binaries ship in the native build's binary itself. JS-bundle (npm) installs don't have them; standard `Glob`/`Grep` tools serve them.

## Summary

v2.1.117 is **maturing internal experiments into general-availability features**:

- **Forked subagents** — was internal, now `CLAUDE_CODE_FORK_SUBAGENT=1` opens it to external builds.
- **Agent `mcpServers`** — was subagent-only, now fires on `--agent` main-thread too.
- **Native search binaries** — `bfs`/`ugrep` shadow `find`/`grep` for native macOS/Linux builds, big perf win.
- **Advisor Tool** — gets a stability label and a fix for its on-every-call crash.

The pattern: **previously-internal or partial-coverage features get cleaned up to "ready for users."** Adding observability (OTEL `command_name`) and retention (`cleanupPeriodDays` coverage) makes the feature surface a more disciplined system.

The model-config bumps (default effort `high` for Pro/Max on Opus 4.6+) and the Opus 4.7 1M context fix are *follow-throughs* on the v2.1.111 launch — telemetry showed where the defaults under-delivered, and they were corrected.
