# v2.1.113 — Native binary + sandbox hardening

## 1. Native binary launch via per-platform optional dependency (NEW)

**Type:** infra · **Modules:** CLI bootstrap, Packaging

### v2.1.88 baseline

The npm `claude` shim invoked the bundled JS entrypoint directly. Every invocation paid Node startup + bundle parsing cost. The bundle was the same across platforms.

### v2.1.113 change

The CLI now spawns a native per-platform binary (a thin Bun-built executable) shipped as a per-platform optional npm dependency (`@anthropic-ai/claude-code-darwin-arm64`, `-linux-x64`, etc.). The bundled JS only acts as a fallback when the native binary is not installable (e.g. uncommon arch, npm `--no-optional`).

### Why this approach

**Startup speed.** Bundled JS through Node had a ~500ms cold-start budget. The native binary starts in tens of milliseconds — felt immediately by the user on every `claude` invocation, `claude -p` headless invocation, and SDK subprocess.

**No engine deps.** Users without Node installed (or with an old Node) can still run `claude` once the native binary is in place. The npm shim selects the right platform tarball at install time.

**Why optional dependencies (not separate binaries):** npm's optional-dependency resolution is *the* standard way to ship platform-specific native modules. Other tooling (esbuild, sharp) uses the same shape; users don't need a new installer.

**Why keep the JS fallback:** Network-restricted environments, niche architectures (riscv, ppc, openbsd) where no native binary exists, and "I just need it to work in this CI" cases still need a working CLI. The JS path remains the universal back-stop.

**Trade-off:** Slight install-time surface area (the per-platform tarball is downloaded once). For everyday-use users, the per-launch savings dwarf the one-time download.

## 2. `sandbox.network.deniedDomains` setting (NEW)

**Type:** security · **Modules:** Sandbox

### v2.1.88 baseline

`sandbox.network.allowedDomains` was a whitelist. To block a single domain on an otherwise wildcard allow (`*.example.com`), you had to enumerate the *complement* — tedious and brittle.

### v2.1.142 state

```javascript
// ============================================
// sandboxNetworkDeniedDomainsCheck - blocks even allowed domains
// Location: cli_inner_pretty.js:196348, schema 196846
// ============================================

// ORIGINAL (for source lookup):
for (let _ of e9.network.deniedDomains) if (hA6(K, _)) return (e6(`Denied by config rule: ${$}:${H}`), !1);

// READABLE (for understanding):
for (const denyPattern of sandboxConfig.network.deniedDomains) {
  if (matchesDomain(requestedDomain, denyPattern)) {
    logDeny(`Denied by config rule: ${policyLabel}:${rule}`);
    return false;
  }
}

// Schema:
deniedDomains: F8.array(SA6).describe("List of denied domains")

// Mapping: e9→sandboxConfig, hA6→matchesDomain, e6→logDeny, F8→zod, SA6→domainPatternSchema
```

The deny list is checked **before** the allow list — deny wins regardless of broader allow patterns.

### Why this approach

**Whitelists alone are too coarse.** A team trusts `*.amazonaws.com` for most workloads but wants to keep IAM out of reach. Without deny, they enumerate every other AWS service — fragile.

**Why deny-first ordering:** Security policies are easier to reason about when deny is absolute. `{allow: ["*.amazonaws.com"], deny: ["iam.amazonaws.com"]}` reads as "everything AWS *except* IAM." Reversed ordering would let the allow accidentally re-enable the denied target.

**Composition with managed settings:** Org admins can layer a deny list at policy scope while leaving per-project allows untouched, the most useful policy primitive.

## 3. Multiline input: `Ctrl+A`/`Ctrl+E` line-wise + Shift+arrow extends selection past viewport

**Type:** UX · **Modules:** Input, Fullscreen renderer

### v2.1.88 baseline

`Ctrl+A`/`Ctrl+E` moved to buffer start/end. In a multiline buffer (e.g. pasted prompt with newlines), this jumped past your current line — unexpected for readline-trained users.

In fullscreen mode, extending a selection with Shift+↑/↓ past the visible edge stopped at the viewport boundary instead of scrolling.

### v2.1.113 change

`Ctrl+A`/`Ctrl+E` now move to the start/end of the **current logical line**, matching readline. Shift+↑/↓ now extends selection and **scrolls** when the new selection endpoint is past the visible edge.

Windows: `Ctrl+Backspace` now deletes the previous word (parity with macOS/Linux Alt+Backspace).

### Why this approach

**Readline-trained muscle memory is universal.** Bash, zsh, fish, irb, python repl, node repl, and many editors all bind `Ctrl+A`/`Ctrl+E` to line-start/end. Breaking this for "buffer start" was an outlier.

**Selection-scroll:** Without it, "select from current line to the bottom of a long pasted block" required a mouse — defeating the purpose of having keyboard selection. Scrolling on selection extension is the standard editor behavior (VS Code, Vim visual-mode `V`+`G`).

## 4. Bash safety: `find -exec`/`-delete` no longer auto-approved under `Bash(find:*)`

**Type:** security · **Modules:** Bash permissions

### v2.1.88 baseline

A user adding `Bash(find:*)` to their allowlist intended "let find search the filesystem without prompting." But the rule actually auto-approved *any* `find` invocation — including `find . -delete` and `find . -exec rm {} \;`, which are essentially `rm -rf` reskins.

### v2.1.142 state

```javascript
// ============================================
// findDangerousActions - operators that should re-prompt
// Location: cli_inner_pretty.js:205646
// ============================================

gz6 = new Set(["-exec", "-execdir", "-ok", "-okdir", "-delete", "-fprint", "-fprint0", "-fprintf", "-fls"])

// regex enforcing only the safe form of `find`:
/^find(?:\s+(?:\\[()]|(?!-delete\b|-exec\b|-execdir\b|-ok\b|-okdir\b|-fprint0?\b|-fls\b|-fprintf\b)[^<>()$`|{}&;\n\r\s]|\s)+)?$/

// Mapping: gz6→FIND_DANGEROUS_OPERATORS
```

When a `find` command contains any of these actions, the auto-approve under `Bash(find:*)` is bypassed and a permission prompt fires.

### Why this approach

**Allowlist semantics should match user intent, not raw command surface.** Users who allowlist `find` mean "search for files" — they don't mean "let find run arbitrary commands on every matched file." `-exec` is *not* find; it's a generic command runner shaped like find.

**Why action-set deny, not regex around commands:** The same shell escape works in many places (`xargs` can do similar things). Per-command deny lists per the canonical action are easier to maintain than ad-hoc regex sprawl.

**Trade-off:** Power users who *did* want auto-approve for `find -delete` (e.g. cleanup scripts) need an explicit `Bash(find * -delete *)` rule. Defaulting to safer was deliberate.

## 5. Bash safety: exec-wrapper deny matching (`env`/`sudo`/`watch`/`ionice`/`setsid`)

**Type:** security · **Modules:** Bash permissions

### v2.1.88 baseline

`Bash(rm:*)` deny rules saw the literal `rm ...` but not `sudo rm ...` or `env FOO=bar rm ...`. Wrappers let an attacker (or careless model) sneak around deny rules.

### v2.1.142 state

```javascript
// ============================================
// commandWrappers - parser strips before checking deny
// Location: cli_inner_pretty.js:421182, 403959
// ============================================

// chunks at 403959: exec wrappers (recognized as not-the-real-command)
Uh6 = [...XP$, "zsh", "fish", "eval", "exec", "env", "xargs", "sudo"]

// chunks at 421182: timing/IO wrappers
["ionice", "setsid"]

// chunks at 421271: allowed flags per wrapper (so parser can advance past them)
ionice: new Set(["-c", "-n", "-p", "-P", "-u", "--class", "--classdata", "--pid", "--pgid", "--uid"]),
setsid: new Set([]),

// Mapping: Uh6→EXEC_WRAPPERS, XP$→SHELL_WRAPPERS
```

The Bash classifier now strips known wrappers + their flags before checking the inner command against deny rules.

### Why this approach

**Wrappers are not the program.** `sudo rm -rf /` is fundamentally `rm -rf /` — a deny rule that fails to recognize this is broken.

**Why an explicit wrapper list (not heuristic):** Heuristics would conflate "wrapper with no side effect" (`env FOO=bar cmd`) with "wrapper with major side effects" (`xargs cmd-template`). The list approach is exact and auditable.

**Why include `xargs`:** `xargs rm` produces an `rm` invocation just as surely as `sudo rm`. Even with arguments, the *targeted* command is `rm`. A user's deny rule on `rm` should catch this form.

**Why not include `nohup` / `time`:** Those are pure passthroughs without re-exec semantics. Conservative wrapper list keeps false positives low.

## 6. Bash safety: macOS `/private/{etc,var,tmp,home}` as dangerous removal targets

**Type:** security · **Modules:** Bash permissions

### v2.1.88 baseline

macOS represents `/etc`, `/var`, `/tmp`, `/home` as symlinks to `/private/etc`, etc. A deny rule on `/etc` saw `/etc/passwd` (caught) but not `/private/etc/passwd` (missed). Same OS, same file, different deny outcome.

### v2.1.113 change

`/private/{etc,var,tmp,home}` are now recognized as dangerous removal targets alongside their canonical paths. `Bash(rm:*)` allow rules no longer auto-approve `rm /private/var/...`.

### Why this approach

**Path canonicalization for deny is mandatory.** Otherwise, an attacker (or an over-confident model) can dodge deny rules just by using the underlying canonical path. macOS makes this trivial.

**Why hardcode the four paths (not `realpath`):** Resolving symlinks runtime is slow and racy (TOCTOU). Hardcoding the documented macOS canonical layout is correct and fast.

## 7. Bash sandbox safety: `dangerouslyDisableSandbox` without permission prompt — fixed

**Type:** security · **Modules:** Bash, Sandbox

### v2.1.88 baseline

When the model supplied `dangerouslyDisableSandbox: true` on a Bash call, the command ran outside the sandbox *without* a permission prompt. The flag was treated as the model's authority — but escaping a sandbox is exactly the case where the user should confirm.

### v2.1.142 state

```javascript
// ============================================
// sandboxOverrideRecheck - re-prompt when model sets dangerouslyDisableSandbox
// Location: cli_inner_pretty.js:419534-419543
// ============================================

// ORIGINAL (for source lookup):
if (
  H.dangerouslyDisableSandbox &&
  ...
  bV({ ...H, dangerouslyDisableSandbox: !1 })
) {
  return {
    decisionReason: { type: "sandboxOverride", reason: "dangerouslyDisableSandbox" },
    ...
  }
}

// READABLE (for understanding):
if (
  toolInput.dangerouslyDisableSandbox &&
  // Would this command have used the sandbox without the override?
  shouldUseSandbox({ ...toolInput, dangerouslyDisableSandbox: false })
) {
  // The model is trying to escape the sandbox — re-prompt
  return {
    decisionReason: { type: "sandboxOverride", reason: "dangerouslyDisableSandbox" },
    ...
  };
}

// Mapping: bV→shouldUseSandbox
```

The decision now: "would this command have been sandboxed in the absence of the flag? If yes, the flag is an escape attempt — prompt the user."

### Why this approach

**The flag was intended for the *user* to assert, not the model.** A model setting it on every other call defeats the sandbox.

**Why re-prompt (not deny):** Genuine cases exist (a Docker build inside a sandboxed Bash). The user, not the model, should decide.

**Why also block when policy denies it:** The flag is gated by the `allowSandboxBypass` setting (added in earlier versions) which can policy-deny it entirely. The 2.1.113 fix sits *on top of* that gate.

## 8. `cd <current-directory> && git …` no longer prompts

**Type:** UX · **Modules:** Bash permissions

### v2.1.88 baseline

A common model idiom is `cd /current/repo && git status`. The classifier saw "compound command including `cd`" and prompted, even though the `cd` was a no-op.

### v2.1.113 change

The classifier now detects a `cd` whose target is the *current* working directory and treats the compound as if only the inner command ran.

### Why this approach

**Saves thousands of prompts.** The model uses this pattern frequently to be explicit about scope; without the fix, users approved the same thing dozens of times per session.

**Why only for `cd <current-dir>` (not arbitrary `cd`):** A real `cd` changes the security context — `cd /etc && ls` has different implications than `ls /etc`. The current-dir special case is provably safe because the working directory is identical.

## Summary

v2.1.113 is a **packaging + safety release**:

- **Packaging:** Native binary via optional dependency for snappy startup, JS fallback retained.
- **Sandbox surface:** `deniedDomains` for fine-grained allow-then-deny network policy.
- **Bash permission classifier:** Closes three loopholes (find-exec, exec wrappers, macOS `/private`) and fixes the `dangerouslyDisableSandbox` flag that previously bypassed prompts.
- **Multiline input:** Readline parity for `Ctrl+A`/`Ctrl+E`, scrolling on Shift+arrow selection.

The pattern: previously-flexible permission rules become tighter on the dangerous edges *without* widening the prompt burden on the common case (`cd` no-op).

v2.1.114 is a one-fix patch for an agent-teams-introduced crash.
