## 2. `settings.autoMode.hard_deny` (NEW)

**Type:** feature · **Modules:** Auto mode

### v2.1.136 state

```javascript
// ============================================
// autoModeHardDeny - unconditional block rules for auto mode
// Location: cli_inner_pretty.js:49979-50010, consumer at :52590, :337724
// ============================================

// ORIGINAL (for source lookup):

    })
}

// Consumer logic (cli_inner_pretty.js:52590):

// Default hard-deny rule injection (cli_inner_pretty.js:337644 — system prompt):
// `<user_hard_deny_rules_to_replace>- Data Exfiltration: ...
//                                    - Safety-Check Bypass: ...
// </user_hard_deny_rules_to_replace>`

// READABLE (for understanding):
const autoModeHardDeny = z.array(z.string()).optional();
// Added rules are concatenated unconditionally — no allow exceptions, no user-intent override.
```

| | |
|---|---|
| **Type** | Feature (settings policy) |
| **Modules touched** | Auto mode, System prompt |
| **Before** | Auto mode rules could be overridden by `allow:` exceptions and user intent. Admins couldn't pin a rule that *always* denies. |
| **After** | `autoMode.hard_deny: [...]` adds rules that fire regardless of allowlists. Two built-in hard-deny templates: data exfiltration, safety-check bypass. |
| **Why** | Enterprise compliance needs an "always block" tier. Examples: external data uploads, bypass-via-aliases. The hard-deny rules go into the system prompt at a structural level (`<user_hard_deny_rules_to_replace>` block), so the classifier sees them as non-negotiable. |

**Key insight:** The default body for `<user_hard_deny_rules_to_replace>` is two paragraphs that *teach the model what kinds of patterns to block*, not just enumerate denied tools. The "Safety-Check Bypass" entry is particularly clever — it tells the model "if the agent's stated reason is routing around a safety mechanism, that intent itself is the violation, regardless of the actual command." This catches the prompt-engineering "I'm just running this for testing" tunneling.

### Why this matters

This release is *almost* entirely fixes. Two observations:

- **The MCP OAuth refresh-tokens-concurrent issue** (#3) is the most-impactful for active users — daily re-auth had been a chronic pain. The fix is a per-server lock around the refresh-token write.
- **`/clear` silently dropping MCP servers** (#1) was a regression from MCP being scoped to "session" state. Cross-restart MCP config (from `.mcp.json`/plugins) needs to survive `/clear`. Fix: re-initialize MCP from config sources after `/clear`, not just from session state.
- **Plan mode not blocking file writes when `Edit(...)` allow rule exists** (#6) was the most security-relevant — the allow rule shortcut bypassed plan mode's read-only constraint. Plan mode is supposed to be a hard mode lock.
