**Theme:** **Performance and resilience pass** — `/resume` 67% faster on 40MB+ sessions, MCP startup faster via deferred `resources/templates/list`, smoother fullscreen scrolling in VS Code/Cursor terminals, **inline thinking spinner** progress, plus a long quality-of-life list (Devanagari rendering, Ctrl-Z hang, scrollback duplication).

v2.1.115 was skipped (internal-only or never shipped).

## 1. `/resume` performance pass (up to 67% faster on 40MB+ sessions)

**Type:** Performance · **Modules:** /resume, Session loader

### v2.1.88 baseline

Loading a session file was line-by-line JSON parse with a synchronous scan for dead forks (rewind targets that never followed up). For 40MB+ sessions, this took 8-12 seconds — visibly slow even with a progress indicator.

### v2.1.116 change

Three changes combined for the speedup:
- Pre-pass identifying dead-fork ranges so the second pass can skip them.
- Streaming parse over the JSONL with bounded memory.
- Cached enrichment metadata reused across loader calls.

```javascript
// Location: cli_inner_pretty.js:517504 (enrichment log)
N(`/resume: enriched ${z} sessions, ${Y} filtered out, ${K.length} visible (${H.length - A} remaining on disk)`);
```

### Why this approach

**The shape:** 40MB+ sessions exist when a user does long autonomous runs (`/loop`, agent teams). They were the worst-affected by slow `/resume`, yet most of the data was *not* visible content (it was tool-call detail). Skipping known-dead ranges is most of the saving.

**Why a pre-pass rather than streaming with backreferences:** Dead-fork detection is a forward graph traversal; you need to see all fork-points before knowing which to skip. A pre-pass is the simplest correct algorithm. The pre-pass itself is fast because it only reads message IDs/parent IDs (skipping content payloads).

**Trade-off:** Memory used briefly during the pre-pass for the ID graph. Bounded by message count, not message size, so safe even for huge sessions.

## 2. Faster MCP startup: defer `resources/templates/list`

**Type:** Performance · **Modules:** MCP

### v2.1.88 baseline

On session start, every MCP server got `tools/list`, `resources/list`, and `resources/templates/list` requests in parallel. `resources/templates/list` was paid for even though templates are only used at `@`-mention time.

### v2.1.116 change

`resources/templates/list` is now deferred to first `@`-mention. The other lists still happen at startup.

### Why this approach

**Why defer this list specifically:** Templates are only consumed when the user types `@` in the prompt. A session that never `@`-mentions a resource never needs templates. The deferred call is amortized for users who *do* `@`-mention.

**Trade-off:** First `@`-mention has a small (~50ms) delay while the lists fetch. Mitigated by parallel fetch when multiple servers are configured.

## 3. Smoother fullscreen scrolling in VS Code, Cursor, Windsurf

**Type:** UX · **Modules:** /terminal-setup, Scroll

### v2.1.88 baseline

In VS Code's integrated terminal, scrolling in fullscreen Claude Code was jumpy because the terminal sent oversized scroll events (whole-page deltas). Cursor and Windsurf inherited the same.

### v2.1.116 change

```javascript
// Location: cli_inner_pretty.js:174506
`Set ${H} terminal scroll sensitivity to ${jz$}`
```

`/terminal-setup` now configures the editor's `terminal.integrated.mouseWheelScrollSensitivity` (or equivalent) to a value that produces smooth per-line scroll.

### Why this approach

**Why configure the editor (not adjust internally):** The terminal's scroll deltas are reported to the application *as configured by the user*. Claude Code can't second-guess; the only knob is the editor setting. `/terminal-setup` is the existing one-shot config command, so the new fix slots in naturally.

## 4. Inline thinking spinner progress

**Type:** UX · **Modules:** Spinner, Thinking

### v2.1.88 baseline

A separate hint row appeared during long thinking ("Thinking…"). The hint row stole vertical space and the user had no sense of progress.

### v2.1.116 state

```javascript
// ============================================
// thinkingSpinnerLabel - duration-based label
// Location: cli_inner_pretty.js:328461-328466
// ============================================

// ORIGINAL (for source lookup):
function oB_(H) {
  if (H >= rB_) return "almost done thinking";
  if (H >= iB_) return "thinking some more";
  if (H >= nB_) return "thinking more";
  if (H >= lB_) return "still thinking";
  return "thinking";
}

// READABLE (for understanding):
function thinkingSpinnerLabel(elapsedMs) {
  if (elapsedMs >= THINKING_ALMOST_DONE_MS) return "almost done thinking";
  if (elapsedMs >= THINKING_SOME_MORE_MS)   return "thinking some more";
  if (elapsedMs >= THINKING_MORE_MS)        return "thinking more";
  if (elapsedMs >= THINKING_STILL_MS)       return "still thinking";
  return "thinking";
}

// Mapping: oB_→thinkingSpinnerLabel, rB_→ALMOST_DONE_MS, iB_→SOME_MORE_MS,
//          nB_→MORE_MS, lB_→STILL_MS
```

The progress is also shown inline (replacing the separate hint row) so users get the duration feedback without taking up extra vertical space.

### Why this approach

**The unknown-duration problem:** Thinking blocks have no upfront completion estimate (unlike a tool with a known runtime). The only signal that's available is elapsed time. Mapping elapsed time to varying labels gives users a sense of "this is taking long" without overpromising progress.

**Why the time-stepped labels (not %-progress):** A % requires a known total. With thinking, there's no total. Labels like "still thinking" → "almost done" are honest about uncertainty.

**Why inline (not separate row):** Vertical real estate in the TUI is at a premium. Moving the progress *onto* the spinner line halves the footprint.

## 5. `/config` value search

**Type:** UX · **Modules:** /config

The `/config` search box now matches setting *values* in addition to keys. Searching "vim" finds the `editorMode: "vim"` setting even though the key is `editorMode`.

The shape: users remember the value they set ("I set this to vim") more reliably than the key (`editorMode` vs `vim_mode` vs `vimMode`). Value-search bridges the gap.

The shape: when something is going wrong, the user wants `/doctor` *now*, not "after the slow thing finishes."

## 10. Agent frontmatter `hooks:` fire on `--agent` main-thread mode

**Type:** feature · **Modules:** Hooks, Agents

When an agent definition (`.claude/agents/<name>.md`) had a `hooks:` frontmatter and the agent ran as a *main-thread* agent via `--agent`, the hooks were being silently ignored (they only ran in subagent dispatch). Now main-thread mode also fires them.

### Why this approach

**Symmetry.** Agent-level hooks are part of the agent's contract; the user expects them to fire regardless of dispatch mode. Silent skip in main-thread mode was a foot-gun.

When the slash command filter had zero results, the picker disappeared entirely. Users typing `/xxx` thought they'd dismissed the picker. Now shows "No commands match" until the filter changes.

## 12. Sandbox auto-allow respects dangerous-path safety

**Type:** security · **Modules:** Sandbox

### v2.1.88 baseline

`autoAllowBashIfSandboxed` was an override on the prompt-for-permission decision. But the dangerous-path check (which rejects `rm /`, `rm $HOME`, etc.) was being *bypassed* by the auto-allow, which would itself approve the request.

### v2.1.116 change

The dangerous-path check now fires *before* `autoAllowBashIfSandboxed` is consulted. The auto-allow can't approve removal of critical system directories — sandboxed or not.

```javascript
// Location: cli_inner_pretty.js:420630
decisionReason: { type: "other", reason: "Auto-allowed with sandbox (autoAllowBashIfSandboxed enabled)" }
```

### Why this approach

**Auto-allow should never make things less safe.** Without this fix, enabling auto-allow effectively defeated the deny-critical-dirs check. The intended semantics: auto-allow saves prompts on safe sandboxed commands; it doesn't reduce the safety floor.

## 13. Migration: `downloads.claude.ai/claude-code-releases`

**Type:** infra · **Modules:** Updates, Plugins

### v2.1.88 baseline

The release artifact bucket was on Google Cloud Storage at `storage.googleapis.com/claude-code-dist-86c565f3-f756-42ad-8dfa-d59b1c096819/`. Long URL, GCS-tied, opaque bucket name. Same for plugin mirrors.

### v2.1.116 state

```javascript
// Location: cli_inner_pretty.js:313405, 314051, 399575, 399601
Ab_ = "https://downloads.claude.ai/claude-code-releases";

// chunks at 219018 / 453885: GCS host still present as a fallback / legacy reference
"storage.googleapis.com" (allowlist fallback)
"https://storage.googleapis.com/claude-code-dist-.../plugin-stats/plugin-details.json" (legacy stats endpoint)
```

Updates and the installer now use `https://downloads.claude.ai/claude-code-releases`. The legacy GCS URL is still referenced in fallback paths (stats endpoint, allowlist) for back-compat.

### Why this approach

**Branding + ownership.** `downloads.claude.ai` is a stable Anthropic-controlled DNS surface. The GCS URL was leaking a bucket UUID and tying the team to GCS forever; the indirection lets the artifact host change.

**Why keep the GCS fallback:** Existing installations with caching/proxy rules pinned to the old host still need to work. A flag-day cutover would break enterprise users.

## 14. Devanagari / Indic script rendering

**Type:** fix · **Modules:** Renderer

Devanagari and other Indic scripts were rendering with broken column alignment because the visual cell-width calculation didn't account for combining-marks/consonant-conjunct sequences. Now correctly measured.

The shape: Hindi/Marathi/Sanskrit users couldn't read aligned content (tables, prompts). The fix uses the canonical Unicode East Asian Width tables with the Indic extensions.

## Summary

v2.1.116 is a **performance + resilience release**. The big-rock changes are `/resume` on 40MB+ sessions (67% faster), MCP startup (deferred templates list), and terminal scrolling parity in editor-embedded terminals.

The "polish" tail is unusually long for a non-launch release: Devanagari rendering, Kitty keyboard protocol input bindings, scrollback duplication on inline mode, VS Code redraw artifacts. These are the issues that surface when users push the CLI into corner-case environments — and the team's investment here signals expanding multilingual + multi-terminal scope.

The security micro-fix (auto-allow respecting dangerous-path safety) is the one with permanent semantic weight — it closes a foot-gun where enabling a convenience setting accidentally lowered the safety floor.
