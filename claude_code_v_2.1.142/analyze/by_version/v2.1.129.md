# v2.1.129 — Source Diff Analysis

**Theme:** `--plugin-url` for one-session plugins, force-sync output env, plugin manifest `experimental` namespace, **opt-in reversal of gateway model discovery**, several cache-correctness fixes, and the `user:inference` OAuth scope fallback.

## 1. `--plugin-url <url>` flag

**Type:** feature · **Modules:** Plugins, CLI flags

Fetches a plugin `.zip` archive from a URL for the current session only. Repeatable.

```javascript
// ============================================
// pluginUrlFlag - CLI option definition
// Location: cli_inner_pretty.js:606265-606266, 605930-605932
// ============================================

// ORIGINAL (for source lookup):
"--plugin-url <url>",
"Fetch a plugin .zip from a URL for this session only (repeatable: --plugin-url A --plugin-url B)",
// ...
let O = A.getOptionValue("pluginUrl");
if (O) (kv8(O), V0("preAction: --plugin-url inline plugins"));

// READABLE (for understanding):
program.option(
  "--plugin-url <url>",
  "Fetch a plugin .zip from a URL for this session only (repeatable: ...)"
);
// preAction hook:
async function loadInlinePluginsFromUrl(parsedOpts) {
  const url = parsedOpts.pluginUrl;  // commander returns array for repeatable
  if (url) {
    await fetchAndExtractPluginZips(url);
    logDebug("preAction: --plugin-url inline plugins");
  }
}

// Mapping: kv8→fetchAndExtractPluginZips, V0→logDebug
```

### Why this approach

- **Complements `--plugin-dir`:** local dir = your dev work; URL = "try this plugin a colleague linked." No clone, no install.
- **Session-only:** the install isn't persisted to `installed_plugins.json`, so a one-time experiment doesn't pollute future sessions.
- **`.zip` only:** archives are self-contained and easy to fetch/verify; preserves the manifest+code shape that the directory loader expects.
- **Why not auto-detect URL in `--plugin-dir`:** separates intent. Directory load assumes local trust; URL load is a deliberate "I'm pulling code from the internet" act with future security policy hooks.

## 2. `CLAUDE_CODE_FORCE_SYNC_OUTPUT=1`

**Type:** infra · **Modules:** Renderer, Terminal detection

```javascript
// ============================================
// forceSyncOutputCheck - bypass DEC 2026 auto-detection
// Location: cli_inner_pretty.js:150074
// ============================================

// ORIGINAL (for source lookup):
if (bH(process.env.CLAUDE_CODE_FORCE_SYNC_OUTPUT)) return !0;

// READABLE (for understanding):
if (parseEnvBoolean(process.env.CLAUDE_CODE_FORCE_SYNC_OUTPUT)) return true;

// Mapping: bH→parseEnvBoolean
```

Some terminals (Emacs `eat`, several embedded terminals) support synchronized output (DEC 2026) but don't respond to the auto-detection probe. The env var lets the user force-enable it.

Without sync output, the renderer falls back to atomic batched writes, which is more conservative but slower. The env var unlocks the fast path for those terminals.

## 3. `CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE`

**Type:** feature · **Modules:** Update mechanism

For Homebrew / WinGet installations, when this env var is set CC runs the package manager's upgrade command **in the background** and prompts the user to restart when ready.

```javascript
// ============================================
// pkgManagerAutoUpdateCheck - background upgrade kick
// Location: cli_inner_pretty.js:544021
// ============================================

// ORIGINAL (for source lookup):
let HH = bH(process.env.CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE), ...

// READABLE (for understanding):
const pkgManagerAutoUpdateOn = parseEnvBoolean(process.env.CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE);
// ... if true, spawn `brew upgrade claude` / `winget upgrade claude` in background

// Mapping: HH→pkgManagerAutoUpdateOn, bH→parseEnvBoolean
```

### Why this approach

Distro-packaged installs (brew, winget) want users to update via the package manager — not via CC's built-in npm/binary auto-update. But brew/winget upgrades are user-initiated; users forget. The env var bridges the gap: CC kicks the package manager when the user is already opted in.

## 4. Plugin manifest `experimental` namespace for `themes`/`monitors`

**Type:** schema · **Modules:** Plugins

```javascript
// ============================================
// experimentalReadFallback - reads new+old paths
// Location: cli_inner_pretty.js:229966, 230072, 230091, 230223
// ============================================

// ORIGINAL (for source lookup):
let _ = $.experimental?.monitors ?? $.monitors,
// ...
((qH = Y.experimental?.themes ?? Y.themes), (a = []),
 Y.experimental?.themes) a.push("experimental.themes");

// READABLE (for understanding):
function readPluginMonitors(manifest) {
  // New path: manifest.experimental.monitors (preferred)
  // Old path: manifest.monitors (still supported, but warns on validate)
  return manifest.experimental?.monitors ?? manifest.monitors;
}

// Mapping: $→manifest, Y→manifest (outer scope), _→monitors (local)
```

Plugin manifests should declare `themes` and `monitors` under `experimental: { ... }`. Top-level still works, but `claude plugin validate` now warns.

### Why this approach

These two features are still iterating — manifest fields might change. The `experimental:` namespace signals "this is not yet stable, opt-in," letting Anthropic evolve the schema without breaking stable plugins that don't touch these features.

The dual-read (new path falls back to old) is the **backward-compat strategy**: existing plugins keep working, new ones get the warning, eventually the old path is removed.

## 5. Gateway `/v1/models` discovery becomes opt-in

**Type:** behavior reversal · **Modules:** Model picker, Gateway

```javascript
// ============================================
// gatewayModelDiscoveryGate - opt-in env check
// Location: cli_inner_pretty.js:433813
// ============================================

// ORIGINAL (for source lookup):
if (!bH(process.env.CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY)) return !1;

// READABLE (for understanding):
if (!parseEnvBoolean(process.env.CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY)) return false;

// Mapping: bH→parseEnvBoolean
```

In v2.1.126–v2.1.128 this was automatic when `ANTHROPIC_BASE_URL` was set. Some gateways:
- Returned 404 on `/v1/models` (breaking startup with confusing errors).
- Logged the discovery probe to security telemetry as a suspicious request.
- Responded with their own catalogs that overrode the Anthropic catalog incorrectly.

Now off by default. Set `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1` to opt in.

### Why this approach

**Two-step rollout reversal**: ship the feature with discovery automatic to gather feedback, then move to opt-in based on what broke. Better than removing the feature outright (existing satisfied users keep it via env var).

## 6. Ctrl+R history picker defaults to all-projects

**Type:** UX reversal · **Modules:** History picker

Ctrl+R now defaults to "search all prompts across all projects" — restoring pre-2.1.124 behavior. Press Ctrl+S to narrow.

### Why this approach

The 2.1.124 narrow-by-default change was unpopular: users typically want to find a prompt they remember writing, regardless of which project they were in at the time. The narrow scope hid relevant matches. Wide-by-default + Ctrl+S narrow is the better UX.

## 8. `skillOverrides` setting now works

**Type:** fix · **Modules:** Skills

```javascript
// ============================================
// skillOverridesLookup - read across scopes
// Location: cli_inner_pretty.js:476886-476895, 513849
// ============================================

// ORIGINAL (for source lookup):
let q = v8("policySettings")?.skillOverrides?.[$];
// ...
return v8("projectSettings")?.skillOverrides?.[H] ?? v8("userSettings")?.skillOverrides?.[H];
// ...
return m6().skillOverrides?.[H.name] ?? "on";

// READABLE (for understanding):
function getSkillOverrideMode(skillName) {
  // Priority: policy > flag > project > user > "on"
  const policy = readSettings("policySettings")?.skillOverrides?.[skillName];
  if (policy) return policy;
  const flag = readSettings("flagSettings")?.skillOverrides?.[skillName];
  if (flag) return flag;
  return readSettings("projectSettings")?.skillOverrides?.[skillName]
      ?? readSettings("userSettings")?.skillOverrides?.[skillName]
      ?? "on";
}

// Mapping: v8→readSettings, m6→readSettings (config root), $→skillName, H→skillName, q→policy
```

Override values:
- `off` — hidden from model **and** `/<skill>`
- `user-invocable-only` — hidden from model, still works via `/`
- `name-only` — visible to model with name+description collapsed (no full body)
- `on` — default

### Why this approach

The override modes match different user intents:
- **`off`** — "I don't want this skill at all"
- **`user-invocable-only`** — "Don't let Claude pick it, but I want it available when I type `/`"
- **`name-only`** — "Don't waste tokens on the description"

Separating the cases lets users tune per-skill cost without the all-or-nothing toggle.

## 20. OAuth scope `user:inference` fallback

**Type:** fix · **Modules:** Auth, Managed settings

```javascript
// ============================================
// OAUTH_SCOPE_INFERENCE - the minimal inference-only scope
// Location: cli_inner_pretty.js:40247, 130163-130173
// ============================================

// ORIGINAL (for source lookup):
op = "user:inference",
// ...
scopes: ["user:inference"],

// READABLE (for understanding):
const OAUTH_SCOPE_USER_INFERENCE = "user:inference";
// Used in token requests; if credential lacks it, fall back.

// Mapping: op→OAUTH_SCOPE_USER_INFERENCE
```

### Bug

Enterprise/team users whose stored OAuth credentials lacked the `user:inference` scope (the minimum scope for API access) couldn't have server-managed settings applied. The settings-loader was checking for `user:inference` and bailing if absent, even though the user could clearly auth (they had a *different* scope set that also grants inference).

### Fix

The scope check now treats `user:inference` as **one** of several equivalent inference-granting scopes. Long-lived tokens, scoped service tokens, and the standard interactive token all grant inference; the loader accepts any of them.

## 21. OAuth refresh race on wake-from-sleep

**Type:** fix · **Modules:** Auth

When a laptop wakes from sleep with multiple CC sessions running, all of them might trigger a credentials refresh simultaneously. The race could end with one session writing a stale credential, logging out all the others.

Fix: file-locked credentials read-then-write, and a "refresh in progress" cache that lets concurrent reads share a single refresh result.

## 22. 1-hour cache TTL downgraded to 5 minutes

**Type:** fix · **Modules:** Prompt caching

```javascript
// Location: cli_inner_pretty.js:524776-524793
// ============================================

  // ...

// READABLE (for understanding):

  return {
    type: "ephemeral",
    ...(ttl && { ttl }),                            // "1h" if extended
    ...(scope === "global" && { scope }),
  };
}
function isOneHourCacheEnabled(sessionLabel) {
  if (parseEnvBoolean(process.env.FORCE_PROMPT_CACHING_5M)) return false;
  if (
    parseEnvBoolean(process.env.ENABLE_PROMPT_CACHING_1H) ||
    (getProvider() === "bedrock" && parseEnvBoolean(process.env.ENABLE_PROMPT_CACHING_1H_BEDROCK))
  ) return true;
  // ...allowlist match against session label

// Mapping: Xi→buildCacheControl, ivH→isOneHourCacheEnabled, H→scope/sessionLabel, $→ttl,
//          bH→parseEnvBoolean, vq→getProvider
```

### Bug

A `cache_control` block with `ttl: "1h"` was being silently rewritten to 5-minute. The TTL field was being filtered out by an older "strip unknown fields" pass before the request was sent. Fixed by retaining `ttl` when the 1h beta is active.

### Why this approach

1h cache saves serious tokens for long-running agentic loops where the system prompt + early-conversation prefix don't change for hours. The silent downgrade meant users thought they'd opted in but got 5m anyway — paying the create cost every five minutes.

## Summary

v2.1.129 retreats from one decision (gateway model discovery becomes opt-in), promotes one direction (`experimental:` namespace for plugin manifests, signaling unstable APIs), and fixes a cluster of cache and credential issues. The pattern: **rapid iteration in 2.1.126–128 needed a cleanup release** — and 2.1.129 is that release for the auth/cache/plugin surfaces.
