## 1. `worktree.baseRef` setting (NEW)

**Type:** feature · **Modules:** Worktrees, Settings

### v2.1.88 / v2.1.128 baseline

`claude-code-kim/src/tools/EnterWorktreeTool/EnterWorktreeTool.ts` always branched off `origin/<default-branch>` (a "fresh" base). v2.1.128 changed `EnterWorktree` to instead branch off local `HEAD` so the tool's worktrees would inherit any unpushed work. That broke the v2.1.88-era invariant — `--worktree` users who wanted an isolated tree got their dirty local state copied in.

### Why this approach

**The dilemma — fresh vs head:**
- **`fresh`** (default): clean tree, no risk of unpushed local state leaking into a sub-agent or `--worktree` shell. Best for "spin up a worker on a hot bugfix while my main checkout is mid-refactor."
- **`head`**: inherits current branch state. Best for "I have an experimental branch with WIP commits and want a parallel worktree to keep building on it."

The v2.1.128 switch to `head` was popular for the second use case but silently regressed the first. By exposing the choice as a setting (rather than separating the tools), the team keeps a single mental model: `EnterWorktree`/`--worktree` always branch from "the agreed base," and what the base means is policy.

**Why "fresh" is the default again:** `--worktree` and `EnterWorktree` are most often invoked when the user explicitly wants isolation. Inheriting WIP commits is the surprising behavior, not the expected one.

**Migration footnote:** the changelog explicitly tells users who liked the v2.1.128 behavior to set `worktree.baseRef: "head"`. The default change is a behavior break, so it's flagged.

```javascript
  socatPath: optionalString.describe("Path to a custom socat binary (Linux/WSL)."),

```

Diagnostic message when override is invalid (cli_inner_pretty.js:197401):
> `sandbox.bwrapPath is set to {path} but it is not an executable file. Fix the path in managed settings, or set CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=0 to disable (loses subprocess isolation).`

### Why this approach

**Use case:** Enterprise Linux distros where `bwrap`/`socat` aren't on `$PATH` for non-interactive shells (custom installs, NixOS, Toolbox containers). The sandbox subprocess scrubbing path was failing because the binary wasn't findable.

**Why managed settings:** The path is an admin/install-time configuration, not a per-session knob. Putting it under `sandbox.*` keeps related sandbox tuning grouped (`seccompConfig` already lives there).

**Why the explicit error mentions `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=0`:** The fallback isn't "skip sandboxing silently" — it's an explicit security-tradeoff exit hatch. The error tells the admin both options.

## 3. `parentSettingsBehavior` admin key (NEW)

**Type:** feature · **Modules:** Settings, Policy

### v2.1.133 state

```javascript
// ============================================
// parentSettingsBehaviorSetting - merge SDK managedSettings under admin?
// Location: cli_inner_pretty.js:50659-50666, consumer at :52044
// ============================================

// ORIGINAL (for source lookup):
parentSettingsBehavior: y
  .enum(["first-wins", "merge"])
  .optional()
  .describe(
    'Controls whether the SDK parent tier (Options.managedSettings / --managed-settings) layers under this admin tier. "first-wins" ' +
      "(default): parent is dropped — admin tiers are the only policy " +
      `source. "merge": parent's restrictive-only-filtered settings union under the admin winner. Has no effect when no admin tier exists (parent applies as the sole policy tier, still filtered restrictive-only).`,
  )

// Consumer:
if (!H || H.parentSettingsBehavior === "merge") return ...   // cli_inner_pretty.js:52044

// READABLE (for understanding):
const parentSettingsBehavior = z.enum(["first-wins", "merge"]).optional();
// "first-wins": admin tiers win; SDK parent dropped
// "merge":      restrictive-only filter on SDK parent, then union below admin
```

### Why this approach

**The problem:** SDK clients (e.g. an embedded IDE running `Options.managedSettings`) historically *replaced* the admin tier when present. Two policy sources, two ways of merging — admins couldn't reliably constrain SDK callers if SDK passed its own managed settings.

**The fix:** Default `first-wins` says "admin wins, SDK parent is dropped." `merge` opts in to the SDK parent contributing *only restrictive-only* fields underneath the admin layer, so admins can preserve more permissive policies while the SDK adds further restrictions.

**Why "restrictive-only-filtered":** Settings classified as restrictive (deny lists, hook locks, sandbox requirements) are safe to layer; permissive settings (allow lists, env additions) are not — they could be used to widen admin policy.

**Trade-off:** Pre-2.1.133, embedded SDK products needed admin coordination to pass managed settings. Now they can pass settings opportunistically and admins decide whether they apply.

## 4. Hooks receive `effort.level` + `$CLAUDE_EFFORT` env var

**Type:** feature · **Modules:** Hooks, Bash, Effort

### v2.1.133 state — JSON shape and env

```javascript

//   "effort": { "level": "low" | "medium" | "high" | "xhigh" | "max" }
// Location: cli_inner_pretty.js:231790 (schema example),
//           cli_inner_pretty.js:237710 (description)

// Env var injection (replaceAll-based templating, cli_inner_pretty.js:399003, 406269):
g = g.replaceAll("${CLAUDE_EFFORT}", aT(E ?? F.options.mainLoopModel, h ?? F.getEffortValue()))

// Bash subprocess gets CLAUDE_EFFORT via env var passing
// cli_inner_pretty.js:419635
{ CLAUDE_EFFORT: aT($.options.mainLoopModel, $.getEffortValue()) }
```

Hook docs (cli_inner_pretty.js:237710):
> "Active effort level for the current turn (e.g., 'low', 'medium', 'high', 'xhigh', 'max'), after any silent downgrade for the selected model. Also exposed to hook commands and Bash as the CLAUDE_EFFORT env var."

### Why this approach

**The "after silent downgrade" subtlety:** A user can set `xhigh` but if the active model doesn't support it (e.g. Sonnet 4.5), the effort gets silently downgraded to `high` at dispatch. Hooks/Bash see the *applied* effort, not the requested one.

**Why both JSON and env var:**
- Hook authors writing JSON-aware hooks (Node, Python) prefer the JSON field — typed, consistent shape.
- Bash hooks / shell-script `Bash(...)` calls prefer `${CLAUDE_EFFORT}` — string-substitutable, no JSON parsing needed.

**Use case:** A pre-commit hook that runs lighter linters at `low` effort, full type checks at `xhigh`. Or a test runner that does a smoke pass when effort < `high` and full integration tests otherwise.

## 6. Warm-spare background worker release under memory pressure

**Type:** performance · **Modules:** Background daemon

The daemon pre-warms a spare background worker (so dispatching a `--bg` job has zero startup cost). Under memory pressure, this is now released. Trade-off: cold start on the next dispatch in exchange for not OOM-ing while the user does heavy work in foreground.

**Why this matters:** Pre-warming was added in earlier versions to make `--bg` feel instant. But the warm spare holds ~50-100 MB resident. On 8 GB laptops with Chrome + IDE + browser open, that's the difference between a smooth main session and a swap-thrash.

## 7. Parallel sessions dead-ending at 401 after refresh-token race

**Type:** fix · **Modules:** Auth

**Before:** Two parallel sessions could race on OAuth refresh; one would succeed, the other would write its now-invalid old refresh token over the freshly-rotated one. Both sessions then 401 on the next call.

**After:** The credentials file write path now validates the rotation order before persisting. The race loser sees the winner's token and uses it instead of overwriting.

**Why this surfaces in 2.1.133:** Parallel sessions are more common with `claude agents` / `--bg` workflows that 2.1.139+ codifies. Older single-session users rarely hit the race.

## 8. `Edit`/`Write` allow rules scoped to drive root incorrectly matching

**Type:** fix · **Modules:** Permissions, Edit, Write

**Before:** A permission rule like `Edit(C:\)` (Windows drive root) or `Edit(/)` (POSIX root) was being matched in a way that *didn't* cover all the drive's children — every file under the drive still prompted. Effectively the rule did nothing.

**After:** Drive-root rules now act as a true wildcard match — all paths under the drive are permitted.

**Why the regression existed:** The path-matching algorithm normalized paths with a trailing-slash strip, which turned `C:\` into `C:` (an unrooted bareword) and `/` into the empty string. Both then failed the `path.startsWith(rule)` check. Fix: special-case the drive-root and POSIX-root forms before normalization.

## 9. Unhandled `ECOMPROMISED` from history/session-log file lock

**Type:** safety · **Modules:** File lock

```javascript
// ============================================
// staleLockErrorCode - ECOMPROMISED on clock skew or slow disk
// Location: cli_inner_pretty.js:99111-99125
// ============================================

if (K.code === "ENOENT" || A) return gi8(H, q, Object.assign(K, { code: "ECOMPROMISED" }));
// ...
Object.assign(Error("Unable to update lock within the stale threshold"), { code: "ECOMPROMISED" }),
```

**Before:** A history/session-log file lock could be classified as "compromised" if the lock's mtime drifted past the stale threshold (clock-skew on the machine, or a slow disk that took >threshold to update the lock). The error bubbled as an unhandled rejection, killing the session.

**After:** The error code `ECOMPROMISED` is now handled — the lock is treated as no longer valid, a new lock attempted, and the original error logged rather than thrown.

**Why this surfaces:** Cloud-synced home directories (Dropbox, iCloud, OneDrive) often have lag between local writes and the filesystem mtime as observed by another process. Lock files on those volumes were spuriously marked compromised.

## 10. Esc during compaction showing spurious error

**Type:** fix · **Modules:** Compact, UI

**Before:** Pressing Esc during conversation compaction (to cancel) raised a "Error compacting conversation" notification. Compaction was *cancelled* correctly, but the user got a misleading error.

**After:** The Esc cancellation path is detected and handled silently — only a quiet "compaction cancelled" message.

**Why:** The compaction promise was rejecting with `AbortError`, and the error handler didn't distinguish user-initiated abort from genuine compaction failure. Now `AbortError` is short-circuited before the error UI fires.

## 11. MCP OAuth flow now respects `HTTP(S)_PROXY` / `NO_PROXY` / mTLS

**Type:** fix · **Modules:** MCP, Proxy, Auth

**Before:** MCP OAuth flow used a default `fetch` agent that ignored `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, and any custom client certificate config. Enterprise users behind corporate proxies couldn't add HTTP/SSE MCP servers — discovery, dynamic client registration, token exchange, and refresh all bypassed the proxy.

**After:** The OAuth fetch path now uses the same proxy-aware agent as the rest of the network stack. mTLS via `NODE_EXTRA_CA_CERTS` or per-request `cert`/`key` also flows through.

**Why this was missed:** OAuth was hand-rolled with `fetch()` inside the MCP module rather than going through the central API client wrapper. The proxy wiring lived only in the wrapper. Now the OAuth client uses the wrapper.

## 12. Read/Write/Edit denied on mapped network drives via `--add-dir` / SDK `additionalDirectories`

**Type:** fix · **Modules:** Read, Write, Edit, Path resolution

**Before:** A user passing `--add-dir Z:\shared` (or via SDK `additionalDirectories`) found that `Read`/`Write`/`Edit` against files on `Z:` were denied as "not in an allowed directory." The check was being done with the wrong path normalization for network drives.

**After:** Network-drive (`\\?\UNC\` / `Z:\`) paths are normalized consistently with the allow-list entries.

**Why:** Windows mapped network drives have multiple syntactic forms — `Z:\`, `\\server\share\`, `\\?\UNC\server\share\`. The allow-list check was comparing canonicalized form against original form. Fix: canonicalize both sides before comparison.

## 13. Remote Control stop/interrupt not fully canceling

**Type:** fix · **Modules:** Remote Control

**Before:** When a remote (claude.ai) client clicked Stop or Interrupt, the local CLI received the signal but didn't run the same cleanup path as a local Esc. Symptom: queued messages stayed queued (never advanced) after interrupting a stuck tool.

**After:** Remote stop/interrupt now feeds into the same abort path as local Esc — both clear in-flight work and dequeue/advance.

## 14. `/effort` cross-session leak

**Type:** fix · **Modules:** Effort, Settings

**Before:** Setting effort with `/effort xhigh` in one session also changed the effort in other concurrently-running sessions (via shared settings file). Worse: an IDE-side effort change could be lost entirely if a CLI session was also writing settings.

**After:** Effort changes are now scoped to the current session unless explicitly persisted, and the cross-session writes use a CAS pattern to avoid clobbers.

**Related (v2.1.139):** the autocompact threshold has the same fix in v2.1.139 — see `v2.1.139.md`.

## 15. Subagents not discovering project/user/plugin skills

## 17. [VSCode] `claudeCode.claudeProcessWrapper` failing with "Unsupported platform"

**Type:** fix · **Modules:** VSCode extension

**Before:** When the extension build didn't bundle a Claude binary for the host platform (e.g. Linux ARM64), setting `claudeCode.claudeProcessWrapper` to point at an external binary still errored with "Unsupported platform" because the platform check happened before the wrapper override.

## Summary

v2.1.133 reverts the v2.1.128 worktree-base-ref behavior (back to `fresh`) but exposes the choice as a setting. The release adds policy plumbing (`parentSettingsBehavior`) for SDK-embedded callers and tightens sandbox path discovery for unusual Linux installs. The most impactful safety fix is the parallel-session refresh-token race — silent and easy to miss until your second concurrent session 401s. The remaining work is a long tail of small reliability fixes (Esc-compaction error, MCP OAuth proxy, mapped network drives, Remote Control interrupt, parallel `/effort`) that together close the most common "weird failure" reports from the v2.1.128–132 window.
