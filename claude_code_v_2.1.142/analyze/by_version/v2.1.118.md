## 1. Vim visual mode + visual-line mode

**Type:** feature · **Modules:** Vim mode, Input

### v2.1.88 baseline

Vim mode supported NORMAL and INSERT modes. The standard chord `v` (character visual) and `V` (line visual) were unbound.

### v2.1.118 state

```javascript
// ============================================
// vimVisualMode - selection + operators
// Location: cli_inner_pretty.js:549785-549828
// ============================================

// ORIGINAL (for source lookup):
selectionLinewise: q === "VISUAL LINE",
$.current = { mode: "VISUAL", kind: V, anchor: G, command: { type: "idle" } };
let v = V === "line" ? "VISUAL LINE" : "VISUAL";

// READABLE (for understanding):
const isLinewiseSelection = (currentMode === "VISUAL LINE");
visualState.current = {
  mode: "VISUAL",
  kind: visualKind,   // "char" or "line"
  anchor: anchorPosition,
  command: { type: "idle" }
};
const displayMode = visualKind === "line" ? "VISUAL LINE" : "VISUAL";

// Schema describing the mode string set:
// "INSERT" | "NORMAL" | "VISUAL" | "VISUAL LINE"
```

`hideVimModeIndicator` setting (chunks 50600) lets statusline scripts render the mode themselves:

```javascript
// chunks:50600-50604
hideVimModeIndicator: y...
description: "Hide the built-in `-- INSERT --` / `-- VISUAL --` indicator below the prompt. Use this when your status line script renders `vim.mode` itself."
```

### Why this approach

**Completing the vim mental model.** Users with vim muscle memory expect `v` to select a character range, `V` to select line-wise. Without it, vim-mode users had to use shift+arrow (TUI-native) selection. The mode mismatch was a friction point.

**Why also `VISUAL LINE` (not just `VISUAL`):** Linewise selection is qualitatively different — operators (`d`, `c`, `y`) act on whole lines including newlines. Conflating the two kinds would surprise users.

**Why `hideVimModeIndicator`:** Power users with custom status lines were already rendering `vim.mode`. The dual-render created visual duplication. Letting them suppress the built-in is the polite path.

## 2. `/cost` + `/stats` merged into `/usage`

**Type:** UX · **Modules:** /usage, Slash commands

### v2.1.88 baseline

`/cost` showed billing/cost info. `/stats` showed session statistics (tokens, requests). They lived as separate commands.

### v2.1.118 change

Both are merged into `/usage` with tabbed sub-views. `/cost` and `/stats` remain as typing shortcuts that open the relevant tab.

### Why this approach

**Topic affinity.** Cost and stats are both "how am I doing in this session" questions — users frequently want both. A unified screen with tabs is the natural shape.

**Why keep `/cost` and `/stats` as shortcuts:** Muscle memory + Don't-break-users.

## 3. Custom themes — named, switchable, shippable

**Type:** feature · **Modules:** Theme

### v2.1.88 baseline

A small enum of built-in themes (`dark`, `light`, etc.) was selectable via `/theme`. No custom theme path.

### v2.1.118 state

Users can:
1. Create and switch themes from `/theme`.
2. Hand-edit JSON files in `~/.claude/themes/<name>.json`.
3. Install plugins that ship a `themes/` directory.

### Why this approach

**Themability as ecosystem.** Custom themes go beyond personalization — they let teams ship branded TUI experiences via plugins (e.g. a `corp-theme` plugin). The JSON shape is portable.

**Why allow `themes:` plugin manifest key with directory override:** If a plugin wants both auto-load *and* a curated subset, it can list specific files; otherwise the directory is the default.

**Plugin-shipped themes get the same lifecycle as plugin commands/agents/skills — install, enable, disable, uninstall.**

## 4. `mcp_tool` hook type — hooks can call MCP tools directly

**Type:** feature · **Modules:** Hooks, MCP

### v2.1.88 baseline

Hook types were `command` (run a shell command), `prompt` (text fed to the model), `agent` (run a subagent). No way to call an MCP tool directly from a hook.

### v2.1.118 state

```javascript
// ============================================
// mcp_tool hook type
// Location: cli_inner_pretty.js:48793, 137535, 352548
// ============================================

type: y.literal("mcp_tool").describe("MCP tool hook type"),

// Routing:
if (H.startsWith("mcp__")) return "mcp_tool";

// Execution case:
case "mcp_tool":
  // ... call the MCP tool directly via the hook framework
```

A hook can now declare `type: "mcp_tool"` and have its `args` interpreted as an MCP tool invocation.

### Why this approach

**Composability.** Many hook use cases want to call into MCP tools (e.g. a `PostToolUse` hook that calls an MCP `validation:run` tool to check the produced output). Without an `mcp_tool` hook type, the user wrote a `command` hook that ran `mcp-shim --call ...` — fragile, slow.

**Why a dedicated type (not a flag on `command`):** MCP calls have rich input/output structure (JSON), authentication, and a different timeout model than shell commands. A dedicated type matches the underlying contract.

## 5. `DISABLE_UPDATES` env var

**Type:** safety · **Modules:** Updates

### v2.1.88 baseline

`DISABLE_AUTOUPDATER` blocked the background auto-update path but didn't block manual `claude update`. A user wanting *no* updates whatsoever had no single switch.

### v2.1.118 state

```javascript
// Location: cli_inner_pretty.js:140500, 532847, 605143
if (bH(process.env.DISABLE_UPDATES)) return { type: "env", envVar: "DISABLE_UPDATES" };
```

`DISABLE_UPDATES` blocks *all* update paths including manual `claude update`. Strictly stronger than `DISABLE_AUTOUPDATER`.

### Why this approach

**Enterprise pinning.** An admin who deploys a specific Claude Code version (and approves the bundle) doesn't want `claude update` to drift the binary out of compliance. A single env var lets them lock it down at deploy.

**Why a *new* var (not deprecate `DISABLE_AUTOUPDATER`):** The two have different semantics. `DISABLE_AUTOUPDATER` lets users still opt-in via `claude update`. `DISABLE_UPDATES` is the lockdown. Different switches.

## 6. `wslInheritsWindowsSettings` policy key

**Type:** feature · **Modules:** WSL, Managed settings

### v2.1.88 baseline

WSL had its own `~/.claude/settings.json`. Windows-side admin policy didn't reach WSL — admins had to duplicate config in both.

### v2.1.118 state

```javascript
// Location: cli_inner_pretty.js:50427, 51500-51543, 51938, 52373
wslInheritsWindowsSettings: y...
// Check in WSL bootstrap:
if (((A = q?.settings.wslInheritsWindowsSettings === !0 || GI9()), !A))
// Extract setting at multiple sites
```

When `wslInheritsWindowsSettings: true` is set, WSL Claude Code inherits the host Windows-side managed settings.

### Why this approach

**Single source of truth for org policy.** Admins manage one Windows GPO/MDM rule and WSL conforms. Without it, WSL ran with whatever the user configured locally — defeating org enforcement.

**Why opt-in:** Some users intentionally run WSL with different settings (e.g. enterprise Windows, personal WSL). Default-off respects that.

## 7. Auto mode: `$defaults` sentinel in `autoMode.allow`/`soft_deny`/`environment`

**Type:** feature · **Modules:** Auto mode

### v2.1.88 baseline

Configuring `autoMode.allow` *replaced* the built-in allow rules entirely. Users adding one custom rule lost all defaults.

### v2.1.118 state

```javascript
// Location: cli_inner_pretty.js:338615, 49996-50015
llH = "$defaults"

// Schema descriptions:
'Rules for the auto mode classifier allow section. Include the literal string "$defaults" to inherit the built-in rules at that position.'
'Rules for the auto mode classifier SOFT BLOCK section — destructive/irreversible actions that user intent can clear. Include the literal string "$defaults" to inherit the built-in rules at that position.'
'Rules for the auto mode classifier HARD BLOCK section — security boundaries that user intent does NOT clear. Include the literal string "$defaults" to inherit the built-in rules at that position.'
'Entries for the auto mode classifier environment section. Include the literal string "$defaults" to inherit the built-in entries at that position.'
```

Users can include the literal string `"$defaults"` in any of the auto-mode lists to inherit built-in rules *at that position*.

### Why this approach

**Composition over replace.** Replace was the only option — fine for "I want to start fresh" but a foot-gun for "I want to add one thing." The sentinel-include pattern is borrowed from CSS (`unset`), shell `$PATH:newentry`, and many other config systems.

**Why a literal string sentinel (not a flag):** A flag like `inheritDefaults: true` would compose poorly with multiple lists. The sentinel lets you control *position* — inherit-then-add, add-then-inherit, etc.

## 14. MCP OAuth fixes — many

**Type:** fix · **Modules:** MCP, OAuth

A pack of related OAuth fixes:
- `/mcp` Auth/Re-authenticate actions hidden for servers with `headersHelper` — now shown.
- HTTP/SSE MCP servers with custom headers stuck in "needs authentication" after transient 401 — now retry-on-401.
- MCP servers whose OAuth response omits `expires_in` requiring re-auth every hour — now use refresh token instead.
- Step-up authorization silently refreshing instead of prompting for re-consent when `insufficient_scope` 403 names a scope the current token already has — now prompts.
- Unhandled promise rejection when MCP OAuth flow times out or is cancelled — now handled.
- MCP OAuth refresh proceeding without its cross-process lock under contention — now lock-protected.

### Why this matters

OAuth races in a multi-server, multi-process setup (CLI + IDE extension + SDK) caused mysterious "Please run /login" prompts. The fixes are individually small; together they make OAuth feel stable.

## 23. `/fork` writing full conversation per fork → pointer-based

**Type:** Performance · **Modules:** /fork

### v2.1.88 baseline

Each fork was a full copy of the parent session's transcript on disk. For a 40MB session forked 5 times, that's 200MB of duplication.

### v2.1.118 change

Forks now write a *pointer* to the parent. On read, the parent is hydrated and the fork-specific delta is applied on top.

### Why this approach

**Diff over duplicate.** Forks share most of the parent's content; the delta is tiny. Pointer-based storage is O(parent + delta) instead of O(forks × parent).

**Trade-off:** A fork's read requires reading the parent first. For short forks this is a tiny overhead; for long forks it amortizes well. Net win.

## Summary

v2.1.118 has **three pillars**:

1. **Vim feature parity** — VISUAL/VISUAL LINE modes complete the vim-mode value prop.
2. **Theme ecosystem** — custom themes (JSON files, plugin-shipped, switchable) turn themes from an enum into a first-class extension surface.
3. **`/usage` unification + auth reliability** — Cost/stats merge is UX consolidation; the OAuth/credentials fix pack addresses the most common "Please run /login" tickets.

The pattern: **previously-thin features get the depth they need to be useful.** Vim mode was halfway; now it's vim. Themes were enum; now they're an ecosystem. Auto-mode rules were replace-or-nothing; now they compose.

The `/fork` pointer change is a quiet algorithmic win that won't show up in CHANGELOG screenshots but will matter quietly for users running heavily-forked workflows.
