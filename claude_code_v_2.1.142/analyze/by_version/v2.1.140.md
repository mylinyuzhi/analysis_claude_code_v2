# v2.1.140 — Source Diff Analysis

**Theme:** Small polish + fix release between the v2.1.139 agent-view debut and v2.1.141's heavy feature load. The main visible change is forgiving `subagent_type` matching; the rest is a fix sweep focused on Windows reliability, `--bg` startup, and settings hot-reload.

---

## 1. `Agent` tool `subagent_type` — case- and separator-insensitive matching

**Type:** UX · **Modules:** Agent tool, Subagent

### v2.1.139 baseline

`subagent_type` was a strict-string lookup against agent definitions. A model invoking `Agent(subagent_type: "Code Reviewer")` when the actual definition was `code-reviewer` would 404.

### v2.1.140 state

The matcher now normalizes both sides — lowercase + collapse-separators. So `"Code Reviewer"`, `"CodeReviewer"`, `"code_reviewer"`, and `"code-reviewer"` all resolve to the same definition.

### Why this approach

**The pain:** The model would correctly identify the user's described agent but get the casing/separator wrong on dispatch. Users were filing "Claude says agent not found but it's right there" reports.

**Why a normalize-and-compare:** A naive `toLowerCase().replace(/[-_\s]/g, '')` covers the four common forms (Title Case with space, kebab-case, snake_case, PascalCase). Edge cases:
- Names with leading/trailing whitespace — normalized.
- Names with double underscores or hyphens — normalized (multiple separators collapse to nothing).
- Names with non-alpha separators (e.g. `code.reviewer`) — *not* matched (since `.` isn't in the separator class).

**Trade-off:** Ambiguity if a user defines both `Code-Reviewer` and `code_reviewer` — both now alias to the same key, and the second overwrites the first. Acceptable: distinct casing variants of the same logical name aren't a common pattern.

## 3. `/goal` silently hanging when `disableAllHooks` or `allowManagedHooksOnly` is set

**Type:** fix · **Modules:** /goal, Hooks

### v2.1.139 baseline

`/goal` set a session-scoped Stop hook. If `disableAllHooks` or `allowManagedHooksOnly` was set, the Stop hook silently couldn't fire — the indicator would spin forever waiting for a goal condition that the hook would never check.

### v2.1.140 state — clear message

```javascript
// cli_inner_pretty.js:486762
"/goal can't run while hooks are disabled (disableAllHooks or allowManagedHooksOnly is set in settings or by policy)."
```

The command now refuses up-front with a clear explanation.

### Why this approach

**Pattern:** A feature relying on hooks must check hook policy before activating. Otherwise the user gets a silent failure with no actionable signal. v2.1.140 fixes the symptom; the deeper lesson is "any new hook-based feature needs a startup precondition check."

## 4. Settings hot-reload — symlinked settings files

**Type:** fix · **Modules:** Settings

### v2.1.139 baseline

A regression in v2.1.139's settings hot-reload code caused symlinked settings files (`~/.claude/settings.json -> ~/dotfiles/.claude/settings.json`) to fire misattributed change events. Each edit to the real file would trigger `ConfigChange` hooks against the symlink's *path string* (not contents), spuriously.

### v2.1.140 state

Settings hot-reload now follows symlinks and watches the *target* of the symlink (not the symlink itself), with proper change attribution.

### Why this matters

Dotfile users who symlink settings into a git-managed dotfiles repo are a meaningful slice. Their entire `/usage` was getting spammed with phantom `ConfigChange` events.

## 5. `claude --bg` failing with "connection dropped mid-request"

**Type:** fix · **Modules:** --bg, Daemon

### v2.1.139 baseline

When the background service was about to idle-exit (the daemon's idle timeout), and a `claude --bg` dispatch arrived in the same moment, the dispatch saw a half-open connection and reported "connection dropped mid-request."

### v2.1.140 state

The dispatch now retries on connection drop. The daemon also defers idle-exit for a grace window after each successful dispatch acknowledgment.

### Why this approach

**Race window:** Server says "ack, I'm going to exit" → Client sends new request → Server has closed → Client sees "dropped mid-request." Without retry, the client errors. With retry, the dispatch transparently re-establishes (spawning a fresh daemon if needed).

## 6. Background service startup failing on enterprise endpoint security

**Type:** fix · **Modules:** Daemon

**Before:** Some endpoint security suites delay process startup with EDR scanning. The daemon startup had a tight timeout (a few seconds) and would fail before the scan completed.

**After:** The startup timeout is now more permissive on Linux/Windows where EDR is common.

## 7. Remote managed settings — 401 retry

**Type:** fix · **Modules:** Auth, Settings

**Before:** When remote managed settings (an enterprise-managed JSON pulled from a corporate URL) returned 401, the settings fetch errored without retry. A stale-token-after-refresh race could effectively lock users out.

**After:** A single retry with a force-refreshed token resolves the race.

## 8. Managed `extraKnownMarketplaces` not persisted to `known_marketplaces.json`

**Type:** fix · **Modules:** Plugins, Marketplaces

### v2.1.140 state

```javascript
// extraKnownMarketplaces consumption (cli_inner_pretty.js:218015-218016)
if (!K?.extraKnownMarketplaces) continue;
Object.assign(H, K.extraKnownMarketplaces);

// known_marketplaces.json path (cli_inner_pretty.js:228733)
return sE.join(H, "known_marketplaces.json");
```

**Before:** Managed `extraKnownMarketplaces` setting added entries at runtime but didn't write through to `known_marketplaces.json`. If admin policy changed and the runtime didn't re-fetch, the local file was missing the entries.

**After:** The auto-update policy now persists to `known_marketplaces.json`, making the marketplaces available offline.

## 9. `/loop` scheduling redundant wakeups

**Type:** fix · **Modules:** /loop, Scheduling

**Before:** `/loop` (the scheduler that polls for background task completion) was scheduling redundant wakeups for tasks that *already* notify on completion. Result: extra CPU/timer fires for no benefit.

**After:** `/loop` checks whether the task has its own notification path; if so, skips the polling wakeup.

## 10. Windows event-loop stall on missing executable (`where.exe` re-spawn)

**Type:** performance · **Modules:** Windows, Subprocess

### v2.1.140 state

```javascript
// where.exe path used for executable discovery (cli_inner_pretty.js:42778)
K = Yfq.join(q, "System32", "where.exe");
```

**Before:** When a referenced executable (e.g. `gh` for GitHub CLI commands) was missing, the discovery path re-spawned `where.exe` synchronously *on every check*. The event-loop blocked for the lifetime of each spawn.

**After:** Missing-executable results are cached for the session, avoiding the repeat spawn.

**Why this is bad:** Synchronous `where.exe` spawn on Windows takes 50-200ms. If the CLI checks for `gh` 20 times in a session, that's 1-4 seconds of cumulative event-loop stall.

## 11. `Read` tool `offset` whitespace-padded / `+`-prefixed string

**Type:** fix · **Modules:** Read tool

**Before:** A model passing `"offset": " 12"` or `"offset": "+12"` (string with whitespace or unary plus) failed Zod schema validation.

**After:** The schema now accepts coercible string forms.

**Why:** Models occasionally produce these forms — common JSON serializers add the leading whitespace, or the model "helpfully" prefixes a `+`. Strict coercion would force the model to learn the exact format; lenient coercion accepts variation.

---

## 12. Native terminal cursor at input caret on focus loss

**Type:** fix · **Modules:** Native renderer

**Before:** When the terminal lost focus (alt-tab to another app), the native renderer wasn't keeping the cursor at the input caret. On focus return, the cursor appeared at the last-drawn position (usually somewhere mid-transcript), not the input.

**After:** Focus-loss/return correctly anchors the cursor at the input caret.

---

## 13. Plugin warning: default component folder ignored when `plugin.json` key shadows

**Type:** UX · **Modules:** Plugins

**Before:** A plugin with both a `commands/` folder and a `"commands": [...]` key in `plugin.json` would silently use the manifest entry, ignoring the folder. Users couldn't tell why their commands weren't loading.

**After:** A warning is shown in `/doctor`, `claude plugin list`, and `/plugin` explaining that the manifest key takes precedence and the folder is ignored.

## Summary

v2.1.140 is a "smooth the edges" release. Most fixes target the v2.1.139 feature surface (agent view, `/goal`, settings hot-reload) and clean up Windows-specific reliability issues. The `subagent_type` lenient matching is the most user-visible change — it converts a recurring "agent not found" failure into a transparent success.
